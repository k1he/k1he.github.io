内存层次与 HBM · GPU 真正的“地形图” 第一章 · 04/08

LLM 推理不是“算力不够”，大多数时候是“数据搬不过来”。本篇把 Register、Shared Memory、L1、L2、HBM、NVLink 的容量/延迟/带宽放在一张地图上，解释为什么 decode memory-bound、为什么 FlashAttention 要把数据困在片上、为什么 KV Cache 是服务系统的第一等公民。

§1内存金字塔：越近越快，越近越小

GPU 上的数据搬运不是“从显存读到 ALU”这么简单。一次矩阵乘法通常经历：

HBM → L2 → L1/Shared Memory → Register → Tensor Core/CUDA Core → Register → HBM

每一级都有不同的容量、延迟、带宽、可控性。高性能 kernel 的本质就是：把昂贵的 HBM 访问变成便宜的片上复用。

关键直觉：HBM 带宽看起来很大（TB/s），但 Tensor Core 算得更大（PFLOPS）。H100 FP8 峰值约 1979 TFLOPS，而 HBM 只有 3.35 TB/s。要喂满算力，每 1 Byte 从 HBM 读入后必须被复用几百次。复用不够，就 memory-bound。

§3Coalescing：32 个线程要像“一排人一起取货”

HBM 不是按单个 thread 访问的。warp 的 32 个 lane 发出的地址会被硬件合并成 32B/64B/128B transaction。理想情况：

lane0 读 A[0]
lane1 读 A[1]
...
lane31 读 A[31]
→ 32 × 4B = 128B，正好一个连续事务

理想：连续 128B

糟糕：stride / random

LLM 里的典型 coalescing 问题

  • 权重矩阵布局：GEMM kernel 要保证连续 lane 读连续 K 维或 N 维，避免 transpose 后 stride 访问。
  • KV Cache layout：paged attention 中 page/block 的内部布局会直接影响 K/V load 是否连续。
  • GQA/MQA：多个 query head 共享 KV head，读 K/V 时更容易出现复用，但也要小心 head 维度 stride。
  • Sampling logits：vocab 维通常连续，适合 warp/block 分片 reduce；如果按 batch major 错排，会让每个 batch 的 top-k 访问碎裂。

§4HBM：不是“一条大内存”，而是很多 bank/channel 并行

HBM（High Bandwidth Memory）通过 2.5D 封装放在 GPU die 旁边：多层 DRAM die 垂直堆叠，通过 TSV 连接到底部 logic die，再通过硅中介层（interposer）连到 GPU。

为什么 HBM 适合 GPU

  • 宽：HBM 的 I/O 位宽远大于 GDDR，单次能搬更多 bit。
  • 近：和 GPU die 同封装，线路短，能耗低。
  • 并行：多 stack、多 channel、多 bank 可以同时服务很多 SM 的请求。
但 HBM 仍然很慢：它的延迟仍是几百 cycle。HBM 的强项是吞吐，不是单次访问延迟。所以 GPU 不能像 CPU 一样等一次 load 返回；它必须靠大量 warp、异步拷贝、tile 复用把延迟藏起来。

§5L2 / L1 / Shared Memory：片上才是真战场

L2：全 GPU 共享的“中转仓”

L2 cache 连接所有 SM、HBM memory controller、NVLink copy engine。它是跨 SM 数据复用的唯一大容量片上缓存。

  • H100 L2 约 50MB；B200 增到约 192MB，意义巨大：更多 KV hot page、权重 tile、activation 能在片上停留。
  • L2 命中能把几百 cycle 的 HBM load 降到 ~100-200 cycle，且省掉 HBM 带宽。
  • 多 CTA 访问同一权重 tile 时，L2 命中率决定 GEMV/decode 的有效带宽。

Shared Memory：程序员可控的 L1

Shared Memory 是每个 SM 内的一块 SRAM，生命周期属于 thread block/cluster。它最大的价值是：你知道它里面有什么、什么时候被覆盖、如何被复用。

extern __shared__ half smem[];
// 典型 tile 流程：
// 1. 从 HBM/L2 把 A_tile/B_tile 搬到 smem
// 2. __syncthreads()
// 3. 多个 warp 从 smem 反复读，喂 Tensor Core
// 4. 下一 tile 覆盖 smem

Bank conflict：SMEM 也会堵车

Shared Memory 被切成多个 bank。若一个 warp 多个 lane 同时访问同一 bank 的不同地址，硬件要串行服务，形成 bank conflict。

访问形态结果常见修复
smem[lane]32 lane 分布到 32 bank，理想无需处理
smem[lane * 32]全落同一 bank，32-way conflictpadding：stride = 33

§6从 KV Cache 看内存层次：decode 为什么卡在 HBM

LLM decode 每生成一个 token，需要读历史所有 token 的 K/V。对于 batch 内每个请求：

Q: 当前 token，一小块，通常在 register/smem 内
K/V: 历史上下文，长度 = context_len，放在 HBM 的 KV Cache
Attention: scores = Q · K^T，然后 weighted sum V

一个具体算例

模型: 32 层，GQA: num_kv_heads=8，head_dim=128，dtype=FP16
每 token KV = 2(K,V) × 32层 × 8 heads × 128 × 2B
             = 131,072 B = 128 KB/token

若上下文 8K tokens：
单请求 KV = 8192 × 128KB = 1GB
每 decode 一步至少要扫描相当一部分历史 K/V
→ 这不是算力问题，是“每步都要从 HBM 翻旧账”
Paged Attention 的意义：它不让 KV Cache 必须连续分配，而是按 page/block 管理。但 page table 只解决“显存碎片与调度复用”，不消灭读 K/V 的 HBM 流量。因此 paged attention 仍需要 layout、coalescing、block sparse、prefix cache、spec decode 等手段继续降流量。

判断一个 kernel 是不是 memory-bound

算术强度 AI = FLOPs / Bytes_from_HBM
若 AI < 峰值算力 / 峰值带宽 → memory-bound

H100 FP16 Tensor Core: ~989 TFLOPS
HBM: 3.35 TB/s
ridge point ≈ 989 / 3.35 ≈ 295 FLOP/Byte

decode GEMV 通常 AI 只有 1~10 FLOP/Byte
→ 离 295 太远，必然 memory-bound

§8带走的八句话

  1. GPU 内存层次是性能地图：Register/SMEM 是片上，HBM 是片外；片外访问再宽也慢。
  2. HBM 强在吞吐，不强在延迟：几百 cycle 延迟必须靠多 warp、异步拷贝、tile 复用隐藏。
  3. Tensor Core 太快，HBM 相对太慢：要喂满 PFLOPS，1 Byte 必须复用数百次。
  4. Coalescing 是基础税：warp 内连续 128B 是理想，random/stride 访问会把有效带宽打穿。
  5. Shared Memory 是程序员可控缓存：快，但要处理 bank conflict、容量、同步。
  6. L2 是跨 SM 的中转仓：B200 大幅扩大 L2，正是为了提高热数据命中。
  7. KV Cache 是 decode 的 HBM 税：上下文越长，每步翻旧账越重。
  8. 所有推理优化最终都能归类到三件事：少搬、复用、重叠。
