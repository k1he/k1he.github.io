SM 内部解剖 · 一个 SM 里到底塞了什么 第一章 · 02/08

SM（Streaming Multiprocessor）是 GPU 的最小"独立计算单元"——一块 CUDA 程序里的 thread block 永远被完整地放进某一个 SM。本章把 H100 SM 的一平方毫米拆到每一个 ALU。

§1SM 的大图：先看全貌

H100 一个 SM 的逻辑框图（白皮书 Figure 5 简化重绘）：

核心信息：一个 SM 被切成四个完全相同的 sub-partition，每个 sub 有自己的 warp scheduler、寄存器堆、ALU 组、tensor core 单元——它们之间几乎不交流，只共享下方的 SMEM 和 L1 I$。

§2Sub-Partition：为什么 SM 要切 4 份

最好奇的就是：为什么不直接做一个大 SM、一个大 warp scheduler？为什么要切 4 个并列的"小 SM"？

答案：warp 调度的物理极限

warp scheduler 每个时钟周期要做：

  1. 看一眼 16-64 个 resident warp 的状态（ready？stalled？）
  2. 选一个 ready warp
  3. 解码它下一条指令
  4. 从 register file 读 1-3 个源操作数（每个 32 线程 × 32bit = 128 字节）
  5. 把操作数通过 crossbar 送到对应的 FU
  6. issue 执行

这一堆事必须在 1 个 cycle 完成。如果一个 scheduler 要管 64 个 warp、128 个 ALU，读寄存器的 crossbar 会复杂到无法上到 ~2GHz 时钟。所以 NVIDIA 的工程折中：把 SM 切成 4 份，每份只管 16 warp、32 ALU——物理距离短、扇入扇出小、时序易满足。

4 个 sub-partition 的具体分工（Hopper）：
组件每 sub 数量每 SM 总数
Warp Scheduler14
Dispatch Unit1（issue 1 指令/cycle）4
Register File16K × 32bit = 64KB256KB
FP32 CUDA core32128
INT32 CUDA core1664
FP64 CUDA core1664
Tensor Core1（4 代）4
LD/ST unit832
SFU416
Max resident warp1664

thread 怎么分到 4 个 sub 上？

一个 thread block（比如 256 线程 = 8 warp）进入 SM 时，按 warpID 静态分：

warpID       sub-partition
--------    ---------------
warp 0      sub 0
warp 1      sub 1
warp 2      sub 2
warp 3      sub 3
warp 4      sub 0
warp 5      sub 1
...  (round-robin)

这意味着 block 内 warp 到 sub 的映射是确定的——你写 kernel 时如果希望某个 warp 做特殊工作（比如 warp specialization），可以 warpID = threadIdx.x / 32 直接定位。

§3Register File · GPU 的真·宝地

很多人以为 GPU 的灵魂是 Tensor Core，其实是寄存器。每个 SM 有 256KB 寄存器（4 sub × 64KB），全 die 合计 33MB——比 L2 Cache 还大。

每 sub 容量
64KB = 16384 个 32-bit 寄存器
每线程可用
最多 255 个（硬件上限）· 常用 32-64 个
带宽
每 cycle 读 3 个操作数 × 32 线程 × 32 bit = 384 B · 约 20 TB/s（per SM）
延迟
~4 cycle（pipeline 完全隐藏）
形态
SRAM · 分 bank · 多端口

每线程能用多少个寄存器？

一个 sub 同时 resident 多少个 warp，除以 32 线程就是每线程的寄存器配额：

每 sub 寄存器数 ÷ (resident warps × 32 线程)
= 16384 ÷ (16 × 32)
= 32 个 寄存器/线程  ← 满 occupancy 下限

如果每线程用 64 个 register，resident warps 降到 8，occupancy = 50%
如果每线程用 128，resident warps 降到 4，occupancy = 25%
如果每线程用 255，resident warps 降到 2，occupancy = 12.5%
Register Pressure：编译器如果发现变量太多塞不下，会"spill"到 local memory（其实是 HBM）——延迟从 4 cycle 变 400 cycle。一旦 spill 性能会塌方。用 -maxrregcount=N 或 __launch_bounds__ 限制每线程寄存器数是 kernel 调优的常规操作。

Bank 冲突（register bank conflict）

register file 物理上是多 bank 结构——Hopper 有 2 bank（旧架构 4 bank）。如果一条指令需要 3 个源操作数且它们落在同一 bank，就要多花 1 cycle 解决。编译器会做寄存器分配时避开，偶尔还是会遇到，可通过 cuobjdump --dump-sass 看到 HMMA.16816.F16 之类指令前有没有 REUSE flag（reuse cache 避免读 bank）。

§4Shared Memory + L1：最珍贵的片上 SRAM

SMEM 是"程序员可控的 L1 Cache"——既享受 SRAM 速度，又能精确决定哪份数据留哪份走。

总容量
256 KB / SM（Hopper）· 可配置 0 ~ 228 KB 给 SMEM
Bank 数
32 · 每 bank 4 Byte 宽 · 128 Byte 一行
带宽
128 B/cycle · ~19 TB/s per SM
延迟
~20 cycle（无 bank conflict）
寻址
kernel 内 __shared__ float a[N] · 或 dynamic extern __shared__

Hopper 的 228KB 是关键数字

为什么 FlashAttention-3、Warp-Specialized GEMM 都需要 Hopper？因为它们需要把 Q/K/V 三块 tile 同时装进 SMEM，预算大概：

FlashAttention-2 H100 典型配置：
  Q tile: 128×128 BF16 = 32 KB
  K tile: 128×128 BF16 = 32 KB  (乘以 stage 数可能 ×2)
  V tile: 128×128 BF16 = 32 KB
  S buffer: 128×128 FP32 = 64 KB
  --------------------------------
  约 ~160 KB  → 正好能塞进 Hopper 228 KB
                放不进 Ampere 164 KB
这是为什么 Hopper 最大 SMEM 涨到 228KB：不是工艺富余了，是 NVIDIA 明确知道"FlashAttention 们需要这么大"才给的。Blackwell 进一步到 228KB + 独立 Tensor Memory（TMEM）256KB。

Bank 冲突图解

SMEM 32 个 bank 的规则：连续 4 字节在不同 bank。如果一个 warp 的 32 线程访问的地址都落到不同 bank，0 冲突；如果两个线程落同一 bank（且不是同一地址），冲突 +1。

SMEM vs L1：为什么合并

从 Volta 开始 SMEM 和 L1 Data Cache物理上是同一块 SRAM，只是 kernel 启动时用 cudaFuncSetAttribute 决定分配比例。动机：L1 是自动 cache，SMEM 是手动，两者都是 SRAM，不如共用。

Hopper 允许的分配方案（KB）：
  SMEM  / L1
   228  /  28   ← FlashAttn 配置
   164  /  92
   100  / 156
    64  / 192
     0  / 256   ← 纯 L1 自动 cache，image-style kernel

§5各种 ALU：FP32 / INT / FP64 / SFU

sub-partition 里的"标量 ALU"们（即 CUDA core）。Hopper 每 sub 有：

类型数量/sub吞吐 (ops/clk/sub)用途
FP32 core3232 × FMA = 64 opslayer norm、softmax、epilogue、elementwise、激活
INT32 core1616 opsindex 计算、bitwise、loop counter
FP64 core1616 × FMA = 32 ops科学计算；LLM 几乎不用（消费卡干脆砍成 1/64 FP32）
SFU（Special Function Unit）44 ops（吞吐较低）sin/cos/exp/log/rsqrt/reciprocal
注意 FP32 和 INT32 可并行（Turing 开始）。如果你的循环里 index 算术（INT32）和浮点计算（FP32）错开，调度器会 co-issue，相当于免费提速。

SFU 的"单周期"假象

你写 __expf(x) 看起来一条指令，实际是 SFU 查表 + 插值（MUFU.EX2）。吞吐比 FP32 FMA 低 8-16 倍——softmax、gelu 这些函数里如果出现一大堆 expf/erff，它们往往变成瓶颈（所以 H100 的 __half2bfloat16、__expf 都有 fast-math 版本走更少 SFU cycle）。

Hopper SFU 典型吞吐：
  MUFU.EX2 (exp)     1 op/cycle/SFU  → 1 × 4 = 4 op/cycle/sub
  MUFU.LG2 (log2)    同上
  MUFU.RSQ (rsqrt)   同上
  MUFU.SIN / COS     同上
  MUFU.RCP (1/x)     2 op/cycle/SFU （快）

VS FP32 FMA:        32 op/cycle/sub

→ SFU 比 FP32 慢 8× 的吞吐。softmax 加速一大招就是 先乘 log2(e) 再用 exp2 代替 exp，把 erf 精度换速度。

§6Tensor Core · 如何塞进 SM

Tensor Core 在 sub-partition 里只有 1 个，但它吃下来的 FLOPS 比旁边 32 个 FP32 CUDA core 加起来还多一个数量级。

Hopper TC 的"4×8×16 per cycle"

物理上一个 Tensor Core 每个 cycle 完成一个 m=4, n=8, k=16 的 MMA（对 FP16/BF16）：

C[4][8] += A[4][16] × B[16][8]
      = 4 × 8 × 16 × 2 (乘+加) = 1024 FMA-equivalent

@ 1.83 GHz × 4 TC/SM × 132 SM
= 1024 × 1.83e9 × 4 × 132
= 989 × 10¹² FLOPS
= 989 TFLOPS dense FP16   ✓ 和白皮书对上

但软件看到的 MMA 形状更大

你用 PTX mma.sync.aligned.m16n8k16.row.col.f16.f16.f16.f16 时，写的是 16×8×16；用 Hopper 新的 wgmma.mma_async.m64n128k16（warp group MMA）写的是 64×128×16。硬件怎么变出来的？

  • m16n8k16 per warp：1 个 warp（32 线程）的协同，累计 4 个 cycle 的硬件 4×8×16。
  • wgmma m64n128k16 per warp group：4 个 warp（128 线程）的协同，占用 TC 16+ cycle。关键：async——warp group 发起后继续干别的，TC 自己跑完再通知。
wgmma 是 Hopper 的灵魂 feature：TC 第一次脱离 warp 级同步，能和 TMA copy、FP32 epilogue 真正流水并行。FlashAttention-3、CUTLASS 3.x、Triton 都重度依赖。第 5 章专门讲指令级细节。

§7Hopper 新成员：TMA（Tensor Memory Accelerator）

Ampere 及之前，从 HBM 搬数据到 SMEM 是靠 warp 内 32 线程每个发一条 LDG（global load），然后 STS（store to SMEM）。问题：

  • 每 warp 要专门"浪费"线程做 address 计算（tile → global 地址很烦）
  • 占用 LD/ST 单元 cycle
  • 寄存器被 load 的值占着，压缩其他用途

Hopper 引入 TMA（Tensor Memory Accelerator）——一个专门的 DMA 引擎，用一条指令就能描述"把 HBM 里某个 N 维张量的子块异步复制到 SMEM"：

// PTX 指令（TMA bulk copy）
cp.async.bulk.tensor.2d.shared::cluster.global
    [dst_smem], [tma_descriptor, {x, y}], [mbar]
// ↑ 整个 warp 只要一个线程调用就够了
//   硬件自己算 stride、swizzle、跨 page boundary

// 等待
mbarrier.try_wait.parity.shared [mbar], phase
TMA 带来的四点提升：
  1. 不占寄存器：数据直通 SMEM，不像 LDG 必须先到寄存器。
  2. 不占 warp 线程：只需一个 issuer thread，省 31 个线程干别的。
  3. 硬件 swizzle：32-bank conflict 自动解决，kernel 作者不用手动排列。
  4. 异步 + mbarrier 同步：和 wgmma 一起组成 Hopper 的 warp-specialized 流水线：一组 warp 只管 TMA（producer），另一组 warp 只管 wgmma（consumer）。

TMA descriptor

host 端一次性在 global memory 构造好一个 tensor map（128 字节）——里面写清楚这个张量的 shape、stride、数据类型、swizzle 模式。后续 kernel 每次调用只要给 offset 坐标 {x, y, z, w, v} 就能拉走一个子块。

§9带走的七句话

  1. SM = 4 个几乎独立的 sub-partition + 共享的 SMEM/L1 + 共享的 TMA。block 的 warp 静态映射到 sub。
  2. 寄存器是 GPU 上最快最多的存储——每 SM 256KB，比 L1 还大；pipeline 隐藏后延迟近乎 0。
  3. Register Pressure 是性能杀手：超出每线程 32 个就会降 occupancy，超出 255 就 spill 到 HBM 直接塌方。
  4. SMEM = 手动 L1：同一块 SRAM，228KB / 28KB 的分配决定你是 flash-style 还是 image-style kernel。
  5. 32 bank + 4B 宽度——避免 stride 是 32 的访问（全挤 bank 0），用 padding 或 swizzle 破冲突。
  6. Tensor Core 每 cycle 做 4×8×16 MMA，软件 API（mma/wgmma）是硬件的 4~64 cycle 聚合。
  7. TMA 让 copy 脱离 warp——Hopper 走向 warp-specialized 流水线（producer/consumer warp）的硬件基础。
