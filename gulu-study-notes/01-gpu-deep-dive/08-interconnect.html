多卡互联 NVLink/NVSwitch · LLM 为什么需要“卡间高速公路” 第一章 · 08/08

当模型大到一张卡放不下，或 batch/吞吐需要多卡，性能瓶颈就从 SM/HBM 扩展到互联网络。Tensor Parallel 的 all-reduce、Pipeline Parallel 的 activation 传递、MoE 的 expert dispatch，全都在考验 PCIe/NVLink/NVSwitch/NCCL。本篇建立多卡通信的硬件与软件全图。

§1为什么 LLM 需要 GPU 互联

单卡性能再强，也会遇到三类墙：

墙表现多卡方案通信代价
显存墙模型权重/KV Cache 放不下Tensor Parallel、Pipeline Parallel、Expert Parallel层内 all-reduce、层间 activation 传输、expert dispatch
吞吐墙单卡 tokens/s 不够Data Parallel、continuous batching 分散推理 DP 通信少，训练 DP 需要梯度同步
延迟墙单请求必须拆多卡才能跑TP/PP 组合每层或每 stage 通信进入关键路径
多卡不是免费扩容：一旦模型层内切到多卡，每层 forward 都可能有通信。互联带宽/延迟不够，Tensor Core 再快也会等通信。

§2PCIe vs NVLink：一条通用路，一条 GPU 专用高速路

互联典型带宽量级拓扑优势短板
PCIe Gen4 x16约 32GB/s 单向GPU → PCIe switch/root complex → GPU通用、成本低带宽远低于 NVLink，延迟更高
PCIe Gen5 x16约 64GB/s 单向同上新平台通用互联仍难支撑高 TP all-reduce
NVLink 3(A100)约 600GB/s 双向/卡GPU 直连或经 NVSwitchGPU 专用高带宽需要 SXM/HGX 平台
NVLink 4(H100)约 900GB/s 双向/卡HGX 8 卡 NVSwitch支撑大模型 TP节点内为主
NVLink 5(B200)约 1.8TB/s 双向/卡NVL72 机柜级 fabricrack-scale 加速域系统复杂、成本高

§3NVSwitch：让任意两张 GPU 都像“邻居”

如果只是 GPU 之间点对点直连，8 张卡会遇到拓扑不均匀：有些卡近，有些卡远。NVSwitch 的目标是提供高带宽 crossbar，让任意 GPU-GPU 通信路径尽量均匀。

NCCL 会读拓扑：实际通信路径由 NCCL 根据 NVLink/NVSwitch/PCIe/NUMA 拓扑选择 ring/tree/channel。相同 8 卡，PCIe 机器和 HGX SXM 机器的 TP 性能完全不是一个量级。

§4NCCL 集合通信：all-reduce 不只是“大家加一下”

Collective语义LLM 中出现在哪里
all-reduce所有 GPU 的张量求和，结果返回所有 GPUTensor Parallel row-parallel linear 输出汇总
all-gather每 GPU 一片，拼完整结果给所有 GPU列切分结果拼接、sequence parallel
reduce-scatter先 reduce，再把结果分片给各 GPU训练梯度、某些 TP 优化
broadcast一张卡发给所有卡参数/metadata 同步
all-to-all每张卡给每张卡不同数据MoE expert parallel token dispatch

Ring all-reduce 的两阶段

1. reduce-scatter: 每张卡把数据分块，沿 ring 传递并累加
2. all-gather: 每张卡把累加后的分块沿 ring 分发给所有卡

通信量近似：2 * (N-1)/N * tensor_size
N 越大，总步数越多；带宽够高还要看延迟。

§5Tensor Parallel 中通信到底在哪里

以 Transformer MLP/Attention 的 Linear 为例，常见两种切法：

切法权重形状每卡做什么是否通信
Column ParallelW[:, shard_n]每卡算一部分输出 channel下一层若能吃 shard，可暂不 gather
Row ParallelW[shard_k, :]每卡算 partial sum需要 all-reduce 求和

一个粗略 all-reduce 时间估算

tensor_size = 64 MB
H100 NVLink 有效带宽假设 600 GB/s
ring all-reduce 通信量 ≈ 2*(N-1)/N*64MB, N=8 → 112MB
纯带宽时间 ≈ 112MB / 600GB/s ≈ 0.19 ms
再加 latency、NCCL launch、拓扑损耗、同步等待
→ 每层 0.2ms 量级就足以影响 decode latency

§6推理服务影响：互联决定 TP 度数和 batch 策略

选择互联好时互联差时
TP 度数可以提高 TP，降低单卡显存压力TP 太高通信吞吐/延迟爆炸
Batch 大小大 batch 摊薄通信固定开销小 batch decode 延迟被通信放大
模型放置优先放在同 NVSwitch 域内跨 PCIe/跨节点尽量避免层内 TP
MoEall-to-all 可接受，expert parallel 更灵活expert dispatch 成为瓶颈
长上下文可考虑跨卡 KV/上下文并行远程 KV 访问会拖垮 decode
实践原则：层内通信（TP all-reduce）必须放在最快互联域内；跨节点更适合 pipeline/data parallel，不适合频繁层内 all-reduce，除非有非常强的网络和专门优化。

§7排障指标：怎么判断卡在互联

  • NCCL 时间占比：profile 中 ncclAllReduce/ncclAllGather 占比高。
  • SM 利用率低但 GPU 忙：Tensor Core 空等通信。
  • batch 增大吞吐不线性：通信或 KV 带宽成为 shared bottleneck。
  • 不同卡 step 时间不一致：拓扑不均、NUMA、某张卡链路退化。
  • NCCL 日志显示走 PCIe：没有走 NVLink/NVSwitch，或拓扑识别异常。
# 常见排查方向（示意）
nvidia-smi topo -m        # 看 GPU-GPU 是 NVLink 还是 PCIe
NCCL_DEBUG=INFO           # 看 NCCL 选择的 ring/tree/channel
nsys profile              # 看 compute 与 nccl 是否重叠
nccl-tests all_reduce_perf # 测实际互联带宽
不要只看理论带宽：实际有效带宽受消息大小、并发 channel、ring/tree 算法、GPU affinity、CPU NUMA、驱动/NCCL 版本影响。服务端要用真实模型 workload profile。

§8带走的八句话

  1. 多卡扩容的代价是通信，通信进入关键路径后，FLOPS 不是唯一指标。
  2. PCIe 是通用路，NVLink 是 GPU 高速路，TP 推理强依赖后者。
  3. NVSwitch 让 8 卡/72 卡形成更均匀的高带宽域，减少拓扑不均。
  4. NCCL collective 是多卡程序的真实执行层，all-reduce/all-gather/all-to-all 要逐个看。
  5. Row Parallel Linear 通常需要 all-reduce，这是 TP 每层通信的核心来源。
  6. Decode 小 batch 时通信更伤延迟，因为固定延迟难以摊薄。
  7. 跨节点层内 TP 要非常谨慎，除非网络和框架都为此优化。
  8. 排障要看实际 profile：NCCL 时间、SM 利用率、topo、NCCL_DEBUG、nccl-tests 缺一不可。
