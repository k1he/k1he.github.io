为什么要有 MultiTransport

同一个 engine 可能面对不同 segment：本机 GPU 走 NVLink/本地路径，远端 GPU 走 RDMA，没有 RDMA 的目标走 TCP，持久层可能走 NVMe-oF。路由层把统一 API 与具体协议解耦。

03注册不是“记录一个指针”

应用视角

addr + length 看起来只是虚拟地址区间。

transport 视角

  1. 校验范围与重叠。
  2. 锁页或注册 GPU memory。
  3. 为 NIC 生成 MR 与 lkey/rkey。
  4. 把可访问信息发布到 metadata。
  5. 保持 buffer 与 key 生命周期一致。

未注册：CPU 指针存在，但 NIC 不能凭它安全 DMA。

性能原则：为 KV pool 整体注册一次并长期复用。若每请求 register/unregister，固定成本和内核/驱动交互会吞掉小传输收益，还容易制造生命周期竞态。

04一个大请求如何变成并行小任务

切片太大：并行度不足、慢路径拖尾。切片太小：WQE、doorbell、CQ 与调度开销变多。最优值取决于 NIC、PCIe、GPU memory、并发和 transport 实现，不能只从网络线速推导。

07BatchID 的实现：一个整数其实是一根裸指针

multi_transport.cpp · allocateBatchID/freeBatchIDhot-path handle

allocateBatchID 在堆上创建 BatchDesc，然后把指针值强转成 uint64_t 返回。后续所有 API 再把这个整数 reinterpret_cast 回引用。这样省掉了全局 map 查找，但把生命周期责任交给调用者。

auto batch_desc = new BatchDesc();
batch_desc->id = BatchID(batch_desc);
return batch_desc->id;

auto& batch = *reinterpret_cast<BatchDesc*>(batch_id);
只有所有 task 都 is_finished 后才能 freeBatchID。提前 free 会产生 use-after-free；忘记 free 会泄漏 BatchDesc。源码在 free 时逐 task 检查，未完成直接返回 BatchBusy。

这也解释了 Python wrapper 常见的完整模板为什么必须是：allocate → submit → poll → free，而不是 submit 返回成功就释放。

08MultiTransport::submitTransfer：路由发生在 task 粒度

capacity check

已有 task 数 + entries 数不能超过申请 batch 时声明的容量，否则返回 TooManyRequests。

resize task_list

为每个 request 建一个 TransferTask，写入 batch_id、request 指针和最终选中的 transport。

selectTransport

根据 target segment 的协议/拓扑选择 backend。一个 batch 可以同时被拆给不同 transport。

group by Transport*

用 unordered_map<Transport*, vector<TransferTask*>> 聚合，减少逐 request 虚函数提交。

submitTransferTask

逐 backend 提交。源码会保留最后一次非 OK 状态，但其他 backend 可能已经接单，所以这是“部分提交可能发生”的接口。

重要错误语义：submit 返回错误不自动回滚已经提交给其他 transport 的 task。上层必须继续处理 batch 状态，不能假定整个 batch 原子失败。

09状态为什么有两层：Task 与 Slice

TransferRequest 是业务提交粒度；RDMA backend 会再按 globalConfig().slice_size 切成 Slice。一个 task 只有在所有 slice 都成功后才完成。

层级关键字段完成条件
BatchDesctask_list、batch_size、finished_transfer_bytes、is_finished所有 task 完成
TransferTaskslice_count、success_slice_count、failed_slice_count、transferred_bytessuccess+failed == slice_count
SlicePENDING/POSTED/SUCCESS/TIMEOUT/FAILED、ts、retry_cntCQE 成功，或重试耗尽/超时

getBatchTransferStatus 会逐 task 调 getTransferStatus。这不是一个只读 getter：某些 backend 会在查询时推进异步完成，例如 NVLink 路径可能在这里查询 CUDA stream。

submitTransfer == OK 只表示任务被 backend 接受；getBatchTransferStatus == COMPLETED 才表示所有 slice 已完成。若要让 GPU kernel 消费，还要满足调用方自己的 stream/event 可见性。
