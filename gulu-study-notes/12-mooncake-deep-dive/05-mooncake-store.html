Store 的关键不是 Put/Get，而是何时算可见

Master 分配空间与维护元数据，Client 之间直传 payload。PutStart 与 PutEnd 把“预留了副本”与“完整对象已提交”分开，这正是大对象分布式写入必须有的事务边界。

01三类角色与所有权

Master

key/replica 元数据、segment 挂载、空间分配、心跳、lease 与淘汰协调；通过 etcd 做 HA。它不承载对象 payload。

Client

既可发 Put/Get，也可贡献内存成为 storage server；用 Transfer Engine 直连别的 client。

DFS

可选持久/大容量层。内存写完成后异步下沉；内存 miss 时可从 DFS 回源。

02Put 为什么必须分三段

01PutStart(key,size)Master allocates replicas
02ALLOCATEDnot readable yet
03Direct Writeclient → replicas
04PutEndcommit metadata
05COMPLETEvisible to readers

核心不变量：Get 只能返回 COMPLETE 的 replica。若客户端 PutStart 后崩溃，Master 必须通过 timeout/lease 回收 ALLOCATED 空间，不能把半写数据暴露给读者。

03Get 不是从 Master 下载

client → master.GetReplicaList(key)
       ← [segment_id, offset, size, state=COMPLETE, ...]
client → chosen replica client  // Transfer Engine direct read
       ← payload bytes
client → local buffer / GPU cache

副本选择可以考虑拓扑、健康状态和负载。Master 只回几十到几百字节的描述；GB 级 payload 走 client-to-client 数据面。

04Lease、soft pin、hard pin 解决不同问题

机制保护什么典型取舍
Lease读者在规定窗口内使用副本，避免刚取得位置就被回收过长降低回收效率，过短导致慢读失败
Soft pin尽量保留热点，但空间紧张时仍可淘汰性能提示，不是强正确性保证
Hard pin明确禁止淘汰必须限额，否则可把 allocator 锁死

为什么推荐 offset allocator

大内存 segment 内只分配 offset/length，不为每个对象单独 malloc/free。元数据紧凑，分配路径可做到近 O(1)，也更适合远端以 segment + offset 寻址。

07Replica 不是一个地址：先读状态与数据变体

mooncake-store/include/replica.hsnapshot f7330a635747

Replica 的 payload 位置是一个 variant：Memory、NoF SSD、普通 Disk、Local Disk 各有不同 descriptor。状态机共有六态：

UNDEFINED尚未初始化
INITIALIZED空间已分配
PROCESSING写入进行中
COMPLETE允许 Get 返回
REMOVED / FAILED不可再读

ReplicateConfig 不只有 replica_num：还包含 NoF 副本数、soft/hard pin、preferred segments、同节点分配、data type、host_id 与 group_ids。分配策略的输入就是这些字段。

GetReplicaList 只访问满足 fn_is_completed 的副本。地址已分配甚至 payload 已写完，都不等于可见；只有 PutEnd 推进到 COMPLETE 才建立读者可见性。

08Client::Put：真实代码不是“写失败就全部失败”

slice_lengths

把用户的多个 Slice 长度提取出来交给 Master；Store 对象可以由多段 buffer 组成。

AttachHostId

把 client 所在 host 注入配置，供同机优先和拓扑分配使用；CXL 路径还会强制 preferred segment。

PutStart

Master 返回一组 Replica::Descriptor。OBJECT_ALREADY_EXISTS 在普通 Put 中被当作幂等成功。

disk first

若有 storage backend，源码先从返回列表尾部寻找 disk replica 并写本地文件，保证之后能明确 PutEnd/PutRevoke。

TransferWrite

逐 memory/NoF replica 传输，ReplicaTransferSummary 分类型记录成功和错误。

finalize

DetermineFinalizeDecision 根据副本模式与成功数决定对哪些类型 PutEnd、对哪些 PutRevoke，以及整体是否成功。

这意味着写语义由 ReplicaWriteMode 决定：单副本、flexible dual replica、reliable multi replica 对“部分成功”有不同判断，不能把 Store 简化成固定 all-or-nothing。

部分成功路径：payload 可能已经写入某些副本，但最终策略判失败并 revoke 另一些副本。排查空间泄漏时要同时看 PutEnd 与 PutRevoke，而不是只搜 transfer error。

09MasterService::PutStart：真正复杂的是并发与旧写清理

master_service.cpp:3043 · PutStartallocation transaction begin
  1. 规范化 tenant，并校验 key、slice length、副本数与构建能力。
  2. 更新 client→host 映射，计算 group route 和本次 quota charge。
  3. 取得 object operation lock，避免同一个 tenant/key 的并发写互相穿透。
  4. 在 metadata shard 内查旧对象：若已有 COMPLETE 副本，或旧 PutStart 尚未超过 discard timeout，返回 OBJECT_ALREADY_EXISTS。
  5. 若旧写已陈旧，取出 PROCESSING replicas 放入延迟释放队列，再删除旧 metadata。
  6. 调用 AllocateAndInsertMetadata 分配副本并插入 PROCESSING 状态。
  7. 若 tenant quota 超限，尝试为该 tenant 淘汰内存后重试，次数耗尽才拒绝。
这里存在三层锁/路由概念：全局 snapshot shared lock、按 metadata shard 的 accessor、按 object 的 operation lock。只看到“Master 有锁”远远不够；它们分别保护快照一致性、分片 metadata 和同 key 操作串行化。

10PutEnd：谁有资格提交，提交了哪些副本

PutEnd 首先重新定位 tenant/key metadata；不存在返回 OBJECT_NOT_FOUND。随后比较调用方 client_id 与 PutStart 记录的 owner，不一致返回 ILLEGAL_CLIENT，避免另一个 client 提交不属于它的半成品。

接着按 ReplicaType 筛选副本：MEMORY、NOF_SSD 或 ALL，只把 handle 有效的对应副本 mark_complete。最后把预留 quota 分成 commit 与 abort 两部分进行结算。

PutEnd 不是“给 key 设一个 completed=true”。完成状态属于各个 Replica；同一对象的不同介质副本可以处于不同状态，quota 也按实际完成的 memory replica 结算。

11Get 路径：lease 在数据搬完以后还要再检查

Query

MasterClient::GetReplicaList 返回 COMPLETE descriptors 与 lease_ttl_ms；client 用本地 steady_clock 计算绝对 expiry。

FindFirstCompleteReplica

没有完整副本返回 INVALID_REPLICA。range read 还额外要求 memory replica。

hot cache redirect

若本地 hot cache 命中，把 descriptor 改指本地副本并增加引用，传输后释放。

TransferRead

通过 Transfer Engine 把 replica 数据读入调用方 slices；记录 get_latency_us。

lease check

数据传完后再次检查 QueryResult::IsLeaseExpired；若期间过期，返回 LEASE_EXPIRED，而不是把可能已被回收的数据当成功。

promotion

频率准入通过后异步提升到本地 hot cache；已从 hot cache 命中则不重复提升/计数。

Master 侧 GetReplicaList 在持有 metadata 只读访问时收集 COMPLETE replicas 并 GrantLease；promotion-on-hit 的入队刻意放在释放只读 accessor 之后，避免 lock upgrade 的复杂性。
