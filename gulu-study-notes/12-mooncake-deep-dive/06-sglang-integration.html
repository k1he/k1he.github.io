同一个 Mooncake，两种完全不同的语义

PD connector 把已知源地址的 KV 一次性交给已知目标；HiCache 把 KV 作为可按 key 查找、复用、淘汰的对象存入 Mooncake Store。前者是搬运协议，后者是缓存系统。

03HiCache：上层决定“对象的 key 与层级”

L1 · GPU cache

最快、容量最小，模型执行直接消费。

EVICT / LOAD

L2/L3 · Mooncake Store

容量更大、远端可共享；以对象方式 Put/Get，需要 key、一致性和淘汰。

HiCache 的价值不在一次 P→D 交接，而在 GPU cache miss 时仍能从更大层级取回已计算 KV，避免完整重算。它可能与 PD 同时存在：P/D 是计算阶段的部署分离，HiCache 是缓存层级。

07MooncakeTransferEngine wrapper：异常为何被压成 -1

构造函数导入 mooncake.engine.TransferEngine，根据 GPU 选择 IB device；MC_FORCE_TCP=1 时清空 HCA。initialize 最终调用：

engine.initialize(hostname, "P2PHANDSHAKE", protocol, device_name)

session_id 不是随机 UUID，而是 hostname + engine.get_rpc_port()。接收端把它通过 bootstrap 发给 Prefill，Prefill 用它建立 Mooncake peer。

register、deregister、transfer_sync 都捕获任意 Exception 并转成 -1；因此上层日志若只打印返回码，会丢失 binding 原始异常栈。batch API 还会用 hasattr 区分“运行失败”和“安装的 Mooncake 版本过旧”。

SGLang 的 transfer_sync 是同步封装，不等于底层没有 batch/slice/CQ。它只是把 allocate/submit/poll/free 隐藏在 binding 中，上层线程仍会被这一调用占住。

08MooncakeKVManager 初始化：为什么要在请求前注册整个池

init_engine

从 parallel_state 取得共享 MooncakeTransferEngine，避免同 rank 重复初始化。

batch_register KV

一次注册 kv_data_ptrs/kv_data_lens，通常对应各层或各 pool 的长期 buffer。

batch_register aux

注册辅助 metadata buffer；状态空间模型还逐组注册 state_data_ptrs。

role threads

Prefill 创建 transfer queues、ThreadPoolExecutors 和 transfer_worker；Decode 启动接收线程。staging 模式再注册 staging buffer/allocator。

Prefill 的线程池大小默认按 CPU 数计算并限制在 4–12 之间，再分配给多个 transfer queue；源码断言 worker 数不得小于 queue 数。这里的性能瓶颈可能是 Python 线程/队列和地址构造，而不只是 RDMA。

09Decode 如何把“目标地址”告诉 Prefill

MooncakeKVReceiver._register_kv_args 把以下内容打包成 ZMQ multipart：

  1. Decode IP、rank port、Mooncake session_id；
  2. 所有 kv_data_ptrs 与 aux_data_ptrs，指针以 unsigned 64-bit 打包；
  3. state ptrs/item lengths/dim；
  4. 目标 TP rank、attention TP size、kv_item_len；
  5. 启用 staging 时的 base ptr 与总大小。

之后 send_metadata 再发送本请求的 bootstrap_room、目标 page indices、aux index、state indices、required_dst_info_num 和 decode_prefix_len。

Mooncake session 解决“连接哪台进程”，裸 ptr 解决“哪个池”，page index 解决“池里的哪个 slot”。三者缺一不可。把 pointer 交换称为“Mooncake 自动识别 KV page”是错误的；page 语义完全来自 SGLang。

10M→N TP 不一致时，地址是怎样切出来的

send_kvcache_slice 是最值得精读的函数。它先用总 KV head 数，而不是每 rank 的截断值，计算：

src_heads_per_rank = max(1, total_kv_heads // prefill_tp)
dst_heads_per_rank = max(1, total_kv_heads // decode_tp)
bytes_per_head = dst_kv_item_len // page_size // dst_heads_per_rank

若 Prefill TP > Decode TP，多 Prefill rank 汇入一个 Decode rank；反之一个 Prefill rank 要按 head slice 扇出。GQA 情况下 src_replication = prefill_tp // total_kv_heads 用来识别哪些 rank 持有重复 KV head。

随后 page index 与 page 内 token offset 做二维广播，生成每层每个 token slot 的精确 source/destination 地址，再为 K、V 的每一层分别提交到 executor。

源码自己明确标注的代价：为保证任意 page_size 与 head slicing 正确，这条路径会对每个 token slot 构造 transfer；长序列会增加调用数与 TTFT。正确性优先，但必须用 staging/batching 或同 TP fast path 避免它成为热点。

11Sender/Receiver 的 KVPoll 并不是同一个等待状态

角色入口中间态超时检查
Sendersend() 把 chunk 加入 transfer queueBootstrapping / Transferringbootstrap timeout
Receiversend_metadata() 发布目标 slotsWaitingForInputwaiting timeout

Sender 的最后一个 chunk 还携带 aux/state indices；非最后 chunk 只排 KV。poll 达到 Success/Failed 后把状态固化到 conclude_state，避免重复读取共享状态。跨 rank 失败可能只留下“another rank unknown reason”，因此 failure_records 必须在原始失败 rank 就记录。

12HiCache 为什么能复用同一个 Transfer Engine

MooncakeStore.__init__ 只有在三个条件同时满足时复用已经初始化的 engine：IB device 相同、metadata_server 为 P2PHANDSHAKE、protocol 为 rdma。否则 Store 自己创建 engine，避免配置不一致导致 segment/key 错配。

standalone_storage 路径则要求 MooncakeHostTensorAllocator，并统计 KV buffer 与 Mamba 等 sidecar hybrid buffers 的总字节，交给独立 mooncake_client 进程映射。这里体现了 HiCache 与 PD 的根本差别：它管理长期 host object，而 PD 只完成一次请求的已知地址交接。
