先用一句话建立全景

传统系统把“模型计算、KVCache 和请求调度”都局限在某台 GPU 服务器里；Mooncake把 Prefill、Decode 和 KVCache 分成三个可独立调度的资源池，再由 Conductor 选择计算位置，用高速网络把可复用 KV 送到需要它的地方。

Mooncake = P/D 计算分离 + 全局 KVCache 池 + KV-aware 调度 + 高速传输

01论文背景：LLM 服务为何出现了新的系统问题

一次 LLM 请求有两个性质完全不同的阶段。Prefill 一次读入整段 prompt，并行计算每个 token 的 K/V；Decode 则反复读取已经生成的 KVCache，每次只产生一个新 token。KVCache 是模型对历史上下文计算出的中间状态：保留它，就不必为旧 token 重做 attention 的 K/V 投影。

Prefill · 读题并做笔记

输入越长，计算量越大；适合大矩阵并行，通常是 compute-bound。结束后产生整段上下文的 KVCache。

prompt tokens → GPU compute → K/V blocks
THEN

Decode · 翻笔记逐字作答

每一步都读取历史 KV，只追加一个 token；并行度小、持续访问显存，通常更偏 memory-bound。

existing KV + one query → next token
关键背景：聊天不是互相独立的短请求。第二轮会携带系统提示词、第一轮问题和回答；第三轮又携带前两轮历史。传统系统若没有跨请求复用，每轮都要重新 prefill 已经计算过的历史。

为什么“相同前缀”的 KV 可以复用

自回归 Transformer 中，一个 token 的 K/V 只依赖它自己和它之前的 token。两次请求若从第 1 个 token 开始有一段完全相同的前缀，这段前缀产生的 KV 也相同；后一次请求可以从命中位置继续计算。

请求 A： [system][history ───────][question A]
请求 B： [system][history ───────][question B]
         └── 可复用 prefix KV ──┘

为什么只缓存 token ids 不够

token ids 只是“题目”；KVCache 才是模型逐层算出的“中间答案”。保存 token 只能省去 tokenizer，不能省去几十层 Transformer 的 prefill 计算。

复用前提：模型权重/版本、tokenizer、chat template、token 序列、位置语义和 KV layout/dtype 必须兼容。不是文字看起来相似就能复用。

02Mooncake 要解决的不是一个问题，而是三个问题同时发生

① 重复计算

多轮对话和共享系统提示词形成大量相同前缀。GPU 一遍遍为相同 token 生成同样的 KV，昂贵算力被浪费。

② HBM 装不下

KVCache 随层数、KV heads、上下文长度和并发线性增长。论文的 LLaMA3-70B 配置约为 320KB/token：8K KV 约 2.5GB，128K 约 40GB。

③ 两阶段互相干扰

长 prefill 会占据计算资源，decode 又要求稳定的 token 间隔。统一 GPU 池里，大 prefill 容易把 decode 的 TBT 拉长。

多轮对话：重复 prefill 是怎样累积的

首轮 4,096 token，每轮新增 256 token
传统重算
复用 KV

朴素解法的局限：把 prefix cache 留在生成它的 GPU 上，容量受 HBM 限制，也把请求调度绑在那台机器上；把所有 KV 永久放远端又可能让网络代价超过省下的计算。Mooncake 必须同时解决容量、位置、传输和全局调度。

03Mooncake 的解决方案：把 KVCache 提升为一等系统资源

论文标题是 Trading More Storage for Less Computation。核心思想不是简单“把 KV 搬到另一台机器”，而是构建一个由 GPU HBM、CPU DRAM、SSD 和高速网络共同组成的分布式 KVCache 池，让计算节点可以按需复用历史状态。

01 · CONTROLConductor掌握负载、SLO 与 KV 位置，做准入和全局调度
02 · REUSEPrefix Lookup按 block 哈希寻找已存在的历史 KV
03 · COMPUTEPrefill Cluster只计算未命中的增量 token
04 · MOVEStore / Transfer Engine管理 KV block，并流式搬到 Decode
05 · SERVEDecode Cluster隔离长 prefill 干扰，稳定逐 token 生成

空间换计算

历史 KV 放入更大、更便宜的 CPU DRAM/SSD/远端内存，命中后直接取回，只计算新增内容。

分离换稳定性

Prefill 与 Decode 使用不同 GPU 池，可分别扩缩容；Conductor 根据 SLO、负载与 KV 位置做全局选择。

版本提示：FAST’25 论文使用 Mooncake Store 管理分布式 KV block，并由其中的 Transfer Engine 执行零拷贝、多 NIC 传输；当前开源仓库把 Transfer Engine、Mooncake Store 等进一步模块化。阅读较早的技术报告或旧资料时可能遇到不同命名，应以概念职责而不是类名对应。

和几种常见基线相比，Mooncake 多做了什么

方案缓解了什么仍然受限于什么
统一 P+D架构简单、KV 本地可读长 Prefill 会干扰 Decode；两类资源无法独立配比
Local Prefix Cache命中时避免部分重复计算受单机 HBM/DRAM 容量与局部热点限制；请求被 KV 位置绑住

04为什么这个方案在 Mooncake 的生产负载中成立

FAST’25 论文没有只用一个平均数概括全部流量，而是拆成三类 workload。它们共同特点是输入很长、输出相对短，并且存在可观的 prefix cache ratio：

Workload平均输入平均输出Prefix cache ratio请求数复用来源
Conversation12,03534340%12,031多轮对话历史
Tool & Agent8,59618259%23,608长且重复的 system prompt
Synthetic15,32514966%3,993受控构造的共享前缀

为什么本地缓存不够

论文以 LLaMA3-70B 分析：约 1TB 本地 DRAM 只能存约 300 万 token，在多数 workload 中达不到理论最大命中率的一半；约 5,000 万 token 才接近最大值，需要聚合至少 20 台节点的 DRAM。

为什么热点需要副本

全局容量解决“装不下”，却可能让热门 block 的所在节点成为新瓶颈。Mooncake 会增加热点 KV 的副本、迁移冷块，在命中率与访问带宽之间平衡。

热前缀：为什么缓存容量不是越大越线性

绿色 = 命中；颜色越亮 = 越热

05方案何时有收益：必须算清这笔账

传统路径：重复计算

请求到来后重新 prefill 全部历史。无网络依赖，但相同 token 的 attention/KV projection 被反复执行。

T = Tqueue + Tprefill(all)
VERSUS

Mooncake 路径：复用并搬运

命中旧 KV，只为增量 token 做 prefill，再把需要的 KV 送到 Decode 节点。

T = Tlookup + Tprefill(Δ) + Ttransfer
成立条件：省下的 prefill 时间必须大于 lookup、KV 传输、排队和一致性管理中未被 overlap 的部分。“使用 RDMA”本身不等于端到端一定更快。

06为什么解决方案里还需要 early rejection

即使 KV 可以复用，系统过载时仍可能无法满足服务目标。SLO 不是“GPU 最终能不能做完”，而是请求经过排队、Prefill、KV 传输和 Decode 后，是否仍能按时返回首 token 并维持稳定 TBT。Conductor 用全局视图预测完成时间，尽早拒绝注定违约的请求，避免它继续占资源并拖累可完成请求。

09读完自测：能回答这些，才算理解动机

Q1：为什么缓存 token ids 不能替代 KVCache？
因为 token ids 只是输入，仍需经过所有 Transformer 层计算 K/V；缓存 KV 才能跳过已命中前缀的计算。

Q2：为什么不把 KV 全留在生成它的 GPU？
HBM 容量小、跨请求全局命中差，并会让调度被 KV 位置绑定；但放远端又必须支付传输成本。

Q3：Mooncake 的核心只是 P/D 分离吗？
不是。论文的完整命题是 P/D 分离、分布式 KVCache、KV-aware 全局调度与高性能传输共同工作。

Q4：什么时候复用反而不划算？
前缀短/命中低、网络慢或拥塞、固定开销大、重算很快，且传输无法与计算 overlap 时。
