04四组最有信息量的对照实验

A · TCP vs RDMA

固定 payload、并发、buffer、拓扑，只换 transport。若差异很小，瓶颈可能在注册、调度、PCIe 或上层等待。

B · 1 NIC vs N NIC

画 per-NIC 带宽和 batch 完成时间。线性差说明上游饱和；波动差说明切片/路径不均。

C · 预注册 vs 每请求注册

尤其测 1–64MiB 小对象 p99。它能直接暴露固定注册成本是否进入关键路径。

D · 搬运 vs 重算

按 prefix tokens 分桶，找到复用 break-even，而不是对全量请求给一个平均提升。

05上线前清单

  • GPU/host buffer 在进程生命周期内注册复用；地址、长度、设备/NUMA 绑定已记录。
  • 控制面与数据面端口、网卡名、GID/协议、路由可达性在每台节点一致验证。
  • submit accepted 与 transfer complete 有独立指标；超时后 buffer 不会提前复用。
  • PD 路径验证 rank/page/layer/offset/dtype；Store 路径验证 PutEnd/lease/replica state。
  • 至少有 TCP fallback 或明确 fail-fast 策略；多 NIC 单路故障演练过。
  • 容量、带宽、QP/CQ/线程池均有余量；告警以 p99 与 SLO 为主。

08一个可复现排障记录应该长什么样

source commit: Mooncake f7330a635747 / SGLang 495ae9aaa609
request: room, src/dst rank, TP/PP, page_size, pages, bytes
memory: ptr range, registered range, device/location, register time
metadata: session_id, target_id, segment version, target offset
transfer: batch_id, tasks, slices, selected local NIC → peer rail
completion: submit ts, first/last CQE ts, retries, wc.status
business: KV ready ts, decode consume ts, TTFT/TBT

没有这些字段的“偶现 timeout”很难定位，因为下一次重试可能换了 NIC、segment 或 page。调试日志的目标不是越多越好，而是能把同一个 slice 从业务请求关联到 CQE。
