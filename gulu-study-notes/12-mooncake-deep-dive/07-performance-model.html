LESSON 07 / 08 · QUANTITATIVE MODEL

不要问“Mooncake 快不快”，要算这批 KV 值不值得搬

先由模型结构算每 token KV 字节，再把传输分解为固定开销、字节时间、排队和 overlap。最后与被省掉的 prefill 计算比较，而不是拿网络线速做结论。

01从 GQA 结构算 KV 字节数

KV bytes/token = 2(K+V) × nlayers × nkv_heads × head_dim × dtype_bytes

注意这里用 n_kv_heads，不是 query heads。若 TP 对 KV heads 分片，每 rank 实际传输量还要结合复制/分片策略；若只搬增量或命中后的缺失部分，token 数也不是完整 context。

03Break-even 判断

复用值得做 ⇔ Tprefill_saved > Tlookup + (1-overlap) × Ttransfer + Tmiss/risk

04评估时必须拆开的时间点

05容量与带宽是两个独立预算

容量预算

cache bytes ≈ active prefixes × avg cached tokens × KV bytes/token × replicas

还要加入 allocator 碎片、对象 metadata、硬 pin 余量和恢复副本的临时峰值。

带宽预算

required BW ≈ requests/s × transferred KV/request ÷ target utilization

目标利用率不要设 100%；为热点、恢复、重传和 p99 留余量，并按 NUMA/NIC 分布看而非只看整机总和。

06把论文公式和源码参数接起来

论文对 LLaMA3-70B 写出的 KV 大小是 p × layers × (2 × d / GQA) × element_size；Prefill FLOPs 同时包含随长度平方增长的 attention 项和线性 MLP 项。复用是否降低 TTFT，本质是：

KV loading time < saved prefill compute time

论文代入 8×A800、8K prefix 得到最低有效加载带宽约 6GB/s；8×H800 因计算更快，门槛升到约 19GB/s。计算硬件越快，网络越容易成为复用瓶颈，这一点常被“模型更快所以系统都更快”掩盖。

07Benchmark 不能只跑一个 payload

至少做二维矩阵：payload size（128KB、1MB、16MB、256MB、数 GB）× concurrency（1、8、32、64），并分别报告：

  • application goodput GB/s，而不是只读 NIC counter；
  • submit→complete 的 p50/p95/p99；
  • 每请求 slice 数、WQE/CQE 数和 retry 数；
  • 每 NIC/NUMA lane 的带宽与不均衡；
  • 注册是否在计时区间内；
  • 最终 TTFT/TBT 与 recompute baseline。

FAST’25 的 87/190GB/s 是 40GB KV、并发 64、特定 4×200G/8×400G 环境下的结果。若你的请求是大量 1MB slice，不能用那组数字代入。
