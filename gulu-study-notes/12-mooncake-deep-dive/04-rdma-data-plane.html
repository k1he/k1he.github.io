04所谓“零拷贝”的成本账本

固定成本

segment lookup、endpoint 建连/恢复、WQE/CQE、线程调度。小 KV 时支配延迟。

字节成本

bytes / effective bandwidth。有效带宽是 GPU memory、PCIe、NIC、fabric、对端写入能力中的最小值。

排队与抖动

QP 深度、CQ poll、共享 NIC、PFC/ECN、重传、NUMA 跨 socket。尾延迟往往在这里。

Ttransfer = Tlookup + Tsubmit + bytes / BWeffective + Tqueue + Tcompletion

05三条正确性红线

  1. 地址有效：提交到 CQ 完成期间，源/目标 buffer 不得释放、重分配或被错误复用。
  2. key 有效：MR 重新注册后旧 rkey 不能继续缓存使用；endpoint/metadata 更新必须一致。
  3. 完成可见：硬件完成与业务可读之间还可能有跨线程信号、GPU stream/event、Store PutEnd 等上层屏障。

06registerLocalMemoryInternal：一次注册穿过哪些层

rdma_transport.cpp:210 · registerLocalMemoryInternalsnapshot f7330a635747
access rights

基础权限同时包含 LOCAL_WRITE、REMOTE_WRITE、REMOTE_READ；配置允许时再加入 RELAXED_ORDERING。

pre-touch

多 context、CPU 核足够且区域 ≥4GiB 时，先并行触页，避免注册阶段集中 page fault。

register per context

同一段内存要在每个 RdmaContext/NIC 上建立 MR。是否并行由 parallel_reg_mr、context 数量和 pre-touch 决定。

collect keys

逐 context 收集 lkey/rkey，所以 BufferDesc 中 key 是数组，不是单值。

resolve location

location 为通配符时查询内存位置，用于 NUMA/GPU/NIC 拓扑选择。

publish metadata

addLocalMemoryBuffer 把 addr、length、location、keys 加入本地 segment 描述并按配置发布。

// 一个 buffer 对多个 NIC/context 各有一对 key
for (auto& context : context_list_) {
  buffer_desc.lkey.push_back(context->lkey(addr));
  buffer_desc.rkey.push_back(context->rkey(addr));
}
“注册一次”不是产生一个 rkey，而是为可用的每个 context 建 MR。注册部分成功后若某个 context 失败，清理是否完整、metadata 是否发布，是排查泄漏和 stale key 的关键。

07submitTransferTask：大请求如何切 Slice

rdma_transport.cpp:571 · RdmaTransport::submitTransferTaskrequest → slices

函数先读取三个全局参数：slice_size 决定常规切片，fragment_limit 决定是否把很小的尾片并入上一片，max_wr × num_qp_per_ep 是一次向 context 下发的 watermark。

for (offset = 0; offset < request.length; offset += slice_size) {
  merge_final = remaining <= slice_size + fragment_limit;
  slice->source_addr = request.source + offset;
  slice->rdma.dest_addr = request.target_offset + offset;
  slice->length = merge_final ? remaining : slice_size;
}

随后对 source 范围调用 selectDevice，找到覆盖该地址的本地 BufferDesc 与活跃 context，从对应数组取 lkey[device_id]。找不到就返回 AddressNotRegistered，任务不会神奇地退化成 TCP。

切片必须同时满足三件事：source 范围被本地 MR 覆盖；target offset 被远端某个 BufferDesc 覆盖；选择的 local context 与 key 数组下标一致。任一映射错，都会在 submit 或 CQ 阶段失败。

08WorkerPool 的真实线程模型

Transfer workers

构造函数创建 kTransferWorkerCount 个线程执行 transferWorker。它们负责从分片队列取任务、准备 endpoint/QP、post send 和 poll CQ。

Monitor worker

额外线程执行 monitorWorker，处理 context async event、恢复调度、rail 健康状态和拓扑重新发布。

队列不是一把全局锁：源码按 kShardCount 分片，并维护每 shard 的计数和锁；worker 按分配的 shard 扫描，再把任务合并到 thread-local 的 endpoint 队列。这样降低多 producer/worker 在高并发下的锁竞争。

09performPostSend：连接失败不是统一重试

context health

本地 RNIC/context 不活跃时，不把它误判成远端 rail 坏；任务尝试 handoff 给另一张本地 NIC。

rail availability

peer rail 被暂停或标记失败时，slice 进入 failed list，后续重新选择远端路径。

endpoint cache

按 peer NIC path 查/建 RdmaEndPoint；未连接则主动 handshake 建 QP。

ready ACK

QP connected 后仍要等待 ready ACK。超时会删除 endpoint、标记 rail 并触发 redispatch。

post send

把 endpoint 指针写入 slice，再由 endpoint 构造 WR、检查 QP depth 并提交。

这段代码刻意区分“本地 context 坏”和“远端 rail 坏”：前者换本地 NIC，后者保留本地 context、换 peer rail。把两者都做成重连同一 QP，会造成无效重试和长尾。

10performPollCq：从 CQE 到业务完成

每次每个 CQ 最多 poll 64 个 completion。wr_id 直接保存 Slice 指针，因此取到 CQE 后能 O(1) 回到所属 task。成功路径调用 slice->markSuccess()，原子累加 task 的成功 slice 数与 transferred bytes。

CQE 情况源码策略
IBV_WC_SUCCESS释放 QP depth，slice 成功，逐层汇总 task/batch
IBV_WC_WR_FLUSH_ERR常见于 endpoint 正常销毁导致 QP→ERR；不直接当真实网络故障，按 context 状态重新分发
本地 context 故障记录 local failure，尝试另一 local RNIC
远端/默认 completion error标记 peer rail，删除/重建 endpoint，按 retry budget 换路径
CQE 成功只证明 RNIC 完成了这条 WR。业务层还要等一个 task 的所有 slice 成功、一个 batch 的所有 task 成功，并完成 CPU/GPU stream 间的同步。

11读 RDMA 源码时可直接回答的细节题

为什么 BufferDesc 里是 lkey/rkey 数组？
同一 buffer 会向多个 RdmaContext 注册，每张 NIC 有自己的 MR/key。
为什么 4GiB 以上区域可能 pre-touch？
减少多 context 注册时的 page fault 成本；未触页内存盲目并行注册反而可能更慢。
为什么 slice 要保存 endpoint 指针和 qp_depth 指针？
CQ 回来时需要归还具体 QP 的 outstanding depth，并把失败精确归因到路径。
多 NIC failover 为什么需要区分 local/peer？
决定是换本地 RNIC 还是换远端 rail；错误归因会让任务不断选择同一坏路径。
