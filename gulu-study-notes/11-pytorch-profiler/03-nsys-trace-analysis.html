§1模式一：GPU 空闲 · "GPU 大部分时间在发呆"

nsys 中的症状

  • CUDA HW 行有大段空白——GPU 没在执行任何 kernel
  • GPU SM Utilization < 50%（在 nvml 行看）
  • 总 wall time 远大于 GPU kernel 总时间

常见原因与修复

原因nsys 中的验证修复策略
DataLoader 太慢CPU 线程行中 pthread_mutex_lock 等待长num_workers=8, pin_memory=True
CPU 预处理重CPU 行密集，CUDA HW 行空白把 transform 移到 GPU 或离线化
模型太小 / batch 太小kernel 很快结束，但 launch 间隙大增大 batch size / CUDA Graph
频繁 CPU-GPU 同步CUDA API 行出现 cudaStreamSynchronize见 §3 隐式同步
黄金法则：GPU idle 意味着你的 GPU 算力白白浪费。解决思路永远是：让 GPU 有事做——要么让 CPU 更快喂数据，要么让 GPU 的 kernel 更密集。

§2模式二：CPU 瓶颈 · "CPU 在拼命干，GPU 在等"

nsys 中的症状

  • CPU 线程行密密麻麻，CUDA HW 行稀疏
  • OS Runtime 行有大量 malloc / free / pthread 调用
  • GPU SM Utilization < 40%

典型场景：Python GIL 限制

# 单线程 Python 推理：GIL 导致 CPU 无法并行 launch kernel
# nsys 中看到：CPU 线程只有一个活跃，kernel launch 之间有大段空白

# 修复：使用多进程 (torchrun) 或 CUDA Graph 减少 launch 开销

典型场景：数据加载瓶颈

# nsys 中看到：CPU 线程在 pthread_mutex_lock 上等待
# 修复：DataLoader 调优
DataLoader(
    dataset,
    num_workers=8,             # GPU 数 × 4
    pin_memory=True,            # H2D 快 2x
    persistent_workers=True,    # 不杀 worker 进程
    prefetch_factor=3,          # 预取队列深度
)

诊断命令

# 看 CPU 热点函数（需要 --sample=cpu）
nsys stats --report=cpu sglang_trace.nsys-rep

# 看 OS Runtime 调用统计
nsys stats --report=osrt sglang_trace.nsys-rep

§3模式三：隐式同步 · "一行代码让 GPU 停摆"

nsys 中的症状

  • CUDA API 行出现 cudaStreamSynchronize 或 cudaDeviceSynchronize
  • CUDA HW 行突然出现空白间隙，然后恢复
  • 同步调用期间，GPU 排队的 kernel 全部排空后 GPU 空闲
性能杀手 No.1：隐式同步让 CPU 停下来等 GPU 完成，GPU 排队中的 kernel 被排空，之后 GPU 只能等 CPU 继续投喂。整条流水线断裂。

常见的隐式同步触发点

操作为什么触发同步替代方案
.item()需要把 GPU 标量拷贝到 CPU → 必须等 GPU 算完累积 tensor，周期性 .item()
print(tensor)隐式 .item()用 tensor.shape 或 tensor.dtype 代替
.cpu()D2H 拷贝必须等 GPU 就绪用 non_blocking=True
if tensor > 0:需要 CPU 端的 bool 值用 torch.where 在 GPU 上做判断
读 .grad（刚 backward 后）梯度还在 GPU 上延迟读取，或用 hook
torch.cuda.synchronize()显式同步只在 benchmark 时使用

真实案例：一行 .item() 吃掉 15% 性能

# ❌ 每步都同步
for step in range(steps):
    loss = train_step()
    running_loss += loss.item()  # ← 每步都触发 cudaStreamSynchronize!

# ✅ 累积 tensor，周期性同步
loss_accum += loss.detach()
if step % 50 == 0:
    print(f"loss: {loss_accum.item()/50:.4f}")
    loss_accum = 0

§4模式四：数据搬运与通信 · H2D/D2H/NCCL

nsys 中的症状

  • Memcpy 行有大量 Memcpy HtoD / Memcpy DtoH 事件
  • NCCL 行有大量 AllReduce / AllGather 事件
  • 这些事件的时间占比 > 20%

数据搬运速度对比

传输类型典型带宽1GB 耗时nsys 中怎么看
HBM (GPU 内部)~3350 GB/s~0.3msCUDA HW 行的 kernel
NVLink (GPU 间)~900 GB/s~1.1msNCCL 行
PCIe Gen5 (CPU↔GPU)~60 GB/s~17msMemcpy 行
PCIe Gen4 (CPU↔GPU)~25 GB/s~40msMemcpy 行
RDMA (跨节点)~100 Gb/s~80msNCCL / 自定义 RDMA 行

优化策略

# H2D 优化：用 non_blocking 异步传输
inputs = inputs.cuda(non_blocking=True)

# 数据预取：用单独 CUDA Stream 重叠计算和传输
class DataPrefetcher:
    def __init__(self, loader):
        self.loader = iter(loader)
        self.stream = torch.cuda.Stream()
        self.preload()

    def preload(self):
        try:
            self.next_input, self.next_target = next(self.loader)
        except StopIteration:
            self.next_input = self.next_target = None
            return
        with torch.cuda.stream(self.stream):
            self.next_input = self.next_input.cuda(non_blocking=True)
            self.next_target = self.next_target.cuda(non_blocking=True)

§5模式五：CUDA Stream 竞争 · nsys 才能发现的问题

nsys 中的症状

  • 多个 CUDA Stream 上的 kernel 在时间上重叠
  • 但 GPU 总利用率没有显著提升——说明 Stream 之间在争抢 GPU 资源
  • 某些 Stream 上的 kernel 执行时间异常变长（被另一个 Stream 的 kernel 抢占）
这是 PyTorch Profiler 看不到的问题。PyTorch Profiler 只记录 op 级别的耗时，不会告诉你"这个 decode kernel 执行时间变长是因为另一个 Stream 上的 D2H 在争抢显存带宽"。只有 nsys 的多 Stream 时间线才能看到这种竞争。

真实案例：HiCache D2H/H2D 与 evict 的 Stream 竞争

# P800 GLM5 PD 分离集群中，HiCache 长期运行后 host memory 碎片化
# nsys 中看到：
#   - Stream 7 (decode) 的 kernel 执行时间从 0.06s 逐步增长到 0.3s
#   - Stream 13 (HiCache D2H) 和 Stream 15 (H2D) 的传输时间也在增长
#   - 两者在时间上重叠，争抢显存带宽
#   - evict 操作与 D2H/H2D 访问同一块显存 → 非法访问风险

§6模式六：内存瓶颈 · OOM 与碎片化

nsys 中的症状

  • CUDA API 行出现 cudaMalloc 调用耗时异常（碎片化导致分配慢）
  • GPU Memory 行显示显存使用持续上升（内存泄漏）
  • nsys stats 中 cudaMalloc 的总耗时占比异常

排查步骤

# 1. nsys stats 看 cudaMalloc 统计
nsys stats --report=cudaapi sglang_trace.nsys-rep | grep -i malloc

# 2. GPU 指标看显存趋势
# 采集时加 --gpu-metrics-device=all
# GUI 中看 "Memory Used" 曲线是否持续上升

# 3. 对比优化前后的 trace
nsys stats before_fix.nsys-rep | grep malloc
nsys stats after_fix.nsys-rep | grep malloc

常见内存问题

问题nsys 表现修复

Host Memory 碎片化HiCache D2H/H2D 时间逐步增长改进 Host Memory 分配策略，定期 compaction

§7决策树 · 一张图判断你的瓶颈类型

GPU 空闲 CUDA HW 行有大段空白 → CPU-bound 或 I/O-bound CPU 瓶颈 CPU 线程行密集，CUDA HW 行稀疏 → 优化数据加载 / 去 GIL 隐式同步 CUDA API 行出现 cudaStreamSynchronize → 去掉 .item()/.cpu() 数据搬运 Memcpy/NCCL 行时间占比 > 20% → Overlap、non_blocking、RDMA Stream 竞争 多 Stream kernel 重叠但利用率不升 → nsys 独有发现 内存瓶颈 cudaMalloc 耗时异常 / Memory Used 持续上升 → 碎片化或泄漏
