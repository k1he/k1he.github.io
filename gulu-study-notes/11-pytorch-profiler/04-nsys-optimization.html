§0优化全景图

优化原则：不同瓶颈的优化策略可能冲突。比如增大 batch size 能提高 GPU 算术强度（Memory-bound 优化），但也增加显存压力（可能引发 OOM）。先 nsys profile 确定瓶颈类型，再针对性地做——不要盲目堆所有优化。

§1CPU / IO 优化 · "让 GPU 别等"

适用场景：nsys 中 CUDA HW 行空白 > 30%，GPU SM Utilization < 50%。

低成本

1.1 DataLoader 调优

DataLoader(
    dataset,
    batch_size=64,
    num_workers=8,             # GPU 数 × 4
    pin_memory=True,            # 预分配 pinned memory, H2D 快 2x
    persistent_workers=True,    # 不杀 worker 进程, 省 fork 开销
    prefetch_factor=3,          # 预取队列深度
    drop_last=True,             # 最后不完整 batch 丢弃
)

nsys 验证：对比优化前后 CUDA HW 行的空白比例，应显著减少

低成本

1.2 去掉隐式同步

# ❌ 每步都同步
running_loss += loss.item()

# ✅ 累积 tensor, 周期性同步
loss_accum += loss.detach()
if step % 50 == 0:
    print(f"loss: {loss_accum.item()/50:.4f}")
    loss_accum = 0

nsys 验证：CUDA API 行中 cudaStreamSynchronize 消失

中成本

1.3 CUDA Graph 消除 Launch 开销

# 对于小 batch: kernel launch 本身比 kernel 执行还慢!
# CUDA Graph 把一系列 kernel launch "录制"下来, 一次 replay

# Warmup
static_input = torch.randn(1, 3, 224, 224, device="cuda")
for _ in range(3):
    static_output = model(static_input)

# 录制
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    static_output = model(static_input)

# 回放（零 launch 开销）
static_input.copy_(new_input)
g.replay()

nsys 验证：CUDA HW 行中 kernel 之间的空白（launch 间隙）消失，变成连续的 kernel 执行

中成本

1.4 torch.compile (PyTorch 2.0+)

model = torch.compile(model, mode="reduce-overhead")

# 三种 mode:
# "default"        → 轻量优化, 兼容性好
# "reduce-overhead" → 减少 Python 开销 + CUDA Graph (推荐推理)
# "max-autotune"    → 暴力搜索最优 kernel, 编译慢但运行快

nsys 验证：对比编译前后的 CUDA HW 行，kernel 数量减少（fusion）、launch 间隙缩小

§2Memory-bound 优化 · "减少显存搬运"

适用场景：nsys 中 CUDA HW 行密集（GPU 在忙），但 kernel 执行慢。LLM decode 几乎总是 memory-bound。

为什么 LLM decode 是 memory-bound：从 HBM 读取 1 byte 的时间，足够 GPU 做约 300 次乘加。如果 kernel 每读 1 byte 只做 1-2 次运算（decode 就是如此），GPU 算力就浪费了。优化目标是最大化数据复用——每读一次 HBM，做尽可能多的计算。
中成本

2.1 Kernel Fusion · 减少 HBM 读写次数

# 未融合: 3 个 kernel, 各自读写 HBM (6 次 HBM 访问)
x = linear(x)      # 读 x,w1 → 写 y1
x = gelu(x)        # 读 y1 → 写 y2
x = linear(x)      # 读 y2,w2 → 写 y3

# 融合: 1 个 kernel, 中间结果在寄存器/shared memory (2 次 HBM 访问)
x = fused_linear_gelu_linear(x, w1, w2)  # 读 x,w1,w2 → 写 y3

nsys 验证：CUDA HW 行中 kernel 数量减少，每个 kernel 执行时间稍长但总时间缩短

低成本

2.2 FlashAttention · Attention 的终极 Memory-bound 优化

# 标准 Attention: 实例化 O(N²) QK^T 矩阵到 HBM, 3 次 HBM 读写
# FlashAttention: 在 SRAM 中分块计算, O(N) 内存, 1 次 HBM 读写

# PyTorch 2.0+ 自动选择 FlashAttention
output = torch.nn.functional.scaled_dot_product_attention(Q, K, V)

nsys 验证：CUDA HW 行中 sdpa 或 flash_attn kernel 替代了多个小 kernel；NSight Compute 可进一步验证 HBM 访问减少

低成本

2.3 量化 · 减少每次搬运的数据量

# FP16 量化 (最简单)
model = model.half()

# INT8 量化 (W8A8, P800 W8A8 算力优势)
from transformers import BitsAndBytesConfig
config = BitsAndBytesConfig(load_in_8bit=True)

# FP8 量化 (最新)
# 需要硬件支持 (H100+, P800 W8A8)

nsys 验证：Memcpy 行的传输时间减半；GPU Memory 使用减半；可支持更大 batch

高收益

2.4 Speculative Decoding（投机解码）

# 核心思想: 用小模型猜 K 个 token, 大模型一次 prefill 验证
# 效果: K 次 decode (memory-bound) → 1 次 prefill (compute-bound)
#
# SGLang EAGLE / Medusa 就是这个方案
# 在 P800 GLM5 集群中, D 侧启用了 EAGLE 投机推理

nsys 验证：CUDA HW 行中，多个小 decode kernel 被替换为一个长 prefill kernel；TPOT 显著下降

§3Compute-bound 优化 · "让计算更快"

低成本

3.1 混合精度训练 (AMP)

from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()

with autocast(dtype=torch.float16):
    output = model(inputs)
    loss = criterion(output, targets)

scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()

nsys 验证：CUDA HW 行中 kernel 名称变为 ampere_fp16_sgemm 等 FP16 kernel；执行时间约为 FP32 的 1/2-1/4

中成本

3.2 Tensor Core 友好的维度

# ❌ 维度不对齐, Tensor Core 无法使用
nn.Linear(769, 513)   # 不是 8 的倍数

# ✅ 对齐到 8 (FP16) 或 16 (INT8)
nn.Linear(768, 512)   # Tensor Core 友好

# Llama vocab 32000 → 实际 pad 到 32768

nsys 验证：未对齐时 CUDA HW 行出现 volta_sgemm（CUDA Core fallback）；对齐后变为 ampere_fp16_sgemm（Tensor Core）

§4通信优化 · 多卡与 PD 分离场景

低成本

4.1 梯度通信与计算 Overlap

# DDP: 调小 bucket 大小, 更早开始通信
model = DDP(model, bucket_cap_mb=10, gradient_as_bucket_view=True)

nsys 验证：NCCL 行的 AllReduce 与 CUDA HW 行的 backward kernel 在时间上重叠（而不是串行）

中成本

4.2 NCCL 环境变量调优

# 禁用 IB (如果没有 InfiniBand)
NCCL_IB_DISABLE=1

# 指定网卡
NCCL_SOCKET_IFNAME=eth0

# 调试模式 (排查通信问题)
NCCL_DEBUG=INFO

# 选择算法
NCCL_ALGO=Ring   # 或 Tree

nsys 验证：对比调优前后 NCCL 行的 AllReduce 耗时

高收益

4.3 PD 分离与 KV Transfer 优化

# PD 分离架构下, P/D 之间通过 Mooncake 基于 RDMA 传输 KV Cache
# nsys 中可以看到:
#   - NCCL 行或 NVTX 标注的 "kv_transfer" 区间
#   - RDMA 传输带宽利用率
#   - KV Transfer 与 prefill/decode 的重叠情况
#
# 优化方向:
#   1. 确保 RDMA 带宽打满 (nsys 中看传输速率 vs 理论带宽)
#   2. KV Transfer 与 decode overlap (nsys 中看两者时间线是否重叠)
#   3. 减少 KV 搬运量 (HiCache L3 预取命中 → 不需要从 P 重新传)

nsys 验证：kv_transfer 区间占总时间比例下降；RDMA 传输带宽接近理论值

§5显存优化 · "OOM 了怎么办"

中成本

5.1 Gradient Checkpointing · 用时间换空间

from torch.utils.checkpoint import checkpoint

# 不保存中间激活 → ~60-70% 激活显存减少
# 代价: ~33% 额外计算 (反向时重算 forward)
def _forward(self, x):
    return self.layers(x)

output = checkpoint(self._forward, x, use_reentrant=False)

nsys 验证：GPU Memory 行峰值下降；CUDA HW 行出现重复的 forward kernel（重算）

中成本

5.2 CPU Offload

# FSDP CPU Offload: 权重常驻 CPU, 用时搬回 GPU
from torch.distributed.fsdp import CPUOffload

model = FSDP(model, cpu_offload=CPUOffload(offload_params=True))

nsys 验证：Memcpy 行出现更多的 H2D/D2H 传输；GPU Memory 行峰值显著下降

低成本

5.3 其他常用技巧

# 推理时关闭梯度
with torch.no_grad():
    output = model(inputs)

# 手动释放 + 清理碎片
del large_tensor
torch.cuda.empty_cache()

# PyTorch 显存分配器调优
# 避免大块分割导致的碎片化
PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:128

nsys 验证：GPU Memory 行更平稳（无突然暴涨）；cudaMalloc 调用次数和耗时减少
