§0为什么需要系统级 Profiling · 直觉不可靠

初学者通常凭直觉优化，结果往往踩坑：

常见错误直觉
  • "模型推理慢 → 一定是 GPU 算力不够"
  • "加了 GPU → 一定跑满了"
  • "推理服务卡 → 模型本身的问题"
  • "KV Cache 搬运很快 → 不可能是瓶颈"
nsys 真相
  • 70% 的慢来自 CPU→GPU 的数据搬运或调度延迟
  • GPU 利用率可能只有 30%（在等 CPU）
  • HiCache D2H/H2D 与 evict 的 CUDA stream 竞争导致性能退化
  • NCCL AllReduce 占了 40% 的 step 时间
性能优化的第一法则：不要猜，要测。系统级 Profiler 告诉你真正的瓶颈在哪——可能和你想的完全不一样。

真实案例：P800 上 HiCache 长流量退化

关键区别：PyTorch Profiler 需要在源码中插入 with profile(...)，对 SGLang 这类已经部署的服务无法使用。Nsight Systems 可以对任何运行中的进程直接抓取，零代码修改。

§1Nsight Systems 是什么

nsys 是 NVIDIA 官方的系统级性能分析工具，基于底层 CUPTI (CUDA Profiling Tools Interface) 采集数据。它能同时看到：

核心能力一览

维度采集内容分析目标
CPU 线程线程调度、OS Runtime (malloc/pthread)、CUDA API 调用CPU 是否在等、线程是否空闲
GPU Kernelskernel 名称、执行时间、所属 CUDA StreamGPU 是否吃满、Stream 间是否竞争
内存搬运H2D / D2H / D2D memcpy、带宽搬运开销、隐式同步
通信NCCL AllReduce / P2P / RDMA 传输多卡通信瓶颈、跨节点延迟
NVTX 标注自定义区间标记、框架内部标注将 kernel 关联回业务逻辑
和 PyTorch Profiler 的核心区别：PyTorch Profiler 需要在代码中插入 with profile(...)，采集的是 Python/ATen 层的 op 调用；Nsight Systems 是进程外部工具，不需要改任何代码，而且能看到 PyTorch Profiler 看不到的 CUDA stream 并发、OS Runtime 调用和 NCCL 通信细节。

§2Profiling 工具全景 · 各自适合什么场景

工具粒度适用场景需要改代码？上手难度
Nsight Systems系统级时间线CPU-GPU 交互、kernel launch、多 Stream 并发、NCCL 通信、对运行中进程抓取不需要中
PyTorch ProfilerOp / Kernel 级快速定位哪个 PyTorch op 慢、TensorBoard 可视化需要加 with profile()低
Nsight Compute单 kernel 指标SM 占用率、内存吞吐、warp stall 原因、指令级分析不需要高
NVIDIA DCGM设备级多卡集群 GPU 利用率 / 温度 / 功耗监控不需要低
perf / eBPF系统调用级CPU 火焰图、系统调用延迟、内核态瓶颈不需要中
nvidia-smi dmon设备级GPU 利用率 / 显存 / 功耗实时监控不需要低
选择策略：先用 nsys 看全局时间线，判断"是哪一类问题"（GPU 空闲？CPU 瓶颈？通信？Stream 竞争？）。如果某个 kernel 特别慢，再上 ncu (Nsight Compute) 深挖。对于 SGLang / vLLM 这类推理服务，nsys 是首选——因为你可以直接对运行中的进程抓取。

为什么推理服务场景优先用 Nsight Systems

  • 不需要改代码——推理服务是独立部署的，你不太可能为了 profiling 去改 SGLang 源码
  • 对运行中进程抓取——nsys profile -p <PID> 一条命令就能采集
  • 看到 CUDA Stream 并发——HiCache D2H/H2D 与 evict 的 stream 竞争只有 nsys 能看到
  • 看到 NCCL / RDMA 通信——PD 分离场景下 KV Transfer 跨节点传输的时间占比
  • 远程抓取 + 本地分析——服务器上 nsys profile，生成 .nsys-rep 拖回本地 GUI 看

§3核心概念速览

1. CPU 线程 vs GPU Stream

CUDA 操作是异步的：CPU 线程调用 cudaLaunchKernel 后立即返回，GPU 在另一个 stream 上异步执行。这意味着：

阅读 nsys 时间线的核心技能：CPU 行和 GPU 行是两条独立的时间线，kernel launch 和 kernel 执行之间有时间差。GPU 行的空白 = GPU 在等（CPU 没来得及喂数据，或在等同步）。

2. Trace 的时间线结构

nsys 生成的 .nsys-rep 文件在 GUI 中呈现为多层时间线：

行 (Row)内容怎么看
CPU 线程行每个 OS 线程一条行，显示函数调用和 CUDA API找空白 = 线程空闲；找密集 = CPU 瓶颈
CUDA API 行cudaLaunchKernel、cudaMemcpy、cudaStreamSynchronize 等找同步调用 = 性能杀手
CUDA HW 行GPU 上实际执行的 kernel找空白 = GPU 空闲；看密集度 = 利用率
Memcpy 行H2D / D2H / D2D 数据搬运看带宽和时间占比
NCCL 行AllReduce / P2P 等通信操作看通信时间占比
NVTX 行自定义标注区间定位业务逻辑（"这是 prefill 还是 decode"）

3. NVTX 标注

NVTX (NVIDIA Tools Extension) 是 NVIDIA 提供的代码标注 API，让你在 trace 中插入命名区间：

# Python (PyTorch 内置)
import torch.cuda.nvtx as nvtx

nvtx.range_push("prefill")       # 开始标注
output = model(inputs)
nvtx.range_pop()                  # 结束标注

# C/C++
nvtxRangePushA("prefill");
run_prefill(...);
nvtxRangePop();
NVTX 的价值：没有标注的 trace 里，你只能看到 ampere_gemm_128x64 这样的 kernel 名字，不知道它属于 prefill 还是 decode。加了 NVTX 后，trace 中会出现彩色标注区间，一眼就能定位"这段是 prefill，那段是 KV transfer"。PyTorch 和 SGLang 内部已经大量使用了 NVTX，所以即使你不手动添加，trace 里也会有有用的标注。

4. Wall Time vs Kernel Time

指标含义用途
Wall Time从 CPU 视角看的经过时间（包含排队、同步等待）端到端延迟分析
Kernel TimeGPU 上实际执行 kernel 的时间GPU 计算效率分析
GapWall Time - Kernel Time = 排队/等待时间GPU 空闲时间分析
常见误区：看到 kernel time 短就觉得没问题，但 wall time 很长 → 说明 GPU 大部分时间在等（等 CPU、等同步、等数据）。性能瓶颈往往不在 kernel 执行本身，而在 kernel 之间的间隙。
