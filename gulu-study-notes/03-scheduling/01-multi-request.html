二、三个 Manager 的协同模型

请求的状态机是 Pending → Prefill batch → Decode running set。下面这张图展示 4 个并发请求 R1~R4 在系统中的位置，以及四个 Manager 之间的数据流向。

读这张图的核心要点：
  • 请求的状态机：ZMQ Inbox → PrefillManager.pending_list → Batch(phase="prefill") → DecodeManager.running_reqs → 完成回收
  • TableManager 维护"槽位号"——每个活跃请求拿到一个 table_idx，对应 page_table 里的一行
  • CacheManager 维护"前缀复用 + 物理页池"——Radix 树用 ref_count 锁住正在用的前缀，evict 不会动它
  • DecodeManager 只是个 Set，filter_reqs 把 prefill 完的请求"过户"进来，schedule 时一锅端
  • 三者相互引用 ref_count + table_idx，没有任何全局锁——因为整个 scheduler 是单线程主循环

五、Chunked Prefill 的"接续机制"细节

这是 mini-sglang 调度层最巧妙的地方之一。让我们追踪 R4 在 3 个 iteration 里经历了什么：

iterpending R4.chunked_reqadd_one_req 走的分支产物R4.cached_len
3None_try_allocate_one (新分配)ChunkedReq#1（含 8192 token）0 → 8192 (forward 后)
3 末ChunkedReq#1—R4 留在 pending_list 队首—
4ChunkedReq#1"chunked_req" 复用分支Req（普通，含 1808 token）8192 → 10000
4 末None (清空)—R4 出 pending_list，进 decode10000 (即将 +1)
# scheduler/prefill.py:92  try_add_one
def try_add_one(self, pending_req):
    if self.token_budget <= 0: return None

    if chunked_req := pending_req.chunked_req:    ★ 接续分支
        return self._add_one_req(
            pending_req=pending_req,
            cache_handle=chunked_req.cache_handle,    # 复用
            table_idx=chunked_req.table_idx,           # 复用
            cached_len=chunked_req.cached_len,         # 复用
        )

    if resource := self._try_allocate_one(pending_req):  ★ 新分配分支
        cache_handle, table_idx = resource
        return self._add_one_req(...)
    return None
关键不变量：
  • chunked req 的 cache_handle 一直锁着初始命中的前缀（root 在 R4 case 里）
  • table_idx 一直被这个请求占用，不会被回收给别人
  • 每个 chunk forward 后，complete_one() 把 cached_len 推进到 device_len，但 KV 写入靠 attention backend 在 forward 时直接写 page_table 指向的物理页

六、OOM 与回退（当资源真不够时）

Mini-SGLang 的策略相对保守："调度时不入，绝不让 forward 中 OOM"。这通过 PrefillAdder 的"两次 check" 来保证：

# scheduler/prefill.py:39  _try_allocate_one
estimated_len = extend_len + req.output_len
if estimated_len + self.reserved_size > self.cache_manager.available_size:
    return None                         # check 1: 没 lock 之前
self.cache_manager.lock(handle)
if estimated_len + self.reserved_size > self.cache_manager.available_size:
    return self.cache_manager.unlock(handle)  # check 2: lock 后再来一次

为什么要 check 两次？因为 lock 操作本身会改变 evictable_size。 lock 一个前缀会让那部分 KV 从"evictable"变成"protected"，available_size = evictable + free_pages，所以 lock 后 available 可能变小。

当 PrefillAdder 第一个 req 都装不下时，schedule_next_batch 返回 None，调度器只跑 decode batch。

没有 preemption / restart：与 vLLM 不同，mini-sglang 没有"为新请求腾空间而 preempt 已有 decode 请求"的逻辑。这意味着：
  • 如果 decode pool 把 KV 占满了，新请求会一直 starve 在 pending_list
  • 实际中靠 memory_ratio（默认 0.85）和 max_running_req（默认 256）保证不会到这种极端
  • 这是 mini-sglang"教学优先"的取舍——SGLang 主线有完整的 preempt/restart 机制

七、Radix Cache Eviction 在多请求下的实战

当 decode 一段时间后某些请求 finish，它们 cache_req(finished=True) 把整段插入 Radix Tree 并解锁。当后续新请求需要的页超过 free_slots 时：

# scheduler/cache.py:106  _allocate
def _allocate(self, needed_pages):
    if needed_pages > (free_pages := len(self.free_slots)):
        evicted = self.prefix_cache.evict((needed_pages - free_pages) * self.page_size)
        self.free_slots = torch.cat([self.free_slots, evicted[::self.page_size]])
    allocated = self.free_slots[:needed_pages]
    self.free_slots = self.free_slots[needed_pages:]
    return allocated

# kvcache/radix_cache.py:148  evict
def evict(self, size):
    leave_nodes = self._collect_leave_nodes_for_evict()  # 所有 ref_count==0 的叶子
    heapq.heapify(leave_nodes)                          # 按 timestamp 最小堆
    evicted_size = 0
    while evicted_size < size:
        node = heapq.heappop(leave_nodes)              # 最老的优先
        evicted_size += node.length
        evicted_indices.append(node.value)
        del parent.children[key_fn(node._key)]
        if parent.is_leaf() and parent.ref_count == 0:
            heapq.heappush(leave_nodes, parent)         # 新叶子可能也能 evict
    return torch.cat(evicted_indices)

多请求场景下的副作用：

  • 共享前缀不会被 evict（ref_count > 0 时不可 evict）—— 多个并发 req 共享 system prompt 时尤其有效
  • arrive 时间戳影响 eviction 顺序—— 老的请求留下的"独占" tail prefix 会先被 evict
  • 整段 evict—— evict 会一直 pop 直到累计 size ≥ 需要量

八、throughput 推算（4 并发的理论上限）

假设 H200, Qwen3-0.6B：

阶段耗时说明
Iter 1 prefill 30 token~12 msR1, eager mode
Iter 2 prefill 30+80=110 token (with radix hit -20)~13 msR2+R3 mixed prefill
Iter 3 prefill 8192 token~25 msR4 chunk1
Iter 4 prefill 1808 token~10 msR4 chunk2
Iter 5+ decode bs=4 (CUDA Graph)~4 ms / iter每 iter 出 4 个 token

稳态吞吐：4 token / 4 ms = 1000 token/s aggregate。R1/R2/R3 在 Iter 5 启动 decode，R4 因为 chunked prefill 延迟了 12 ms 才进 decode 队列。

对长 prompt 友好的优化思路：
  • 提高 max_extend_tokens（默认 8192）→ 减少 chunk 次数，但峰值显存增加
  • R4 的 system prompt 若与 R1/R2 共享 → Radix 命中可以省掉前面几千 token 的 prefill
  • 如果实际场景有大量长 prompt，考虑用 --cache naive 测试基线（去掉 Radix 开销看 prefill 限速）

九、调度核心思想总结

① Continuous Batching

请求随时进，每 iteration 重新组 batch。Prefill batch 和 decode batch 严格分开，不混合。

② Prefill-First

每 iter 先尝试 prefill batch；只有 pending_list 空了才走 decode。决策代价：长 prefill 期间 decode ITL 抖动。

③ Radix-Aware

match → lock → unlock → cache_req，是每个 prefill req 的标准生命周期。ref_count 是并发安全的关键。

④ Chunked Prefill

token_budget + chunked_req 的组合，把超长 prompt 切成多个 iter 完成。期间 cache_handle/table_idx 保持不变。

⑤ Reserved-for-Decode

PrefillAdder 用 reserved_size = decode.inflight_tokens 给 decode 预留空间，防止"prefill 一时爽，decode OOM 火葬场"。

⑥ Overlap Scheduling

两条 stream，CPU 处理上批结果时 GPU 已在跑下批。事件 + wait_stream 控制顺序。
