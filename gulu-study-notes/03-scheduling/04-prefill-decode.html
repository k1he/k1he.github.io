PrefillManager & DecodeManager · 调度策略全解 15

这俩是调度核心。PrefillManager 决定"下一批算什么"，DecodeManager 记账"谁在 decode"。看似简单但藏着最多的设计决策。
两者分工 PrefillManager 的状态 schedule_next_batch 全流程 PrefillAdder · 装箱器 reserved_size 的博弈 chunk 接续的状态保持 DecodeManager · 40 行的艺术 inflight_tokens 的计算 filter_reqs · 状态转移 两者如何协作 踩坑合集

PART 1两者的分工（vs CacheManager / TableManager）

调度层的四个 Manager 分工清晰：

Manager类比职责调用时机
TableManager"号码牌发放处"分配 table_idx，持有 page_table/token_poolreq 进入/离开时
CacheManager"仓库管理员"管 KV 物理页 + Radix Treematch, allocate, cache_req
PrefillManager"接待员 + 装箱工"pending_list 队列，决定"下批装哪些"每 iter, 优先级高
DecodeManager"跟踪进度的记账本"running_reqs 集合，为 decode batch 服务每 iter, 优先级低

数据流

记忆锚点：
  • PrefillManager = 生产者（接 UserMsg，生产 prefill Batch）
  • DecodeManager = 消费者（接收已 prefill 的 req，生产 decode Batch）
  • Table/Cache = 资源仓库（两者都会去取）

字段的演化推导

v1: 就一个 pending_list — 但没有资源管理器就装不了箱

pending_list: List[PendingReq]

v2: 需要访问 cache + table — 加依赖注入

pending_list: List[PendingReq]
cache_manager: CacheManager      # 问"能不能装", 分配资源
table_manager: TableManager      # 分配 table_idx

v3: 需要感知 decode 占用 — 加 decode_manager

pending_list: List[PendingReq]
cache_manager: CacheManager
table_manager: TableManager
decode_manager: DecodeManager    # 读 inflight_tokens 避免 OOM
关键设计：PrefillManager 知道 DecodeManager，但反过来不成立。
这是因为 prefill 需要 为 decode 预留——prefill 必须知道 decode 在占多少 KV。而 decode 不需要知道 prefill（它只是消费 filter_reqs 塞进来的 req）。
这种单向依赖防止循环引用。

为什么 pending_list 用 List 而不是 Queue？

  • List 支持随机访问（abort 时按 uid 遍历找）
  • List 支持 slicing（self.pending_list = chunked_list + self.pending_list[len(reqs):]）
  • append / pop 都是 O(1)
  • Scheduler 单线程 → 不需要线程安全的 Queue

PART 3schedule_next_batch · 全流程解剖

# scheduler/prefill.py:126
def schedule_next_batch(self, prefill_budget: int) -> Batch | None:
    if len(self.pending_list) == 0:
        return None

    adder = PrefillAdder(
        token_budget=prefill_budget,
        reserved_size=self.decode_manager.inflight_tokens,    ★ 给 decode 留地
        cache_manager=self.cache_manager,
        table_manager=self.table_manager,
    )
    reqs: List[Req] = []
    chunked_list: List[PendingReq] = []
    for pending_req in self.pending_list:
        if req := adder.try_add_one(pending_req):
            pending_req.chunked_req = None
            if isinstance(req, ChunkedReq):
                pending_req.chunked_req = req
                chunked_list.append(pending_req)
            reqs.append(req)
        else:
            break                                    ★ 失败就停, 保持 FIFO
    if len(reqs) == 0:
        return None
    self.pending_list = chunked_list + self.pending_list[len(reqs) :]    ★ 队列重排
    return Batch(reqs=reqs, phase="prefill")

每一行在做什么

步骤做什么设计决策
pending_list 空 → return None没活儿，让 scheduler 走 decode短路优化
创建 PrefillAdder装箱器，预算 + 预留每次 schedule 新建，不复用
循环 try_add_one逐个尝试装箱FIFO 顺序，不 reorder
失败就 break（不 continue）head-of-line 阻塞保证先来的不饿死
chunked 记下来未完成的放 chunked_list下轮继续
队列重排chunked 放队首, 未装的仍排其后未完成的优先接续
return Batch交给 schedulerphase="prefill"

try_add_one · 两条路径

# scheduler/prefill.py:92
def try_add_one(self, pending_req: PendingReq) -> Req | None:
    if self.token_budget <= 0:
        return None

    # 路径 A: 这个 req 上轮有未完成的 chunk
    if chunked_req := pending_req.chunked_req:
        return self._add_one_req(
            pending_req=pending_req,
            cache_handle=chunked_req.cache_handle,     # 复用上轮
            table_idx=chunked_req.table_idx,           # 复用上轮
            cached_len=chunked_req.cached_len,         # 接续
        )

    # 路径 B: 新 req, 要全新分配
    if resource := self._try_allocate_one(pending_req):
        cache_handle, table_idx = resource
        return self._add_one_req(
            pending_req=pending_req,
            cache_handle=cache_handle,
            table_idx=table_idx,
            cached_len=cache_handle.cached_len,
        )
    return None

_try_allocate_one · 4 步资源申请

# scheduler/prefill.py:39
def _try_allocate_one(self, req) -> Tuple[BaseCacheHandle, int] | None:
    # ① 表满了直接失败
    if self.table_manager.available_size == 0:
        return None

    # ② Radix 查命中
    handle = self.cache_manager.match_req(req).cuda_handle
    cached_len = handle.cached_len
    extend_len = req.input_len - cached_len
    estimated_len = extend_len + req.output_len

    # ③ 第一次容量 check (未 lock 时)
    if estimated_len + self.reserved_size > self.cache_manager.available_size:
        return None

    # ④ lock 这个 handle (会让 available_size 变小因为 ref+1 → 从 evictable 变 protected)
    self.cache_manager.lock(handle)
    # ⑤ 第二次容量 check (lock 之后)
    if estimated_len + self.reserved_size > self.cache_manager.available_size:
        return self.cache_manager.unlock(handle)   # 回滚, 返回 None

    # ⑥ 分配 table_idx
    table_idx = self.table_manager.allocate()

    # ⑦ 把命中的 token ids 和 page indices 写到 token_pool 和 page_table
    if cached_len > 0:
        device_ids = self.table_manager.token_pool[table_idx][:cached_len]
        page_entry = self.table_manager.page_table[table_idx][:cached_len]
        device_ids.copy_(req.input_ids[:cached_len].pin_memory(), non_blocking=True)
        page_entry.copy_(handle.get_matched_indices())

    return handle, table_idx

为什么要"两次 check"？

lock 会改变 available_size！
  • lock 前：命中的 Radix 节点处于 evictable 状态，计入 available
  • lock 后：变成 protected 状态，不再 evictable，available_size 减小
  • 因此 lock 后原本通过的 check 可能失败——需要再 check 一次

例：available=100, estimated=80, reserved=10 → 第一次 check 通过 (80+10 ≤ 100)。lock 后命中的 30 page 变 protected，available 降到 70 → 第二次 check 失败 (80+10 > 70)，立刻 unlock 回滚。

_add_one_req · 创建 Req 对象

# scheduler/prefill.py:65
def _add_one_req(self, pending_req, cache_handle, table_idx, cached_len) -> Req:
    remain_len = pending_req.input_len - cached_len
    chunk_size = min(self.token_budget, remain_len)       # 最多装多少
    is_chunked = chunk_size < remain_len                     # 装不下 → chunked
    CLS = ChunkedReq if is_chunked else Req

    self.token_budget -= chunk_size                          # 扣预算
    self.reserved_size += remain_len + pending_req.output_len  # 为这个 req 预留

    # 把本 chunk 的 token ids 写到 token_pool
    _slice = slice(cached_len, cached_len + chunk_size)
    device_ids = self.table_manager.token_pool[table_idx, _slice]
    device_ids.copy_(pending_req.input_ids[_slice].pin_memory(), non_blocking=True)

    return CLS(
        input_ids=pending_req.input_ids[: cached_len + chunk_size],   # 注意 slice!
        table_idx=table_idx,
        cached_len=cached_len,
        ...
    )

input_ids 为什么 slice 到 cached_len + chunk_size？

Req 的 input_ids 表示"本步 forward 要算到哪"。
对 chunked req，只算 chunk_size 个 token，所以 input_ids 只包含 cached_len + chunk_size 个 token。
这也保证了 Req 的不变式 cached_len < device_len = len(input_ids)。
pending_req.input_ids 仍然完整（后续 chunk 还要用），没有被修改。

PART 5reserved_size 的博弈 · 不让 prefill 饿死 decode

这是整个调度的核心权衡。

没有 reserved_size 会怎样？

假设 KV 池容量 100, 当前:
- 3 个 req 在 decode, 已用 60, 还会用 15 (remain_len sum)
- available = 40 (free + evictable)

来一个新 req, input_len=30, output_len=10 → estimated=40
check: estimated (40) < available (40)? ... 刚好! 装!

prefill 完, 用掉 30 页 → free 剩 10
decode 继续算下一 token:
  - 3 个 req 各需 1 新 page → 需要 3, 有 10, ok
  - 新 req 也开始 decode → 需要 1
- 再下一轮 decode, 继续消耗...
- 几步后 KV 池满 → 新 req 要 allocate 找不到页 → OOM

加上 reserved_size 后

相同场景:
- decode_manager.inflight_tokens = 15 + 3*(page_size-1)    # remain + page 冗余
  假设 page_size=1 → inflight = 15
- adder.reserved_size 初始 = 15

新 req check: estimated (40) + reserved (15) = 55 > available (40)?
  是! 装不下 → 不装

等 decode 消化些 inflight_tokens 后, reserved 减小, 才能装新 req

reserved_size 累加策略

# PrefillAdder._add_one_req:
self.reserved_size += remain_len + pending_req.output_len
#                     ^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^^^^^
#                     本 req 的     本 req 的
#                     新 prefill    所有 decode
#                     token         output token

装进一个 req 后，立刻把这个 req 的总 token 预算加到 reserved_size。下一个 req 尝试装时面对的 check 是：

estimated_len (新 req 需要) + reserved_size (之前所有 req 预留)
> available_size (总容量)? → 不装

所以同一批 prefill 里的请求是串行排除——前面装进去的占地一部分，后面的要在剩余空间里装。

inflight_tokens 的精确公式

# scheduler/decode.py:27
@property
def inflight_tokens(self) -> int:
    tokens_reserved = (self.page_size - 1) * len(self.running_reqs)   # 每 req 多留 page-1 个
    return sum(req.remain_len for req in self.running_reqs) + tokens_reserved
为什么要额外留 (page_size - 1) × N？
想象 page_size=16, 一个 req 当前 cached_len=100 (用了 7 页), remain_len=20。
它还会消耗 20 个 token。但这 20 个不一定都在新页上——可能前 12 个补满当前页 (page 7 的剩余 12 格), 后 8 个开新页。
最坏情况: 所有 req 的每个 new token 都开新页 → 需要 remain_len + (page_size-1) 个 token 的 KV
这个 (page_size-1) * N 就是 "最坏情况的对齐浪费" 保守估计。
对 page_size=1 这项 = 0。对 page_size=16, 256 个 req 在 decode 时多留 256×15=3840 token 的空间。

PART 6chunk 接续的状态保持 · 跨 iter 不释放资源

Chunked prefill 最关键的性质：cache_handle 和 table_idx 在 chunk 之间保持不变。

观察含义

abort 时的特别处理

# scheduler/prefill.py:153
def abort_req(self, uid):
    for i, req in enumerate(self.pending_list):
        if req.uid == uid:
            self.pending_list.pop(i)
            return req.chunked_req              # ★ 返回 ChunkedReq (或 None)
    return None

关键点：abort 一个处于 chunked 状态的 PendingReq 时，req.chunked_req 指向上次 forward 产出的 ChunkedReq。这个 ChunkedReq 持有 cache_handle + table_idx，这些资源需要被释放。

所以 abort_req 返回 ChunkedReq，调用方看到返回值不为 None 就调 _free_req_resources：

# scheduler/scheduler.py (abort 分支)

req_to_free = req_to_free or self.decode_manager.abort_req(uid)
if req_to_free:
    self._free_req_resources(req_to_free)              # table.free + cache_req(finished=True)

PART 7DecodeManager · 40 行的艺术

# scheduler/decode.py 全文
@dataclass
class DecodeManager:
    page_size: int
    running_reqs: Set[Req] = field(default_factory=set)

    def filter_reqs(self, reqs: Iterable[Req]) -> None:
        self.running_reqs = {req for req in self.running_reqs.union(reqs) if req.can_decode}

    def remove_req(self, req: Req) -> None:
        self.running_reqs.discard(req)

    def abort_req(self, uid: int) -> Req | None:
        for req in self.running_reqs:
            if req.uid == uid:
                self.running_reqs.remove(req)
                return req
        return None

    @property
    def inflight_tokens(self) -> int:
        tokens_reserved = (self.page_size - 1) * len(self.running_reqs)
        return sum(req.remain_len for req in self.running_reqs) + tokens_reserved

    def schedule_next_batch(self) -> Batch | None:
        if not self.runnable:
            return None
        return Batch(reqs=list(self.running_reqs), phase="decode")

    @property
    def runnable(self) -> bool:
        return len(self.running_reqs) > 0

为什么这么简单？

DecodeManager 只做记账——它不决定谁该 decode（所有满足 can_decode 的 req 都一起 decode），也不管资源分配（那是 CacheManager 的事）。

为什么 Set 而不是 List？

操作Set 复杂度List 复杂度
addO(1) avgO(1) append
removeO(1) avgO(n)
containsO(1) avgO(n)
去重自动需手动

最关键是去重：filter_reqs 会 union 新进来的 reqs 和已有的 running_reqs，同一个 req 不会重复——Set 自动保证。

回顾 13 章：Req 用 @dataclass(eq=False) 让 hash 基于 id，所以同一个对象放进 set 只有一份，不同对象即使内容相同也算不同元素。这是 DecodeManager 能用 Set 的前提。

schedule_next_batch 为什么不挑 req？

def schedule_next_batch(self) -> Batch | None:
    if not self.runnable: return None
    return Batch(reqs=list(self.running_reqs), phase="decode")   # 全部打包

decode batch 一锅端：所有 running_reqs 都进这一个 batch。

为什么不分批？

  • decode 阶段每 req 只算 1 token，各 req 算力成本相同
  • 分成多个小 batch 反而降低 GPU 利用率（decode 是 memory-bound，bs 大才有效率）
  • 容量由 CacheManager.allocate_paged 检查，不够会触发 evict
  • bs 上限由 max_running_req 隐式控制（TableManager.allocate 失败时 prefill 就装不进了）

这是 mini-sglang 的"简单策略"——可能不是最优，但 99% 场景下够用。SGLang 主线在极端场景下有更精细的 decode 批策略。

PART 8filter_reqs · 状态转移的精妙时机

# scheduler/decode.py:14
def filter_reqs(self, reqs: Iterable[Req]) -> None:

这一行做了三件事

  1. 合集：把 reqs（本轮 forward 完的 batch 里的 reqs）加进 running_reqs
  2. 过滤：只保留 can_decode=True 的（排除 ChunkedReq、remain_len=0 的）
  3. 覆盖：结果赋回 running_reqs

幂等性

filter_reqs 对同一个 req 可以重复调用——union 的去重特性保证 set 里只有一份。这对某些重入场景（例如 overlap 下同一 req 跨 iter）很友好。

PART 9两者如何协作 · 完整调度一轮

Prefill-First 策略

or 短路：先试 prefill，组得出就走 prefill batch；组不出才走 decode。

为什么 prefill 优先？
  • 用户感知：新请求的 TTFT（首 token 延迟）比已有请求的 ITL（间 token 延迟）更敏感——先把新请求的 prefill 做了，TTFT 就开始减少
  • 吞吐考虑：decode 是 memory-bound，算力利用率低；prefill 是 compute-bound，trade-off 上 prefill 先做能打满 GPU
  • 负面：长 prompt 的 prefill 会"堵住" decode —— 这就是为什么要 chunked prefill（控制单次 prefill 的最大时长）

PART 10踩坑合集

坑 1 · Prefill-First 的 starvation 风险

持续有新请求进 pending_list 时，decode 可能长时间得不到调度。只有 pending_list 真正空时才会走 decode。
实际系统靠 prefill_budget 限制单次 prefill 大小来避免：每次 prefill 最多 8192 token，不会霸占 GPU 太久（~10ms 级）。如果还想更公平，需要改成 "轮询" 或 "加权" 策略——mini-sglang 的 TODO 注释指向这个方向。

坑 2 · pending_list 的 break 导致的 HOL 阻塞

当队首的大 req 装不下时，整个 pending_list 都 break 掉。
这是故意的——避免小 req 插队让大 req 饿死（head-of-line 公平）。
但代价是：如果队首有个 10000 token 的请求，而此时系统 KV 池紧张装不下，但后面有个 100 token 的小请求本可以装下——它也会被阻塞。要缓解需要改用 "work conserving" 策略。

坑 3 · reserved_size 未归零的隐患

注意 reserved_size 在每次 schedule_next_batch 开始时重新从 inflight_tokens 初始化——PrefillAdder 是每次新建的，不跨 iter 保持状态。
这意味着：单次 schedule 内装完的 req 的 reserved 会累加；但下一 iter 这些 req 还没出现在 decode_manager.running_reqs 里（filter_reqs 还没执行），它们的 KV 占用暂时 "不计入" reserved_size。

会不会导致 OOM？
不会——因为本轮装进来的 req 的 page 在 PrefillAdder 内部就扣了 (通过 available_size 检查)。lock 让它们的 KV 从 evictable 移到 protected，available_size 自动下降。下一 iter 的 schedule 看到的是新的 available_size，已经反映了上轮装进来的占用。
所以 reserved_size 只需覆盖"decode_manager 里已在跑的"，不需要覆盖"本轮刚装进来的"——后者已通过 available_size 自动跟踪。这是一个非常精妙的协议。

坑 4 · filter_reqs 的时机关系到正确性

# scheduler.py
self.engine.stream.wait_stream(self.stream)
ongoing_data = (forward_input, self._forward(forward_input))   # _forward 里调 filter_reqs
...
self._process_last_data(last_data)   # 处理上轮结果

filter_reqs 在 _forward 里调用——本轮 batch 刚 launch 完立刻执行。此时 GPU 可能还在算，但 CPU 端已经更新了 running_reqs。
所以下一 iter 的 schedule_next_batch 看到的 running_reqs 是最新的——已经包括本轮 prefill 完的 req，已经排除本轮完成的 req。这是 overlap scheduling 能正确运转的关键。

坑 5 · abort 的 chunked 清理

abort 一个 chunked req 时，如果只从 pending_list 删除会泄露资源——ChunkedReq 持有的 table_idx 和 cache_handle 永远不会释放。
所以 prefill_manager.abort_req(uid) 必须返回 chunked_req，让 scheduler 调 _free_req_resources 把资源清理掉。

坑 6 · DecodeManager.Set 的 iteration 可能慢

inflight_tokens 和 schedule_next_batch 都要遍历 running_reqs。bs=256 时，每 iter 都要遍历 256 个 req。
解决方案：把 inflight_tokens 做成增量维护（add 时 +remain_len, remove 时 -remain_len）。
但 mini-sglang 没这么做——因为 per-iter 遍历 256 个对象在 Python 里也就几十 µs，相比 forward 时间可忽略。简单代码 > 提前优化。

总结 · 记住这 5 点

  1. PrefillManager 是生产者，DecodeManager 是消费者——前者从 UserMsg 生成 Req，后者管理"已经 prefill 过的 req"
  2. Prefill-First 策略：优先调度 prefill，组不出才 decode。背后有 TTFT 和算力打满的考虑
  3. reserved_size 是防 OOM 的关键：prefill 为正在跑的 decode 留好 KV 空间。adder 累加式预算确保同一批 prefill 里的 req 依次受约束
  4. chunked 接续靠 cache_handle + table_idx 跨 iter 保持：ChunkedReq 作为"进度书签"挂在 PendingReq 上
  5. DecodeManager 只 40 行，它就是一个 Set + 几个查询方法。decode 的复杂度在 CacheManager（allocate_paged）而不是在它

从这里看到 sglang 的设计哲学：职责分解极其清晰，每个 manager 只管一件事，状态转移靠显式调用（filter_reqs / cache_req / free）而不是隐式事件。代码行数很少（总共不到 200 行），但每一行都有用——删任何一行都会破坏某条不变式。这正是 05 章那种"演化推导"方法论的真实体现：字段和方法是一个一个加出来的，每一条都有确切的动机。
