PART 1它是谁的中间人？

CacheManager 本身不存 KV、不存树结构——它是两者的粘合剂：

CacheManager 粘合三层：

       上面：RadixPrefixCache                     # 前缀树 (逻辑结构)
              │
              │ insert_prefix / match_prefix / evict
              │ → 操作 "前缀能不能复用"
              ▼
       中间：CacheManager                         # ★ 这一章的主角
              │
              │ free_slots + page_table (GPU)
              │ → 把 "前缀树的叶子" 和 "真正的物理页号" 桥接
              ▼
       下面：MHAKVCache._kv_buffer                 # 物理 KV tensor (08 章讲过)
              # 一个巨大 GPU tensor，CacheManager 决定 "谁用哪一页"

一句话：它干什么

"给我一组 token id，告诉我 Radix 命中了多少，然后把 KV 物理页号分给我。"

调用者是 PrefillAdder 和 Scheduler——他们不关心 Radix Tree 的节点结构，也不关心 page 是怎么从池里出来的。他们只想问：

  • "这个请求能命中多少前缀？"（match_req）
  • "给这个 req 的新 token 分配 page"（allocate_paged）
  • "req 完成了/前缀该插入树了"（cache_req）

CacheManager 内部处理所有"物理 ↔ 逻辑"的转换细节。

你会同时用到 13、14、15 章的知识：
  • 13 章 (Req) 告诉你 "一个请求的状态是怎么维护的"
  • 本章 (CacheManager) 告诉你 "请求的 KV 物理资源是怎么被分配和复用的"
  • 15 章 (PrefillManager/DecodeManager) 告诉你 "这些 API 在什么时机被调用"

PART 2内部状态 · 演化推导

让我们再用 05 章的"每加一个字段都问为什么"的方法构建 CacheManager。

v0 · 最小版本：只有一个 free_slots 池

class CacheManagerV0:
    free_slots: List[int]    # 空闲页号列表

    def allocate(n) -> List[int]:
        return [self.free_slots.pop() for _ in range(n)]

    def free(indices):
        self.free_slots.extend(indices)

够用吗？不够——alloc 速度慢（Python list pop 会触发多次内存操作），且不能前缀复用。

v1 · free_slots 改为 GPU tensor

free_slots: torch.Tensor    # GPU int32 [num_pages]

为什么要 GPU tensor？因为后续 page_table 的写入是 GPU 操作，free_slots 的 page 号需要直接写入 page_table，不想来回 CPU/GPU。所以整个 free_slots 本身就存 GPU。

v2 · 加入 Radix Tree 支持前缀复用

free_slots: torch.Tensor
prefix_cache: BasePrefixCache    # RadixPrefixCache 或 NaivePrefixCache

前缀命中的 page 号来自 Radix 树的节点 value；新分配的来自 free_slots。两者并存但分工不同：

  • free_slots 里的 page：尚未被任何 req 占用
  • Radix 树某节点的 page：已经被当前 req 占用 (ref_count > 0) 或可被驱逐 (ref_count = 0)

v3 · 加入 page_size 支持（非 1 页大小）

free_slots: torch.Tensor        # 现在存的是 page 的起始 token 位置 (按 page_size 对齐)
prefix_cache: BasePrefixCache
page_size: int

当 page_size=16 时，free_slots 里的值是 [0, 16, 32, 48, ...]。这让 TRT-LLM 后端（要求 page_size=16/32/64）也能工作。

# cache.py:20
self.free_slots = torch.arange(num_pages, dtype=torch.int32, device=device) * page_size
# 例: num_pages=1M, page_size=1 → [0, 1, 2, ..., 999999]
# 例: num_pages=65536, page_size=16 → [0, 16, 32, ..., 1048560]

v4 · 需要 page_table 引用

所有 allocate_paged 的结果最终要写进 page_table[req.table_idx, ...]。CacheManager 直接持有 page_table 的引用就能写。

free_slots: torch.Tensor
prefix_cache: BasePrefixCache
page_size: int
page_table: torch.Tensor         # ← TableManager 也持有, 同一个 GPU tensor 共享引用
num_pages: int

最终实际源码（cache.py:16）

内部状态总览

空闲，要么在 Radix 树某节点的 value 里，不存在第三种状态 check_integrity 就是在验证这条
不变式：page 只能在一个地方。 要么在 free_slots 列表里（空闲），要么在 Radix 树的某个节点的 value 里（被占用或可驱逐）。绝不能同时在两个地方——这是整个 cache 模块的正确性根基。

PART 3完整 API 地图

CacheManager 对外暴露 8 个公开方法 + 3 个 property。我把它们按"被谁调用"分类。

① PrefillAdder 用的（装箱时）

match_req(pending_req) → MatchResult

走 Radix Tree 看这个 req 的 input_ids 前缀能命中多少。只看 input_ids[:-1]（最后一个 token 要算，不能只 match）。

available_size (property) → int

当前可用的 page 容量 = evictable 的 Radix 节点 + 真正空闲的 pages。PrefillAdder 用来判断能不能装下新 req。

lock(handle) / unlock(handle)

把 Radix 节点的 ref_count+1 或 -1。lock 后这个节点（和所有祖先）不会被 evict。

② Scheduler 用的（准备 batch 时）

allocate_paged(reqs)

为整个 batch 的 req 按"缺多少页"批量分配，并写 page_table。本章最复杂的方法。

③ Scheduler 用的（处理结果时）

cache_req(req, finished)

prefill 完或 req finish 时插入 Radix 树 + 释放冗余页。cache_req 就是整套 cache 逻辑的"心脏"。

lazy_free_region() (contextmanager)

批量释放场景下，把多次 _free 攒起来最后一次性 torch.cat——优化性能。

④ 诊断用的

check_integrity()

每次 iteration 后（可选）检查不变式是否成立。调试利器。

内部私有

方法作用
_allocate(n) → Tensor从 free_slots 取 n 个 page，不够就触发 Radix evict
_free(indices)把 indices 加回 free_slots
_page_to_token(pages) → Tensorpage_size > 1 时把"页号"展开成"每个 token 的位置"

PART 4match_req · 前缀匹配的微妙细节

# cache.py:27
def match_req(self, req: PendingReq) -> MatchResult:
    input_len = req.input_len
    assert input_len > 0, "Input length must be greater than 0."
    return self.prefix_cache.match_prefix(req.input_ids[: input_len - 1])
    #                                                          ^^^^^^^^^^^^^^
    #                                                          注意 -1!

为什么不 match 完整的 input_ids？

因为最后一个 token 必须参与 prefill 计算。
  • 如果 input 长度为 N，模型要做 prefill 就需要算至少 1 个新 token 的 KV（不然 forward 就没任何 Q 了）
  • 假设完整 match 了 N 个 token → extend_len = 0 → kernel 拿不到任何 Q，根本跑不起来
  • 所以永远至少留 1 个给新算。match 只看前 N-1 个。

返回的 MatchResult 是啥？

# kvcache/base.py:62
class MatchResult(NamedTuple):
    cuda_handle: BaseCacheHandle
    # TODO: support HiCache (CPU offload)

目前只有 cuda_handle（GPU 上的 Radix 节点引用）。将来 HiCache 会加个 cpu_handle——从 CPU 内存里命中的前缀。现在的接口已经为此预留。

BaseCacheHandle 是什么？

# kvcache/base.py:41
@dataclass(frozen=True)
class BaseCacheHandle(ABC):
    cached_len: int                                 # 命中了多少 token
    @abstractmethod
    def get_matched_indices(self) -> torch.Tensor: ...  # 取出物理页号序列

对 Radix 来说 cuda_handle 是 RadixCacheHandle(cached_len, node)——拿到 node 之后可以回溯到 root 拼出整条 page 路径。

零命中的情况

新请求进来，Radix 树空或 root 没有匹配的子节点 → 返回 RadixCacheHandle(cached_len=0, node=root_node)。cached_len=0 就是"空命中"的表示。后续 PrefillAdder 知道要全量 prefill。

PART 5allocate_paged · 最精妙的一块

# cache.py:42
def allocate_paged(self, reqs: List[Req]) -> None:
    needed_pages = 0
    allocation_info: List[Tuple[int, int, int]] = []
    for req in reqs:
        first_page = div_ceil(req.cached_len, self.page_size)
        last_page = div_ceil(req.device_len, self.page_size)
        if last_page > first_page:
            needed_pages += last_page - first_page
            allocation_info.append((req.table_idx, first_page, last_page))
    if needed_pages > 0:
        allocated = self._page_to_token(self._allocate(needed_pages))
        _write_page_table(self.page_table, allocated, allocation_info, self.page_size)

div_ceil 的作用

# utils
def div_ceil(a, b): return (a + b - 1) // b

它计算"向上取整的除法"。例：div_ceil(25, 16) = 2。

first_page 和 last_page 的语义

2 页 (page 2, 3) 注意: page 1 的 [20, 32) 部分也是"新的", 但 page 1 的 page# 已经在 page_table 里了（cached 时分配的）, 所以不算新页
为什么用 div_ceil 而不是 div_floor？
  • first_page = div_ceil(cached_len) → cached_len=20 向上取到 page 2（第 1 页满了）
  • last_page = div_ceil(device_len) → device_len=50 向上取到 page 4
  • 需要的新页 = last - first = 4 - 2 = 2
  • 这个计算隐含一个关键点：cached 区域的最后一页 (page 1) 已经被之前的 allocate 写入 page_table，这次不需要再分配——它半满半新，但物理页是同一页

为什么 batch 批量分配比逐个分配好？

把整个 batch 的需求汇总 (needed_pages) 然后一次 _allocate(needed_pages)——只触发 一次 可能的 evict，一次 free_slots 切片，一次 GPU H2D（通过 _write_page_table）。如果逐个 req 分配就会触发多次。

_write_page_table · 批量写入魔法

# cache.py:127
def _write_page_table(page_table, allocated, allocation_info, page_size):
    needed_tokens = len(allocated)
    table_idx_host = torch.empty(needed_tokens, dtype=torch.int64, pin_memory=True)
    positions_host = torch.empty(needed_tokens, dtype=torch.int64, pin_memory=True)
    offset = 0
    for table_idx, first_page, last_page in allocation_info:
        first_pos, last_pos = first_page * page_size, last_page * page_size
        length = last_pos - first_pos
        table_idx_host[offset : offset + length].fill_(table_idx)
        torch.arange(first_pos, last_pos, out=positions_host[offset : offset + length])
        offset += length
    assert offset == needed_tokens
    table_idxs = table_idx_host.to(page_table.device, non_blocking=True)
    offsets = positions_host.to(page_table.device, non_blocking=True)
    page_table[table_idxs, offsets] = allocated   # ★ 一次性 advanced indexing 写入

这个函数的精妙：

  • pin_memory：CPU buffer 用 pinned memory，支持 non-blocking H2D copy
  • 一次 H2D：只有两次 cpu→gpu copy（table_idxs 和 offsets），不是每个 req 一次
  • advanced indexing：page_table[table_idxs, offsets] = allocated 是 PyTorch 的高级索引，一个 kernel 搞定整批写入

PART 6cache_req · 五段式注释的真相

这是整个 CacheManager 最难的方法。作者在源码里贴了一段五段式的注释——我们把这段注释逐行解剖。

# cache.py:55
def cache_req(self, req: Req, *, finished: bool) -> None:
    # ==================================== valid cache region ====================================
    # [0, req.cached_len)                       This part is valid for attention kernel read/write.
    # [0, old_handle.cached_len)                This part is in the prefix cache before prefill.
    # [old_handle.cached_len, req.cached_len)   This part is allocated by cache manager for this request.
    # ================================== allocated cache region ==================================
    # [old_handle.cached_len, cached_len)       This part was not in the prefix cache when prefill,
    #                                           but later cached by other requests.
    #                                           We must free them to avoid memory leak.
    # [cached_len, new_handle.cached_len)       This part is newly inserted into the prefix cache.
    # [new_handle.cached_len, req.cached_len)   This part is tailing part that can not inserted into the prefix cache.
    #                                           We should free it if the request has finished.
    insert_ids = req.input_ids[: req.cached_len]
    page_indices = self.page_table[req.table_idx, : req.cached_len]
    old_handle = req.cache_handle
    cached_len, new_handle = self.prefix_cache.insert_prefix(insert_ids, page_indices)
    self.unlock(old_handle)
    self._free(page_indices[old_handle.cached_len : cached_len])
    if finished:
        self._free(page_indices[new_handle.cached_len :])
    else:
        req.cache_handle = new_handle
        self.lock(new_handle)

5 段各自是什么？

设 req.cached_len = 100，old_handle.cached_len = 20，insert_prefix 返回 cached_len = 50, new_handle.cached_len = 96。这些数字对应图中：

B 段的故事 · 最难理解的一段

"为什么 [old_handle.cached_len, cached_len) 区间的 page 要 free？"

想象并发场景：

  1. t=0: req X 开始 prefill，match 命中前 20 个 token，分配了 page 21-50 存新算的
  2. t=1: 同时 req Y 也来了，它的 prompt 前 50 个 token 跟 X 一样
  3. t=2: req Y 先完成 prefill，把自己的 page 21-50 insert_prefix 进树
  4. t=3: req X 也完成 prefill，准备 cache_req(X)
  5. t=3': insert_prefix(X.input_ids[:100], X.page_indices[:100])—— 但 Radix 树里已经有"前 50 个 token"的节点了（Y 插的），所以 insert 返回 cached_len=50——X 新插的只是 [50, 96) 这段
  6. t=4: X 原本分配的 page 21-50 现在 被两份 KV 代表同一 prefix——Y 的已经入树，X 的多余了
  7. → X 必须 free 自己的 page 21-50（区间 B），否则同一份 KV 逻辑上重复占用 60 页
这就是注释里 "later cached by other requests, We must free them to avoid memory leak" 的意思。

D 段的故事 · 尾巴为什么可能不入树？

insert_prefix 里有个 align_down(len(input_ids), self.page_size)——只有整页的 token 才能入树。如果 req.cached_len=100, page_size=16，那可以入树的最多是 96 个 token（6×16），尾巴 [96, 100) 不能入树。

此时分两种情况：

  • finished=False（prefill 完, 还要 decode）：保留这些 page，req.cache_handle 更新成 new_handle（持有前 96 个）。尾巴的 4 个 token 继续跟着这个 req，下次 cache_req 时可能被下次 insert 顺带插入
  • finished=True（req 结束）：这些 page 没人要了，_free 回池
page_size=1 时 D 段永远为空——任何长度都是"整页"。这也是 page_size=1 让逻辑简化的原因之一（08 章也提过）。

PART 7_allocate · evict 兜底机制

# cache.py:106
def _allocate(self, needed_pages: int) -> torch.Tensor:
    if needed_pages > (free_pages := len(self.free_slots)):
        evicted = self.prefix_cache.evict((needed_pages - free_pages) * self.page_size)
        self.free_slots = torch.cat([self.free_slots, evicted[:: self.page_size]])
        assert len(self.free_slots) >= needed_pages
    allocated = self.free_slots[:needed_pages]
    self.free_slots = self.free_slots[needed_pages:]
    return allocated

流程

  1. 检查 free_slots 够不够
  2. 不够的话，从 Radix 树 evict 差额 × page_size 个 token 的 KV（挑 ref_count=0 的 leaf 节点）
  3. 把 evict 出来的 page 号加回 free_slots
  4. 从 free_slots 前面切 needed_pages 个返回

evict 策略是什么？

RadixPrefixCache.evict 用 时间戳最小堆：

# kvcache/radix_cache.py:148
def evict(self, size):
    leave_nodes = self._collect_leave_nodes_for_evict()    # 所有 ref_count=0 的叶子
    heapq.heapify(leave_nodes)                             # 按 timestamp 建堆
    ...
    while evicted_size < size:
        node = heapq.heappop(leave_nodes)                  # 最老的先 evict
        del parent.children[...]
        if parent.is_leaf() and parent.ref_count == 0:
            heapq.heappush(leave_nodes, parent)            # 父节点变孤儿后也可能被 evict
    return torch.cat(evicted_indices)

关键细节

细节说明
只 evict leaf中间节点有 children，不能直接删
只 evict ref_count=0被锁住的（正在用的）不能动
evict 可能连锁删掉叶子后父节点变叶子，可能也被 evict
timestamp 最小的先死LRU-like 策略：最近没访问的先被清
可能 evict 超过 sizeevict 的单位是节点的 length，不一定刚好等于 size
一个节点被 walk 到时会更新 timestamp热点 prefix 自动续命

evict 失败会怎样？

assert len(self.free_slots) >= needed_pages, "Eviction did not free enough space."

如果所有叶子都被锁住（evictable_size < 需求），evict 会先触发 assert size <= self.evictable_size 在 Radix 内部就崩。实际上 PrefillAdder 的 available_size 检查已经保证了这不会发生——装箱前先检查 available ≥ 需求，装不下的就不进 batch。

两层防护：
  • PrefillAdder 层：装箱前 check available_size，装不下就不装
  • _allocate 层：真需要了才 evict，evict 不够就 assert 崩
第一层是"预期路径"，第二层是"假设失败时立刻暴露 bug"。

PART 8lazy_free_region · 批量 free 优化

# cache.py:93
@contextmanager
def lazy_free_region(self):
    def lazy_free(indices: torch.Tensor) -> None:
        lazy_free_list.append(indices[:: self.page_size])

    lazy_free_list: List[torch.Tensor] = []
    try:
        self._free = lazy_free        # ★ 临时替换 _free 方法
        yield
    finally:
        del self._free                 # 移除临时方法, 恢复原 _free
        self.free_slots = torch.cat([self.free_slots] + lazy_free_list)
        # ↑ 一次性 cat 所有累积的 free 请求

这是什么 Python 技巧？

它用了"运行时方法替换"：在 contextmanager 期间把 self._free 指向一个临时闭包函数（只收集，不真 free）。退出时恢复并批量提交。

为什么这是 Python 的"运行时替换"？

正常情况下 self._free(x) 会调用类上定义的 _free 方法。但 Python 属性查找顺序是 instance dict → class dict，如果实例字典里有 _free，它会覆盖类上的同名方法。

所以 self._free = lazy_free 这一行就是在实例字典上加了个 _free 引用，暂时屏蔽掉类方法。del self._free 再把它删掉，后续调用就回到类方法了。

调用场景

# scheduler/scheduler.py:_process_last_data
with self.cache_manager.lazy_free_region():           # ★ 区域开始
    for i, req in enumerate(batch.reqs):
        if isinstance(req, ChunkedReq): continue
        ...
        if finished:
            self.decode_manager.remove_req(req)
            self._free_req_resources(req)                # 可能调用 _free 多次
        elif batch.is_prefill:
            self.cache_manager.cache_req(req, finished=False)  # 也可能 _free
# ★ 区域结束, 一次性 torch.cat 所有 free 请求

为什么不直接多次 _free？

# 如果每次 _free 都真 cat:
def _free(self, indices):
    self.free_slots = torch.cat([self.free_slots, indices[:: self.page_size]])
    # ↑ 每次 cat 都是 O(n), 10 个 req 调 10 次 → 10 次 cat

batch size 100 时，每 req 可能 free 多次（cache_req 就可能 free 两段）——一轮可能有几百次 torch.cat。每次 cat 要分配新 GPU tensor + 拷贝旧数据，累积开销巨大。

lazy 版本把几百次 cat 压缩成一次。CPU 端的 list.append 几乎免费。

PART 9check_integrity · 自我诊断

# cache.py:81
def check_integrity(self) -> None:
    self.prefix_cache.check_integrity()
    cache_pages = self.prefix_cache.size_info.total_size // self.page_size
    if len(self.free_slots) + cache_pages != self.num_pages:
        raise RuntimeError(
            "CacheManager integrity check failed:"
            f" free_pages({len(self.free_slots)}) +"
            f" cache_pages({cache_pages}) != num_pages({self.num_pages})"
        )
    if self.page_size > 1:
        assert torch.all(self.free_slots % self.page_size == 0)

它检查什么？

  1. 不变式 1：free + cache = total 
    free_pages + cache_pages == num_pages
    即每一页都能被定位（要么空闲、要么在树里）。
  2. 不变式 2：page_size 对齐 
    all(free_slots % page_size == 0)
    free_slots 里存的必须都是"页起始位置"。
  3. Radix 树自己的完整性：self.prefix_cache.check_integrity()（子类实现，目前空操作）

什么时候调用它？

# env 控制, 默认关
if ENV.ENABLE_INTEGRITY_CHECK:
    cache_manager.check_integrity()

调试/开发时打开，生产不开（每次 check 是 O(num_pages)，有性能代价）。

什么情况会触发失败？

  • 某个 req finish 时忘记 free page → cache_pages 少了
  • 某次 evict 把 page 号 free 了两次 → free_pages 多了
  • cache_req 的 5 段计算出错 → 漏 free 某段

你自己改代码时，最好每轮 loop 都开 check_integrity——能快速定位"page 泄露"或"page 重复"。这是 CacheManager 维护正确性的"后验证明"。

SUM总结 · CacheManager 的四条不变式

四条不变式

不变式说明违反意味着
①每个物理页要么在 free_slots 里，要么在某个 Radix 节点的 value 里page 泄露或重复使用
②free_slots 里的元素都是 page_size 对齐的分配出去的 page 基址非法
③Radix 节点的 ref_count > 0 ⟺ 被某个 Req.cache_handle 持有evict 会清掉正在用的 prefix
④page_table[req.table_idx, :req.device_len] 全部指向合法 pageattention kernel 读到垃圾 KV

每个方法维护哪条不变式？

方法维护哪些
allocate_paged④（写 page_table）, ①（从 free 拿到分配）
cache_req①（free 冗余、free 尾巴）, ③（unlock old、lock new）
_allocate①（从 free 取或 evict）
_free①（加回 free_slots）, ②（按 page_size 步长切片）
lock / unlock③（增减 ref_count）

为什么 API 这么"脆"？

CacheManager 没做防御性编程——它假设调用者按正确顺序调用。
  • cache_req 之前必须先 allocate_paged（否则 page_table 是零）
  • lock/unlock 必须配对（否则 ref_count 不对)
  • cache_req 的 req 必须有合法的 cache_handle (从 match_req 得来)
这些契约没有断言强制，只靠 scheduler 逻辑保证。这是"核心逻辑 < 700 行"的代价——代码简洁但调用方必须严格遵守顺序。

学习建议

  1. 先把 PART 2（内部状态）和 PART 6（cache_req 五段）弄明白
  2. 打开 ENABLE_INTEGRITY_CHECK，跑一些 benchmark 看有没有触发
  3. 试着写一个 print_tree 函数把 Radix 树打印出来，观察一次长 prefill 前后的变化
  4. 试着让 memory_ratio 调到 0.95+，触发 evict，观察 evict 时 free_slots 的变化
