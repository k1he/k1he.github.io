PART 1为什么需要 Req？不能直接用 UserMsg 吗？

先看数据流里都有哪些"请求对象"：

# 从客户端到完成, 一个请求会经历 4 种身份：

UserMsg     (message/backend.py)     # 跨进程传输消息，跨 ZMQ 边界
  ↓  scheduler 收到，需要排队等 prefill
PendingReq  (scheduler/utils.py)     # 排队中，还没分配任何资源
  ↓  PrefillAdder 装箱成功，分配 table_idx + cache_handle
Req / ChunkedReq  (core.py)         # 进入 forward 流水线，有完整状态
  ↓  finish / abort
资源释放

为什么不直接用 UserMsg 一路到底？

角色关心什么不关心什么
UserMsguid · input_ids · sampling_paramsKV 在哪、槽位、长度状态（它只是一个"网络消息"）
PendingReq上面 3 样 + chunked_req 指针table_idx、cache_handle（还没分配）
Req上面 + table_idx / cached_len / device_len / cache_handle—（它是"运行时全态"）
关键设计：这 4 个对象严格分层，字段只增不减。
  • UserMsg 是 msgpack 可序列化的，跨进程安全
  • PendingReq 活在 scheduler 主进程 CPU 内存里
  • Req 额外持有 GPU 资源（cache_handle 锁、table_idx 占位）
  • 每次 transition 都是"加字段 + 绑定资源"，没有任何 transition 会丢字段

这样设计的好处：每一层都只携带该层需要的信息。UserMsg 不需要知道 table_idx 是啥（跨进程传也没用）；PendingReq 不需要 GPU 资源（它在排队，可能等很久）；只有进入 forward 流水线的那一刻才升格成 Req，此时必须有完整状态。

PART 2三个长度 · 理解 Req 的核心 30 分钟

Req 有 3 个长度字段: cached_len / device_len / max_device_len。读错任何一个后面所有调度逻辑都会崩。我用"一个请求从到达到生成结束"整个生命周期铺开来看。

三个长度的物理意义

cached_len

"KV cache 里已经有的 token 数"

  • 等价说法："attention 可以读到的历史长度"
  • Radix 命中时初始 > 0
  • 每次 forward 完后推进
  • kernel 里 cu_seqlens_k[i+1] − cu_seqlens_k[i] 的前半部分

device_len

"本次 forward 想让 KV cache 到达的长度"

  • prefill 时 = input_len（要把全部 prompt 塞进去）
  • decode 时 = cached_len + 1（每次算 1 个新位置）
  • kernel 的 cu_seqlens_k 的整体长度
  • 决定 allocate_paged 需要多少新页

max_device_len

"这个请求一生的上限"

  • = input_len + max_tokens
  • 创建后不变（sampling_params 决定）
  • 决定 can_decode 什么时候变 False
  • "完结线"

两个派生属性

# core.py:44
@property
def extend_len(self) -> int:
    return self.device_len - self.cached_len
    # = "本次 forward 要新算的 token 数"
    # prefill 时 = input_len - cached_len (大)
    # decode 时 = 1 (小, 每次只新算 1 个)

@property
def remain_len(self) -> int:
    return self.max_device_len - self.device_len
    # = "还剩多少 token 没生成"
    # 0 时 can_decode 返回 False
记忆技巧（永远不混）：
  • cached_len = "过去" (已经完成)
  • device_len = "现在" (正在算到这)
  • max_device_len = "未来上限" (最多能到这)
  • extend_len = 现在 − 过去 = "本步活儿"
  • remain_len = 未来上限 − 现在 = "还剩多少工作"

最终版本（core.py:28 实际源码）

@dataclass(eq=False)        # ★ eq=False: 用 id() 判断相等, 放进 set 安全
class Req:
    input_ids: torch.Tensor    # cpu tensor - 每次 decode 后 append
    table_idx: int
    cached_len: int
    output_len: int
    uid: int
    sampling_params: SamplingParams
    cache_handle: BaseCacheHandle

    def __post_init__(self) -> None:
        assert self.input_ids.is_cpu
        self.device_len = len(self.input_ids)
        self.max_device_len = len(self.input_ids) + self.output_len
        assert 0 <= self.cached_len < self.device_len <= self.max_device_len
注意 @dataclass(eq=False)。默认 dataclass 会根据所有字段生成 __eq__ 和 __hash__，但 Req 里有 tensor（不可 hash）。eq=False 让它回退到 object.__eq__（按 id 比较）和 object.__hash__（id 哈希）——这样 Req 可以直接放进 set，这是 DecodeManager 能用 Set 存 running_reqs 的前提。
__post_init__ 里的断言极其重要： 
assert 0 <= self.cached_len < self.device_len <= self.max_device_len
这个不等式是 Req 类的不变式：
  • cached_len < device_len （严格小于）→ 至少有 1 token 要算，否则这个 req 进 forward 没意义
  • device_len ≤ max_device_len → 不能超过上限
  • cached_len 可以 = 0 → 没命中 Radix 时的初始状态
任何时候违反这个不变式都会 assert 崩溃——这是防御性编程的典范。

PART 4complete_one / append_host · 两个至关重要的"时刻"

complete_one · 推进长度状态机

# core.py:52
def complete_one(self) -> None:
    self.cached_len = self.device_len    # "现在" 变成 "过去"
    self.device_len += 1                 # "现在" 向前推一步

两行，但调用时机是整个系统最精妙的一环：

# engine/engine.py:198  forward_batch
def forward_batch(self, batch, args) -> ForwardOutput:
    ...
    with self.ctx.forward_batch(batch):
        if self.graph_runner.can_use_cuda_graph(batch):
            logits = self.graph_runner.replay(batch)
        else:
            logits = self.model.forward()

    for req in batch.reqs:
        req.complete_one()          ★ 这里！GPU 还在 async 跑，但 CPU 已经更新状态

    next_tokens_gpu = self.sampler.sample(logits[:batch.size], args)
    ...
为什么 complete_one 发生在 sampler.sample 之前？

这是 overlap scheduling 的刚性需求。调度流水线的下一步（下一轮 overlap_loop 的 _schedule_next_batch）需要立刻用最新的 cached_len 和 device_len 来决定：
  • 下一轮要给 decode 这个 req 分配哪些新 page（需要最新 device_len）
  • 下一轮的 cu_seqlens_k 是多少（需要最新 device_len）
  • can_decode 还是 True 吗（需要最新 remain_len）
如果 complete_one 放到 _process_last_data 里才调用，意味着下一轮调度看到的还是"老的" cached_len——正好晚一步，会导致 KV 重算或越界。

append_host · 追加新生成的 token 到 input_ids

# core.py:56
def append_host(self, next_token: torch.Tensor) -> None:
    self.input_ids = torch.cat([self.input_ids, next_token])

调用点在 _process_last_data：

# scheduler/scheduler.py:149
next_token = next_tokens_cpu[i]
req.append_host(next_token.unsqueeze(0))     # 把新 token 接到 CPU input_ids 尾部
finished = not req.can_decode or next_token == self.eos_token_id
为什么要维护 CPU 侧的 input_ids？
  • GPU 上的 token_pool[table_idx] 也存着完整 token 序列，理论上够用
  • 但某些场景（abort、resume、Radix Cache insert_prefix）要在 CPU 上用 input_ids 做树查，读 GPU 要同步开销大
  • cache_req 时的 req.input_ids[:req.cached_len] 就是在 CPU 上访问
  • 另外 CPU 侧留一份也是容错备份——GPU OOM 时还能序列化状态
代价是每次 decode 要做一次 torch.cat（在 CPU 上），不到 1µs，可以忽略。

这两个方法加起来就是 Req 的"成长"：

所以状态演化其实分两拍：

  1. complete_one (GPU 算完后立即) → cached_len / device_len 推进，让下一轮调度用上新状态
  2. append_host (下一轮 _process_last_data) → input_ids 追加，让 CPU 侧也有完整上下文

PART 5PendingReq · 为什么不直接用 Req

# scheduler/utils.py:14
@dataclass
class PendingReq:
    uid: int
    input_ids: torch.Tensor
    sampling_params: SamplingParams
    chunked_req: ChunkedReq | None = None

    @property
    def input_len(self) -> int:
        return len(self.input_ids)

    @property
    def output_len(self) -> int:
        return self.sampling_params.max_tokens

注意它没有：table_idx / cached_len / cache_handle——这些字段是 Req 独有的。

为什么需要分开？

原因说明
排队期间不占 GPU 资源PendingReq 可能在队列里等几秒——如果一进来就分配 table_idx 和锁 Radix 节点，系统很容易资源耗尽
Radix 状态会变等到真要跑时才 match_prefix，这时才反映最新的 Radix 树——如果提前 match 保存，其他 req 可能已经让树长出了新节点
Req 的 cached_len 必须 > 0 && input_ids 对齐Req 的 __post_init__ 有不变式约束，PendingReq 阶段还没分配资源无法满足
abort 更轻量PendingReq 直接从 list 删除即可；Req 要 free table_idx + unlock cache_handle

chunked_req 这个字段干啥的？

它是 "状态机桥接指针"——让一个 PendingReq 可以跨多轮 schedule，其中某些轮产出了 ChunkedReq（部分 prefill），并把这个 ChunkedReq 挂回 PendingReq 供下一轮接续：

# scheduler/prefill.py:140  PrefillManager.schedule_next_batch
for pending_req in self.pending_list:
    if req := adder.try_add_one(pending_req):
        pending_req.chunked_req = None           # 默认清除
        if isinstance(req, ChunkedReq):
            pending_req.chunked_req = req            # 没装完，记下来下轮接续
            chunked_list.append(pending_req)
        reqs.append(req)

然后在 try_add_one 里：

# scheduler/prefill.py:96
if chunked_req := pending_req.chunked_req:       # ★ 上轮有未完成的 chunk
    return self._add_one_req(
        pending_req=pending_req,
        cache_handle=chunked_req.cache_handle,      # 复用上轮的
        table_idx=chunked_req.table_idx,             # 复用上轮的
        cached_len=chunked_req.cached_len,           # 接上次结尾
    )
关键洞察：一个 PendingReq 的 cache_handle 和 table_idx 在 chunked prefill 期间不会释放、不会变，ChunkedReq 作为"进度书签"挂在 PendingReq 上。下一轮 schedule 时直接从书签接续，不需要重新 match_prefix、不需要重新 allocate table_idx。

PART 6ChunkedReq · 禁止被采样的特殊 Req

# scheduler/prefill.py:23
class ChunkedReq(Req):
    def append_host(self, next_token: torch.Tensor) -> None:
        raise NotImplementedError("ChunkedReq should not be sampled")

    @property
    def can_decode(self) -> bool:
        return False  # avoid being added to decode manager

整个类就 2 个覆盖——但这 2 个覆盖封死了所有错误路径。

为什么要"禁止采样"？

设想：一个 long prompt 被切成 chunk 1 (8192 token) + chunk 2 (1808 token)。chunk 1 跑完 forward，得到 logits。但这个 logits 对应的是 prompt 的第 8192 个位置，不是下一个要生成的位置——采样它会产出错误的 token！

所以 ChunkedReq 用这两个覆盖：

覆盖防住了什么
append_host → raise如果 _process_last_data 不小心采样了它然后 append_host，会立刻崩溃而不是悄悄产出错误输出
can_decode → False防止 filter_reqs 把它加进 DecodeManager（否则它会跟正常 req 一样参与 decode，但它的 KV 还没完全建好）

_process_last_data 里的防御

# scheduler/scheduler.py:147
for i, req in enumerate(batch.reqs):
    if isinstance(req, ChunkedReq):
        continue                    # ★ 显式跳过 ChunkedReq
    next_token = next_tokens_cpu[i]
    req.append_host(next_token.unsqueeze(0))
    ...

就算上面的 continue 被误删，append_host 也会 raise 兜底——两层保险。

继承 Req 但重写关键方法这种模式：看起来简单，但这是把"不变式"编码进类型系统——只要你给 scheduler 一个 ChunkedReq，它绝不可能被当作普通 req 产出错误结果。比用 if-else 控制流安全得多。

PART 7TableManager 要解决什么问题

现在转到 TableManager。它只有 22 行代码，但定位极其关键。

它是什么？

"请求槽位号"的发号器 + page_table / token_pool 这两个 GPU 大数组的拥有者。

TableManager 维护：
├── _free_slots      : List[int]             # 空闲槽位号池
├── page_table       : GPU int32 tensor      # [max_running_req+1, max_seq_len]
└── token_pool       : GPU int32 tensor      # [max_running_req+1, max_seq_len]

为什么需要"槽位号"？

回到 paged attention 的设计：每个活跃请求占 page_table 的一行。这行就是它的"寄存器"，所有针对这个请求的操作（写 KV 物理位置、查历史 token id）都在这一行上进行。

为什么用 List[int] 而不是 bitmap 或 freelist?

Python list 的 append/pop 都是 O(1)，且 max_running_req 通常 ≤ 256，线性操作也快。用 bitmap 反而增加复杂度。简单暴力最优雅。

page_table 和 token_pool 的形状为什么相同？

# table.py:11
self.page_table = page_table
self.token_pool = torch.zeros_like(page_table, dtype=torch.int32)   # ★ 同 shape, 同 dtype
维度page_table[i, j] 含义token_pool[i, j] 含义
row i请求的 table_idx请求的 table_idx
col j第 j 个 token 所在的物理 KV 页号第 j 个 token 的 token_id (int32)

每个请求两份数据，按同样的 [table_idx, pos] 索引：一份告诉 attention kernel "KV 在 pool 哪一页"，另一份告诉 model 输入"这个位置是哪个 token id"。

PART 8TableManager 全量源码（22 行）

# scheduler/table.py 全文
class TableManager:
    def __init__(self, max_running_reqs: int, page_table: torch.Tensor) -> None:
        self._max_running_reqs = max_running_reqs
        self._free_slots = list(range(max_running_reqs))    # 初始全部空闲
        self.page_table = page_table
        # NOTE: dummy request also use this pool to get the input ids, so we need to
        # make sure the token pool is initialized with valid values (token_id = 0).
        self.token_pool = torch.zeros_like(page_table, dtype=torch.int32)

    @property
    def available_size(self) -> int:
        return len(self._free_slots)

    def allocate(self) -> int:
        return self._free_slots.pop()             # 从末尾取, O(1)

    def free(self, slot: int) -> None:
        self._free_slots.append(slot)             # 放末尾, O(1)

核心接口只有 3 个

接口语义被谁调用
allocate() -> int分配一个空闲槽位，返回 table_idxPrefillAdder._try_allocate_one（req 新进入时）
free(slot)释放一个槽位回池Scheduler._free_req_resources（req finished 或 abort 时）
available_size剩余槽位数PrefillAdder 先检查再 allocate

分配的"LIFO" 策略

_free_slots = [0, 1, 2, 3, ..., 254, 255]
              ↑ 前面                  后面 ↑
            .pop() 从这里取   = 255
            .append() 放回这里

所以前几个活跃请求会分到 table_idx = 255, 254, 253, ...——从大到小分配。这是个无所谓的实现细节，但解释了为什么你日志里看到的 table_idx 常常是高位。

无锁并发安全？

不需要锁——因为 Scheduler 是单线程事件循环。TableManager 的所有接口都只在主循环里调用，没有并发冲突。这是 mini-sglang 整个调度层都没加锁的设计根基。

PART 9dummy_req · 为什么 page_table 行数是 max_running_req + 1

    input_ids=torch.tensor([0], dtype=torch.int32, device="cpu"),

self.page_table[self.dummy_req.table_idx].fill_(num_tokens)
# ↑ 让 dummy 行的所有位置都指向"dummy 页"（池的最后一个位置, 边界外但合法）

这 dummy 行的作用

CUDA Graph 录制需要"形状固定"的输入（见 07 章）。bs=8 的 graph 需要 batch 里真的有 8 个 req。当实际只有 3 个真 req 时，PrefillAdder 之后 pad_batch 会塞 5 个 dummy_req 凑到 8。

# engine/graph.py:161
batch.padded_reqs = batch.reqs + [self.dummy_req] * (padded_size - batch.size)

为什么 dummy_req 能安全地被 attention kernel 读？

  • 它的 table_idx = max_running_req（page_table 的最后一行，不跟任何真实 req 冲突）
  • 这一行所有位置都指向 page_indices = num_tokens（KV pool 最后一个位置，算是"占位页"——不是真实数据但是合法地址，读不会越界）
  • 它的 cached_len = 0，input_ids = [0]（1 个假 token，值为 0）
  • 它参与 forward 会产出一行垃圾 logits，但 _process_last_data 用 batch.size（不是 padded_size）来切片，垃圾 logits 根本不会被采样

设计的精妙

整个系统的"不变式"被 dummy_req 精巧地维护：
  • attention kernel 不需要知道 dummy 的存在，它把 dummy 当真 req 正常算
  • sampler 只看 logits[:batch.size]，自动裁掉 dummy 那几行
  • page_table 多开一行的代价：max_seq_len × 4 字节，几十 KB，微不足道
  • dummy 不占 _free_slots（初始化时 list(range(max_running_req)) 不含 max_running_req），永远不会被分出去给真 req
这是用一个固定的"假身份"来让 CUDA Graph 的形状假设成立——优雅的 workaround。

把上面所有知识点串起来：一个请求从 HTTP 进来到最终释放，经历了哪些对象和 TableManager 的哪些调用？

# ============= 阶段 1: 进入 scheduler =============
1. Tokenizer 把 UserMsg 推给 scheduler
2. _process_one_msg → prefill_manager.add_one_req(msg)
   → PendingReq 创建, 入 pending_list  (uid, input_ids, params, chunked_req=None)

# ============= 阶段 2: 被 PrefillAdder 选中 =============
3. scheduler._schedule_next_batch() → PrefillAdder.try_add_one(pending)
4. PrefillAdder._try_allocate_one:
   a. table.available_size 检查 → 通过
   b. cache_manager.match_req(pending) → handle (cached_len=0 或 >0)
   c. 容量检查 → 通过
   d. cache_manager.lock(handle)        # 锁住 Radix 节点
   e. table.allocate() → table_idx=255
   f. 写 token_pool[255, :cached_len] (如果有 cache 命中)
5. PrefillAdder._add_one_req:
   - 创建 Req(input_ids[:cached_len+chunk_size], table_idx=255, cached_len=..., cache_handle=handle)
   - 或 ChunkedReq (如果 chunk_size < remain)
   - 写 token_pool[255, cached_len:cached_len+chunk_size]

# ============= 阶段 3: forward (prefill) =============
6. scheduler._prepare_batch:
   - cache.allocate_paged([req]) → 写 page_table[255, cached_len:device_len]
   - attn.prepare_metadata(batch) → cu_seqlens, indices 等
7. engine.forward_batch → model forward
8. req.complete_one() → cached_len=device_len, device_len+=1
9. sampler.sample → next_tokens (on GPU)
10. 下一轮 loop 开始, last_data = 这轮的 forward_output

# ============= 阶段 4: _process_last_data (上一轮结果) =============
11. copy_done.synchronize() → next_tokens_cpu 可读
12. req.append_host(next_token) → input_ids 长度 +1
13. finished = not req.can_decode or next_token == eos_token_id
14. batch.is_prefill → cache.cache_req(req, finished=False)
    → prefix_cache.insert_prefix(input_ids[:cached_len], page_table[255, :cached_len])
    → 可能更新 req.cache_handle 指向新节点
15. req 加入 decode_manager.running_reqs (通过 filter_reqs)

# ============= 阶段 5: decode 循环 =============
16. 每轮 decode: device_len += 1, 算 1 token, append_host, 判断 finished
17. 需要新 page 时: cache.allocate_paged → page_table[255, 新位置] = 新页号

# ============= 阶段 6: 结束 =============
18. 某轮 remain_len==0 or next_token==eos → finished=True
19. decode_manager.remove_req(req)
20. scheduler._free_req_resources:
    a. table.free(255)                  # 槽位回池
    b. cache.cache_req(req, finished=True)
       → insert_prefix (让后续请求可命中)
       → unlock old_handle
       → _free(冗余 pages) 送回 free_slots

关键时刻图

PART 11容易踩错的 6 个细节

坑 1 · 为什么 PendingReq 不持有 cache_handle？

如果 match_prefix 的时机在 PendingReq 创建时就做了，保存的 handle 会快速过时——其他 req 可能让 Radix 树重建、让命中的节点 evict 或 split。所以每次 PrefillAdder 尝试装箱才 match 一次。

坑 2 · try_add_one 成功 != 进入 batch

# scheduler/prefill.py:139
for pending_req in self.pending_list:
    if req := adder.try_add_one(pending_req):
        ...
    else:
        break   # ★ 一遇到失败就 break, 不 continue!

pending_list 按 FIFO 顺序处理，一遇到装不下就停——不会跳过这个去试下一个。这保证 head-of-line 的请求不会饿死（后面小请求插队）。如果改成 continue，先来的大 req 可能一直排不上。

坑 3 · PrefillAdder 的 reserved_size 初值

# scheduler/prefill.py:131
adder = PrefillAdder(
    token_budget=prefill_budget,
    reserved_size=self.decode_manager.inflight_tokens,   # ★ 关键
    ...
)

初始就把"已经 running 的 decode req 未来还会用到的 token 数"占上，防止 prefill 贪心吃光 KV 导致 decode OOM。没有这一行系统会间歇性崩。

坑 4 · page_table / token_pool 多出的那一行永远指向 0

self.token_pool = torch.zeros_like(page_table, dtype=torch.int32)

初始化全零——dummy_req 的 token_id 就是 0（vocab 里通常是 <pad> 或 <unk>）。这样 dummy 在 CUDA Graph capture 期间被 embed_tokens 读时不会出错。如果初始化为 garbage，embed 可能越界。

坑 5 · abort 的两条路径

# scheduler/scheduler.py:_process_one_msg
req_to_free = self.prefill_manager.abort_req(msg.uid)    # 路径 A
req_to_free = req_to_free or self.decode_manager.abort_req(msg.uid)  # 路径 B
if req_to_free:
    self._free_req_resources(req_to_free)
  • A: req 还在 pending_list（PendingReq 阶段）→ 直接 pop，返回它的 chunked_req（可能为 None）
  • B: req 已经在 running_reqs（Req 阶段）→ 从 set 删除，返回 Req
  • 无论哪种，只要拿到 Req 就 _free_req_resources（回收 table_idx + cache handle）
  • PendingReq 没有资源可释放 → 如果 chunked_req 为 None 就啥都不做

坑 6 · @dataclass(eq=False) 和 Set 的隐含约束

DecodeManager.running_reqs 是 Set[Req]，依赖 Req 可 hash。eq=False 让 dataclass 用 object.__hash__（按对象 id）。这意味着：

  • 即使两个 Req 内容相同（假设能），它们也是不同的 set 元素
  • 永远不能用 copy.copy 或 deepcopy 一个 Req 丢进同一个 set——id 会变，行为不可预测
  • 一个 Req 在 filter_reqs 里被 union 多次是安全的——id 相同，set 只保留一份
