§1从一条请求讲起

假设用户发来：

Prompt: "给我讲讲 GPU 架构"  (10 tokens)
期望输出: 200 tokens 的回答

模型要做的事情被天然切成两段：

两段的本质区别

  • Prefill：一次拿到 10 个 token，并行算 Q/K/V，一次 forward 把 10 个位置全跑完
  • Decode：每次只有 1 个新 token（刚生成的那个），但要用它的 Q 去看前面所有 token 的 K/V
核心差异在"batch 维度的 seq_len"：Prefill 的单请求 seq_len = prompt 长度（可以几千），Decode 的单请求 seq_len = 1。这一点把两个阶段的算术强度分开到两个极端。

§2Prefill · Compute-Bound 的一次性狂欢

权重搬 1 次 → 在 seq_len 个 token 上都用

考虑一层 FFN（d=4096、mid=11008）。权重 shape 是 [d, mid]：

Prefill 处理 seq_len=4096 tokens:
  输入 X: [4096, 4096]      # 16 MB
  权重 W: [4096, 11008]     # 180 MB
  输出 Y = X @ W: [4096, 11008]

# 搬的 byte
  X:   32 MB  (bf16)
  W:  360 MB  (bf16)
  Y:   90 MB  (bf16)
  总计 ~482 MB

# 算的 FLOPs
  2 · 4096 · 4096 · 11008 ≈ 370 GFLOPs

AI = 370e9 / 482e6 = ~770 FLOPs/byte  ← 远超 H100 拐点 295
结论：Prefill compute-bound。GPU 的 Tensor Core 被喂得很饱，算力利用率可以打到 60~80%。TTFT (Time To First Token) 基本由"算多少"决定。

性质一览

时间复杂度
O(seq_len² · d) （attention）+ O(seq_len · d²) （FFN）
瓶颈
算力 · Tensor Core
调度建议
单独跑一次、跑满卡、尽快出第一个 token
痛点
长 prompt 时 TTFT 很长（seq_len² 项开始主导），用户等不住
常用优化
Chunked Prefill · FlashAttention · Speculative Decoding

§3Decode · Memory-Bound 的循环苦役

每步只有 1 个 token → 权重搬了也只用一次

Decode 单步（batch=1）:
  输入 X: [1, 4096]        # 8 KB
  权重 W: [4096, 11008]    # 180 MB  ← 和 prefill 一样大!
  输出 Y: [1, 11008]       # 22 KB

# 搬的 byte
  W: 360 MB  # 最大头
  X/Y: 可忽略
  总计 ~360 MB

# 算的 FLOPs
  2 · 1 · 4096 · 11008 ≈ 90 MFLOPs   ← 比 prefill 少 4000 倍

AI = 90e6 / 360e6 = 0.25 FLOPs/byte
结论：Decode 极度 memory-bound。GPU 大部分时间在等 HBM 把权重搬进来，Tensor Core 几乎闲着。算力利用率常常只有 1~5%。

性质一览

时间复杂度
O(1 · d²) + O(ctx · d)（KV attention）· 每步都要把权重+KV重新搬一次
瓶颈
HBM 带宽 · launch 开销（kernel 跑得快，CPU 追不上）
调度建议
塞 batch · 用 CUDA Graph · 把小请求拼大请求
痛点
长上下文时 KV 搬运成本线性涨 · 单卡可同时 serve 的并发数被 KV 吃死
常用优化
Continuous Batching · Paged Attention · CUDA Graph · GQA · Speculative Decoding · MTP

最反直觉的点：prefill 和 decode 用同一份权重、跑同一个模型、同一张卡——但它们应该用完全不同的调度策略。这就是为什么 mini-sglang 专门开两个 Manager：PrefillManager 和 DecodeManager（对应 15 章）。

§6两阶段分化 → 五大调度技巧的根源

mini-sglang 的五大核心优化，每一个都能用"prefill/decode 哪个瓶颈"来解释：

优化针对哪个阶段核心思想对应章节
Continuous Batching Decode 把 N 个 decode 请求拼成大 batch，AI 从 1 提到 N 04
Radix Cache / Prefix Cache Prefill 相同前缀的 prompt 共享 KV，跳过已算过的 token 14
Chunked Prefill Prefill 长 prompt 切小块，和 decode 混批，不让 TTFT 阻塞 ITL 04/15
Paged Attention Decode KV 用 page 管理，避免碎片化，提高显存利用率 → 更大 batch 05/08
CUDA Graph Decode decode 时 kernel 太快，CPU launch 追不上 → 录制 replay 07
Tensor Parallel 两者 权重切到多卡 → 总 HBM 带宽变 N 倍 06
Overlap Scheduling 两者 prepare（CPU 重）和 forward（GPU 重）两条 stream 并行 11
学习提示：后续每章出现一个优化时，先问自己 3 个问题——
① 这是在优化 prefill 还是 decode？
② 它把 memory-bound 变 compute-bound，还是反之？
③ 它用什么资源（算力/带宽/显存/CPU 时间）换了什么？
只要能回答，就说明你真读懂了。
