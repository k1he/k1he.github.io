§1KV Cache 的体积公式 · 为什么吓人

回顾第 03 节的结论：decode 时每一步，当前 token 的 K、V 要存起来，后面所有 token 的 attention 都要读它们。所以 KV Cache 随上下文长度线性增长。

精确公式

KV Cache size (byte) = 2 (K和V) · L (层数) · N_kv (KV 头数) · d_head · seq_len · dtype_size
注意是 N_kv 不是 num_heads——这是 GQA 能省内存的关键点。MHA 时 N_kv = num_heads；MQA 时 N_kv = 1；GQA 时 N_kv = num_heads / group。

代入 Qwen3-8B 试算

L          = 36 层
num_heads  = 32
N_kv (GQA) = 8     # 4 个 Q 共享 1 组 K/V
d_head     = 128
dtype      = bf16 (2 byte)

每 token 每层 KV = 2 · 8 · 128 · 2 = 4 KB
每 token 全部 KV = 4 KB · 36 = 144 KB
1024 tokens KV   = 144 MB
8192 tokens KV   = 1.15 GB       # 单个请求！

想象一下 batch=32、每个 seq_len=4096 的场景——KV Cache 就得吃 18 GB。80 GB 的 H100 满打满算，权重占 16 GB 后，剩下只有 64 GB，能并发的 batch 立刻被 KV 卡死。

这就是 KV Cache 体积 = 并发上限的 dominant 因素。所以 GQA 能把 N_kv 从 32 砍到 8（省 4 倍），意味着同样显存下 batch 能开大 4 倍，吞吐直接翻倍多。

§2MHA · Multi-Head Attention · 原教旨版

原论文 2017 年的设计：每个 Query 头独享自己的 Key 头、Value 头。三组数量完全相同。

# PyTorch 伪代码
K = x @ W_K    # [N, 8, 128]
V = x @ W_V    # [N, 8, 128]
# 每个 Q 头 i 只读自己的 K[_,i,:] 和 V[_,i,:]

代表模型：GPT-2, Llama-1, OPT, 绝大多数 2020 前的模型。

§3MQA · Multi-Query Attention · 激进省法

2019 年 Shazeer 提了一个极端方案：所有 Q 头共享同一组 K/V。K/V 只有 1 个头。

问题：表达力跌得有点狠。精度下降几个点，大模型上明显能感觉到。只有在非常看重 decode 速度的小模型上（比如 PaLM-540B 用了）才值得。

§4GQA · Grouped Query Attention · 工业级共识

2023 年 Google 提了折中方案：每 g 个 Q 头共用一组 K/V。例如 32 Q 头分 8 组，每组 4 个 Q 共享 1 组 KV。

为什么几乎无损

  • 实验证明：注意力头里确实有大量冗余——相邻的头 K/V 高度相似
  • 让它们共享一份 K/V，等于轻度参数约束——几乎不影响拟合
  • 节省的显存 → 更大 batch → 更高吞吐 → 整体更划算
代表模型：Llama-2/3、Qwen-2/3、Mistral、GLM-4、几乎所有 2023 之后的开源模型都用 GQA。比例从 2:1 到 8:1 都有。

代码层面只是一个 "扩维"

# K: [N, n_kv_heads, d_head]  → 重复成 [N, n_q_heads, d_head]
K = K.repeat_interleave(n_q_heads // n_kv_heads, dim=1)
V = V.repeat_interleave(n_q_heads // n_kv_heads, dim=1)
# 后面 attention 代码和 MHA 完全一样

——所以推理 kernel 写一套就能同时支持 MHA/GQA，区别只在存 KV 时按 n_kv_heads 存，读 KV 时按 n_q_heads 展开。

§6mini-sglang 里对应哪段代码

两处要注意：

① 模型配置读的就是 num_kv_heads

# models/qwen3_moe.py
num_heads      = config.num_attention_heads   # 32
num_kv_heads   = config.num_key_value_heads   # 8  ← GQA 的关键
head_dim       = config.head_dim              # 128

# QKV projection 用不同输出维度
self.qkv = QKVParallelLinear(
    hidden_size,
    head_dim,
    total_num_heads=num_heads,       # Q: 32 头
    total_num_kv_heads=num_kv_heads, # KV: 8 头 (不是 32!)
)

② KV Cache 池按 num_kv_heads 分配，不按 num_heads

# kvcache/mha_pool.py · 第 08 章详讲
self.kv_buffer = torch.empty(
    [2, num_pages, page_size, num_kv_heads, head_dim],
    dtype=torch.bfloat16, device="cuda"
)
# ^^^^^^^^^^^^ ← 这里用 num_kv_heads，直接省 4 倍显存

③ Attention kernel 自动把 KV "展开"

# FlashInfer 的 kernel 接口接受独立的 num_q_heads / num_kv_heads
flashinfer.BatchPrefillWithPagedKVCacheWrapper.forward(
    q,                  # [total_tokens, 32, 128]  Q
    paged_kv_cache,     # [pages, 2, page, 8, 128] KV（注意第 4 维是 8）
    num_qo_heads=32,
    num_kv_heads=8,     # ← kernel 内部按 4:1 repeat
)
核心记忆点：num_kv_heads 是贯穿整个 mini-sglang 的参数——从模型配置、到 KV Cache 池形状、到 attention kernel 入参，全都围着它转。理解了 GQA，后面看 08 章 KV Cache 池的 6 维 shape 就丝毫不觉得奇怪。

§∞带走这三条

① KV 体积公式
2 · L · N_kv · d_head · seq · 2byte · batch · N_kv 是杠杆
② 三种 attention
MHA (N_kv=H) / MQA (N_kv=1) / GQA (N_kv=H/g) · 精度几乎无损但显存省 g 倍

2023 之后开源模型几乎全 GQA · 比例常见 4:1 或 8:1
