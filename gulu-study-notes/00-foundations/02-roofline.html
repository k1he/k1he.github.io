§1算术强度 (Arithmetic Intensity) 到底是什么

就一个公式：

AI  =  FLOPs / Bytes   # 每搬 1 byte 数据，做了多少次乘加

两个极端例子

例 1 · 向量加法

c[i] = a[i] + b[i]
# 读 2 个 float = 8 byte
# 做 1 次加法 = 1 FLOP
AI = 1 / 8 = 0.125
极低 · 极端 memory-bound

例 2 · 方阵乘 N×N

C = A × B, 三者都是 N×N
# 读 3·N²·4 byte
# 做 2·N³ FLOPs
AI = 2N³ / 12N² = N/6
N=1024 时 AI ≈ 170 · 基本打满算力
核心洞察：AI 只看"搬的数据"和"在它上面做的运算"的比值。所以同样是矩阵乘，如果读完就丢、不复用，AI 再大也会变小——FlashAttention 的精髓就是改变 AI，把 softmax 压在 Shared Memory 里做、不回写 HBM。

§2Roofline 图 · 一张图讲清 GPU 有没有被吃满

把 X 轴画成"算术强度 AI"，Y 轴画成"实际达到的 TFLOPS"，GPU 给你的上限就长成一个"房顶":

三个关键读法

  • 斜线部分：AI 低于 295 时，能达到的 TFLOPS = AI × 带宽——完全由带宽决定
  • 平顶部分：AI 超过 295 后，带宽不再是瓶颈，算力顶住——完全由算力决定
  • 拐点 295：这是 H100 FP16 特有的数字（不同卡不同：A100 ≈ 208，RTX 4090 ≈ 164）
工程上这叫"找 roofline 位置"——任何 kernel profile 完，都是一个 (AI, 实际 TFLOPS) 点。点贴近斜线 → 你该优化带宽；点贴近平顶 → 你该优化算法/分 tile。贴不到任何一条线 → 你的 kernel 写得有 bug。

§4亲手推 · 为什么 decode 的 AI ≈ 1

取 Qwen3-8B 规模（d=4096、L=32 层、FFN 倍率 3）、BF16、batch=1 decode：

Step 1 · 这一步要读什么

一层 Transformer 的权重 ≈
    QKV_proj   : 3·d·d        = 48M params
    Out_proj   : d·d           = 16M
    FFN (gate/up/down) : 3·d·(3d) = 144M
                                 ─────
                                 208M params × 2 byte = 416 MB / layer
32 层 ×        = 13.3 GB / token   # 每生成 1 个 token 要读完全部权重

Step 2 · 这一步算了多少

一层的乘加数 ≈ 2 · 208M ≈ 416M FLOPs
32 层        ≈ 13.3G FLOPs
  # Attention 部分与 seq 长度相关，此处忽略 seq 不长的情况

Step 3 · 算 AI

AI = 13.3e9 / 13.3e9 = ~1 FLOP/byte
这就是为什么 batch=1 的 LLM decode 永远跑不满 GPU，无论你卡多强：每搬 13 GB，只算 13 G FLOPs。H100 算力 989 TFLOPS 在这一帧里只能发挥到 3.35 TFLOPS，利用率 0.34%。

§5batch 为什么能神奇地提速 · AI 的放大器

关键洞察：一组权重搬进来，可以同时服务 B 个请求的 decode——因为每个请求都要乘同一组权重。所以：

batch=B decode:
  搬的 byte   = 13.3 GB   # 权重只搬一次
  算的 FLOPs  = 13.3 G × B # 每个请求各算一次
  AI          = B
batchAI可达 TFLOPS单 token 延迟吞吐 (tok/s)
113.354 ms250
4413.44 ms1000
161653.64 ms4000
64642144 ms16000
256256858 (近打满)4 ms64000
10241024989 (饱和)15 ms68000

两个关键观察

  1. batch 从 1 涨到 256，单 token 延迟几乎不变——因为瓶颈是带宽，权重总得搬，算力本来就富余
  2. 超过 batch 256，延迟开始线性涨——算力真打满了，再多也只能排队
这就是 mini-sglang 的 "continuous batching" 想解决的事：尽可能把当前正在 decode 的请求塞到 batch 里凑数，让 AI 逼近 GPU 的拐点。而为什么不能无脑塞？——KV Cache 显存有限（几个 GB 就没了），能并发的 batch 是被 KV 而不是算力卡住的。后面章节的 PrefillAdder、reserved_size 博弈，本质都在算这笔账。

§6带走这三条，配套后续章节食用

① AI = FLOPs/Bytes
超过拐点 → GPU 才能真正"忙起来"
② decode 原生 AI=1
永远 memory-bound · 优化只能从"提高 AI"入手
③ batch 是免费午餐
B 个请求共用一次权重搬运 · AI 直接乘 B · 延迟几乎不变
