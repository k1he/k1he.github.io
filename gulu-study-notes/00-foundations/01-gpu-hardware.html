§0为什么 LLM 推理的每一条优化，都要先从硬件讲起

你会在 mini-sglang 里反复看到这些奇怪设计：

  • KV Cache——把算过的 K/V 存下来，换显存省算力
  • Paged Attention——把一段连续 KV 切成 page，页表寻址
  • CUDA Graph——把一整次 forward 录成图，一键 replay
  • Tensor Parallel——权重横切竖切，每卡只存一块
  • Chunked Prefill——长 prompt 切成小块，和 decode 混批

它们看起来五花八门，但全部都在回答同一个硬件问题：

GPU 的算力涨得比显存带宽快 10 倍，但 LLM decode 的本质是搬一堆权重/KV 进来、算一点点、再搬出去——所以推理几乎永远被带宽卡死，而不是被算力卡死。一切优化都在想办法让 HBM 少动、或者让动过的东西被反复用。

这一章的目标：让你看到"搬"和"算"的速度差距，后面所有 trick 你就能一眼看穿。

§1SM 是什么 · 为什么 GPU 有 100+ 个小核心

一块 H100 上有 132 个 SM（Streaming Multiprocessor，流多处理器）。你可以把它理解成 GPU 里的"132 个独立工人小组"。每个 SM 内部长这样：

一句话解读

  • SM 是 GPU "并行的单位"——kernel 启动时，thread block 被分发到不同 SM 上独立跑
  • SM 内部又分三种计算单元：CUDA Core（万金油）、Tensor Core（矩阵乘专用）、SFU（sin/exp 这类特殊指令）
  • SM 内部只有两层快速存储：Register（线程私有）、Shared Memory（block 内共享）
  • 出了 SM 就只剩 HBM（显存）——慢 100 倍以上

§2Warp 为什么是 32 · SIMT 执行模型

GPU 不像 CPU 一次执行一条指令，它一次执行 32 条——这 32 条绑在一起叫一个 warp。理由很简单：

一个指令译码器 + 32 个 ALU 比 32 个指令译码器 + 32 个 ALU 便宜得多。GPU 舍掉了 CPU 的乱序执行、分支预测、大 cache，全部省下的晶体管都堆成了 ALU。代价是——32 个线程必须跑同一条指令。

SIMT 就是"让 32 个线程步调一致"

warp 是隐藏延迟的"神器"

一个 SM 同时驻留 多个 warp（64 个也不奇怪）。当一个 warp 在等 HBM 返回数据（几百个 cycle）时，Warp Scheduler 瞬间切到另一个 warp继续跑——切换 0 开销，因为所有 warp 的寄存器都同时存在于 Register File 里。

这就是 GPU 和 CPU 本质不同：CPU 用大 cache 降低延迟，GPU 用大量 warp 隐藏延迟。后面你会看到 CUDA Graph 章节里提到"decode 时 kernel 跑得太快，launch 追不上"——根因就是 warp 太空、SM 算力真没得发挥。

为什么是 32 不是 16 或 64

  • NVIDIA 从 G80 (2006) 就定下 32，历史原因：刚好对应 32-bit 地址总线 + 一个 SIMD 宽度
  • AMD GPU 用 64（wavefront），所以 ROCm 生态会稍有不同
  • 对 mini-sglang 来说：不需要记，只需要知道 kernel 的线程数最好是 32 的倍数

§3三层内存 · 速度差 100 倍才是一切优化的理由

GPU 上的数据存在哪里，决定了你的 kernel 跑多快。先把三层内存的绝对数字背下来（H100 为例）：

层级容量延迟带宽谁能访问典型用途
Register256 KB / SM1 cycle~∞单线程私有循环变量、累加器
Shared Mem / L1228 KB / SM~30 cycle~19 TB/sblock 内共享FlashAttention 的 Q/K tile
L2 Cache50 MB（全卡）~200 cycle~7 TB/s全 SM 共享跨 block 复用的小量数据
HBM (显存)80 GB~600 cycle3.35 TB/s所有人权重、KV Cache、activation
PCIe → CPU—ms 级64 GB/s (gen5)host 侧权重上卡、输出回传
HBM 比 Register 慢 600 倍，比 Shared Memory 慢 20 倍。 于是所有高性能 kernel 的核心思路只有一条：把数据从 HBM 搬到 Shared Memory 一次，然后在 SM 内部反复用。FlashAttention / Paged Attention / fused MoE 都是这个思路的变体。

§4HBM 真相 · 为什么 LLM 推理被它卡死

H100 的两个指标

算力 (FP16 Tensor Core)
989 TFLOPS
每秒 9.89 × 10¹⁴ 次乘加
显存带宽 (HBM3)
3.35 TB/s
每秒 3.35 × 10¹² 字节

推出一个关键比值：算力 / 带宽 = 295

把单位统一到"每 byte"：

# FP16 一个数 = 2 byte
# 算力: 989e12 FLOPS
# 带宽: 3.35e12 byte/s = 1.675e12 个 FP16 数/s

算术强度阈值 = 算力 / 带宽 = 989e12 / 3.35e12 ≈ 295 FLOPs per byte
                                                 ≈ 590 FLOPs per FP16 数
这个数字意思是：你从 HBM 每读 1 个 FP16 数，至少要对它算 590 次乘加，才能把算力吃满。低于这个比值，GPU 就在空转等数据——memory-bound。

LLM decode 的算术强度是多少

decode 时一个 token 过一层 Transformer（隐藏维 d=4096，FFN 倍率 4）：

阶段读 (byte)算 (FLOPs)强度 (FLOPs/byte)判定
QKV 投影weights: 3·d·d·2 = 100 MB2·d·3d = 100 M~1memory-bound
FFNweights: 2·d·4d·2 = 268 MB2·d·4d·2 = 268 M~1memory-bound
Attention (读 KV)KV: ctx·2·d·2~ctx·2·d~0.5memory-bound
Prefill 矩阵乘权重 + activation~2·B·d²·seq>100compute-bound
decode 阶段的算术强度只有 ~1，距离 GPU 的"经济线" 295 差了两个数量级。这意味着你就算换 4 倍算力的卡，decode 速度几乎不变——瓶颈是把权重从 HBM 搬进 SM 的时间。

所以所有 decode 优化都在做同一件事

  • continuous batching：同一批权重"搬一次、算 N 个 token"——把算术强度从 ~1 提到 ~N
  • CUDA Graph：别让 launch 开销把 memory-bound 变成更差的 "launch-bound"
  • KV Cache：别再重算一次 K/V（重算的是算力，不解决带宽；存下来则是用带宽换算力）
  • Paged Attention：给 KV 连续寻址，让 HBM 读到最高效的 burst 模式
  • TP：把一张卡搬不完的权重切到 4 张——总带宽变成 4 倍，这才是 TP 真正提速的根

这 5 个优化在后面每一章都会展开，但根都在这一节。

§5Tensor Core · 为什么 H100 FP16 比 A100 FP32 快 60 倍

上面 989 TFLOPS 是 Tensor Core 的数字。如果你只用普通 CUDA Core 做 FP32，H100 只有 67 TFLOPS——差了 15 倍。Tensor Core 是一块矩阵乘专用电路。

一条 MMA 指令 = 16×16×16 矩阵乘

# HMMA 指令: D = A × B + C
A: 16×16 FP16
B: 16×16 FP16    # 2 个 warp 协作加载
C: 16×16 FP32
D: 16×16 FP32
# 一条指令在 ~4 cycle 内完成 16·16·16·2 = 8192 次 FLOP
mini-sglang 从不直接写 Tensor Core 汇编——PyTorch / FlashInfer / Triton 会帮你生成。但你得知道精度会被约束：nn.Linear 在 bf16 模式下会走 Tensor Core，FP32 不会；FP8 走最新一代 H100，还能再翻倍。这就是为什么工业推理基本都跑 BF16/FP16，而不是 FP32。

Tensor Core 的连带影响

  • 矩阵乘维度最好是 16 的倍数——否则 Tensor Core 要 padding，效率下降
  • 小矩阵跑不动 Tensor Core——decode 时每次只算 1 个 token，Tensor Core 大量闲置，这也是为什么 decode 是 memory-bound
  • MoE "fused" kernel——把几百个 [1, d] 小矩阵 pack 成一个大矩阵喂 Tensor Core，12 章细讲
  • Ampere (A100) 开始支持 TF32, Hopper (H100) 开始支持 FP8——数字精度越小，Tensor Core 吞吐越高

① 并行单位

⑤ Tensor Core
矩阵乘专用电路 · 只吃规整维度 · decode 小矩阵喂不饱 · prefill 吃得很满
