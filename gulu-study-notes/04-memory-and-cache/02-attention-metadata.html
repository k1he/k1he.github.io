Attention Metadata 为什么这么多？一步步演化

从"最朴素的 attention" 演化到"paged attention + continuous batching"，每一步只新加一个字段，看清楚它解决了什么问题。
Step 0 · 朴素 attention Step 1 · KV Cache Step 2 · Continuous Batching Step 3 · Causal Mask 变形 Step 4 · Paged KV Step 5 · last_page_len Step 6 · GQA / TP 完整的 FIMetadata

STEP 0单条序列 · 最朴素的 attention

如果你的"推理引擎"只能一次处理 1 条请求、每次重新算所有 KV，那 attention 长这样：

# Q, K, V: [seq_len, num_heads, head_dim]
scores = Q @ K.transpose(-2, -1) / sqrt(head_dim)   # [seq_len, seq_len]
mask = causal_mask(seq_len)                          # 下三角
scores = scores.masked_fill(~mask, -inf)
out = softmax(scores) @ V                            # [seq_len, num_heads, head_dim]
需要的元数据：只有 seq_len。它就是 Q.shape[0]，一目了然。
但这种引擎吞吐很低：一次只服务 1 个请求 → GPU 利用率烂；每步 decode 都重算 KV → 浪费。

STEP 1引入 KV Cache · 出现"两个长度"

decode 阶段每步只生成 1 个 token。Q 只有 1 行，但 K/V 包含之前所有 token 的历史：

关键变化：seq_len_q ≠ seq_len_k。kernel 内部循环是 for i in range(seq_len_q): for j in range(seq_len_k)，所以两个长度都得告诉它。
这就是后来要分别有 cu_seqlens_q 和 cu_seqlens_k 的根本原因。

STEP 2Continuous Batching · 用 cu_seqlens 替代 padding

现在要 batch 多条请求一起算，但它们长度不一样。最朴素的想法是 padding：

Req A · 8 token
Req B · 12 token
Req C · 2 token
padding (浪费)
Req A: a₀a₁a₂a₃a₄a₅a₆a₇ ········
Req B: b₀b₁b₂b₃b₄b₅b₆b₇b₈b₉b₁₀b₁₁ ····
Req C: c₀c₁ ··············

batch shape = [3, 16, H, D] · 实际 22 个真实 token，却要算 48 个 · 浪费率 54%

LLM 推理里长度差异极大（有的 50 token，有的 5000 token）。padding 浪费会非常严重，长尾请求拖死整个 batch。

解法：把所有请求的 token 首尾相连拼成一根一维的扁平流，用一个 cumulative sum 数组指示每个请求的边界。

Req A
Req B
Req C
flatten: a₀a₁a₂a₃a₄a₅a₆a₇ b₀b₁b₂b₃b₄b₅b₆b₇b₈b₉b₁₀b₁₁ c₀c₁
kernel 拿到 cu_seqlens_q 就知道：
  • 第 0 个请求在 [0, 8)  = cu_seqlens_q[1] − cu_seqlens_q[0]
  • 第 1 个请求在 [8, 20)
  • 第 2 个请求在 [20, 22)
  • 一共 len(cu_seqlens_q) - 1 = 3 个请求
零 padding，零浪费。FlashAttention 的 flash_attn_varlen_func、FlashInfer 的 BatchPrefillWithPagedKVCacheWrapper 都吃这个格式。

为什么需要两个 cu_seqlens？q 和 k 的 ragged 形状不同！

prefill 时 q 和 k 长度一样，但 decode 或 extend prefill 时它们截然不同：

# attention/fi.py:203
if max_seqlen_q == 1:                           # 纯 decode
    cu_seqlens_q_cpu = torch.arange(0, padded_size + 1, ...)
elif all(l == 0 for l in cached_lens):          # 全新 prefill：q_len = k_len
    cu_seqlens_q_cpu = cu_seqlens_k_cpu          # 复用即可
else:                                           # extend prefill
    cu_seqlens_q_cpu = torch.tensor([0] + seqlens_q, ...).cumsum_(dim=0)

STEP 3Causal Mask 也变形了 · 这就是为什么需要 extend_len

朴素 attention 的 causal mask 是个完美的下三角。但 extend prefill 来了——前缀命中 Radix Cache，只算后面那段：

Req A：总长 10 个 token，前 6 个在 Radix Cache 命中（cached_len=6），这次只算后 4 个（extend_len=4）。

这就是 extend_len 和 device_len 必须同时给 kernel 的根本原因。 没有 cached_len 这个偏移信息，mask 画不出来——左下角的 6 列也得是有效的，否则 query 看不到自己的历史。

STEP 4Paged KV Cache · 出现 page indices

到这里 K、V 还是 contiguous 的 tensor。但有个致命问题：

问题： 每个请求要预留 max_seq_len 大小的 K、V buffer。可是不知道每个请求最终多长，按最大预留就是巨大浪费——max_seq_len=32k，平均请求 2k，浪费 15 倍显存。

解法（vLLM 提出的 PagedAttention）： 把整个 KV 池切成固定大小的"页"，按需申请。物理不连续，逻辑通过"页表"映射。

每个请求按 max_seq_len 预留 16 个槽位，实际只用了少数：

Req A: a₀a₁a₂a₃ ············
Req B: b₀b₁ ··············

⚠️ 浪费 ~80% 显存。kernel 只需要知道每个请求的 seq_len。

① 物理：全局 KV Pool 被切成统一大小的"页"

② 逻辑：每个请求一行 page_table，记录"我用了哪些物理页"

③ kernel 想读 A 的第 18 个 token 的 KV：通过页表"间接寻址"

page_idx = 18 / page_size = 18 / 4 = 4      # 第 4 页
offset   = 18 % page_size = 18 % 4 = 2      # 在该页内偏移 2
物理位置 = page_table[A][4] * page_size + offset
        = ?                                # 但 A 只用了 4 页，访问 [4] 越界！
                                            # （这里只是演示：实际请求按 device_len 限制）

正确逻辑（mini-sglang FI backend, page_size=1）：

# attention/fi.py:215
indices = torch.cat([page_table[req.table_idx, : req.device_len] for req in reqs])

# 例如 batch 里有 A (4 个 KV) + B (2 个 KV)：
# indices = [3, 7, 1, 5,  6, 4]  ← 物理页号一根扁平数组
# cu_seqlens_k 把它切成 [A 段, B 段]
这就是 FIMetadata 里的 indices 字段。 它把所有请求的 page indices 拼成一根扁平数组，与 cu_seqlens_k 一一对应。kernel 内部读 KV 时，先按 cu_seqlens_k 定位到这个 req 的 page 段，再用 page index 跳转到 KV pool 的实际物理位置。

STEP 5last_page_len · 最后一页通常没填满

如果 page_size > 1，每个请求的最后一页通常没填满。比如 page_size=16，请求长度 50：

mini-sglang 默认 page_size=1，所以 last_page_len 永远 = 1：

# attention/fi.py:216
last_page_len_cpu=self._get_ones_cpu(padded_size),   # 全 1
但接口必须留——为了支持 page_size 16/32/64（trtllm 后端要求）。一旦 page_size > 1，last_page_len 就成了不可或缺的字段。

STEP 6num_qo_heads / num_kv_heads / head_dim · 支持 GQA + TP

① 现代模型用 GQA（Grouped Query Attention）：Q 头多，KV 头少

kernel 必须知道这个 ratio，才能内部正确做"4 个 Q 头查同一组 KV"。否则它默认 num_q == num_kv，结果就错了。

② 加上 TP（Tensor Parallel）后，每个 rank 上的 head 数还要再除一次

# attention/fi.py:111
self.qo_head_local = div_even(self.config.num_qo_heads, tp_size)
                                                 # 32 / 4 = 8
self.kv_head_local = div_even(self.config.num_kv_heads, tp_size, allow_replicate=True)
                                                 # 8 / 4 = 2
所以 metadata 里存的是 本 rank 上的 head 数，不是模型原始的 head 数。这就是为什么 num_qo_heads / num_kv_heads / head_dim 必须显式传——kernel 不"知道"模型架构和 TP 配置。

SUM把所有元数据拼回 FIMetadata

理解完每一项的来源，再回头看这个 dataclass 就一目了然——每个字段都对应演化路径上的一步：

字段 来源 step 解决的问题
cu_seqlens_q_cpu
cu_seqlens_q_gpu		 Step 2 query 端的 ragged 边界。把不等长 batch 拼成一根扁平流，告诉 kernel 每个请求 q 的起止位置。
cu_seqlens_k_cpu Step 2 key 端的 ragged 边界。decode/extend 时与 q 不同（q 短 k 长），必须独立。
indices Step 4 所有请求的 page indices 拼接成一根扁平数组。kernel 通过它做 paged 间接寻址。
last_page_len_cpu Step 5 每个请求最后一页的有效行数。page_size>1 时必需，否则会读到垃圾数据。
num_qo_heads
num_kv_heads		 Step 6 本 rank 上的 Q/KV 头数。支持 GQA（不等）+ TP（local 切分）。
head_dim Step 6 每个头的维度。kernel 内部 softmax 缩放因子用。
page_size Step 4 每页 token 数。决定 indices 解析方式 + last_page_len 含义。
seq_lens_cpu Step 1/3 每个请求的 device_len（k 总长度）。kernel decode 路径常用，FlashInfer plan 也要。
pos_encoding_mode 额外 是否让 kernel 顺手做 RoPE。mini-sglang 设 "NONE"（RoPE 单独算）。
dtype 额外 KV cache 精度（fp16/bf16/fp8）。
wrapper 额外 FlashInfer 特有：选 prefill 还是 decode wrapper。

为什么必须放在 prepare_metadata 而不是 model.forward 里临时算？

① 复用

同一份元数据要被所有 transformer layer 复用。模型 28~80 层 attention，如果在 layer 里算就重复 28~80 次。一次性在 prepare_metadata 算好，所有 layer 共享 batch.attn_metadata。

② 异步预热

FIMetadata 里既有 cpu tensor 也有 gpu tensor。cu_seqlens_q_gpu = cu_seqlens_q_cpu.to(device, non_blocking=True)——这是异步 H2D。提前发起让 GPU forward 启动时拷贝早就完成了，避免 stall。

③ FlashInfer plan

FlashInfer 不是无状态 kernel，它有"planning"阶段，预先分析 batch 形状、分配 workspace。这个 plan 一旦做了，整次 forward 的所有层都用同一个 plan（fi.py:123）。所以必须在 forward 之前完成。

一句话总结： prepare_metadata 是调度层视角和 attention kernel 视角之间的翻译器。它把"按请求组织的状态" 翻译成"按 ragged 流组织的扁平张量+边界数组"，让通用 kernel 也能高效服务于 continuous batching + paged KV。
