PART 1为什么 KV 必须是"池"？

先复习一下前面章节埋下的问题：

  • 每个 token 在每一层 attention 会产生一组 K 和 V 向量（用于后续 token 查询）
  • 请求长度不一样：有的 50 token，有的 5000 token
  • 请求数随时变：有的刚到，有的刚走

朴素方案：每个请求预分配 max_seq_len 的连续 KV buffer

Paged 方案：全局 KV 池 + 按需分页

物理上分散，通过 page_table 逻辑映射拼回来 显存利用率 > 95%
KV 池的本质：一块预分配好的大 GPU tensor，所有请求的 K/V 都往里写。分配/释放的最小单位是 page（mini-sglang 默认 page_size=1 token，即一页 = 一个 token 的 KV）。
后面两章所有讨论都围绕这个池：它的 shape、怎么索引、怎么写入、怎么释放。

PART 2物理 tensor 到底长什么样（最关键的 6 维）

mini-sglang 的 KV 池就是一个 6 维 tensor，全部在 GPU 上，从启动就预分配好不再变大小。

# kvcache/mha_pool.py:28  MHAKVCache.__init__
self._kv_buffer = torch.empty(
    (2, num_layers, num_pages, page_size, local_kv_heads, head_dim),
    device=device,
    dtype=dtype,
)

这 6 维每个的"物理意义"

维度对应什么为什么在这个位置
dim 0 (K/V)Key 还是 Value放最外层方便self._k_buffer = self._kv_buffer[0] 拆分
num_layersTransformer 第几层的 KV每层有独立 KV，所以需要这一维区分
num_pages池里的第几页"虚拟地址" 就是这个维度的索引
page_size这一页里第几个 tokenpage_size=1 时这一维退化，留着是为兼容 trtllm 的 16/32/64
local_kv_heads第几个 KV headTP 切片后每卡的 local heads
head_dimhead 内的哪一维每个 head 的向量维度
注意 num_pages 那一维是 page 的"虚拟地址"空间——前面所有章节提到的 page_table[req.table_idx, k] = 某个 page 索引，那个 page 索引就是这一维的下标。这一维最大，决定了池的总大小。

page_size=1 时，每页就是一个 token

当 page_size=1，维度 3（page_size）退化成 1，可以把 `num_pages × page_size` 看作一维 token 地址：

# kvcache/mha_pool.py:37
self._storage_shape = (num_pages * page_size, local_kv_heads, head_dim)

# 在 store/read 时 view 成这个 3D shape:
self._k_buffer[layer_id].view(self._storage_shape)
# shape: (num_pages, local_kv_heads, head_dim)  ← 对于 page_size=1
#        ↑ 现在每个 page 就一个 token 的 K 向量

这就是 mini-sglang 把 page_size=1 作为默认的一个好处——可以"按 token 索引"，逻辑简单。

PART 3page_table 里那个 int32 如何索引 KV 池？

回忆 02 章：page_table[req.table_idx, k] = 某个物理页号。现在看它怎么真正被用来读 KV。

具体流程（以 FlashInfer 为例）

# attention/fi.py:190  prepare_metadata
def prepare_metadata(self, batch: Batch):
    reqs = batch.padded_reqs
    page_table = get_global_ctx().page_table
    ...
    batch.attn_metadata = FIMetadata(
        ...
        indices=torch.cat([page_table[req.table_idx, : req.device_len] for req in reqs]),
        ...
    )

每个请求从 page_table 里取出"自己用过的页号列表"，拼成一根扁平张量 → 这就是 05 章讲过的 `indices`。

举个例子：batch 里两个请求 A, B

读这张图的核心：
  • page_table 是"每个请求的页索引表"——按 token 顺序排列它用过的 pages
  • indices 是把 batch 所有请求的页索引扁平化拼接，给 kernel 做 paged 寻址
  • KV Pool 物理上是连续 tensor，但不同请求的 pages 散布各处
  • kernel 内部循环时，第 j 个 key 的物理位置 = indices[cu_seqlens_k[i] + j]，然后去 pool[那个位置] 取出 [kv_heads, head_dim] 的向量

PART 4store_kv · 算完 K/V 之后往哪写？

每个 attention 层的 forward 会做两件事：先写新算的 K/V，再读完整 KV 算 attention。

触发点：FlashInfer backend 的 forward

# attention/fi.py:176  FlashInferBackend.forward
def forward(self, q, k, v, layer_id, batch):
    metadata = batch.attn_metadata
    self._initialize_metadata_once(metadata)
    self.kvcache.store_kv(k, v, batch.out_loc, layer_id)   # ★ 先写
    kv_cache = (self.kvcache.k_cache(layer_id), self.kvcache.v_cache(layer_id))
    kv_cache = (_flatten_cache(kv_cache[0]), _flatten_cache(kv_cache[1]))
    return metadata.wrapper.run(q=q, paged_kv_cache=kv_cache)            # 再读

store_kv 内部

# kvcache/mha_pool.py:45
def store_kv(self, k, v, out_loc, layer_id):
    from minisgl.kernel import store_cache
    store_cache(
        k_cache=self._k_buffer[layer_id].view(self._storage_shape),   # [num_pages, kv_heads, head_dim]
        v_cache=self._v_buffer[layer_id].view(self._storage_shape),
        indices=out_loc,      # ★ 写入位置
        k=k,                  #   新算的 K, shape [total_tokens, kv_heads, head_dim]
        v=v,
    )

out_loc 从哪来？

回到 scheduler 的 _prepare_batch：

# scheduler/scheduler.py:210
batch.out_loc = self.engine.page_table[input_mapping]
# input_mapping 是 (table_idx_per_token, positions_per_token)
# page_table[input_mapping] 就是"按 token 顺序取出对应物理页号"

所以 out_loc 是一个 GPU int32 tensor，shape 等于 batch 里总 token 数，每个元素指向"这个 token 的 K/V 应该写到 pool 的哪个物理位置"。

store_cache kernel 的语义（简化）

# 对 batch 里每个要写的 token i:
for i in range(total_tokens):
    loc = indices[i]
    k_cache[loc, :, :] = k[i]    # 把新算的 K 写到 pool 的对应物理页
    v_cache[loc, :, :] = v[i]    # V 同理

这是个完全并行的 scatter 操作，每个 token 独立写自己那一页，所以 CUDA 上很快（纯 memory-bound）。

为什么不用 Python 的 index assignment 而要 CUDA kernel？ Python/PyTorch 的 k_cache[indices] = k 在 GPU 上其实也调 scatter kernel，但会多走一层 dispatch + 参数检查。store_cache 是 mini-sglang 自研的 C++ kernel（在 kernel/store.cu 里），省去额外开销，同时可以融合进 CUDA Graph。

PART 5attention kernel 怎么"读"这个池？

store 完之后，轮到 FlashInfer 的 wrapper.run() 真正做 attention 计算。它拿到的是：

wrapper.run(q=q, paged_kv_cache=(k_cache_flat, v_cache_flat))
                            │
                            └─ shape: (num_pages, 1, kv_heads, head_dim)
                               ← 就是 self._k_buffer[layer_id].view(...).view(-1, 1, kv_heads, head_dim)

_flatten_cache 把 (num_pages, page_size=1, kv_heads, head_dim) 展平成 (num_pages·1, 1, kv_heads, head_dim)——FlashInfer 的接口要求后者格式。

FlashInfer 内部怎么用 indices + paged_kv_cache？

参考 05 章的 cu_seqlens + indices。kernel 内部做的事类似：

# 伪代码：对第 i 个 query 算 attention
q_start = cu_seqlens_q[i]
q_end   = cu_seqlens_q[i+1]
k_start = cu_seqlens_k[i]
k_end   = cu_seqlens_k[i+1]

for qi in range(q_start, q_end):
    for kj in range(k_start, k_end):
        page_idx = indices[kj]                       ★ 间接寻址
        K_vec = paged_kv_cache[0][page_idx, 0, :, :]   读物理 K
        V_vec = paged_kv_cache[1][page_idx, 0, :, :]   读物理 V
        score = dot(q[qi], K_vec) / sqrt(head_dim)
        # ... softmax + 加权和 V_vec ...

关键步骤就是那个 page_idx = indices[kj]——把"逻辑位置 kj"翻译成"物理位置 page_idx"，然后用它去索引 pool。

这就是为什么叫"paged attention"：kernel 必须通过页索引间接寻址才能读到正确的 KV。现代高性能实现（FlashInfer、FlashAttention 3 的 paged 版本、TRT-LLM 的 fmha）都在 kernel 内部把这个间接寻址和 softmax/gemm 融合，避免分散的 memory read 变成瓶颈。

PART 6num_pages 怎么定？_determine_num_pages 的算法

KV 池大小不是用户手动设的，而是根据剩余显存自动算的。这决定了系统能同时处理多少 token，是性能的关键。

# engine/engine.py:148
def _determine_num_pages(self, old_free_memory, config):
    new_free_memory = self._sync_get_memory()[1]      # 模型加载完后的剩余

    # 每页需要多少字节？
    cache_per_page = (
        2                                             # K + V
        * config.model_config.head_dim
        * div_even(config.model_config.num_kv_heads, config.tp_info.size, allow_replicate=True)
        * config.page_size
        * self.dtype.itemsize
        * config.model_config.num_layers
    )

    num_pages = config.num_page_override
    if num_pages is None:
        model_memory = old_free_memory - new_free_memory
        available_memory = int(config.memory_ratio * old_free_memory) - model_memory
        num_pages = available_memory // cache_per_page
    return num_pages

算法的三步

① old_free_memory
加载模型之前的剩余
② model_memory
= old − new
③ available
= ratio×old − model
④ num_pages
= available / per_page

举个具体例子 · H200 80GB 跑 Qwen3-0.6B bf16

old_free_memory   = 80 GB              # 启动时剩余
模型 bf16           = 1.2 GB              # Qwen3-0.6B 权重
new_free_memory   = 78.8 GB             # 模型加载后

memory_ratio      = 0.85 (默认)
available_memory  = 0.85 × 80 - 1.2 = 67 GB

# 每页大小 (bf16, 1 token, 2 kv_heads, head_dim=128, 28 层)
cache_per_page    = 2 × 128 × 2 × 1 × 2 × 28 = 28,672 字节

num_pages         = 67 GB / 28,672 B ≈ 2,515,000
# 即能容纳 250 万个 token 的 KV！非常宽裕

为什么 memory_ratio 默认是 0.85 而不是 1.0？

剩下 15% 用于：
  • Activation memory：每次 forward 的中间张量（q/k/v/attention scores 等）
  • CUDA Graph workspace：录制 graph 时的 kernel workspace（见 07 章）
  • FlashInfer workspace：128 MiB 固定分配（fi.py:90）
  • NCCL buffer：all-reduce 的通信 buffer（TP > 1 时）
  • PyTorch 内部缓存：allocator caching pool 等
这些加起来通常 10-15%。留多了浪费 KV 容量，留少了 OOM。默认 0.85 是经验值。

可以调吗？

# 显存紧的话可以调小（给 graph/activation 多让点）
python -m minisgl --model ... --memory-ratio 0.75

# 显存充足、关了 graph，可以调大
python -m minisgl --model ... --memory-ratio 0.92 --cuda-graph-max-bs 0

# 或者完全手动指定
python -m minisgl --model ... --num-page-override 100000

PART 7对比 NaiveCache：没有 Radix 的基线

02 章讲 CacheManager 时提过 --cache naive 是个可选项。看看它和 Radix 的差别。

# kvcache/naive_cache.py (整个文件就几十行)
class NaivePrefixCache(BasePrefixCache):
    def match_prefix(self, input_ids):
        return MatchResult(NaiveCacheHandle(cached_len=0))  # 永不命中

    def insert_prefix(self, input_ids, indices):
        return InsertResult(cached_len=len(indices), ...)  # 假装插入了

    def evict(self, size):
        return self.empty_tensor  # 什么都不 evict

Naive vs Radix 对比表

维度NaiveCacheRadixCache
前缀命中❌ 永远 0✅ 命中共享 prefix 就复用
eviction 策略整个请求结束时一次性释放按 timestamp LRU evict 叶子
物理 pool完全一样完全一样
per-request 开销几乎无树查 + ref_count 维护
适用场景benchmark 做 ablation / prefix 无复用的工作负载生产环境，尤其多轮对话/共享 system prompt
KV 池（MHAKVCache）对两种 cache 类型是共享的——它只负责"物理存储"，不关心"哪些 prefix 可以复用"。Radix/Naive 区别只在上层的 prefix 树结构。这是 mini-sglang 的一个好抽象：BasePrefixCache 和 BaseKVCachePool 完全解耦。

一句话总结每个问题

问题答案
KV 物理池 shape 是什么？6 维 tensor (2, layers, pages, page_size, kv_heads, head_dim)，占显存 60-70%
page_table 里那个 int 是啥？pool 第 3 维（num_pages 维）的下标，即"物理页号"
怎么写？store_kv 用 out_loc 做 scatter，每个新 token 独立写自己的页
怎么读？attention kernel 通过 indices 间接寻址，把逻辑位置翻译成物理页号
池多大？自动算：(memory_ratio × 剩余显存 − 模型大小) / 每页字节数
Radix 和 NaiveCache 区别？上层前缀树不同，下层物理池完全一样

你现在应该能回答这些"隐藏问题"

  • 为什么开 Radix Cache 不会多占显存？（它只是在物理池上加了一层索引，不增加存储）
  • 为什么 page_size=1 是 mini-sglang 的默认？（逻辑简单——"按 token 索引"，paged lookup 和 normal scatter 几乎等价）
  • 为什么 TP 下每张卡都有完整形状的 page_table？（只有 KV pool 按 kv_heads 切了，page 索引空间在所有卡上一致）
  • 为什么 num_layers 在第 2 维而不是第 0 维？（因为 k_cache(layer_id) 和 v_cache(layer_id) 是高频操作，放在 K/V 之后可以快速切片）
