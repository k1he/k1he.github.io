§2Triton 隐藏了什么（你在 CUDA 中需要手动做的）

  1. 1. Shared Memory 分配 + Bank Conflict 避免
    Triton: 自动分配，自动 padding CUDA: __shared__ half A_shared[BM][BK+PADDING] — 需要手动 padding 避免 bank conflict
  2. 2. Global → Shared Memory 搬运
    Triton: tl.load 自动决定搬运策略 CUDA: 手动用 cp.async / ldg.128 + 计算 thread-to-element mapping
  3. 3. Shared → Register 搬运 (LDS → RF)
    Triton: 编译器自动安排 CUDA: ldmatrix 指令 + warp-level layout 约束
  4. 4. Tensor Core MMA 指令编排
    Triton: tl.dot(a, b) 一行搞定 CUDA: wmma::mma_sync 或 PTX mma.sync.aligned.m16n8k16
  5. 5. Software Pipelining（多缓冲区重叠）
    Triton: num_stages=3 一个参数 CUDA: 手动维护 2-4 个 shared memory buffer，用 barrier 同步
  6. 6. Warp 内部的数据分布 (Layout)
    Triton: 编译器决定数据分布 CUDA: swizzle pattern + ldmatrix 的 "warp-arranged" layout
  7. 7. Register Pressure 管理
    Triton: 编译器优化寄存器分配 CUDA: 手动控制寄存器使用量 (__launch_bounds__ / maxrregcount)
这 7 项加起来，就是为什么 CUDA GEMM 代码通常是 500-1000 行而 Triton 只需 50 行。Triton 的编译器 (Triton-IR → LLVM-IR → PTX) 替你做了这些决策。

§3CUDA GEMM 的完整层次

CUDA 让你在 每一层 都有控制权——这既是力量也是负担：

┌─────────────────────────────────────┐ │ Grid Level │ ← grid = 所有 CTA 的集合 │ ┌─────────────────────────────────┐ │ │ │ CTA (Threadblock) Level │ │ ← Triton 的 "program" 在这里 │ │ ┌───────────────────────────┐ │ │ │ │ │ Warp Level │ │ │ ← Triton 隐藏了这层 │ │ │ ┌───────────────────────┐│ │ │ │ │ │ │ Thread Level ││ │ │ ← Triton 完全隐藏 │ │ │ │ (Tensor Core instr.) ││ │ │ │ │ │ └───────────────────────┘│ │ │ │ │ └───────────────────────────┘ │ │ │ └─────────────────────────────────┘ │ └─────────────────────────────────────┘
核心区别：Triton 让你在 CTA level 思考（定义 tile + K 循环），编译器处理 warp/thread level。CUDA 让你在所有 level 都有控制权——但也要求你全部手动管理。

§4CUTLASS 3.x 的 CuTe 抽象

CUTLASS 3.x 引入了 CuTe（Cute Tensor）库——试图在 CUDA 层面提供类似 Triton 的高层抽象：

Layout

描述数据在内存中的排列方式。用代数形式表达 shape + stride，支持组合、分割、补充。

类似 Triton 的 tl.make_block_ptr + stride 信息

Tensor

Layout + 数据指针 = 一个可操作的张量视图。支持 partition、tile 等操作。

类似 Triton 中 pointer + offsets 的组合

TiledMMA

描述一组 Tensor Core 操作的分工：哪些 warp 负责哪些元素，MMA atom 的排列方式。

类似 Triton 的 tl.dot 但暴露了 warp 级细节

Copy

描述数据搬运模式：global→shared、shared→register 的线程映射与指令选择。

类似 Triton 的 tl.load/tl.store 但手动控制

CuTe 试图在 CUDA 层面提供类似 Triton 的高层抽象——但仍然是 C++ template metaprogramming。学习曲线陡峭，但理解后非常强大。

§5CUDA GEMM 学习路线

阶段 0 — 理论基础（你已完成!）

✅ 理解 tiling + K-loop + accumulator

✅ 理解 L2 swizzle + Split-K

✅ 理解 autotune / num_stages / num_warps

阶段 1 — Naive CUDA GEMM

每个 thread 算一个输出元素

理解 threadIdx / blockIdx 到矩阵坐标的映射

性能极差（~18% cuBLAS），但理解基本编程模型

阶段 2 — Shared Memory Tiling

__shared__ 声明 tile buffer

线程协作加载 tile → __syncthreads() 同步 → 从 shared 读取计算

Bank conflict 问题初现

阶段 3 — Tensor Core (WMMA)

wmma::load_matrix_sync / mma_sync / store_matrix_sync

理解 Fragment 概念：数据分布在 warp 的 32 个线程中

性能跳跃 (~5x)

阶段 4 — 高性能 GEMM

cp.async + software pipeline (double/triple buffering)

ldmatrix + swizzle pattern

Register tiling：每个 thread 负责更多输出元素

阶段 5 — 阅读 CUTLASS 源码

mainloop + epilogue 架构分离

CuTe layout algebra（代数式描述数据布局）

Hopper 架构特性：TMA、warp specialization、cluster

§7什么时候必须用 CUDA（Triton 不够的场景）

  • Custom memory layout — 非标准 stride 排列（如 interleaved quantization format）
  • Warp-specialization — Hopper TMA 的 producer/consumer warp 分工
  • 极端低延迟要求 — Persistent kernel（常驻 GPU，不退出）
  • 通信重叠 — 与 NCCL / custom all-reduce 的 computation-communication overlap
  • 非标准数据类型 — FP4、microscaling (MXFP)、custom quantization
  • 跨 CTA 协作 — Cluster-level synchronization (Hopper sm_90+)
经验法则：90%+ 的场景 Triton 够用。只有当你需要压榨最后 5% 性能、或用到 Triton 尚不支持的硬件特性时，才需要下沉到 CUDA。

§9带走

  1. 1. 概念无缝迁移 — Triton 的每个概念都有 CUDA 对应。你在 Triton 学的不会浪费，它们会成为你读 CUDA 代码时的直觉。
  2. 2. 7 层隐藏复杂度 — Shared memory 管理、warp layout、pipeline、register pressure... Triton 编译器替你做了这些决策。
  3. 3. 渐进式学习路线 — naive → shared mem → tensor core → pipeline → CUTLASS。每一步都建立在前一步之上。
  4. 4. 选择的智慧 — 90%+ 场景 Triton 够用。极端性能 / 特殊硬件特性才需要 CUDA。别在不需要的时候增加复杂度。
