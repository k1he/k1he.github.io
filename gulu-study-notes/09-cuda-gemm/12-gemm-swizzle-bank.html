C11 · Bank Conflict 与 Swizzle · 消除 Shared Memory 瓶颈 CUDA GEMM 系列 · 12/15

你的 GEMM 从 82% 到 95% 的最后一步：消除 shared memory 的 bank conflict。理解 swizzle pattern 后，你就知道 CUTLASS 那些"神秘的 XOR"在干什么了。

§1Bank Conflict 回顾

Shared memory 硬件结构：

  • 32 个 bank，每个 bank 宽度 4 bytes
  • bank 编号公式：bank(addr) = (addr / 4) % 32
  • 同一 warp 中多个 thread 访问同一 bank → conflict → 串行化
在 GEMM 中，从 shared memory 加载 tile 到 registers 时，如果 layout 不对，很容易产生 bank conflict。

§2GEMM 中 Bank Conflict 的来源

Case: 从 A_shared[BM][BK] 中按列加载数据：

// A_shared[32][32], float (每个元素 4 bytes)

// Thread 0 loads A_shared[0][k]  → addr = 0*32+k = k      → bank = k%32
// Thread 1 loads A_shared[1][k]  → addr = 1*32+k = 32+k   → bank = (32+k)%32 = k%32
// Thread 2 loads A_shared[2][k]  → addr = 2*32+k = 64+k   → bank = (64+k)%32 = k%32
// ...
// Thread 31 loads A_shared[31][k] → bank = k%32
所有 32 个 thread 都访问 bank k%32 → 32-way bank conflict！最坏情况！

§3解决方案 1: Padding

// 原来:
__shared__ float A_shared[32][32];      // 列访问 → 32-way conflict

// 加 padding:
__shared__ float A_shared[32][32 + 1];  // 33 列！

为什么 +1 能消除 conflict？

// 现在每行有 33 个 float，stride = 33
// Thread i loads A_shared[i][k] → addr = i*33+k → bank = (i*33+k)%32
//
// i=0: bank = (0*33+k) % 32 = k % 32
// i=1: bank = (1*33+k) % 32 = (33+k) % 32 = (1+k) % 32  ← 不同!
// i=2: bank = (2*33+k) % 32 = (66+k) % 32 = (2+k) % 32  ← 不同!
// i=3: bank = (3*33+k) % 32 = (99+k) % 32 = (3+k) % 32  ← 不同!
// ...
// → 32 threads 访问 32 个不同 bank → 无 conflict!
加一列 padding 就能完全消除 conflict。代价：浪费 ~3% shared memory。

§4解决方案 2: XOR Swizzle (CUTLASS 方式)

Padding 简单但浪费内存。更优雅的方法：改变数据存储的位置（swizzle）。

// Swizzle: 存数据时，把行号 XOR 到列号上
int smem_col = col ^ (row % BK);  // XOR swizzle

// Store: A_shared[row][col ^ (row % 32)] = A_global[row][col]
// Load:  val = A_shared[row][col ^ (row % 32)]

为什么 XOR 能消除冲突？

// 所有 thread 加载同一列 k:
// row=0, col=k: stored at [0][k^0] = [0][k]       → bank = k%32
// row=1, col=k: stored at [1][k^1]                 → bank = (32 + k^1) % 32 = (k^1)%32
// row=2, col=k: stored at [2][k^2]                 → bank = (64 + k^2) % 32 = (k^2)%32
// row=3, col=k: stored at [3][k^3]                 → bank = (k^3)%32
// ...
//
// k^0, k^1, k^2, ..., k^31 的低 5 位互不相同!
// → 32 个不同的 bank → 无冲突!
XOR 操作天然把不同行的数据分散到不同 bank——数学上保证无冲突，且不浪费任何内存。

§5ldmatrix + Swizzle 的配合

在 Tensor Core GEMM 中，ldmatrix 指令有自己的数据 layout 期望。数据需要按特定 swizzle pattern 存放才能让 ldmatrix 无冲突加载。

CUTLASS 的 CuTe Swizzle 描述：

// CUTLASS 用 CuTe 的 Swizzle<B, M, S> 描述:
// B = base bits, M = mask bits, S = shift bits
// 实际 swizzle = (row >> S) & ((1<<B)-1) XOR col_in_group

// 例如 Swizzle<3, 3, 3>:
// Takes bits [5:3] of row, XOR with bits [2:0] of col
// → 每 8 行为一个周期，每组 8 列内 swizzle
你不需要记住这个公式——理解核心思想就行：XOR 行号和列号的某些位，把同列元素分散到不同 bank。

§6L2 Cache Swizzle (CTA 调度顺序)

回顾 Triton T10 中的 GROUP_SIZE_M swizzle：

// Triton: GROUP_SIZE_M swizzle
pid_m = first_pid_m + (pid % group_size_m)
pid_n = (pid % num_pid_in_group) // group_size_m

CUDA 等价实现：

// GPU 自己调度 blocks 的顺序，我们无法控制
// 解决方案: 在 kernel 内部 remap blockIdx

int pid = blockIdx.x;  // 使用 1D grid
int num_pid_m = (M + BM - 1) / BM;
int num_pid_n = (N + BN - 1) / BN;
int num_pid_in_group = GROUP_SIZE_M * num_pid_n;
int group_id = pid / num_pid_in_group;
int first_pid_m = group_id * GROUP_SIZE_M;
int group_size_m = min(num_pid_m - first_pid_m, GROUP_SIZE_M);
int pid_m = first_pid_m + (pid % group_size_m);
int pid_n = (pid % num_pid_in_group) / group_size_m;
和 Triton T10 完全一样的公式——Triton 没有隐藏这部分，只是语法不同。核心思想：让相邻 block 访问相邻的 B 矩阵列，最大化 L2 cache 复用。

§7性能影响

优化手段效果
无 swizzle (32-way conflict)~60% peak (受限于 shared memory 带宽)
Padding (+1)~90% peak
XOR swizzle~95% peak
+ L2 CTA swizzle~97% peak
从 82% (C10) + swizzle = ~90-95% cuBLAS。剩下的 5% 来自 NVIDIA 的极致微调（pipeline bubble 消除、寄存器分配优化等）。

§8实战：给 C10 的 kernel 加 Padding

最小改动，立竿见影：

// Before (有 bank conflict):
__shared__ half A_shared[2][BM][BK];

// After (无 bank conflict):
__shared__ half A_shared[2][BM][BK + 8];  // +8 for half type (8×2=16 bytes = 4 banks offset)

为什么 half 类型 padding 8？

  • half = 2 bytes，一个 bank = 4 bytes = 2 个 half
  • Padding 8 个 half = 16 bytes = 4 个 bank 的偏移
  • 相邻行错开 4 个 bank，大幅减少 conflict
  • 完全消除需要让 stride 与 32 互素：BK + 8 如果满足 (BK+8) 与 16 互素即可
注意：padding 后所有对 shared memory 的索引逻辑不需要改变！只是声明时多了一列，硬件寻址自动错开 bank。

§9带走

  1. Bank conflict：同一 warp 中多个 thread 访问同一 bank → 串行化 → 性能暴跌
  2. GEMM 中列访问 shared memory 天然产生 32-way conflict（stride = 32 的倍数）
  3. Padding (+1 或 +8)：简单有效，浪费少量内存，代码改动极小
  4. XOR swizzle：CUTLASS 方式，数学保证无冲突，不浪费内存，但代码更复杂
  5. L2 CTA swizzle：改变 block 调度顺序，与 Triton GROUP_SIZE_M 完全对应
