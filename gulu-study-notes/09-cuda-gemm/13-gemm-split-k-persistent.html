C12 · Split-K 与 Persistent Kernel · 高级并行策略 CUDA GEMM 系列 · 13/15

当标准 tile 分配不够用时（小 M 或极大 K），需要更高级的并行策略：Split-K 增加 wave 数，Persistent Kernel 消除 launch 开销。

§1Split-K 回顾（CUDA 视角）

在 Triton T11 中我们介绍过 Split-K 的概念，现在用纯 CUDA 术语重新理解。

问题：SM 空闲

  • 当 M 很小（如 decode 阶段 M=1~8），output tile 数量很少
  • 标准 grid = cdiv(M, BM) × cdiv(N, BN)
  • M=4, BM=128 → 只有 1 行 tile → 可能只有 32~64 个 block
  • A100 有 108 个 SM，H100 有 132 个 SM，大量 SM 完全空闲

解决方案：K 维度也并行

  • 把 K 切成 SPLIT_K 份，每份由不同 block 处理
  • 每个 block 只计算部分和（partial sum），最后 reduce
  • 3D grid：(num_tiles_n, num_tiles_m, SPLIT_K)
// 3D grid launch — K 维度也参与并行
dim3 grid(cdiv(N, BN), cdiv(M, BM), SPLIT_K);

__global__ void gemm_split_k(
    const half* A, const half* B, float* C,
    int M, int N, int K
) {
    int bid_m = blockIdx.y;
    int bid_n = blockIdx.x;
    int split_id = blockIdx.z;  // 当前 block 负责哪一段 K

    int k_per_split = K / SPLIT_K;
    int k_start = split_id * k_per_split;
    int k_end = min(k_start + k_per_split, K);

    // 只累加 [k_start, k_end) 范围内的部分和
    float partial_sum = 0.0f;
    for (int k = k_start; k < k_end; k += BK) {
        // load A tile, B tile → shared memory
        // compute partial GEMM
        partial_sum += ...;
    }

    // Reduction: atomic add 到最终输出
    atomicAdd(&C[row * N + col], partial_sum);
}
Split-K 的核心思想：用空间换并行度。牺牲一些 reduction 开销，换来更多 block 让所有 SM 都有活干。

§2Atomic vs Two-Pass Reduction

方案 1：atomicAdd（简单直接）

  • 每个 split block 直接用 atomicAdd 写到 C
  • 优点：无额外显存开销，代码简单
  • 缺点：SPLIT_K 大时竞争严重
  • 缺点：FP16 atomicAdd 精度受限（需要 FP32 中间结果）
  • 缺点：结果不确定（non-deterministic）

方案 2：Workspace + Reduction Kernel（两遍法）

// Pass 1: 每个 split 写到独立的 workspace
float* workspace;  // shape [SPLIT_K, M, N]
cudaMalloc(&workspace, SPLIT_K * M * N * sizeof(float));

// 第一个 kernel: 不做 atomic，写到 workspace[split_id][row][col]
gemm_split_k_pass1<<<grid3d, block>>>(A, B, workspace, M, N, K, SPLIT_K);

// Pass 2: 独立的 reduction kernel 沿 split 维度求和
dim3 grid2d(cdiv(N, 32), cdiv(M, 32));
reduce_kernel<<<grid2d, 256>>>(workspace, C, M, N, SPLIT_K);

// reduce_kernel 内部：
// C[i][j] = sum(workspace[s][i][j] for s in 0..SPLIT_K-1)

cudaFree(workspace);
对比AtomicTwo-Pass
额外显存0SPLIT_K × M × N × 4B
精度FP32 atomic 可保证精确（先 FP32 累加再转换）
竞争SPLIT_K 大时严重无竞争
确定性非确定确定性结果
Kernel 数12
适用SPLIT_K ≤ 4SPLIT_K 任意大
工程建议：对于 FP16 精度敏感的推理场景（如 LLM），Two-Pass 更可靠。SPLIT_K ≤ 4 且精度要求不高时可直接用 atomic。

§3Stream-K：动态工作分配

Split-K 的问题：K 不整除 SPLIT_K 时，有些 block 多做有些少做（load imbalance）。更严重的情况：不同 output tile 可能需要不同的 K 长度（如 mask/padding）。

Stream-K 解决方案（CUTLASS 3.x 引入）：

  • Launch 恰好 num_SMs 个 persistent block
  • 把所有 K-iterations 组成一个全局 "stream"
  • 每个 block 动态地 "stream" 消费下一段 K-chunk
  • 没有固定分配 → 完美 load balance
// 传统 Split-K：Block i 处理固定的 tile 的第 split_i 段 K
//   Block 0 → tile(0,0), K[0:1024]       固定分配
//   Block 1 → tile(0,0), K[1024:2048]    固定分配
//   Block 2 → tile(0,0), K[2048:3000]    少做了！imbalance

// Stream-K：Block i 处理"下一个待处理的 K-chunk"（work-stealing）
//   Block 0 → tile(0,0) K[0:1024], tile(0,1) K[0:512]...
//   Block 1 → tile(0,0) K[1024:2048], tile(0,1) K[512:1536]...
//   每个 block 总工作量相等 → perfect balance
Stream-K = Persistent Kernel + Dynamic Scheduling。这是目前最先进的 GEMM 并行策略，CUTLASS 3.x 和 cuBLAS 在小 M 场景默认使用。

§4Persistent Kernel 概念

传统 GEMM：每个 block 计算一个 tile 然后退出。grid 大小 = 总 tile 数。

Persistent GEMM：每个 block 不退出，循环处理多个 tile。grid 大小 = SM 数量。

__global__ void gemm_persistent(
    const half* A, const half* B, half* C,
    int M, int N, int K, int total_tiles
) {
    int num_tiles_n = cdiv(N, BN);

    // 这个 block 会处理多个 tile！不退出！
    for (int tile_id = blockIdx.x; tile_id < total_tiles; tile_id += gridDim.x) {
        int tile_m = tile_id / num_tiles_n;
        int tile_n = tile_id % num_tiles_n;

        // 计算当前 tile 的起始行列
        int row_start = tile_m * BM;
        int col_start = tile_n * BN;

        // ... 标准 GEMM tile 计算 ...
        float acc[TM][TN] = {};
        for (int k = 0; k < K; k += BK) {
            // load A tile to shared
            // load B tile to shared
            // __syncthreads();
            // compute partial products
        }

        // 写回结果
        // store acc to C[row_start..., col_start...]

        // 关键：不退出！继续下一个 tile
        __syncthreads();
    }
}

// Launch: 恰好 num_SMs 个 block（A100 = 108）
gemm_persistent<<<108, 256>>>(A, B, C, M, N, K, total_tiles);

Persistent Kernel 的优势：

  • 零 launch 开销：多个 tile 在同一次 kernel launch 内完成
  • 更好的 L2 cache 利用：block 常驻 SM，相邻 tile 的数据可能还在 L2 中
  • 可实现 work-stealing：用 atomic counter 动态分配 tile
  • 适合 batched/grouped GEMM：多个小 GEMM 在一个 kernel 内完成
注意：Persistent kernel 要求 grid 大小 ≤ SM 数量。如果 grid 太大，block 无法全部 resident，会导致死锁或性能下降。实际中一般 launch num_SMs 或 num_SMs × occupancy 个 block。

§5Hopper 的 TMA + Warp Specialization

H100 (Hopper) 引入了两个革命性硬件特性，配合 persistent kernel 实现极致性能：

TMA（Tensor Memory Accelerator）

  • 专用硬件单元，负责 global memory ↔ shared memory 的 tile 拷贝
  • 不需要线程参与！一条指令即可启动整个 tile 的异步拷贝
  • 支持多维 tensor 描述符，自动处理 stride 和 boundary
  • 释放了计算线程 — 它们可以专注于 MMA 运算

Warp Specialization（Warp 专业化）

// 传统模式（所有 warp 做相同工作）：
//   Warp 0: load → __sync → compute → load → __sync → compute
//   Warp 1: load → __sync → compute → load → __sync → compute
//   → 每个 warp 在 load 和 compute 间切换，有 pipeline bubble

// Warp Specialization（角色分化）：
//   Warp 0 (Producer): load → load → load → load → ...  [TMA]
//   Warp 1 (Producer): load → load → load → load → ...  [TMA]
//   Warp 2 (Consumer): compute → compute → compute → ... [Tensor Core]
//   Warp 3 (Consumer): compute → compute → compute → ... [Tensor Core]
//   → 真正的流水线！Producer 不停填 shared memory，Consumer 不停消费
//   → 通过 async barrier 同步，零空闲时间

通信机制：Producer 和 Consumer 之间通过 Hopper 新增的异步 barrier 同步，配合 TMA 实现零拷贝流水线。

这是 Hopper 能达到 ~990 TFLOPS (FP8) 的关键之一。CUTLASS 3.x 默认在 H100 上使用 TMA + Warp Specialization 模式。相比 Ampere "所有 warp 做同样事情"，利用率显著提升。

§6何时使用哪种策略

大方阵 (4096²)1024+Standard GEMMtile 数 >> SM 数，并行度足够
中等 (1024²)64Standard + L2 Swizzle刚好够 SM，优化缓存命中
Decode (M=1~8)1~32Split-KSM 不够用，需要 K 维并行
多个小 GEMMvariesPersistent Kernel减少 launch overhead

经验法则：如果你的 GEMM 的 output tiles 数 < 2 × num_SMs，就应该考虑 Split-K。如果你有很多连续的小 GEMM（如 batched inference），考虑 Persistent Kernel。cuBLAS 和 CUTLASS 会根据 M/N/K 自动选择策略（heuristic）。

§7对比 Triton

Split-K 在 Triton 里完全能做。但 Persistent Kernel / Stream-K / Warp Specialization 是 CUDA-only 领域——这就是为什么极限性能仍然需要 CUDA。Triton 适合快速原型和 90% 场景，最后的 10% 性能需要 CUDA + CUTLASS。

§8带走

  1. Split-K：K 维度也并行 → 增加 block 数 → SM 不空闲。适用于 decode 等小 M 场景。
  2. Persistent Kernel：block 不退出，循环处理多个 tile → 省 launch overhead，更好的 L2 cache 利用。
  3. Stream-K：Persistent + Dynamic Scheduling → 完美 load balance，CUTLASS 3.x 默认策略。
  4. Warp Specialization (Hopper)：Producer warps 用 TMA 加载，Consumer warps 用 Tensor Core 计算 → 真正的 pipeline。
  5. Triton 边界：Split-K 两边都能做，但 Persistent / Stream-K / Warp-Spec 需要 CUDA — 这是选择 CUDA 的理由。
