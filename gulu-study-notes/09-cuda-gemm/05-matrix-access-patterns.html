C4 · 矩阵访问模式 · Coalescing 与 Tiling 基础

在进入 GEMM 之前，必须理解 coalesced memory access 和 tile-based 数据加载——这两个概念决定了你的 kernel 是跑满带宽还是浪费 90% 的 HBM。

§1 Coalesced Access 深入

回顾：同一 warp 的 32 个 threads 如果访问 128 bytes 连续内存 → 1 次事务（transaction）。

Case Study：矩阵行访问 vs 列访问

// 矩阵 A[M][N], row-major, 存储为 A[row*N + col]

// Case 1: 行方向访问 (coalesced ✓)
// warp 中的 threads: col = 0,1,2,...,31 (同一行不同列)
float val = A[row * N + threadIdx.x];
// 地址: row*N+0, row*N+1, ..., row*N+31 → 连续! 1 transaction

// Case 2: 列方向访问 (strided ✗)
// warp 中的 threads: row = 0,1,2,...,31 (同一列不同行)
float val = A[threadIdx.x * N + col];
// 地址: 0*N+col, 1*N+col, ..., 31*N+col → 间隔 N! 32 transactions

性能影响

~2 TB/s
Coalesced 有效带宽 (A100)
~60 GB/s
Strided (stride=N) 有效带宽

30 倍性能差距！仅仅因为访问模式不同。这就是为什么理解 coalescing 如此重要。

§2 矩阵乘法的访问模式问题

// C[i][j] = Σ_k A[i][k] * B[k][j]
//
// 对于 C 的一行 (固定 i)，不同 j:
//   A[i][k]: 同一行, 对 k 循环 → 读 A 的一行 (coalesced if threads span k)
//   B[k][j]: 不同行同一列 → 读 B 的一列 (NOT coalesced!)

这就是为什么 naive GEMM（每 thread 算一个 C 元素）对 B 的访问是 strided 的——性能极差。

§3 解决方案: Tiling + Shared Memory

核心思路

  1. 一个 block 的所有 threads 协作把 tile 从 global memory 加载到 shared memory
  2. 加载时保证 coalesced
  3. 从 shared memory 读取时没有 coalescing 问题（shared memory 是 bank-based，延迟极低）

关键洞察：Shared memory 是 "中转站"——把不友好的 global memory 访问模式转换为对硬件友好的模式。加载时 coalesced，使用时自由。

§4 协作加载 (Cooperative Loading)

// Block size: (16, 16) = 256 threads
// 要加载 A_tile[BLOCK_M=64][BLOCK_K=64] = 4096 elements
// 256 threads, 每个 thread 加载 4096/256 = 16 个元素

__shared__ float A_shared[64][64];

// 线程编号（展平）
int tid = threadIdx.y * blockDim.x + threadIdx.x;  // 0~255

// 每个 thread 加载 16 个连续元素
int elements_per_thread = (64 * 64) / (blockDim.x * blockDim.y);  // 16
for (int i = 0; i < elements_per_thread; i++) {
    int linear_idx = tid * elements_per_thread + i;
    int smem_row = linear_idx / 64;
    int smem_col = linear_idx % 64;
    int global_row = blockIdx.y * 64 + smem_row;
    int global_col = k_start + smem_col;
    A_shared[smem_row][smem_col] = A[global_row * K + global_col];
}
__syncthreads();

关键：tid * 16 + i 产生连续的 linear_idx → 映射到连续的 global_col → 同一 warp 内的 threads 访问连续内存地址 → coalesced!

更优的加载方式：让 warp 内 threads 同步访问连续地址

// 改进: 让同一 warp 在同一轮加载中访问连续地址
for (int i = 0; i < elements_per_thread; i++) {
    int linear_idx = i * blockDim.x * blockDim.y + tid;  // ← 关键改动!
    int smem_row = linear_idx / 64;
    int smem_col = linear_idx % 64;
    int global_row = blockIdx.y * 64 + smem_row;
    int global_col = k_start + smem_col;
    A_shared[smem_row][smem_col] = A[global_row * K + global_col];
}
// 现在 warp 0 (tid=0~31) 在 i=0 时:
//   linear_idx = 0, 1, 2, ..., 31
//   smem_col = 0, 1, 2, ..., 31 → 连续! Coalesced! ✓

§6 边界处理

当 M、N、K 不能被 tile 大小整除时，越界访问会导致 segfault 或读取垃圾数据。必须做边界检查：

// 安全加载 (处理 M/N/K 不整除的情况)
int global_row = blockIdx.y * BLOCK_M + smem_row;
int global_col = k_start + smem_col;

if (global_row < M && global_col < K) {
    A_shared[smem_row][smem_col] = A[global_row * K + global_col];
} else {
    A_shared[smem_row][smem_col] = 0.0f;  // padding with 0
}

对比 Triton：tl.load(ptr, mask=..., other=0.0) 一行搞定。CUDA 需要手动 if-else，但本质是同一件事——超出边界的位置填 0，不影响乘法累加结果。

源码对照

#define TILE 32

__global__ void transpose_optimized(float* out, const float* in, int M, int N) {
    __shared__ float tile[TILE][TILE + 1];  // +1 padding 避免 bank conflict

    int x = blockIdx.x * TILE + threadIdx.x;  // 输入列
    int y = blockIdx.y * TILE + threadIdx.y;  // 输入行

    // Step 1: 读入 → coalesced (同一 warp 的 threads 读同一行的连续列)
    if (x < N && y < M)
        tile[threadIdx.y][threadIdx.x] = in[y * N + x];
    __syncthreads();

    // Step 2: 写出 → 坐标交换，但 threadIdx.x 仍映射到连续输出列 → coalesced!
    x = blockIdx.y * TILE + threadIdx.x;  // 输出列 = 原来的行方向
    y = blockIdx.x * TILE + threadIdx.y;  // 输出行 = 原来的列方向
    if (x < M && y < N)
        out[y * M + x] = tile[threadIdx.x][threadIdx.y];  // tx/ty 交换 = 转置!
}

为什么 TILE+1 Padding?

Shared memory 由 32 个 bank 组成，每个 bank 宽 4 bytes。tile[32][32] 中，同一列的元素落在同一 bank → bank conflict。tile[32][33] 让每行偏移 1 个 float，使列访问分散到不同 bank → 无 conflict。

关键洞察：Shared memory 让"转置"发生在 SRAM 里（零开销），读和写 Global Memory 时都保持 coalesced。这就是 shared memory tiling 的威力——把不友好的访问模式隐藏在片上高速缓存中。

§9 带走

  1. Coalesced access：同一 warp 访问连续地址 → 1 次内存事务（否则最多 32 次）
  2. 矩阵列访问天然不 coalesced → 需要 shared memory 中转
  3. 协作加载：block 内所有 threads 分工加载 tile → shared → 自由读取
  4. __syncthreads() 确保加载完成后再计算（忘了加 = 经典 bug）
  5. "load → shared → compute" 模式就是 GEMM 的核心——后续的所有优化（向量化加载、double buffering、warp tiling）都建立在此之上
