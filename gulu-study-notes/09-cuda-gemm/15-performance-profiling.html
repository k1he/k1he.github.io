§1NSight Compute 简介

NSight Compute (ncu) 是 NVIDIA 官方的 kernel-level profiler，能给出每个 kernel 的详细性能数据。

基本用法

# Profile a kernel (完整指标集)
ncu --set full -o gemm_report ./gemm_app

# 指定 kernel 名，跳过前 5 次 launch，只分析 1 次
ncu --kernel-name gemm_kernel --launch-skip 5 --launch-count 1 -o report ./app

# 只看特定 metrics
ncu --metrics gpu__time_duration.avg,sm__throughput.avg ./app

关键指标

Metric含义
Durationkernel 执行时间
SM ThroughputSM 利用率 (%)
Memory Throughput内存带宽利用率 (%)
Compute Throughput计算吞吐利用率 (%)
Achieved Occupancy实际 warp 占用率

§2Roofline Model 实战

核心公式：

Performance = min(Peak_Compute, AI × Peak_Bandwidth)

其中 AI = Arithmetic Intensity = FLOPs / Bytes_accessed

A100 参数

Peak Compute (FP16 TC): 312 TFLOPS Peak Bandwidth (HBM): 2039 GB/s Balance Point: 312 / 2.039 = 153 FLOP/Byte

GEMM (M=N=K=4096, FP16) 分析

FLOPs = 2 × 4096³ = 137.4 GFLOP Bytes = (4096² + 4096² + 4096²) × 2 = 100.7 MB AI = 137.4G / 100.7M = 1365 FLOP/Byte AI (1365) >> Balance Point (153) → Compute-bound! Expected peak: 312 TFLOPS

Roofline 图示

解读：Naive 实现在 roofline 图左下角（memory-bound），经过 shared memory 优化后 AI 提升到 32，最终加上 Tensor Core + swizzle 后 AI 飙到 1365，逼近计算峰值。

§3分析你的 Kernel 的步骤

Step 1: 确定理论峰值

你的 kernel 的理论 TFLOPS: - FP16 Tensor Core: 312 TFLOPS (A100) - FP32 CUDA Core: 19.5 TFLOPS

Step 2: 测量实际性能

Actual TFLOPS = 2 × M × N × K / time_seconds / 1e12 Efficiency = Actual / Peak × 100%

Step 3: 判断瓶颈

NSight Compute 会告诉你：

  • Compute-bound: SM throughput 高, memory throughput 低
  • Memory-bound: Memory throughput 高, compute throughput 低
  • Latency-bound: 两者都低 (stalls)

Step 4: 针对性优化

瓶颈类型特征优化方向
Memory-boundMem BW > 80%, Compute < 50%提高 AI (larger tiles, more reuse)
Compute-boundCompute > 80%, Mem < 50%用 Tensor Core, 优化指令
Latency-boundBoth < 50%Double buffer, 提高 occupancy
L2 thrashingHigh L2 miss rateCTA swizzle
Bank conflictShared mem replay 高Padding / swizzle

§6nsys (系统级 Profile)

# 系统级时间线
nsys profile -o timeline ./app

# 查看统计信息：kernel launch、memcpy、GPU idle
nsys stats timeline.nsys-rep

nsys vs ncu 的分工：

  • nsys: "为什么整体慢?" — 多 kernel 之间的关系、CPU-GPU 重叠、launch overhead、memcpy 占比
  • ncu: "为什么这个 kernel 慢?" — tile size 不对、bank conflict、low occupancy
典型发现：nsys 经常暴露出：kernel launch overhead（太多小 kernel）、host-device synchronization（cudaDeviceSynchronize 频繁调用）、memcpy 与 compute 没有 overlap 等问题。

§7Occupancy 调优

Occupancy = active warps / max warps per SM 影响因素: - Registers per thread: 越多 → occupancy 越低 - Shared memory per block: 越多 → 可同时运行的 blocks 越少 - Block size: 太小 → 不能填满 SM

示例：A100

// A100: max 64 warps/SM (2048 threads)
// 假设 block size = 256 threads = 8 warps/block
// Register limit 允许 4 blocks/SM
// → 4 × 8 = 32 active warps → occupancy = 32/64 = 50%

# 查看 occupancy
ncu --kernel-name my_kernel --metrics launch__occupancy ./app
重要认知：高 occupancy 不一定快，低 occupancy 不一定慢。GEMM 通常 occupancy 只有 25-50%，但因为每个 warp 有足够工作（大 register tile），指令级并行 (ILP) 能 hide latency，性能依然很好。
