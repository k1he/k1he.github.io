01什么是 Expert Parallelism

Expert Parallelism (EP) 是 MoE 模型的核心分布式策略：将不同的 Expert 分配到不同的 GPU 上。

与 TP 的对比

Tensor Parallelism (TP)

每个 GPU 持有所有 Expert，但每个 Expert 的权重被切分（沿 intermediate 维度）。

# TP: 切分每个 expert 内部
GPU0: Expert[0..N] 的前半权重
GPU1: Expert[0..N] 的后半权重
# 通信: AllReduce (输出维度)

Expert Parallelism (EP)

每个 GPU 只持有一部分 Expert，Expert 完整不切分。Token 需要路由到正确的 GPU。

# EP: 切分 expert 的分配
GPU0: Expert[0..31]   (完整权重)
GPU1: Expert[32..63]  (完整权重)
...
# 通信: All-to-All (token 路由)
为什么用 EP？ 当 Expert 数量很大时（如 DeepSeek-V3 的 256 个），TP 模式下每个 GPU 都要保存所有 Expert 的（切片）权重，内存占用高。EP 将 Expert 分散到不同 GPU，每个 GPU 只需持有 num_experts / ep_size 个 Expert，大幅降低单卡内存需求。

02TokenDispatcher 接口

所有 dispatcher 实现统一的 TokenDispatcher 抽象接口：

class TokenDispatcher(ABC):
    """Token dispatch 抽象基类，定义 dispatch/combine 两阶段接口。"""

    @abstractmethod
    def dispatch(
        self,
        hidden_states: torch.Tensor,       # [num_tokens, hidden_size]
        router_logits: torch.Tensor,       # [num_tokens, num_experts]
        topk_ids: torch.Tensor,            # [num_tokens, top_k]
        topk_weights: torch.Tensor,        # [num_tokens, top_k]
        ...
    ) -> DispatchOutput:
        """将 token 路由到对应 expert (可能涉及跨 GPU 通信)"""
        ...

    @abstractmethod
    def combine(
        self,
        moe_output: torch.Tensor,          # expert 计算后的输出
        dispatch_output: DispatchOutput,  # dispatch 阶段的元信息
        ...
    ) -> torch.Tensor:
        """收集各 expert 输出并组合回原 token 顺序"""
        ...

class DispatchOutput(NamedTuple):
    dispatched_input: torch.Tensor   # 重排后的输入
    topk_ids: torch.Tensor           # 重映射后的 expert IDs (local)
    topk_weights: torch.Tensor       # 路由权重
    recv_counts: Optional[torch.Tensor]  # EP 通信元数据
    ...

03StandardDispatcher: 单 GPU 路径

当 ep_size=1 时使用，无需任何跨 GPU 通信：

class StandardDispatcher(TokenDispatcher):
    """单 GPU dispatcher — 不做任何通信，直接透传。"""

    def dispatch(self, hidden_states, topk_ids, topk_weights, ...):
        # 单 GPU: 所有 expert 都在本地，无需路由
        return DispatchOutput(
            dispatched_input=hidden_states,
            topk_ids=topk_ids,           # 直接用原始 expert IDs
            topk_weights=topk_weights,
            recv_counts=None,
        )

    def combine(self, moe_output, dispatch_output, ...):
        # 直接返回，无需回传
        return moe_output
适用场景： 调试阶段、Expert 数量少（如 8 个）且单卡内存放得下、或纯 TP 模式。

04DeepEP: 两种通信模式

DeepEP 是 DeepSeek 开源的高性能 Expert Parallelism 通信库，提供两种模式满足不同场景：

Normal 模式 (高吞吐)

基于 NCCL 风格的异步 All-to-All，适合 prefill 等大 batch 场景。

class DeepEPDispatcherNormal:
    def dispatch(self, ...):
        # 1. 计算每个 GPU 要发/收
        #    多少 token
        send_counts = compute_counts(
            topk_ids, self.ep_size,
            self.num_local_experts
        )

        # 2. 异步 All-to-All
        recv_buf, handle = (
            deepep.async_dispatch(
                hidden_states,
                send_counts,
                self.ep_group,
            )
        )

        # 3. 等待完成
        recv_buf = handle.wait()
        return DispatchOutput(
            dispatched_input=recv_buf,
            ...
        )

特点： 大 batch 下通信可与计算 overlap，吞吐高；延迟相对较高。

Low-Latency 模式 (低延迟)

使用 SM-managed RDMA，绕过 NCCL，适合 decode 等小 batch 场景。

class DeepEPDispatcherLowLatency:
    def dispatch(self, ...):
        # 1. 预分配对称内存 (symmetric mem)
        # 2. SM 直接发起 RDMA 写入
        recv_buf = deepep.ll_dispatch(
            hidden_states,
            topk_ids,
            self.symmetric_mem,
            self.ep_group,
            num_tokens_per_expert=
                self.max_tokens_per_expert,
        )

        # 无需等待 —— SM 同步完成
        return DispatchOutput(
            dispatched_input=recv_buf,
            ...
        )

特点： 小 batch 时延迟极低（μs 级）；需要预分配 symmetric memory。

Symmetric Memory 要求： Low-Latency 模式需要在初始化时分配跨 GPU 的对称内存区域（所有 GPU 映射到同一地址空间）。这需要特殊的 CUDA IPC 支持，且内存大小必须预先确定（由 max_tokens_per_expert 决定）。

05Dispatcher 创建逻辑

create_moe_dispatcher 的完整决策树：

def create_moe_dispatcher(
    a2a_backend: str,
    ep_size: int,
    num_experts: int,
    num_local_experts: int,
    topk: int,
    hidden_size: int,
    server_args,
) -> TokenDispatcher:

    # ═══ 决策树 ═══
    if ep_size == 1:
        # 单 GPU / 纯 TP 模式
        return StandardDispatcher(
            num_experts=num_experts,
            topk=topk,
        )

    # EP 模式: 根据 a2a_backend 选择实现
    if a2a_backend == "deepep_normal":
        return DeepEPDispatcherNormal(
            ep_size=ep_size,
            num_local_experts=num_local_experts,
            hidden_size=hidden_size,
            ep_group=get_ep_group(),
        )
    elif a2a_backend == "deepep_low_latency":
        return DeepEPDispatcherLowLatency(
            ep_size=ep_size,
            num_local_experts=num_local_experts,
            hidden_size=hidden_size,
            symmetric_mem_size=server_args.deepep_sym_mem_size,
            max_tokens_per_expert=server_args.max_tokens_per_expert,
        )
    elif a2a_backend == "flashinfer":
        return FlashinferDispatcher(...)
    else:
        raise ValueError(f"Unknown: {a2a_backend}")
a2a_backend 选择建议： Prefill 用 deepep_normal（大 batch 高吞吐），Decode 用 deepep_low_latency（小 batch 低延迟）。SGLang 支持在 prefill 和 decode 阶段使用不同的 dispatcher。

06EPLB: Expert 动态负载均衡

MoE 的一个核心问题是 负载不均衡：某些 hot expert 被频繁路由，而 cold expert 几乎不被使用。EPLB 通过动态调整 Expert 的物理分布来缓解这一问题。

EPLB 核心思路

# EPLB = Expert-Level Load Balancing
# 核心思想: 热门 expert 复制到多个 GPU，冷门 expert 合并

# 1. 统计每个 expert 的负载
expert_load = collect_load_statistics(topk_ids_history)
# expert_load: [num_experts] — 每个 expert 收到的 token 数

# 2. 决定哪些 expert 需要复制
# 热门 expert 复制到多个 GPU
replication_plan = compute_replication(
    expert_load,
    num_physical_slots=num_local_experts * ep_size,
    max_replicas=max_replicas_per_expert,
)
# replication_plan: {expert_id: num_replicas}

# 3. 更新 logical → physical 映射表
logical_to_physical = build_mapping(replication_plan)
# logical_to_physical: [num_experts] → [physical_expert_id, gpu_id]

无 EPLB（静态分配）

GPU0: [E0, E1, E2, E3]  ← E0 过载
GPU1: [E4, E5, E6, E7]  ← E7 空闲
# GPU0 成为瓶颈

有 EPLB（动态复制）

GPU0: [E0, E1, E2, E0'] ← E0 复制
GPU1: [E4, E5, E0'',E7] ← E0 再复制
# E0 负载分散到 3 个副本
# E3, E6 被迁移或合并

07Expert ID 重映射: logical → physical

当 EPLB 启用后，Router 输出的是 逻辑 Expert ID，需要映射为 物理 Expert ID（考虑复制）：

def topk_ids_logical_to_physical(
    topk_ids: torch.Tensor,          # [num_tokens, top_k] logical IDs
    logical_to_physical: torch.Tensor,# [num_logical_experts, max_replicas]
    rand_seeds: Optional[torch.Tensor] = None,
) -> torch.Tensor:
    """
    将逻辑 expert ID 转换为物理 expert ID。
    如果一个逻辑 expert 有多个物理副本，随机选择一个。
    """
    # 例: logical expert 5 有 3 个副本
    # logical_to_physical[5] = [5, 37, 62]  (物理 slot IDs)

    # 随机选一个副本（负载均衡）
    num_replicas = (logical_to_physical >= 0).sum(dim=-1)
    replica_idx = rand_seeds % num_replicas[topk_ids]

    # 查表得到物理 ID
    physical_ids = logical_to_physical[topk_ids, replica_idx]
    return physical_ids

# 使用位置: dispatch 之前
# topk_ids = topk_ids_logical_to_physical(topk_ids, mapping)
# 之后 dispatch 使用物理 ID 确定 token 发往哪个 GPU
重映射时机： 在 Router 输出 topk_ids 之后、dispatch 之前执行。这样 Dispatcher 只需要按物理 ID 做 all-to-all，不需要知道 EPLB 的存在。设计上实现了关注点分离。

完整数据流

# 完整 EP + EPLB 数据流

# 1. Router 输出逻辑 expert IDs
topk_ids_logical = router(hidden_states)  # [tokens, top_k]

# 2. EPLB 重映射为物理 IDs
topk_ids_physical = topk_ids_logical_to_physical(
    topk_ids_logical, mapping_table
)

# 3. Dispatch: 按物理 ID 将 token 发到目标 GPU
dispatch_out = dispatcher.dispatch(
    hidden_states, topk_ids_physical, topk_weights
)

# 4. Local compute: 每个 GPU 只计算本地 expert
moe_output = run_moe_core(dispatch_out)

# 5. Combine: 将结果收回原 GPU
final = dispatcher.combine(moe_output, dispatch_out)
