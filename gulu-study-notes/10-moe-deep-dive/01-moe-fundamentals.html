§0为什么需要 MoE

Dense 模型的困境

传统 Dense 模型（如 LLaMA-70B）对 每一个输入 token 都激活全部参数。这意味着：

  • 参数利用率低 —— 一个 token 问数学题时，模型里关于法律、医学、编程的参数也被计算了，但几乎没贡献
  • FLOPS 与参数量线性绑定 —— 想让模型懂更多知识，就得加参数；加了参数，每个 token 的计算量也跟着涨
  • 推理成本高 —— 每 token 的矩阵乘法（GEMM）固定为全尺寸，无法"省着用"
💡 生活类比：想象一家大公司，不管客户来问什么问题，都要所有部门的员工一起开会讨论。问个 IT 问题，法律部、市场部、行政部也全到场 —— 明显浪费。

MoE 的核心思想：稀疏激活

MoE（Mixture of Experts，混合专家）的做法是：用 N 倍的参数量，但每个 token 只激活其中的 top-k 个 expert。只有被选中的 expert 才参与计算，其余 expert 的权重虽然也在显存里，但不会被使用。

💡 生活类比：公司还是那个大公司，但现在有个"前台调度员"：客户来问 IT 问题，前台就把你转到 IT 部门；问法律问题，转到法律部。不需要全公司开会，只让相关的部门响应就行。
关键等式：MoE 让"总参数量"和"每 token FLOPS"解耦。
例：Mixtral-8×7B 有 ~46.7B 参数，但每 token 只激活 ~12.9B（2/8 expert），计算量 ≈ 一个 13B Dense 模型。
也就是说：你用 13B 的算力，获得了接近 47B 的知识容量。

§1Gate 函数与路由 —— 谁来决定 token 去哪？

Gate 是什么？为什么需要它？

上图的"Gate"就是那个"前台调度员"。它的任务是：

  1. 看一眼 token —— 把 token 的向量表示过一个小型线性层，算出它和每个 expert 的"匹配分"
  2. 打分排序 —— 对匹配分做 softmax，变成概率分布；再取 top-k，选出最匹配的 k 个 expert
  3. 分配权重 —— 被选中的 expert 各获得一个权重（就是匹配分的归一化值），最后把各 expert 的输出按权重加起来
💡 生活类比：你去医院挂号，导诊台的护士（Gate）会问你哪里不舒服，然后给你推荐 2 个科室（top-2）。如果 70% 可能是内科、30% 可能是外科，那你最终诊断结果就是内科医生意见 × 70% + 外科医生意见 × 30%。

Gate 的工作流程（三步走）

下面用代码来展示 Gate 的三个步骤，每一步都解释"在干什么"和"为什么"：

# ━━━ 第 1 步：算匹配分 ━━━
# x 是当前 token 的隐藏向量，形状 [hidden_size]
# W_gate 是 Gate 层的权重，形状 [hidden_size, num_experts]
# 这一步就是：token 的向量 × 矩阵 → 得到和每个 expert 的"匹配分数"
router_logits = x @ W_gate          # 结果形状: [num_experts]，每个 expert 一个分数

# ━━━ 第 2 步：转概率 + 选 top-k ━━━
# softmax 把分数变成概率（所有值加起来 = 1）
# topk 选出概率最高的 k 个 expert
router_weights = softmax(router_logits, dim=-1)   # [num_experts]，概率分布
topk_weights, topk_ids = torch.topk(router_weights, k=top_k)  # 各 [top_k]

# ━━━ 第 3 步：归一化选中权重 ━━━
# 选中的 k 个 expert 的概率之和不等于 1（因为还有没选中的），
# 所以要重新归一化，让选中权重之和 = 1
topk_weights = topk_weights / topk_weights.sum(dim=-1, keepdim=True)

具体例子

假设有 4 个 expert，top_k=2：

步骤计算结果
① 匹配分x @ W_gate[2.1, 0.3, 5.8, 1.0]
② softmax概率化[0.04, 0.01, 0.91, 0.02]
③ top-2选最大的 2 个Expert 2 (0.91), Expert 0 (0.04)
④ 归一化0.91+0.04=0.95 → 重算Expert 2 (0.96), Expert 0 (0.04)

最终输出：y = 0.96 × Expert₂(x) + 0.04 × Expert₀(x)

可以看到 Expert 2 的权重远大于 Expert 0，说明这个 token 确实主要由 Expert 2 处理。

参数速查

符号是什么为什么需要典型值
W_gateGate 线性层权重把 token 向量映射为和每个 expert 的匹配分[hidden_size, num_experts]
top_k每 token 选几个 expert太大会增加计算量，太小则信息不足；k=2 是性价比最优2 (Mixtral) / 8 (DeepSeek)
renormalize是否对选中权重重新归一化保证最终权重之和 = 1，否则输出量级不稳定True
SGLang 优化：Gate 的三步（线性层 → softmax → topk）在朴素实现中是 3 个独立的 kernel launch，中间结果要在 GPU 显存（HBM）上来回读写。 SGLang 把这三步融合为一个 Triton kernel（fused_moe_router_cudacore_kernel），中间结果留在 GPU 片上缓存（SRAM），大幅减少 HBM 访问次数。详见第 3 节。

§2MoE 的三个核心挑战

MoE 的核心思想虽然简单，但落地时会遇到三个工程难题。理解它们的产生场景比记住解决方案更重要。

① 负载不均衡 —— 有的 expert 忙死，有的闲死

怎么产生的？

Gate 是根据 token 的内容来选 expert 的。问题在于：语言数据本身就有天然的不均衡性。

举个例子：如果训练数据里数学题特别多，Gate 学到的模式会让大部分 token 都被路由到"数学 expert"。结果就是：

  • 数学 expert 被海量 token 打爆，变成延迟瓶颈 —— 其他 expert 都算完了，还得等它
  • 法律 expert、医学 expert 空闲，GPU 算力浪费
  • 更严重的是：训练时也会不均衡，热门 expert 被反复训练变得更好，冷门 expert 训练不足变得更差，恶性循环
💡 生活类比：一家餐厅有 8 个厨师，但 80% 的客人都点川菜。川菜厨师忙到出菜慢（延迟高），其他厨师闲着没事干（资源浪费）。整个餐厅的出餐速度被川菜厨师拖慢了。

什么场景特别严重？

  • Expert 数量少（如 8 个）时，每个 expert 覆盖的领域宽，热门领域容易集中
  • 训练数据分布不均时（如代码数据远多于数学数据），Gate 学到的路由模式天然不均衡
  • Expert Parallelism时，不同 GPU 上的 expert 负载差异直接导致跨 GPU 等待

怎么缓解？

  • Auxiliary loss（辅助损失）：训练时额外加一个损失函数，惩罚路由过于集中，强制 Gate 把 token 分散开
  • Correction bias（修正偏置）：推理时给冷门 expert 的匹配分加一点偏置，让更多 token 被路由过去
  • Capacity factor（容量因子）：给每个 expert 设置 token 数上限，超出的 token 丢弃或路由到次优 expert
  • Grouped TopK：DeepSeek-V3 的方案，把 expert 分成组，每组强制选 k 个，避免所有 token 集中在同一组

② All-to-All 通信 —— 多卡之间的"快递"瓶颈

怎么产生的？

当模型太大、expert 太多，一块 GPU 放不下所有 expert，就需要Expert Parallelism（EP）：把不同的 expert 放在不同的 GPU 上。

这带来了一个必然的问题：token 要"搬家"。

  • 假设 GPU 0 收到 100 个 token，其中 60 个需要 GPU 1 上的 expert、40 个需要 GPU 2 上的 expert
  • GPU 0 必须把这 100 个 token 发送到 GPU 1 和 GPU 2（dispatch）
  • 各 GPU 算完后，再把结果发回给 GPU 0（combine）
  • 这个"发出去 + 收回来"就是 All-to-All 通信

每一层 MoE 都要经历 2 次 All-to-All。一个模型可能有几十层 MoE，通信量非常可观。

什么场景特别严重？

  • 跨节点通信时（GPU 分布在不同机器上）：节点间带宽（RDMA/InfiniBand）远低于节点内带宽（NVLink），通信延迟飙升
  • Batch size 大时：要搬运的 token 数量多，通信量 ≈ batch_size × hidden_size × 2
  • MoE 层数多时：每层 2 次 All-to-All，层数 × 2 = 通信次数
💡 生活类比：3 个分公司各有自己的专业团队。北京总部收到客户需求后，要快递到对应分公司处理（dispatch），处理完再快递回总部汇总（combine）。如果分公司在不同城市，快递时间（通信延迟）就成了主要瓶颈。

怎么缓解？

  • DeepEP：DeepSeek 开源的通信库，自动利用 NVLink（节点内高速）+ RDMA（跨节点），同时提供 normal（高吞吐）和 low-latency（低延迟）两种模式
  • 通信-计算重叠（Overlap）：在等 All-to-All 通信完成的同时，先算其他层的计算，不让 GPU 闲着
  • Mooncake：支持 prefill-decode 分离架构的 EP 通信协议

③ 显存带宽压力 —— 算得快但搬不动

怎么产生的？

MoE 虽然每个 token 只激活 k 个 expert，但所有 expert 的权重都必须放在显存里（因为下一个 token 可能选不同的 expert）。

这导致一个尴尬局面：

  • 计算量不大（只有 top-k expert 参与计算）
  • 但要读的权重很多（每次 forward 要从 HBM 读取被选中 expert 的权重）
  • GPU 的计算速度（TFLOPS）远快于显存带宽（TB/s）→ 带宽成为瓶颈

用数字感受一下：假设 8 个 expert 每个 7B 参数，总共 56B 参数。即使每 token 只用 2 个 expert，也要从 HBM 读取 ~14B 参数的权重。以 FP16 计算，每次 forward 至少要读 ~28GB 的权重数据。H100 的带宽是 ~3.35TB/s，光读权重就要 ~8ms，而实际计算可能只需 ~2ms。

什么场景特别严重？

  • Decode 阶段（每次只生成 1 个 token）：batch_size=1 时，计算量极小，但还是要读完整权重，算术强度极低，GPU 大部分时间在等数据
  • Expert 数量多时（如 DeepSeek-V3 有 256 个 expert）：虽然每个 expert 更小了，但 router 选择和 dispatch 的开销增加
  • 推理而非训练时：训练的 batch 大，计算密集度高，带宽压力相对小；推理尤其是 decode，batch 小，带宽是硬伤
💡 生活类比：你有一个 1000 页的百科全书，虽然每次只需读其中 2 页，但每次翻到那 2 页也要先把整本书从书架上搬下来（所有权重都在 HBM 里）。如果书太重（权重太多），搬书的时间比读书的时间还长。

怎么缓解？

  • Fused Kernel：把 dispatch → GEMM → activation → GEMM → combine 合并到一个 kernel 里，中间结果不写回 HBM，留在 GPU 片上缓存（SRAM）
  • 量化（FP8/INT8）：权重用更少的位数存储，HBM 读取量直接减半
  • Expert Parallelism：把 expert 分散到多 GPU，每块 GPU 的权重总量减少
三个挑战是联动的：负载不均衡 → 某个 GPU 上的 expert 被过多 token 打爆 → 显存带宽压力更严重 → All-to-All 等待时间更长 → 整体吞吐下降。MoE 的工程优化本质就是在三者之间找平衡。

§3关键模型对比

模型 Expert 数 Top-K 总参数 激活参数 / token 特殊机制
Mixtral-8×7B 8 2 46.7B ~12.9B 标准 MoE，无 shared expert
Qwen3-MoE-235B 128 8 235B ~22B Fine-grained experts（更多更小的 expert）
DeepSeek-V3 256 (+ 1 shared) 8 (grouped) 671B ~37B Grouped routing + shared expert + correction bias
趋势解读：
  • Expert 越来越多、越来越小（Fine-grained MoE）：DeepSeek-V3 用 256 个小 expert 替代 8 个大 expert。好处是路由更灵活、负载更均衡；代价是 dispatch 更复杂
  • Shared expert：DeepSeek 额外加了一个"公共 expert"，所有 token 都会经过它。类似于"不管看什么病，都先做个基础体检"
  • Grouped TopK：把 256 个 expert 分成几组，每组强制选若干个，避免所有 token 挤在同一个 expert
SGLang 通过 use_grouped_topk 参数支持此模式。

§4SGLang 的解法概览

SGLang 针对上述三个挑战，提供了一整套优化方案：

解决带宽压力：Fused MoE Kernel

朴素实现中，dispatch → GEMM1 → activation → GEMM2 → combine 每一步都是独立的 kernel，中间结果要写回 HBM 再读出来。

Fused Kernel 把 GEMM1 → activation → GEMM2 合并到一个 kernel 里，中间结果留在 SRAM 不写回 HBM，减少 2 次完整的 HBM 读写。

SGLang 支持三种后端：

  • TritonExpMoeRunner — Triton JIT，灵活可调
  • CutlassExpMoeRunner — CUTLASS grouped GEMM，高吞吐
  • FlashinferExpMoeRunner — FlashInfer C++ 融合，低延迟

解决通信瓶颈：Expert Parallelism

把 expert 分散到多块 GPU，每块 GPU 只持有 num_experts / ep_size 个 expert，权重总量减少。

Token 通过 All-to-All 发送到目标 GPU：

  • DeepEPDispatcher — 支持 normal（高吞吐）/ low-latency（低延迟）两种模式
  • MooncakeDispatcher — Mooncake EP 协议，支持 PD 分离
