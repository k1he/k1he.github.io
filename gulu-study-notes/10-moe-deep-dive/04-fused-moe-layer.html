01FusedMoE 类初始化参数

FusedMoE 是 SGLang 中 MoE 层的核心实现类，位于 sglang/srt/layers/moe/fused_moe_triton/layer.py。它统一封装了路由、Expert 并行、量化等复杂逻辑。

核心构造参数

class FusedMoE(nn.Module):
    def __init__(
        self,
        num_experts: int,              # Expert 总数 (e.g., 256 for DeepSeek-V3)
        top_k: int,                    # 每个 token 激活的 expert 数
        hidden_size: int,              # 输入/输出维度
        intermediate_size: int,        # FFN 中间维度
        params_dtype: torch.dtype = None,
        reduce_results: bool = True,  # 是否在 TP 组内 allreduce
        renormalize: bool = True,     # topk 权重归一化
        use_grouped_topk: bool = False,# 分组 topk (DeepSeek 风格)
        num_expert_group: int = None, # 分组数量
        topk_group: int = None,       # 每组选几个 expert
        quant_config: Optional[QuantizationConfig] = None,
        tp_size: Optional[int] = None,
        ep_size: Optional[int] = None,
        ...
    ):
关键理解： num_experts 是全局 expert 总数，实际每张 GPU 上的 expert 数量由 EP/TP 策略决定。对 DeepSeek-V3 来说，num_experts=256，若 ep_size=8，则每 GPU 持有 32 个 experts。

02Expert Parallelism 配置

FusedMoE 同时支持 TP（Tensor Parallelism）和 EP（Expert Parallelism），二者的切分维度不同：

TP 模式（默认）

每个 GPU 持有全部 expert，但每个 expert 的中间维度被切分：

# intermediate_size 按 TP 切分
intermediate_size_per_partition = (
    intermediate_size // moe_tp_size
)

EP 模式

将 expert 分到不同 GPU，每个 GPU 只持有一部分 expert：

# expert 数量按 EP 切分
num_local_experts = num_experts // moe_ep_size

# EP + TP 混合时
# ep_size * tp_size = total_gpus

并行度计算逻辑

# 来自 layer.py __init__
self.moe_ep_size = ep_size or get_tensor_model_parallel_world_size()
self.moe_tp_size = tp_size or (
    get_tensor_model_parallel_world_size() // self.moe_ep_size
)

# 本地 expert 数量
assert num_experts % self.moe_ep_size == 0
self.num_local_experts = num_experts // self.moe_ep_size

# 中间层维度（如果 TP 还需进一步切分）
self.intermediate_size_per_partition = (
    intermediate_size // self.moe_tp_size
)
约束条件： ep_size × tp_size 必须等于总的 tensor parallel world size。若 world_size=8 且 ep_size=4，则 tp_size=2。

03forward_impl 三步流程

FusedMoE 的前向计算遵循经典的 dispatch → compute → combine 三阶段模式：

def forward_impl(self, hidden_states, router_logits, ...):
    # ═══ Step 1: Dispatch ═══
    # 将 token 路由到对应的 expert (可能涉及跨 GPU 通信)
    dispatch_output = self.dispatcher.dispatch(
        hidden_states=hidden_states,
        router_logits=router_logits,
        topk_ids=topk_ids,
        topk_weights=topk_weights,
        ...
    )

    # ═══ Step 2: Run MoE Core ═══
    # 在本地 expert 上执行 FFN 计算
    moe_output = self.run_moe_core(
        dispatched_input=dispatch_output.dispatched_input,
        topk_ids=dispatch_output.topk_ids,
        topk_weights=dispatch_output.topk_weights,
        ...
    )

    # ═══ Step 3: Combine ═══
    # 收集各 expert 的输出并加权求和
    final_hidden = self.dispatcher.combine(
        moe_output=moe_output,
        dispatch_output=dispatch_output,
        ...
    )
    return final_hidden

Dispatch

根据 topk_ids 将 token 发送到正确的 GPU/expert。单 GPU 时就是简单的 index；EP 时需要 all-to-all。

Run MoE Core

核心 FFN 计算：gate_up_proj → activation → down_proj。使用 Triton fused kernel 提升效率。

Combine

将各 expert 输出按 topk_weights 加权求和。EP 时需要 all-to-all 回传。

04Dispatcher 创建策略

create_moe_dispatcher() 根据配置选择不同的 Dispatcher 实现：

def create_moe_dispatcher(
    a2a_backend: str,
    ep_size: int,
    num_experts: int,
    num_local_experts: int,
    ...
) -> TokenDispatcher:
    if ep_size == 1:
        # 单 GPU，无需通信
        return StandardDispatcher(...)

    if a2a_backend == "deepep_normal":
        return DeepEPDispatcherNormal(...)
    elif a2a_backend == "deepep_low_latency":
        return DeepEPDispatcherLowLatency(...)
    elif a2a_backend == "flashinfer":
        return FlashinferDispatcher(...)
    else:
        raise ValueError(f"Unknown a2a_backend: {a2a_backend}")
Dispatcher通信方式适用场景
StandardDispatcher无通信（单GPU）ep_size=1，调试/小规模
DeepEPDispatcherNormal异步 all-to-all高吞吐 prefill 场景
DeepEPDispatcherLowLatencySM-managed RDMA低延迟 decode 场景
FlashinferDispatcherFlashinfer a2a替代 DeepEP 的通信方案

05权重布局: w13 与 w2

MoE FFN 中有三个投影矩阵：gate_proj、up_proj、down_proj。SGLang 将 gate 和 up 融合为 w13：

融合策略

# w13 = [gate_proj, up_proj] 拼接 (SwiGLU 风格)
# Shape: [num_local_experts, 2 * intermediate_size_per_partition, hidden_size]
self.w13_weight = nn.Parameter(
    torch.empty(
        self.num_local_experts,
        2 * self.intermediate_size_per_partition,  # gate + up 拼接
        self.hidden_size,
    )
)

# w2 = down_proj
# Shape: [num_local_experts, hidden_size, intermediate_size_per_partition]
self.w2_weight = nn.Parameter(
    torch.empty(
        self.num_local_experts,
        self.hidden_size,
        self.intermediate_size_per_partition,
    )
)
为什么融合 w13？ gate_proj 和 up_proj 共享相同的输入 x，融合后只需一次 GEMM 就能得到 [gate(x), up(x)]，减少 kernel launch 和内存带宽开销。Triton kernel 对此做了专门优化。

计算流程示意

# 前向计算伪代码
gate_up = x @ w13.T        # [tokens, 2*intermediate]
gate, up = split(gate_up)  # 各 [tokens, intermediate]
activated = silu(gate) * up # SwiGLU activation
output = activated @ w2.T  # [tokens, hidden_size]

06量化方法选择

FusedMoE 通过 quant_method 接口支持多种量化方案，在 __init__ 阶段确定：

# 量化方法映射
if quant_config is None:
    self.quant_method = UnquantizedFusedMoEMethod()

...
量化方法精度典型加速说明
UnquantizedFusedMoEMethodBF16/FP161x（基准）无量化，精度最高
Fp8MoEMethodFP8 E4M3~1.8x支持 per-tensor 和 block-wise 两种 scale

07CUDA Graph 兼容: Piecewise Capture

MoE 的动态路由（每次 token 分配不同）给 CUDA Graph 带来挑战。SGLang 使用 piecewise capture 策略：

问题与解决方案

# 问题：MoE 路由是动态的，topk_ids 每次不同
# → 直接用 CUDA Graph 捕获完整前向会失效

# 解决方案：分段捕获
# 1. Attention 部分可以安全地 CUDA Graph 捕获
# 2. MoE dispatch/combine 标记为 graph-breaking point
# 3. MoE core compute 可以捕获（输入已排好序）

# layer.py 中的标记
self.use_piecewise_cuda_graph = (
    server_args.enable_cuda_graph
    and self.ep_size > 1
)

# 在 forward 中根据标记决定是否断开 graph
if self.use_piecewise_cuda_graph:
    # 插入 graph-breaking barrier
    torch.cuda.current_stream().synchronize()
Piecewise 含义： 不是把整个模型的前向作为一个 CUDA Graph 捕获，而是把它拆成多个片段（piece），每个片段内部是 Graph，片段之间允许动态逻辑。这样 MoE 的动态路由不会破坏其他部分的 Graph 加速。
