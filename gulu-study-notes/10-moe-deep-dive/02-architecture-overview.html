§2权重布局

w13 与 w2 的 Shape

# FusedMoE 权重定义 (layer.py)
self.w13 = torch.empty(
    num_local_experts,         # EP 下每 GPU 持有的 expert 数
    2 * intermediate_size,     # gate_proj + up_proj 合并
    hidden_size,               # 输入维度
    dtype=params_dtype
)

self.w2 = torch.empty(
    num_local_experts,         # 同上
    hidden_size,               # 输出维度
    intermediate_size,         # 中间维度（SiLU 后的结果）
    dtype=params_dtype
)

为什么 w13 合并 gate_proj 和 up_proj？

SwiGLU 激活函数需要两个线性变换的输出：silu(gate_proj(x)) * up_proj(x)。 将两者合并为一次 GEMM（w13），输出 split 成两半，减少一次 kernel launch。

§3Runner Backend 选择

Runner 后端 优势 适用场景 代码路径
TritonExpMoeRunner Triton JIT 灵活、可调参、无编译依赖 开发调试、通用 GPU、小 batch kernels/moe/ep_moe/triton_*.py
CutlassExpMoeRunner CUTLASS Grouped GEMM 高吞吐、充分利用 Tensor Core H100 大 batch prefill kernels/moe/ep_moe/cutlass_*.py
FlashinferTrtllmExpMoeRunner FlashInfer (TRT-LLM style) 极致融合、支持 FP8 decode 小 batch、低延迟 kernels/moe/ep_moe/flashinfer_*.py

选择建议： 默认使用 Triton。在 H100/H200 + 大 batch 场景下切换 CUTLASS 可获得 10-30% 提升。 FlashInfer 在 decode 阶段（batch_size 小、latency-sensitive）效果最佳。

§4Dispatcher 选择

StandardDispatcher

单机模式，无 All-to-All 通信。直接按 expert_id 排序 token 即可。

  • 最简单、最低开销
  • 适用于 EP=1 的部署
  • dispatch = permute by expert

DeepEPDispatcher

DeepSeek 开源的 EP 通信库，支持两种模式：

  • Normal: 高吞吐，适合 prefill
  • Low-latency: 减少等待，适合 decode
  • 自动利用 NVLink（节点内）+ RDMA（跨节点）

FlashinferDispatcher

FlashInfer 原生 dispatch 实现：

  • 与 FlashInfer Runner 深度集成
  • 支持 CUDA Graph 友好的 dispatch
  • 适合 decode 阶段

MooncakeDispatcher

Mooncake EP 协议：

  • 支持 prefill-decode 分离架构
  • Transfer Engine 跨节点通信
  • 适合超大规模部署
配置方式： 通过 --ep-size 和 --enable-deepep-moe / --enable-flashinfer-moe 命令行参数选择。 未指定 EP 时默认使用 StandardDispatcher。
