01MoE Runner Backend 选择

SGLang 通过环境变量 SGLANG_MOE_RUNNER_BACKEND 选择不同的 MoE 执行后端：

Backend说明适用场景
triton默认。使用 Triton fused kernel通用场景，A100/H100/H200
aiterAMD AITer 后端 (ROCm)AMD MI300X 等 GPU
cutlassCUTLASS grouped GEMM特定尺寸下可能更优
pplxPPLX 通信优化后端多节点 EP 场景
 
# 设置方法
export SGLANG_MOE_RUNNER_BACKEND=triton  # 默认值

# 代码中的选择逻辑
def get_moe_runner(backend: str):
    if backend == "triton":
        return TritonMoERunner()
    elif backend == "aiter":
        return AITerMoERunner()
    elif backend == "cutlass":
        return CutlassMoERunner()
    elif backend == "pplx":
        return PPLXMoERunner()
    else:
        raise ValueError(f"Unknown backend: {backend}")

02Autotuning 配置系统

Triton kernel 的性能对 tile 参数极为敏感。SGLang 使用预计算配置文件 + 运行时 fallback：

def try_get_optimal_moe_config(
    M: int, N: int, K: int,
    topk: int, dtype: str,
    is_marlin: bool = False,
):
    # 配置文件路径: configs/{gpu_name}/moe_{N}_{K}_{dtype}.json
    # 例: configs/H100/moe_14336_7168_bf16.json
    config_file = get_config_path(N, K, dtype)

    if os.path.exists(config_file):
        configs = json.load(open(config_file))
        # 查找与 M 最接近的预计算配置
        for m_range, cfg in configs.items():
            if M <= int(m_range):
                return cfg

    # Fallback: 通用默认配置
    return {
        "BLOCK_SIZE_M": 128,
        "BLOCK_SIZE_N": 128,
        "BLOCK_SIZE_K": 64,
        "GROUP_SIZE_M": 8,
        "num_warps": 8,
        "num_stages": 3,
    }
如何生成配置文件？ SGLang 提供 benchmark_moe.py 脚本，针对特定 GPU + 模型参数做 exhaustive search，将最优配置序列化为 JSON。部署前务必为目标 GPU 型号运行一次。

04TBO: Two-Batch Overlap

TBO 是 SGLang 针对 EP 场景的 通信-计算重叠 优化：将一个 batch 拆成两个子 batch，交替执行通信和计算。

核心思想

# 传统串行执行 (无 overlap)
# Time: |--dispatch--||--compute--||--combine--|
#       通信            计算           通信

# TBO (Two-Batch Overlap)
# 将 batch 拆成 batch_A 和 batch_B
# Time:
# Stream1: |dispatch_A|  compute_A  |combine_A|
# Stream2:            |dispatch_B|  compute_B  |combine_B|
# 通信和计算在不同 stream 上重叠执行

class TBOScheduler:
    def forward(self, hidden_states, topk_ids, topk_weights):
        # 拆分 batch
        mid = hidden_states.shape[0] // 2
        batch_a = hidden_states[:mid]
        batch_b = hidden_states[mid:]

        # Stream A: dispatch
        with torch.cuda.stream(self.stream_a):
            disp_a = self.dispatcher.dispatch(batch_a, ...)

        # Stream B: dispatch (overlap with A's compute)
        with torch.cuda.stream(self.stream_b):
            disp_b = self.dispatcher.dispatch(batch_b, ...)

        # 交替 compute + combine ...
收益分析： 在多节点 EP 场景下，跨节点 all-to-all 通信占比可达 30-40%。TBO 可将通信延迟隐藏在计算中，理论加速 ~1.3x。对单节点 EP 收益较小（NVLink 通信已经很快）。

05FP8 量化配置

MoE 的 FP8 量化有两种 scale 粒度，对性能和精度影响显著：

Per-Tensor Scale

# 每个 expert 每个权重矩阵一个 scale
w1_scale: [num_experts, 1]
w2_scale: [num_experts, 1]
a1_scale: [1]  # 激活值 scale

# 优点: 实现简单，开销小
# 缺点: 大矩阵中极值会压缩动态范围

Block-wise Scale (推荐)

# 以 block (128x128) 为粒度分配 scale
w1_scale: [num_experts, N//128, K//128]
w2_scale: [num_experts, N//128, K//128]
a1_scale: [num_tokens, K//128]

# 优点: 精度损失更小
# 缺点: scale 存储和计算开销稍大

FP8 MoE Kernel 适配

# Triton kernel 中的 FP8 处理
if use_fp8_w8a8:
    # 加载时 dequantize: fp8_val * scale → bf16/fp32
    a_block = tl.load(A_ptr + ...).to(tl.float32) * a_scale
    b_block = tl.load(B_ptr + ...).to(tl.float32) * b_scale

    # 或使用硬件原生 FP8 GEMM (SM89+/SM90+)
    # 在 Hopper 上 FP8 Tensor Core 吞吐是 BF16 的 2x
    acc += tl.dot(a_block_fp8, b_block_fp8, out_dtype=tl.float32)

    # gemm1_limit: 防止中间激活溢出 FP8 范围
    if gemm1_limit:
        intermediate = intermediate.clamp(-448.0, 448.0)
精度注意： MoE 模型对量化更敏感（因为每个 expert 训练数据相对少）。建议先用 block-wise scale 测试精度，确认 perplexity 退化在可接受范围内再上线。

06EP 调优要点

ep_size 选择

场景推荐 ep_size原因
单机 8 卡，Expert ≤ 641 (纯 TP)NVLink 带宽足够，TP 通信简单
单机 8 卡，Expert = 2568显存不够装全部 expert
多机 (2 节点 × 8 卡)16充分利用所有 GPU
多机但节点间带宽低8 (节点内)避免跨节点 all-to-all

DeepEP Normal vs Low-Latency 切换阈值

# 根据当前 batch 中 token 数量动态选择
def select_dispatch_mode(num_tokens, threshold=128):
    if num_tokens >= threshold:
        # 大 batch → Normal 模式 (异步 all-to-all)
        # 通信可与计算 overlap，吞吐优先
        return "deepep_normal"
    else:
        # 小 batch → Low-Latency 模式 (SM RDMA)
        # 通信延迟极低，适合 decode
        return "deepep_low_latency"

# Symmetric Memory 大小计算
# 需要能容纳最大可能的 token 数 × hidden_size × dtype_size
sym_mem_size = (
    max_tokens_per_expert * num_local_experts
    * hidden_size * dtype_size
    * 2  # 双缓冲
)

08常见问题与排查

🔴 OOM: 中间缓存溢出

症状： Prefill 阶段 CUDA OOM

原因： token 数太大，intermediate_cache 超出显存

解决：

# 减小 chunk size
export SGLANG_MOE_CHUNK_SIZE=32768
# 或降低 max_prefill_tokens
--max-prefill-tokens 8192

🔴 Triton Kernel 编译慢

症状： 首次启动耗时 5-10 分钟

原因： Triton JIT 编译 + autotuning

解决：

# 持久化 Triton cache
export TRITON_CACHE_DIR=/data/triton_cache
# 使用预编译配置文件
# 放置在 configs/{gpu}/ 下

🔴 EP 通信超时

症状： NCCL timeout / DeepEP hang

原因： 跨节点网络问题或 expert 负载极度不均

解决：

# 增加超时
export NCCL_TIMEOUT=1800
# 启用 EPLB
export SGLANG_EPLB_ENABLED=1
# 检查网络
ib_write_bw / nccl-tests

🔴 FP8 精度退化严重

症状： 输出质量明显下降

原因： per-tensor scale 不适合该模型

解决：

# 切换到 block-wise scale
--quantization fp8_block
# 或仅量化 w2 (down_proj)
# w1 保持 BF16

🟡 Decode 吞吐低

症状： decode 阶段 token/s 远低于预期

原因： 小 batch 下 GPU 利用率低 + 通信占比高

解决：

# 使用 Low-Latency dispatch
--a2a-backend deepep_low_latency
# 增大 decode batch
--max-running-requests 256
# 启用 fused sum+allreduce
export SGLANG_FUSED_MOE_SUM_ALL_REDUCE=1

🟡 CUDA Graph 失效

症状： 性能没有 CG 加速的预期提升

原因： EP dispatch/combine 是 graph-breaking

解决：

# 确认 piecewise capture 启用
--enable-cuda-graph
# 检查日志中 graph 段数
# [INFO] CUDA Graph: N segments
# N 应 > 1 (piecewise 生效)
调优方法论总结： 1️⃣ 先确定 ep_size（受限于显存）→ 2️⃣ 选择 a2a_backend（prefill/decode 分别配置）→ 3️⃣ 开启 FP8 量化 → 4️⃣ 运行 autotuning 生成配置 → 5️⃣ 启用 TBO overlap → 6️⃣ 按需开启 EPLB。每一步验证吞吐和精度。
