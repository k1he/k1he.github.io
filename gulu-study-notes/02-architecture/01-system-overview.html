一、它是什么 / 为什么值得读

Mini-SGLang 是 SGLang 的"教学版精简实现"：用约 5000 行 Python 复现一个工业级 LLM 推理引擎。它不是"小玩具"—— 官方 benchmark 在 H200 上跑 Qwen3-32B/TP4 已能与 SGLang 主版本同台对比。它真正的价值在于：

  • 完整 覆盖 Tokenizer / Scheduler / Engine / KVCache / Attention Backend / CUDA Graph / TP / Sampler 全链路
  • 现代 Radix Cache、Chunked Prefill、Overlap Scheduling、FlashInfer/FlashAttention/TRTLLM 多后端切换
  • 可读 全量 type annotation、模块边界清晰、几乎没有"为优化牺牲可读性"的代码
学习建议：把 mini-sglang 当成"理解 SGLang/vLLM 的钥匙"。读完这套文档后再去看 SGLang 源码，会发现绝大多数概念都能直接对上号。

二、进程拓扑（Process Topology）

Mini-SGLang 不是单进程 monolith，而是由 4 类进程通过 ZMQ + NCCL 协作。这是它最容易被忽略，但最重要的设计决策之一。

4 类进程 · 1 个原则

"Control 走 ZMQ，Tensor 走 NCCL" —— 所有控制消息（请求、token、abort）通过 ZeroMQ 跨进程，所有重型张量（activation、weight）通过 NCCL/pynccl 跨 GPU。这一点是性能与可扩展性的关键。

  • API Server 1 个，FastAPI
  • Tokenizer N 个（默认 1，可调），独立进程避免阻塞
  • De-tokenizer 1 个，复用 tokenize_worker 函数
  • Scheduler = TP size，每 GPU 一个，每个独立进程

为什么 Scheduler 一个 GPU 一个进程？

这是为了规避 Python GIL。每个 TP rank 独立的 Python 解释器，独立的 CUDA stream，独立的内存。多卡之间通过 NCCL 同步张量、通过 GLOO process group 同步 CPU 状态、通过 ZMQ Pub/Sub 同步控制消息（rank0 广播给其他 rank）。

入口源码：python/minisgl/server/launch.py 中 _run_scheduler 用 mp.Process spawn 出 N 个调度器进程。

四、五大核心技术（含源码锚点）

① Radix Cache · 前缀复用

多请求共享 system prompt / few-shot 上下文时，重复 prefix 的 KV 不重算。实现是一棵页对齐的 Radix Tree。

源码：kvcache/radix_cache.py

  • RadixTreeNode：每节点存 (key=token_ids, value=KV物理页索引), 带 ref_count 与 timestamp
  • match_prefix()：树游走 + fast_compare_key CUDA kernel 比对
  • insert_prefix()：找到分歧点后挂新节点；split_at() 按页对齐切分
  • evict()：用最小堆按 timestamp 淘汰 ref_count==0 的叶子节点
关键点：页对齐（page_size 可配 1/16/32/64）让 KV 复用与 paged attention 兼容；ref_count 锁住正在使用的前缀，evict 不会动它。

② Chunked Prefill · 长 context 削峰

来自 Sarathi-Serve。把长 prompt 切成 chunk，跨多个 batch 喂给 GPU，避免单次 prefill 的峰值显存爆 OOM。

源码：scheduler/prefill.py · ChunkedReq

class ChunkedReq(Req):
    def append_host(self, next_token):
        raise NotImplementedError("ChunkedReq should not be sampled")
    @property
    def can_decode(self) -> bool:
        return False  # 不进 decode 队列

核心是 PrefillAdder 维护 token_budget = max_extend_tokens（默认 8192），每次只装到不超额为止。

③ Overlap Scheduling · 隐藏 CPU 开销

NanoFlow 提出。本批 GPU 在算的同时，CPU 已经在为下一批准备调度数据。

源码：scheduler/scheduler.py · overlap_loop

  • 用两条 stream：self.stream 跑调度元数据 H2D，self.engine.stream 跑模型 forward
  • overlap_loop(last_data)：调度本批 → 异步 launch forward → 同时处理 last_data 结果
  • 关键 stream 同步：self.engine.stream.wait_stream(self.stream)

可用 MINISGL_DISABLE_OVERLAP_SCHEDULING=1 关闭做 ablation。

④ Tensor Parallelism · 多卡扩展

每个 GPU 一个 Scheduler 进程，权重按 column/row parallel sharded。

源码：distributed/impl.py · layers/linear.py · kernel/pynccl.py

  • QKV/MLP up: ColumnParallelLinear
  • O/MLP down: RowParallelLinear + all-reduce
  • 小张量优先用自研 pynccl，避免 NCCL 启动开销
  • CPU 控制流通过 GLOO process group barrier 同步

⑤ Optimized Kernels · 多后端切换

三套 attention backend，prefill/decode 可独立选择。

源码：attention/{fa,fi,trtllm}.py

后端优势page_size
FlashAttention 3 (fa)Hopper prefill 最快任意
FlashInfer (fi)decode 通用最强任意
TensorRT-LLM (trtllm)SM100 (Blackwell) 首选仅 16/32/64

启动逻辑见 engine.py · _adjust_config：H100 默认 fa,fi，B100 默认 trtllm。

⑥ CUDA Graph · 消除 launch 开销

decode 阶段每步只生成 1 token，kernel launch overhead 占比极高 → 用 CUDA Graph 录制后 replay。

源码：engine/graph.py

  • 预先按 cuda_graph_bs 多个粒度录制（1, 2, 4, 8, ..., max_bs）
  • pad_batch() 把当前 batch 用 dummy_req 补齐到最近的录制粒度
  • prefill / 超出最大 bs 时回落到 eager 模式

五、消息系统：四类进程怎么"对话"

所有跨进程消息都在 message/，用 msgpack 编解码，4 个 base 类对应 4 类进程之间的方向：

消息类型方向典型成员
BaseTokenizerMsgAPI → TokenizerTokenizeMsg / AbortMsg
BaseBackendMsgTokenizer → Scheduler / 其他 rankUserMsg(已分词) / AbortBackendMsg / BatchBackendMsg
BaseTokenizerMsg (反向)Scheduler → De-tokenizerDetokenizeMsg (含 next_token, finished)
BaseFrontendMsgDe-tokenizer → APIUserReply (含增量字符串)

ZMQ socket 类型映射：

  • PUSH/PULL 用于 tokenizer↔api、tokenizer↔scheduler 等单生产-单消费链路
  • PUB/SUB 用于 rank0 → 其他 ranks 的广播（多 GPU 时）
  • 所有地址用 ipc:///tmp/minisgl_* 同机本地通信，零网络拷贝

六、性能要点速览

吞吐

H200 单卡 Qwen3-0.6B / Qwen3-14B 256 并发，与 SGLang 相当。
关键：CUDA Graph + Overlap Scheduling 双开。

显存

KV pool 在 Engine._determine_num_pages 里用 memory_ratio（默认 ~0.85）自动切分，剩余给 activation。

延迟

Hopper 上 prefill 用 fa，decode 用 fi，是经验最优组合。decode 同时享受 CUDA Graph 与 overlap。
