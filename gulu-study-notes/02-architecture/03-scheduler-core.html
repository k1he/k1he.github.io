一、为什么调度层是核心

对于 LLM 推理引擎而言：

  • Engine（model forward）是"肌肉"——拼算力
  • Scheduler 是"大脑"——决定每一步喂给 GPU 什么 batch

调度的决策直接决定了：显存利用率、throughput、tail latency、是否 OOM。这一层的设计差异，是 vLLM、SGLang、TensorRT-LLM 各自风格的根本来源。

Mini-SGLang 调度层的"风味"：
  • Continuous Batching（混合 prefill + decode 的 inflight batching）
  • Prefill-first 策略（先调度 prefill，再 decode）
  • Chunked Prefill 与 Radix Cache 一等公民
  • Overlap Scheduling 用两个 CUDA stream 隐藏 CPU 开销
  • TP 多卡：rank0 调度 + 广播给其他 rank

二、scheduler/ 子包文件布局

python/minisgl/scheduler/ ├── __init__.py # 暴露 Scheduler / SchedulerConfig ├── config.py # SchedulerConfig（继承 EngineConfig），ZMQ 地址 ├── scheduler.py # ★ Scheduler 主类，run_forever / overlap_loop / normal_loop ├── prefill.py # PrefillManager + PrefillAdder + ChunkedReq ├── decode.py # DecodeManager（最小，<50 行） ├── cache.py # CacheManager: KV 物理页 + Radix Tree 桥接 ├── table.py # TableManager: 槽位号分配（max_running_req 个槽） ├── io.py # SchedulerIOMixin: ZMQ 收发 + TP 广播 └── utils.py # PendingReq / ScheduleResult dataclass

"调度三件套"

核心是这三个 Manager 互相协作：

PrefillManagerDecodeManagerCacheManager

+ TableManager 提供"请求槽位号"。

调度层"不做什么"

它不跑 model forward，不采样，不持有权重。它只决定哪些 Req 进哪个 Batch，然后交给 self.engine.forward_batch()。

每个 TP rank 都有一个 Scheduler

它们调度决策完全相同（rank0 广播）。但 Engine 持有的权重 shard 不同。

三、四个核心数据类（来自 core.py）

Req — 请求状态机

源码：core.py:28-68

28@dataclass(eq=False)
29class Req:
30    input_ids: torch.Tensor    # cpu, int32, 当前已知的所有 token
31    table_idx: int             # 在 page_table 中的行号 = 这个请求的"槽"
32    cached_len: int            # Radix 命中 + 已写入 KV 的 token 数
33    output_len: int            # sampling_params.max_tokens
34    uid: int                   # 用户请求唯一 id
35    sampling_params: SamplingParams
36    cache_handle: BaseCacheHandle  # 锁住的 Radix 节点 handle
38    def __post_init__(self):
40        self.device_len = len(self.input_ids)
41        self.max_device_len = len(self.input_ids) + self.output_len
52    def complete_one(self):     # 完成一步 forward 后
53        self.cached_len = self.device_len
54        self.device_len += 1
59    @property
60    def can_decode(self) -> bool:

三个长度的关系（重点！理解错就读不下去）：
字段含义变化时机
cached_len"已经写入 KV cache、attention 可读" 的前缀长度每次 forward 完，complete_one 推进
device_len"当前这一步 forward 想要算到的长度"（即 cached_len + extend_len）scheduler 准备 batch 时设定
max_device_len"理论上最长能涨到这"初始化时定，= input + max_tokens
extend_len= device_len - cached_len，即"本次 forward 新增 token 数"derived

Batch — 一次 forward 的输入

@dataclass
class Batch:
    reqs: List[Req]
    phase: Literal["prefill", "decode"]
    # 由 scheduler 填充：
    input_ids: torch.Tensor
    positions: torch.Tensor
    out_loc: torch.Tensor       # 写回 KV cache 的物理位置
    padded_reqs: List[Req]      # 含 dummy_req 用于 CUDA Graph 凑数

    attn_metadata: BaseAttnMetadata

纯 prefill batch 或 纯 decode batch，二选一。本版 Mini-SGLang 不做 prefill+decode 混合（这点和 SGLang 主线是相同的）。

PendingReq — 还没被调度的请求

Tokenizer 把 UserMsg 推过来后，第一站就是被包成 PendingReq 进 PrefillManager.pending_list。chunked_req 字段记录"上一个 chunk 用过的 cache handle 和 table_idx"——chunked prefill 的关键。

四、Scheduler 主循环（最关键的 60 行）

所有调度都从这两个函数发起。先看更复杂的 overlap_loop（默认开启），后面再对比 normal_loop。

源码：scheduler/scheduler.py:83-131

83def overlap_loop(self, last_data: ForwardData | None) -> ForwardData | None:
84    """
85    The main loop of overlapping scheduling and execution.
86    It will overlap the execution of current batch and processing of last batch's results.
87    """
90    blocking = not (
91        last_data is not None          # 有上一批要处理
92        or self.prefill_manager.runnable  # 有 pending prefill
93        or self.decode_manager.runnable   # 有正在 decode
94    )
95    for msg in self.receive_msg(blocking=blocking):  # [I/O] 收 ZMQ
96        self._process_one_msg(msg)                       # 入队 / abort / exit
98    forward_input = self._schedule_next_batch()           # [SCHED] 选 batch
99    ongoing_data = None
100    if forward_input is not None:
101        with self.engine_stream_ctx:                # 切到 engine.stream
102            self.engine.stream.wait_stream(self.stream)
103            ongoing_data = (forward_input, self._forward(forward_input))  # [GPU] 异步
105    self._process_last_data(last_data)                  # [CPU] 处理上一批结果
106    return ongoing_data
读这段代码的关键洞察： 第 100-103 行 launch 完 forward 是非阻塞的（异步 CUDA kernel），所以紧接着 105 行 _process_last_data 在 CPU 上运行时，GPU 已经在跑这一批的 forward 了。下一轮循环再回来时，这一批就变成了 last_data，可以采样、写回 token、回复 detokenizer。这就是 overlap scheduling 的精髓。

四个步骤拆解

Step 1 · 收消息（_process_one_msg）

源码：scheduler.py:169-198

def _process_one_msg(self, msg):
    if isinstance(msg, BatchBackendMsg):
        for msg in msg.data:
            self._process_one_msg(msg)        # 递归拆 batch
    elif isinstance(msg, ExitMsg):
        raise KeyboardInterrupt
    elif isinstance(msg, UserMsg):
        # 截断到 max_seq_len, 把 UserMsg 包成 PendingReq
        self.prefill_manager.add_one_req(msg)
    elif isinstance(msg, AbortBackendMsg):
        req_to_free = self.prefill_manager.abort_req(msg.uid)
        req_to_free = req_to_free or self.decode_manager.abort_req(msg.uid)
        if req_to_free:
            self._free_req_resources(req_to_free)

注意 abort 会同时尝试在 prefill 和 decode 队列里找——因为请求生命周期跨两个状态机。

Step 2 · 选 batch（_schedule_next_batch）

源码：scheduler.py:219-225

def _schedule_next_batch(self) -> ForwardInput | None:
    # TODO: support other policies: e.g. DECODE first
    batch = (
        self.prefill_manager.schedule_next_batch(self.prefill_budget)
        or self.decode_manager.schedule_next_batch()
    )
    return self._prepare_batch(batch) if batch else None
"Prefill-first" 策略：每次先尝试组一个 prefill batch，组不出来才走 decode。这是经典 SGLang 风格——优先消化新请求，让 TTFT 更稳定。代码里 TODO 说将来可能支持 "decode first"。

Step 3 · 准备 batch（_prepare_batch）

源码：scheduler.py:204-217

def _prepare_batch(self, batch) -> ForwardInput:
    self.engine.graph_runner.pad_batch(batch)         # 对齐 CUDA Graph 粒度
    self.cache_manager.allocate_paged(batch.reqs)    # 给本次 forward 分配 KV 物理页
    batch.positions = _make_positions(batch, self.device)
    input_mapping = _make_input_tuple(batch, self.device)
    write_mapping = _make_write_tuple(batch, self.device)
    batch.out_loc = self.engine.page_table[input_mapping]
    self.engine.attn_backend.prepare_metadata(batch)
    return ForwardInput(
        batch=batch,
        sample_args=self.engine.sampler.prepare(batch),
        input_tuple=input_mapping,
        write_tuple=write_mapping,
    )

这里发生了所有"为 GPU 算前最后一公里"的元数据制作：positions tensor、input mapping、写回位置、attention metadata、sampling 参数张量化。

Step 4 · 处理上批结果（_process_last_data）

源码：scheduler.py:138-167

def _process_last_data(self, last_data):
    if last_data is None: return
    batch, (_, next_tokens_cpu, copy_done) = last_data[0].batch, last_data[1]
    copy_done.synchronize()                       # 等 D2H copy 完
    with self.cache_manager.lazy_free_region():    # 批量释放页
        for i, req in enumerate(batch.reqs):
            if isinstance(req, ChunkedReq): continue  # 没采样, 跳过
            next_token = next_tokens_cpu[i]
            req.append_host(next_token.unsqueeze(0))
            finished = not req.can_decode or next_token == eos
            reply.append(DetokenizeMsg(req.uid, next_token, finished))
            if finished:
                self.decode_manager.remove_req(req)
                self._free_req_resources(req)
            elif batch.is_prefill:
                self.cache_manager.cache_req(req, finished=False)
    self.send_result(reply)

注意 prefill 完成后才 cache_req(finished=False) 把这段插入 Radix Tree——这是后续请求能享受 prefix cache 的关键。

overlap_loop vs normal_loop 的差异

维度normal_loopoverlap_loop
CUDA stream仅 engine.streamscheduler.stream + engine.stream
函数签名() → None(last_data) → next_data
处理顺序收 → 调度 → forward → 处理收 → 调度 → launch forward → 同时处理 last
开关MINISGL_DISABLE_OVERLAP_SCHEDULING=1默认
开销隐藏无CPU 调度延迟被 GPU forward 时间吃掉

五、PrefillManager · 最复杂的子模块

它要同时回答 4 个问题：

  1. 排队的 PendingReq 谁能进本批？（容量约束）
  2. 这个 req 的前缀有多少能从 Radix Cache 直接复用？
  3. 剩下要算的 token 装得下吗？要不要切 chunk？
  4. chunk 后下一次怎么"接续"——上次的 KV 别再算第二遍。

PrefillAdder · 装箱器

源码：prefill.py:32-113

@dataclass
class PrefillAdder:
    token_budget: int       # 本批最大 token 数
    reserved_size: int      # 已为 inflight decode 预留的空间
    cache_manager: CacheManager
    table_manager: TableManager

    def _try_allocate_one(self, req):
        if self.table_manager.available_size == 0:
            return None                  # 槽位耗尽
        handle = self.cache_manager.match_req(req).cuda_handle
        cached_len = handle.cached_len
        extend_len = req.input_len - cached_len
        estimated_len = extend_len + req.output_len   # 估计这个 req 总共要占多少

        if estimated_len + self.reserved_size > self.cache_manager.available_size:
            return None                  # 装不下，放弃
        self.cache_manager.lock(handle)        # 锁住命中的前缀
        if estimated_len + self.reserved_size > self.cache_manager.available_size:
            return self.cache_manager.unlock(handle)  # 锁后再 check 一次

        table_idx = self.table_manager.allocate()
        if cached_len > 0:                          # 命中部分填回 token_pool / page_table
            ...
        return handle, table_idx

chunked vs full prefill

源码：prefill.py:65-90

def _add_one_req(self, pending_req, cache_handle, table_idx, cached_len):
    remain_len = pending_req.input_len - cached_len
    chunk_size = min(self.token_budget, remain_len)
    is_chunked = chunk_size < remain_len
    CLS = ChunkedReq if is_chunked else Req
    self.token_budget -= chunk_size
    self.reserved_size += remain_len + pending_req.output_len
    # 把当前 chunk 的 token id 拷到 device token_pool
    _slice = slice(cached_len, cached_len + chunk_size)
    device_ids = self.table_manager.token_pool[table_idx, _slice]
    device_ids.copy_(pending_req.input_ids[_slice].pin_memory(), non_blocking=True)
    return CLS(
        input_ids=pending_req.input_ids[: cached_len + chunk_size],
        table_idx=table_idx, cached_len=cached_len, ...
    )
ChunkedReq 的特殊性：它继承 Req 但 can_decode = False，append_host 抛异常——确保它不会被采样、不会进 decode 队列。下一轮 schedule 时会作为"已存在 chunk"继续推进。

schedule_next_batch · 串起 PrefillAdder

源码：prefill.py:126-151

def schedule_next_batch(self, prefill_budget):
    if len(self.pending_list) == 0:
        return None
    adder = PrefillAdder(
        token_budget=prefill_budget,
        reserved_size=self.decode_manager.inflight_tokens,  # 给 decode 让位
        cache_manager=self.cache_manager,
        table_manager=self.table_manager,
    )
    reqs, chunked_list = [], []
    for pending_req in self.pending_list:
        if req := adder.try_add_one(pending_req):
            pending_req.chunked_req = None
            if isinstance(req, ChunkedReq):
                pending_req.chunked_req = req           # 记下来下次接续
                chunked_list.append(pending_req)
            reqs.append(req)
        else:
            break                                       # 装不下了，停
    if len(reqs) == 0: return None
    self.pending_list = chunked_list + self.pending_list[len(reqs):]  # 未完 chunk 排首位
    return Batch(reqs=reqs, phase="prefill")
极易看漏的细节：
  • reserved_size = decode_manager.inflight_tokens——为正在 decode 的请求预留显存，避免 prefill 把 KV 池吃光导致 decode 之后 OOM。
  • self.pending_list = chunked_list + self.pending_list[len(reqs):]——已被切 chunk 的请求，下一轮调度优先尝试，避免被新来的请求抢占。

六、DecodeManager · 最简单也最关键

源码：decode.py 全文（仅 40 行）

@dataclass
class DecodeManager:
    page_size: int
    running_reqs: Set[Req] = field(default_factory=set)

    def filter_reqs(self, reqs):    # 每次 forward 后被调用
        self.running_reqs = {r for r in self.running_reqs.union(reqs) if r.can_decode}

    @property
    def inflight_tokens(self) -> int:
        tokens_reserved = (self.page_size - 1) * len(self.running_reqs)  # 每 req 预留 1 page
        return sum(r.remain_len for r in self.running_reqs) + tokens_reserved

    def schedule_next_batch(self):
        if not self.runnable: return None
        return Batch(reqs=list(self.running_reqs), phase="decode")
关键设计：
  • running_reqs 是 Set——同一个 req 不会进两次。
  • filter_reqs(reqs) 在每次 forward 之后被 scheduler._forward 调用，把 prefill 完成、可以 decode 的 req 加进来。
  • inflight_tokens 是 prefill 的"让位计算"——它估计这些 decode req 还会消耗多少 KV，为它们留好。
  • schedule_next_batch 简单粗暴：所有 running_reqs 一锅端，没有 batch size 上限（上限由 cuda_graph_max_bs / max_running_req 间接控制）。

七、CacheManager · KV 物理页 + Radix 桥接

它是"物理页池 + 前缀树" 的结合层。Engine 提供 page_table 和 num_pages，CacheManager 负责：

  • 用 free_slots（一个 GPU 上的 int32 tensor）维护空闲页号
  • 用 prefix_cache（RadixPrefixCache）维护可复用前缀
  • 把"按页分配"和"按 token 写 page_table"两个粒度桥接起来

关键函数地图

函数作用被谁调用
match_req(req)用 input_ids[:-1] 走 Radix tree，返回 MatchResultPrefillAdder._try_allocate_one
lock / unlock(handle)调 RadixPrefixCache.lock_handle 加 ref_countPrefillAdder · cache_req
allocate_paged(reqs)批量为 batch 中所有 req 分配它们 forward 缺的页scheduler._prepare_batch
cache_req(req, finished)把 req.cached_len 内的 KV 插入 Radix tree，并释放冗余页scheduler._process_last_data
lazy_free_region()contextmanager: 批量收集要 free 的页，退出时一次性 catscheduler._process_last_data
_allocate(n)从 free_slots 切，不够就调 evictallocate_paged

cache_req 的"五段式注释"——必读

# ==================================== valid cache region ====================================
# [0, req.cached_len)                       This part is valid for attention kernel read/write.
# [0, old_handle.cached_len)                This part is in the prefix cache before prefill.
# [old_handle.cached_len, req.cached_len)   This part is allocated by cache manager for this request.
# ================================== allocated cache region ==================================
# [old_handle.cached_len, cached_len)       This part was not in the prefix cache when prefill,
#                                           but later cached by other requests.
#                                           We must free them to avoid memory leak.
# [cached_len, new_handle.cached_len)       This part is newly inserted into the prefix cache.
# [new_handle.cached_len, req.cached_len)   This part is tailing part that can not inserted into
#                                           the prefix cache.
#                                           We should free it if the request has finished.
这是整个 cache 模块最难的地方——共有 4 个长度量、3 段区间，且涉及"另一个请求并发插入了同样前缀"的竞争场景。建议把这段注释打印出来贴显示器旁。

八、TableManager · 简单但必要

源码：table.py 全文（22 行）

class TableManager:
    def __init__(self, max_running_reqs, page_table):
        self._free_slots = list(range(max_running_reqs))
        self.page_table = page_table       # [max_running_req+1, max_seq_len], int32
        self.token_pool = torch.zeros_like(page_table, dtype=torch.int32)

    def allocate(self) -> int:
        return self._free_slots.pop()

    def free(self, slot):
        self._free_slots.append(slot)

它是请求 ID（table_idx）的发号器。 max_running_req 决定了系统能同时容纳多少 active req。page_table 和 token_pool 都按 [max_running_req+1, max_seq_len] 形状预分配——多出的 1 行给 dummy_req（CUDA Graph padding 用）。

九、SchedulerIOMixin · 单卡/多卡的 ZMQ 抽象

源码：io.py

这一层把"是否 TP > 1"的复杂性封装在一个 mixin 里。Scheduler 只调 self.receive_msg(blocking)，背后实际行为根据 rank 而不同：

场景receive_msg 实际指向行为
TP=1_recv_msg_single_rank直接从 tokenizer 拉
TP>1, rank==0_recv_msg_multi_rank0从 tokenizer 拉 → 用 PUB 广播给其他 rank → broadcast 数量到 GLOO
TP>1, rank>0_recv_msg_multi_rank1从 GLOO 收 broadcast 长度 → 从 SUB 收对应数量消息
为什么要用 GLOO 同步消息数量？ ZMQ PUB/SUB 是"send-and-forget"的，没法保证非 rank0 的 SUB 一定能在某个时刻收到 N 条消息。所以 rank0 先用 GLOO process group broadcast 一个 int32 告诉其他 rank "我刚 PUB 了 N 条"，其他 rank 才知道循环 N 次接收。这是显式 control sync，避免分布式调度状态不一致。 
def _recv_msg_multi_rank0(self, blocking):
    # ... 收 + broadcast PUB ...
    src_tensor = torch.tensor(len(pending_raw_msgs))
    self.tp_cpu_group.broadcast(src_tensor, root=0).wait()  # GLOO!
    for raw in pending_raw_msgs:
        self._send_into_ranks.put_raw(raw)
        pending_msgs.append(self._recv_from_tokenizer.decode(raw))
    return pending_msgs

第四遍 · 对比 SGLang 主线

带着 mini-sglang 的脑图回去看：

  • SGLang 的 SchedulePolicy、RadixCache、PrefillAdder 是同一套
  • SGLang 多了：speculative decoding、grammar、constrained decoding、host KV
  • 这些都是 mini-sglang 故意省掉的——读完它你能知道"哪些是必须的、哪些是高级特性"
读完后你应该能回答：
  1. 为什么 prefill 和 decode 不能混进同一个 batch？(attn metadata 不兼容)
  2. 为什么 prefill 之后 cache_req(finished=False) 就行，不需要立刻 evict？(ref_count 锁住了)
