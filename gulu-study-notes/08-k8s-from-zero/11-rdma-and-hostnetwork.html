§0为什么 NCCL 多机推理要绕过 K8S 网络栈

NCCL all-reduce 对网络的要求

多机推理（Tensor Parallelism / Pipeline Parallelism）的核心通信原语是 all-reduce：每张 GPU 需要把梯度/激活值同步给所有其他 GPU。对网络的要求极其苛刻：

  • 带宽：8 卡 A100/H100 节点间通信量 = 模型隐藏层大小 × 2 × (N-1)/N，Qwen3-72B TP=8 每次 all-reduce ~1.2GB 数据
  • 延迟：每个 Transformer 层都有一次 all-reduce，延迟直接叠加到推理延迟上（200 层 × 5us = 1ms 额外 per token）
  • 抖动：NCCL 同步操作是阻塞的，任何一台机器慢了所有人都得等

普通 CNI 的瓶颈

为什么 Overlay CNI 对 NCCL 完全不够用？
NCCL 需要的是 GPU 显存到远端 GPU 显存的直达通道。Overlay 网络的每个包都要经过：用户态拷贝 → 内核协议栈 → veth → VXLAN 封装 → 物理网卡。这条路径上有 2-3 次内存拷贝、大量 CPU 中断处理，带宽上不去、延迟压不下、还占用宝贵的 CPU 资源。

目标：接近裸机的网络性能

方案带宽延迟CPU 开销复杂度
Overlay CNI (VXLAN)~25 Gbps~50 us高（内核协议栈）低
hostNetwork~100 Gbps~20 us中（仍走内核）低
RDMA (RoCE v2)~200 Gbps~2 us极低（绕过内核）中
RDMA (InfiniBand NDR)~400 Gbps~1 us极低高
SR-IOV + RDMA~400 Gbps~1.5 us极低中高

§1hostNetwork 模式 · 最简单的零开销方案

什么是 hostNetwork

设置 spec.hostNetwork: true 后，Pod 直接使用宿主机的网络命名空间——不创建独立的 network namespace，不走 CNI 插件，不经过 veth pair。Pod 看到的网卡、IP、端口就是节点本身的。

效果

  • Pod IP = Node IP：Pod 不再有独立的 cluster IP
  • 零网络开销：数据直接走宿主机网络栈，没有 Overlay 封装
  • 直接访问宿主机网卡：Pod 内可以直接看到 eth0、ib0 等物理网卡
  • 不经过 Service 网络：kube-proxy 的 iptables/IPVS 规则对 hostNetwork Pod 无效

优缺点

优点

  • 配置极简，一行搞定
  • 性能接近裸机（仍走内核但无 Overlay）
  • NCCL 可直接使用宿主机 IB/RoCE 网卡
  • 无需额外安装 CNI 插件或 device plugin

缺点

  • 端口冲突：同节点多个 Pod 不能用同一端口
  • 安全隔离差：Pod 可看到所有网卡、所有端口
  • 不走 Service：无法通过 ClusterIP/NodePort 路由
  • 调度约束：通常需要 1 Pod / Node（推理场景正好）

YAML 示例：多机推理 Pod 配置

apiVersion: v1
kind: Pod
metadata:
  name: sglang-worker-0
  labels:
    app: sglang-inference
spec:
  hostNetwork: true          # 使用宿主机网络命名空间
  dnsPolicy: ClusterFirstWithHostNet  # hostNetwork 时必须显式设置 DNS 策略
  containers:
  - name: sglang
    image: lmsysorg/sglang:latest
    ports:
    - containerPort: 30000    # 直接占用宿主机 30000 端口
      hostPort: 30000
    env:
    # 告诉 NCCL 用哪张网卡做 Socket 通信
    - name: NCCL_SOCKET_IFNAME
      value: "eth0"           # 管理网网卡名，用于 NCCL 初始化握手
    # 如果节点有 IB/RoCE 网卡，NCCL 会自动发现并使用
    - name: NCCL_IB_DISABLE
      value: "0"              # 0=启用 IB（默认）
    resources:
      limits:
        nvidia.com/gpu: "8"
  nodeSelector:
    nvidia.com/gpu.product: "NVIDIA-H100-80GB-HBM3"
NCCL_SOCKET_IFNAME 的重要性：NCCL 初始化时需要通过 TCP Socket 交换各节点的 IB/RoCE 地址。如果不指定 NCCL_SOCKET_IFNAME，NCCL 可能选到一个 Pod 间不互通的网卡（如 lo），导致初始化卡住。hostNetwork 模式下通常设为 eth0 或 bond0。
实战锚点
LWS 多机推理 Pod 用 hostNetwork: true + NCCL_SOCKET_IFNAME=eth0。这是当前最主流、最稳定的多机推理网络配置。IB/RoCE 网卡由 NCCL 自动发现，Socket 只用来做初始化握手，不走数据面。

§2RDMA 基础 · 绕过内核直达远端内存

什么是 RDMA（Remote Direct Memory Access）

RDMA 允许应用程序直接读写远端机器的内存，整个过程不经过操作系统内核：

  • 无内核参与：数据在网卡硬件层面完成传输，CPU 不做任何拷贝
  • 零拷贝：数据从 GPU 显存 → 本地网卡 → 网络 → 远端网卡 → 远端 GPU 显存（GDR：GPU Direct RDMA）
  • 极低延迟：1-2 微秒（TCP 的 1/25）
  • 极低 CPU 开销：CPU 只负责发起请求，不参与数据传输

TCP vs RDMA 数据路径对比

两种 RDMA 实现

技术传输介质带宽部署要求成本
InfiniBand (IB) 专用 IB 网络 NDR 400Gbps / HDR 200Gbps 专用交换机 + IB 网卡（HCA） 高
RoCE v2 (RDMA over Converged Ethernet) 普通以太网 100/200/400 Gbps 支持 PFC 的以太网交换机 + RDMA 网卡 中
云厂商现状：腾讯云 GPU 集群（CVM GN 系列、TACO 训推集群）主要使用 RoCE v2（基于 Mellanox ConnectX-6/7 网卡）。IB 通常在自建 IDC 的超大规模训练集群中使用。两者在 NCCL 层面的 API 完全一致，差别主要在交换网络。

K8S 中使用 RDMA 的前提

  • 硬件：节点上有 RDMA 网卡（如 Mellanox ConnectX-6 Dx），且驱动已加载（mlx5_core）
  • 内核模块：ib_core、rdma_ucm、ib_uverbs 等已加载
  • 设备暴露：通过 rdma-shared-device-plugin 或 k8s-rdma-shared-dev-plugin 将 RDMA 设备注册为 K8S extended resource
  • 容器挂载：Pod 需要挂载 /dev/infiniband/ 设备文件
# Pod 请求 RDMA 设备
resources:
  limits:
    nvidia.com/gpu: "8"
    rdma/hca_shared_devices_a: "1"  # 请求一个 RDMA 共享设备

§3SR-IOV · 网卡虚拟化直通

什么是 SR-IOV

SR-IOV（Single Root I/O Virtualization）允许一块物理网卡在硬件层面切分成多个"虚拟网卡"——每个虚拟网卡（VF）可以直通分配给一个 Pod，绕过宿主机内核。

  • PF（Physical Function）：物理网卡本身，具备完整管理能力
  • VF（Virtual Function）：从 PF 切出的轻量虚拟设备，只有数据通路能力
  • 每个 VF 直通给一个 Pod → Pod 内应用直接操作网卡硬件 → 性能接近裸机

SR-IOV 架构图

sriov-network-operator 自动化管理

手动管理 VF 创建和绑定很复杂。sriov-network-operator 提供了声明式的自动化：

# 1. 定义 SR-IOV 网络策略（创建 VF）
apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetworkNodePolicy
metadata:
  name: rdma-policy
  namespace: sriov-network-operator
spec:
  nodeSelector:
    feature.node.kubernetes.io/rdma: "true"
  resourceName: rdma_vf          # 注册的 K8S resource 名
  numVfs: 8                      # 每块网卡切出 8 个 VF
  nicSelector:
    vendor: "15b3"               # Mellanox 厂商 ID
    pfNames: ["ens4f0"]          # 物理网卡名
  deviceType: netdevice           # netdevice=内核驱动 / vfio-pci=DPDK
  isRdma: true                   # 启用 RDMA 能力

---
# 2. 定义 SR-IOV 网络（Pod 挂载入口）
apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetwork
metadata:
  name: rdma-network
  namespace: sriov-network-operator
spec:
  resourceName: rdma_vf
  networkNamespace: inference     # Pod 所在 namespace
  ipam: '{"type": "host-local", "subnet": "192.168.100.0/24"}'

性能特点

  • 接近裸机：VF 直通意味着 Pod 直接操作网卡硬件，没有额外 CPU 开销
  • 硬件隔离：每个 VF 有独立的收发队列，Pod 间流量互不干扰
  • RDMA 支持：配合 isRdma: true，VF 继承 PF 的 RDMA 能力
  • 多 Pod 共享：一块 400G 网卡可以切出 8-128 个 VF，适合多任务场景
SR-IOV vs hostNetwork：hostNetwork 简单但是"全或无"——Pod 拿到整个宿主机网络。SR-IOV 更精细：每个 Pod 只拿到一个 VF，保持了网络隔离的同时获得裸机性能。对于单节点跑多个推理服务的场景，SR-IOV 更合适。

§4Multus CNI · 一个 Pod 多张网卡

为什么需要多网卡

多机推理的 Pod 同时有两种网络需求：

  • 管理网：被 Service/Ingress 路由、健康检查、日志采集、kubectl exec → 走默认 CNI（Calico/Cilium）
  • 数据网：NCCL all-reduce 通信 → 走 RDMA/SR-IOV 高速网络

Multus CNI 是一个"CNI 的 CNI"——它允许一个 Pod 同时挂载多个网络接口，每个接口由不同的 CNI 插件管理。

架构

NetworkAttachmentDefinition 配置

# 定义一个额外的 RDMA 网络
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: rdma-net
  namespace: inference
spec:
  config: |
    {
      "cniVersion": "0.3.1",
      "type": "sriov",              // 底层使用 SR-IOV CNI
      "name": "rdma-network",
      "ipam": {
        "type": "host-local",
        "subnet": "192.168.100.0/24",
        "rangeStart": "192.168.100.10",
        "rangeEnd": "192.168.100.250"
      }
    }

Pod 使用多网卡

apiVersion: v1
kind: Pod
metadata:
  name: sglang-worker-0
  annotations:
    k8s.v1.cni.cncf.io/networks: rdma-net  # 挂载额外网络
spec:
  containers:
  - name: sglang
    image: lmsysorg/sglang:latest
    env:
    - name: NCCL_SOCKET_IFNAME
      value: "eth0"               # 管理网（默认 CNI）用于握手
    - name: NCCL_IB_HCA
      value: "mlx5_2"            # 指定 RDMA 数据网卡
    resources:
      limits:
        nvidia.com/gpu: "8"
        rdma/rdma_vf: "1"         # 请求一个 SR-IOV VF
Multus 的代价：额外的复杂度。需要部署 Multus DaemonSet、维护 NetworkAttachmentDefinition、处理多网卡的路由表。如果你的场景是"每个节点只跑一个推理任务"，hostNetwork 可能是更务实的选择。Multus 更适合"单节点多任务 + 需要网络隔离"的场景。

§5LWS 多机推理的网络配置实践

LeaderWorkerSet 的 Pod 间通信需求

LWS 部署多机推理时（如 2 节点 16 卡 TP=16），Pod 之间有两种通信：

  • 控制面通信：Leader 与 Worker 的健康检查、任务分发（走普通网络即可）
  • 数据面通信：NCCL all-reduce / all-gather（必须走高速网络，对带宽和延迟极度敏感）

推荐配置：hostNetwork + IB/RoCE

apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata:
  name: sglang-multi-node
  namespace: inference
spec:
  replicas: 1                         # 1 个推理实例（跨 2 台机器）
  leaderWorkerTemplate:
    size: 2                           # 2 个 Pod（1 leader + 1 worker）
    leaderTemplate:
      metadata:
        labels:
          role: leader
      spec:
        hostNetwork: true
        dnsPolicy: ClusterFirstWithHostNet
        terminationGracePeriodSeconds: 90
        containers:
        - name: sglang
          image: lmsysorg/sglang:latest
          command: ["python3", "-m", "sglang.launch_server"]
          args:
          - "--model-path=/models/qwen3-72b"
          - "--tp=16"
          - "--nnodes=2"
          - "--node-rank=0"
          - "--nccl-init-addr=$(LWS_LEADER_ADDRESS):29500"
          env:
          # ===== NCCL 网络配置 =====
          - name: NCCL_SOCKET_IFNAME
            value: "eth0"             # TCP 握手用管理网
          - name: NCCL_IB_DISABLE
            value: "0"                # 启用 InfiniBand/RoCE
          - name: NCCL_NET_GDR_LEVEL
            value: "5"                # GPU Direct RDMA 级别（5=最大）
          - name: NCCL_P2P_LEVEL
            value: "5"                # P2P 通信级别
          - name: NCCL_IB_HCA
            value: "mlx5"             # IB 设备名前缀
          - name: NCCL_IB_GID_INDEX
            value: "3"                # RoCE v2 GID 索引
          # ===== LWS 自动注入的变量 =====
          - name: LWS_LEADER_ADDRESS
            valueFrom:
              fieldRef:
                fieldPath: metadata.annotations['leaderworkerset.sigs.k8s.io/leader-address']
          ports:
          - containerPort: 30000      # 推理服务端口
          - containerPort: 29500      # NCCL init 端口
          resources:
            limits:
              nvidia.com/gpu: "8"
          startupProbe:
            httpGet:
              path: /health
              port: 30000
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 30      # 最多等 330s（模型加载+NCCL init）
    workerTemplate:
      spec:
        hostNetwork: true
        dnsPolicy: ClusterFirstWithHostNet
        containers:
        - name: sglang
          image: lmsysorg/sglang:latest
          command: ["python3", "-m", "sglang.launch_server"]
          args:
          - "--model-path=/models/qwen3-72b"
          - "--tp=16"
          - "--nnodes=2"
          - "--node-rank=1"
          - "--nccl-init-addr=$(LWS_LEADER_ADDRESS):29500"
          env:
          - name: NCCL_SOCKET_IFNAME
            value: "eth0"
          - name: NCCL_IB_DISABLE
            value: "0"
          - name: NCCL_NET_GDR_LEVEL
            value: "5"
          - name: NCCL_P2P_LEVEL
            value: "5"
          - name: NCCL_IB_HCA
            value: "mlx5"
          - name: NCCL_IB_GID_INDEX
            value: "3"
          - name: LWS_LEADER_ADDRESS
            valueFrom:
              fieldRef:
                fieldPath: metadata.annotations['leaderworkerset.sigs.k8s.io/leader-address']
          resources:
            limits:
              nvidia.com/gpu: "8"

NCCL 环境变量详解

变量值含义
NCCL_SOCKET_IFNAMEeth0TCP Socket 通信使用的网卡（仅用于 NCCL 初始化握手）
NCCL_IB_DISABLE00=启用 IB/RoCE，1=禁用（降级到 TCP Socket）
NCCL_NET_GDR_LEVEL5GPU Direct RDMA 级别。5=跨 PCIe switch 也允许 GDR
NCCL_P2P_LEVEL5同节点 GPU 间 P2P 通信级别。5=允许跨 NUMA
NCCL_IB_HCAmlx5选择哪些 IB 设备参与通信（前缀匹配）
NCCL_IB_GID_INDEX3RoCE v2 使用的 GID 索引（通常 3 = IPv4 RoCE v2）
NCCL_DEBUGINFO/WARN调试时设为 INFO 可以看到 NCCL 选择了哪条通信路径

排障：nccl-tests 验证带宽

# 在两个节点上运行 nccl-tests 的 all_reduce_perf
# Node 0（Leader）:
$ mpirun -np 16 --hostfile hostfile \

    -x NCCL_IB_DISABLE=0 \

常见排障场景：
  • NCCL 卡住不动：通常是 NCCL_SOCKET_IFNAME 选了错误的网卡，或节点间 TCP 29500 端口不通
  • busbw 只有 20-30 Gbps：NCCL 降级到了 TCP Socket 通信。检查 NCCL_DEBUG=INFO 日志中是否出现 "NET/IB" 还是 "NET/Socket"
  • "No IB device found"：Pod 内看不到 RDMA 设备。检查 device-plugin 是否正常、/dev/infiniband/ 是否挂载
  • GDR 没启用：日志显示 "GPU Direct RDMA Disabled"。检查 nvidia-peermem 模块是否加载
实战锚点
调试 NCCL 网络问题的标准步骤：① 设置 NCCL_DEBUG=INFO 看日志 → ② 确认 "NET/IB" 出现（而非 "NET/Socket"） → ③ 跑 all_reduce_perf 确认 busbw → ④ 对比理论带宽判断是否正常。如果一切正确但推理延迟仍高，问题可能在 GPU 拓扑（NUMA affinity）而非网络。

§6带走这些

① 核心矛盾
NCCL 需要 400Gbps/1us 的网络，Overlay CNI 只能给 25Gbps/50us——差 16 倍带宽、50 倍延迟
② hostNetwork
最简单的方案：Pod 直接用宿主机网络。零开销，但牺牲隔离性。适合"一节点一任务"的推理场景
③ RDMA
应用直接读写远端内存，绕过 CPU 和内核。IB (400G) 或 RoCE v2 (200G) 是多机推理的性能保障
④ SR-IOV
网卡硬件切 VF 直通给 Pod，隔离+高性能兼得。适合单节点多任务场景
⑤ Multus CNI
一个 Pod 两张网卡：管理网走 Calico + 数据网走 RDMA/SR-IOV。最灵活但最复杂
⑥ 实战选择
多机推理首选 hostNetwork + NCCL 自动发现 IB/RoCE。有隔离需求时升级到 SR-IOV + Multus
