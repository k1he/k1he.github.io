§0为什么推理服务的可观测性特别重要

推理服务和传统 Web 服务的可观测性需求差异巨大：

维度传统 Web 服务LLM 推理服务
核心资源CPU / 内存（便宜）GPU 显存 + 算力（一张 A100 = ~15 元/小时）
延迟特征毫秒级，分布均匀秒级，长尾严重（同模型短 prompt 0.5s，长 prompt 30s）
资源浪费信号CPU idle 高 = 浪费GPU 利用率低 + 队列深 = batching/调度有问题
故障隐蔽性500 错误立刻可见KV Cache 溢出→截断输出，用户感知慢
成本敏感度中等极高——8×A100 闲置一天 = ~2880 元浪费
经典陷阱：Dashboard 显示 GPU Utilization = 80%，你觉得"挺好的"。但一看 waiting_queue_length = 47，TTFT P99 = 12s。原因：continuous batching 的 max_batch_size 设太小，GPU 在做小 batch 低效计算，大量请求排队等待。没有应用层指标，你永远发现不了这个问题。

可观测性三支柱

  • Metrics（指标）：数值型、可聚合、支持告警和 Dashboard —— "正在发生什么"
  • Logs（日志）：事件流、细节丰富、适合 debug —— "为什么发生"
  • Events（事件）：K8S 内建的状态变更记录 —— "集群里出了什么事"
推理服务场景下，Metrics 是最核心的支柱——因为你需要实时看到延迟分布和队列状态才能做扩缩容决策。Logs 用于事后排查细节，Events 用于定位 K8S 层面的编排问题。

§1监控三层模型

推理服务的监控必须覆盖三层，任何一层缺失都会让排障变成盲人摸象：

基础设施层：DCGM-exporter

NVIDIA DCGM (Data Center GPU Manager) Exporter 以 DaemonSet 形式部署在每个 GPU 节点上，采集 GPU 硬件指标并暴露给 Prometheus。

DCGM 指标名含义告警阈值建议
DCGM_FI_DEV_GPU_UTILGPU SM（计算单元）利用率 %推理时持续 < 10% → 空跑告警
DCGM_FI_DEV_FB_USED帧缓冲区（显存）已使用量 MB> 总量 95% → OOM 预警
DCGM_FI_DEV_FB_FREE帧缓冲区剩余量 MB< 2GB → 紧急扩容/限流
DCGM_FI_DEV_GPU_TEMPGPU 核心温度 °C> 83°C → 即将触发降频
DCGM_FI_DEV_POWER_USAGE当前功耗 W接近 TDP → 功耗墙限频
DCGM_FI_DEV_ECC_DBE_VOL_TOTAL不可纠正 ECC 错误累计数> 0 → 需要下线检修

K8S 对象层：kube-state-metrics

kube-state-metrics 是一个只读服务，watch apiserver 的所有资源对象，将其状态转换为 Prometheus 格式指标：

指标名含义典型用途
kube_pod_status_phasePod 当前阶段统计 Pending/Failed Pod 数量
kube_pod_container_status_restarts_total容器累计重启次数检测 CrashLoopBackOff
kube_pod_container_resource_requests资源 requests 声明值对比实际用量，发现超配/欠配
kube_deployment_status_replicas_available可用副本数检测 rollout 卡住/副本不足
kube_node_status_condition节点状态条件检测 NotReady / DiskPressure

应用层：推理引擎内置 /metrics

SGLang / vLLM 等主流推理引擎内置了 Prometheus 格式的指标端点，暴露推理特有的业务指标：

指标类型含义健康范围
TTFT (Time To First Token)Histogram从收到请求到输出第一个 token 的延迟P99 < 2s
ITL (Inter-Token Latency)Histogram相邻两个输出 token 之间的间隔P99 < 100ms
Token ThroughputCounter单位时间内生成的 token 总数接近理论峰值
GPU UtilizationGaugeGPU SM 利用率推理繁忙时 60-90%
GPU Memory UsedGauge显存使用量< 总量 95%
Waiting Queue LengthGauge当前等待调度的请求数< 10（持续 > 50 需扩容）
Cache Hit RateGaugeRadixAttention 前缀缓存命中率> 60%（多轮对话场景）
实战锚点
排障时先看应用层：TTFT P99 暴涨了吗？队列积压了吗？确认问题存在后，再下钻到 K8S 层：Pod 在重启？副本不足？最后看基础设施层：GPU ECC 错误？温度降频？磁盘满？
口诀：自顶向下定位问题，自底向上确认根因。

§2Prometheus 生态

Pull 模型：Prometheus 主动拉 /metrics 端点

与 Push 模型（应用推送指标到监控中心）不同，Prometheus 采用 Pull 模型：由 Prometheus Server 定期 HTTP GET 每个目标的 /metrics 端点。

ServiceMonitor / PodMonitor：声明式配置抓取目标

在 Prometheus Operator 体系下，不需要手动编辑 prometheus.yml。通过 CRD 声明"谁需要被抓取"：

# ServiceMonitor：通过 Service 发现 Pod 的 /metrics 端点
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: sglang-inference-monitor
  namespace: inference
  labels:
    release: prometheus             # 必须匹配 Prometheus 实例的 serviceMonitorSelector
spec:
  selector:
    matchLabels:
      app: sglang                  # 匹配目标 Service 的 label
  endpoints:
  - port: metrics                 # Service spec.ports 中定义的 port name
    path: /metrics                # 端点路径
    interval: 15s                 # 抓取间隔，推理服务建议 15s
    scrapeTimeout: 10s            # 单次抓取超时
  namespaceSelector:
    matchNames:
    - inference                     # 限定 namespace 范围

# PodMonitor：直接匹配 Pod（适合 DaemonSet 场景，如 DCGM-exporter）
apiVersion: monitoring.coreos.com/v1
kind: PodMonitor
metadata:
  name: dcgm-gpu-monitor
  namespace: monitoring
  labels:
    release: prometheus
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: dcgm-exporter
  podMetricsEndpoints:
  - port: metrics
    interval: 15s                 # GPU 指标建议 15s，默认 30s 太慢
  namespaceSelector:
    matchNames:
    - gpu-operator                  # DCGM-exporter 通常在 gpu-operator namespace

PromQL 常用查询示例

# ① TTFT P99（5 分钟窗口）
histogram_quantile(0.99,
  sum(rate(sglang_time_to_first_token_seconds_bucket[5m])) by (le, pod)
)

# ② ITL P50 和 P99 对比
histogram_quantile(0.50, sum(rate(sglang_inter_token_latency_seconds_bucket[5m])) by (le))
histogram_quantile(0.99, sum(rate(sglang_inter_token_latency_seconds_bucket[5m])) by (le))

# ③ 集群总 Token 吞吐量 (tokens/s)
sum(rate(sglang_generated_tokens_total[1m]))

# ④ 每个 Pod 的等待队列深度
sglang_waiting_queue_length{namespace="inference"}

# ⑤ GPU 利用率低但队列深 = batching 异常
DCGM_FI_DEV_GPU_UTIL{namespace="inference"} < 50
  and on(pod) sglang_waiting_queue_length > 20

# ⑥ GPU 显存使用率百分比
DCGM_FI_DEV_FB_USED / (DCGM_FI_DEV_FB_USED + DCGM_FI_DEV_FB_FREE) * 100

# ⑦ 容器内存使用接近 limit（OOM 预警）
container_memory_working_set_bytes{namespace="inference"}
  / on(pod,container) kube_pod_container_resource_limits{resource="memory"} > 0.9

# ⑧ 过去 1 小时 Pod 重启次数 > 3
increase(kube_pod_container_status_restarts_total{namespace="inference"}[1h]) > 3

Grafana 面板设计

推理服务 Dashboard 建议按以下行（Row）组织：

Row 1: 用户体验指标

  • TTFT P50 / P99 时间序列
  • ITL P50 / P99 时间序列
  • 请求成功率 / 错误率
  • QPS 趋势

Row 2: 引擎内部状态

  • Token throughput (tokens/s)
  • Waiting queue length
  • Running batch size
  • Prefix cache hit rate

Row 3: GPU 资源

  • GPU utilization %（per GPU）
  • GPU memory used/total（per GPU）
  • GPU temperature
  • GPU power usage

Row 4: K8S 状态

  • Pod 状态分布（Running/Pending/Failed）
  • 容器重启次数趋势
  • HPA 当前/期望副本数
  • 节点 CPU/Mem 剩余
反模式：高基数标签爆炸
不要把 user_id、session_id、prompt_hash 作为 Prometheus label——这会导致时间序列数量爆炸，TSDB 内存耗尽。规则：单个指标的 label 组合 < 1000 条时间序列。需要细粒度分析时用日志（ES/Loki），不用 metrics。
反模式：只看平均值
GPU 利用率"平均 50%"可能是"一半 GPU 跑满 + 一半 GPU 空转"。推理延迟"平均 1s"可能是"大部分 200ms + 少数 30s 长尾"。必须看分位数（P50/P95/P99）和 per-GPU 视图。
实战锚点
DCGM-exporter 默认采集周期是 30s。对推理服务建议改为 10-15s——GPU 利用率的突变（如 batch 切换、OOM）在 30s 间隔下会被平滑掉，你看不到尖刺。修改方式：Helm values 中设 serviceMonitor.interval: 15s，或在 DaemonSet 环境变量中设 DCGM_EXPORTER_INTERVAL=10000（毫秒）。

§3日志收集

日志收集架构

K8S 日志路径机制

# K8S 约定：容器的 stdout/stderr 被 containerd 写到固定路径
/var/log/pods/<namespace>_<pod-name>_<pod-uid>/<container-name>/0.log

# /var/log/containers/ 下是软链接（兼容旧工具）
/var/log/containers/sglang-0_inference_sglang-server-a1b2c3d4e5f6.log
  → /var/log/pods/inference_sglang-0_xxxx/sglang-server/0.log

# 日志格式（containerd 的 JSON 行格式）
{"log":"2026-05-08T10:30:00.123Z INFO  Model qwen3-72b loaded in 45.2s\n","stream":"stdout","time":"2026-05-08T10:30:00.123456789Z"}

# logrotate：默认 10MB/文件，保留 5 个旧文件，不会撑爆磁盘

结构化日志最佳实践

# 反模式：非结构化纯文本，海量日志中 grep 是噩梦
[2026-05-08 10:30:01] INFO: Request req-abc123 completed, TTFT=850ms, tokens=256, user=u789

# 正确：JSON 结构化日志，每个字段可被索引和聚合
{"ts":"2026-05-08T10:30:01Z","level":"info","msg":"request_complete",
 "request_id":"req-abc123","ttft_ms":850,"itl_ms":42,
 "prompt_tokens":1024,"output_tokens":256,
 "model":"qwen3-72b","cache_hit":true,"batch_size":8}
推理服务日志该记什么：
  • 必记：request_id, ttft_ms, itl_ms, prompt_tokens, output_tokens, error（如有）, status_code
  • 建议记：model_name, batch_size, cache_hit, gpu_id, queue_wait_ms
  • 禁止记：完整的 prompt/response 内容（合规风险 + 日志量爆炸 + 泄密风险）

kubectl logs 使用技巧

# 查看指定容器的日志
kubectl logs pod/sglang-0 -n inference -c sglang-server

# 查看上一次崩溃的容器日志（CrashLoopBackOff 排障第一步）
kubectl logs pod/sglang-0 -n inference --previous

# 只看最近 5 分钟的日志
kubectl logs pod/sglang-0 -n inference --since=5m

# 实时跟踪（等价于 tail -f）
kubectl logs pod/sglang-0 -n inference -f

# 只看最后 200 行
kubectl logs pod/sglang-0 -n inference --tail=200

# 按 label 查看所有匹配 Pod 的日志（多副本排查）
kubectl logs -l app=sglang -n inference --all-containers --max-log-requests=10

# 组合使用：看上次崩溃的最后 50 行
kubectl logs pod/sglang-0 -n inference --previous --tail=50
反模式：日志写到容器内文件
有些旧代码把日志写到 /app/logs/server.log 而不是 stdout。后果：① kubectl logs 看不到任何输出 ② DaemonSet Agent 无法自动收集 ③ 容器重启后日志丢失。
解法：优先改代码输出到 stdout；无法改代码时，加一个 sidecar 容器用 tail -F /app/logs/server.log 转到 stdout。
反模式：推理服务开 DEBUG 日志上生产
SGLang/vLLM 的 DEBUG 级别会打印每个 token 的调度决策——单 Pod 每秒可产生几百 KB 日志。大规模集群下日志 agent CPU 飙高、ES 写入积压。生产环境只开 INFO/WARNING，需要排查时临时调整单 Pod 的日志级别。

§4事件与排障

kubectl describe 的 Events 字段

K8S Events 是集群内建的短期事件记录（默认保留 1 小时）。每次调度、拉镜像、探针失败、OOM 都会产生 Event——是排障的第一手线索。

# 查看某个 Pod 的所有事件
$ kubectl describe pod sglang-0 -n inference

  Normal   Pulling           5m    kubelet            Pulling image "registry.example.com/sglang:v0.4.1"
  Normal   Pulled            3m    kubelet            Successfully pulled image in 120s
  Normal   Created           3m    kubelet            Created container sglang-server
  Normal   Started           3m    kubelet            Started container sglang-server
  Warning  Unhealthy         90s   kubelet            Readiness probe failed: HTTP probe failed with statuscode: 503
  Warning  Unhealthy         60s   kubelet            Readiness probe failed: HTTP probe failed with statuscode: 503
  Normal   Ready             30s   kubelet            Container became ready

全局事件查询

# 按时间排序查看所有事件（最常用）
kubectl get events -n inference --sort-by='.lastTimestamp'

# 只看 Warning 类型（过滤掉 Normal 噪音）
kubectl get events -n inference --field-selector type=Warning

# 实时 watch 新事件（排障时开着）
kubectl get events -n inference -w

# 查看某种原因的事件
kubectl get events -n inference --field-selector reason=OOMKilling

# 查看全集群的 FailedScheduling 事件
kubectl get events -A --field-selector reason=FailedScheduling --sort-by='.lastTimestamp'

排障决策树：Pod 不正常时的排查步骤

实战锚点

§5推理服务 SLI/SLO 设计

概念区分

术语定义谁负责示例
SLI
Service Level Indicator		量化衡量服务质量的指标SRE / 平台开发TTFT P99、成功率、错误率
SLO
Service Level Objective		SLI 的目标值SRE + 产品TTFT P99 < 2s、可用性 > 99.9%
SLA
Service Level Agreement		对外承诺 + 违约赔偿条款商务 + 法务可用性 < 99.9% 赔偿月费 10%

推理服务的 SLI 选择

延迟类 SLI

  • TTFT P99：首 token 延迟，用户"等了多久才看到第一个字"
  • ITL P99：token 间延迟，用户"输出是否流畅"
  • E2E Latency P99：完整请求端到端耗时

流式场景重 TTFT + ITL；批量场景重 E2E Latency

可用性 / 质量类 SLI

  • 成功率：非 5xx 响应的请求占比
  • 错误率：返回错误码的请求占比
  • 截断率：因 KV Cache 溢出/max_tokens 被截断的比例

注意：HTTP 200 但内容为空/被截断也算"质量问题"

SLO 示例

< 2s
TTFT P99
99% 请求首 token 延迟低于 2 秒
99.9%
月度可用性
每月最多允许 43 分钟不可用
< 0.1%
错误率
每千次请求最多 1 次 5xx 错误

Error Budget 概念

Error Budget = 1 - SLO。如果可用性 SLO 是 99.9%，那你每月有 0.1% = 43 分钟的"出错预算"。这个预算用来做发布、实验、容忍小故障。当 budget 消耗过快时——冻结变更，集中排查稳定性。

告警规则：PromQL 表达式示例

# PrometheusRule CRD：部署到 Prometheus Operator
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: inference-slo-alerts
  namespace: monitoring
  labels:
    release: prometheus             # 匹配 Prometheus 实例的 ruleSelector
spec:
  groups:
  - name: inference.slo.rules
    rules:

    # 告警 1：TTFT P99 超过 SLO 阈值
    - alert: InferenceTTFTP99High
      expr: |
        histogram_quantile(0.99,
          sum(rate(sglang_time_to_first_token_seconds_bucket{namespace="inference"}[5m])) by (le)
        ) > 2
      for: 3m                        # 持续 3 分钟才触发，避免瞬时毛刺
      labels:
        severity: critical
        team: inference-platform
      annotations:
        summary: "TTFT P99 超过 SLO 2s（当前: {{ $value | humanizeDuration }}）"
        runbook: "https://wiki/runbook/inference-high-ttft"
        action: "① 查 waiting_queue_length ② 考虑 HPA 扩容 ③ 查 GPU util"

    # 告警 2：等待队列持续积压 → 需要扩容
    - alert: InferenceQueueBacklog
      expr: sglang_waiting_queue_length{namespace="inference"} > 50
      for: 2m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.pod }} 队列积压 {{ $value }} 个请求"

    # 告警 3：GPU 显存即将耗尽 → OOM 风险
    - alert: GPUMemoryNearlyFull
      expr: |
        DCGM_FI_DEV_FB_USED /
        (DCGM_FI_DEV_FB_USED + DCGM_FI_DEV_FB_FREE) * 100 > 95
      for: 1m
      labels:
        severity: critical
      annotations:
        summary: "GPU {{ $labels.gpu }} on {{ $labels.node }} 显存超 95%"

    # 告警 4：Pod 频繁重启
    - alert: InferencePodCrashLooping
      expr: |
        increase(kube_pod_container_status_restarts_total{
          namespace="inference", container="sglang-server"
        }[1h]) > 3
      for: 0m                        # 立即触发
      labels:
        severity: critical
      annotations:
        summary: "{{ $labels.pod }} 1h 内重启 {{ $value }} 次"

    # 告警 5：可用性低于 SLO
    - alert: InferenceAvailabilityBreach
      expr: |
        (
          sum(rate(sglang_requests_total{status=~"2.."}[5m]))
          / sum(rate(sglang_requests_total[5m]))
        ) < 0.999
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "可用性低于 99.9% SLO（当前: {{ $value | humanizePercentage }}）"
实战锚点 · 设计推理服务 SLI/SLO

三条设计原则：

  • 面向用户体验选 SLI：TTFT 比 GPU Util 更重要。GPU 跑满但用户等 10 秒才看到第一个字 = 服务质量差。
  • 用 Error Budget 管理变更节奏：budget 充足时大胆迭代；budget 告急时冻结发布、集中修复。
  • 告警必须 actionable：每条告警的 annotation 里写清楚"该做什么"（runbook URL）。一天收 200 条没人能处理的告警 = 形同虚设。
反模式：告警风暴
一台 8×GPU 节点异常 → 8 条 GPU 告警 + 4 条 Pod 告警 + 2 条 Node 告警 = 14 条通知轰炸值班人。
正确做法：Alertmanager 配置 group_by: [alertname, node]，同一节点的同类告警聚合成一条；配合 group_wait: 30s 等初始告警都到齐再发送。
