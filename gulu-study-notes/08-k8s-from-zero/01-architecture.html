§0为什么要先理解集群架构

K8S 的日常使用就是写 YAML + kubectl apply，看起来很简单。但你一定遇到过这些问题：

  • Pod 一直 Pending，kubectl describe 说 "no nodes available"——是 scheduler 的锅还是 kubelet 的锅？
  • 刚 apply 的 Deployment 没反应——是 apiserver 没收到还是 controller-manager 没 reconcile？
  • 集群突然不响应——etcd 挂了还是 apiserver 过载？
  • 想给推理服务配 GPU 资源，发现 nvidia.com/gpu 不识别——是 device plugin 没注册到 kubelet 还是 scheduler 不知道？
如果你不知道请求经过了哪些组件，排障就是盲人摸象。理解架构 = 拿到一张完整的地图。

§1两个平面 · K8S 就是一个分布式状态机

整个 K8S 集群拆成两半：

一句话总结

K8S = 一个分布式状态机。你写 YAML 声明"期望状态"，控制平面持续对比"当前状态 vs 期望状态"，数据平面负责执行差异。所有通信的枢纽是 API Server，所有状态的持久化只在 etcd。

§2API Server · 集群的唯一入口

kube-apiserver 是整个集群中唯一暴露 HTTP API 的组件。无论是你的 kubectl、Dashboard、CI/CD 工具、kubelet、scheduler——全部通过它交互。

请求处理链路（六步）

关键设计特点

  • 无状态：API Server 本身不存数据，重启不影响集群状态（状态全在 etcd）
  • 水平可扩展：多副本部署 + 前面挂 LB，生产集群通常 3 个
  • Watch 机制：其他组件通过 HTTP long poll（watch）实时获取变更事件，不需要轮询
  • 乐观并发：每个资源有 resourceVersion，更新时必须匹配——类似数据库乐观锁
实战锚点：当你的推理服务集群有 1000+ Pod 频繁调度时，API Server 最先成为瓶颈。理解它是"无状态 + watch"的设计，就知道扩容 apiserver 副本数 + 给 etcd 独立 SSD 是正确的优化方向。
机制适用场景特点
X.509 客户端证书管理员 / 系统组件kubeconfig 中配置证书路径，CA 验证
ServiceAccount Token集群内 Pod自动挂载到 /var/run/secrets/，kubelet 自动管理
OIDC多用户环境对接企业 SSO（如腾讯云 CAM）
Webhook Token自定义认证转发到外部服务验证

§3etcd · 集群的唯一真相来源

etcd 是一个分布式键值数据库，它存了整个集群的全部状态：每个 Pod、每个 Service、每条 RBAC 规则、每个 ConfigMap——全在这里。

为什么用 etcd 而不是 MySQL / Redis

需求etcd 的回答
强一致性Raft 共识协议，写入必须过半节点确认
Watch 支持原生支持 watch key 变更，延迟 < 10ms
高可用3/5/7 节点奇数部署，任何少数派节点挂掉不影响
数据量适中K8S 状态通常 < 8GB，etcd 的 B+ tree 完全能搞定

数据在 etcd 里长什么样

# 每个 K8S 资源在 etcd 中是一个 key
/registry/pods/default/my-sglang-pod-0
/registry/deployments/inference/sglang-deploy
/registry/services/inference/sglang-svc
/registry/nodes/gpu-node-01

# value 是 protobuf 编码的完整资源对象（含 spec + status）
etcd 是整个集群的单点真相——它挂了，集群就"失忆"了。生产环境必须：① 3 节点起步 ② 独立 SSD（不跟 apiserver 混部） ③ 定期快照备份。

etcd 的瓶颈在哪

  • 写延迟：每次写入需要 Raft 过半确认，跨 AZ 部署时延迟会从 2ms 涨到 10ms+
  • 存储大小：默认 2GB quota，超了就拒绝写入（你会看到 "NOSPACE" 告警）
  • Watch 数量：几万个 watch 连接时 CPU 开销明显——这就是为什么大集群要做 watch 聚合
实战锚点
当你的 GPU 集群频繁扩缩（Karpenter 动态加减节点），etcd 的写 QPS 会突增。如果看到 etcdserver: request timed out，第一反应是查 etcd 磁盘 IOPS 和 Raft 延迟，而不是怀疑业务代码。

§4Scheduler · Pod 放到哪台机器

kube-scheduler 只做一件事：给还没有 nodeName 的 Pod 选一台合适的 Node。选完之后把 spec.nodeName 写回 apiserver，kubelet 就会认领它。

调度两阶段：过滤 → 打分

Scheduler 的关键行为

  • Watch 机制：scheduler watch apiserver 的 Pod 列表，一旦发现 spec.nodeName == "" 的 Pod，立刻开始调度
  • 调度是全局最优的尝试：但不保证是最优解（NP-hard 问题，只能启发式近似）
  • 抢占（Preemption）：如果高优先级 Pod 无法被调度，scheduler 会尝试驱逐低优先级 Pod 腾出空间
  • 插件化架构：从 K8S 1.19 开始用 scheduling-framework，每个调度步骤都是可插拔的 plugin
注意：scheduler 只负责"决策"，不负责"执行"。它把 nodeName 写入 Pod spec 后，实际拉起容器的是目标节点的 kubelet。

§5Controller Manager · 状态持续对齐的幕后推手

kube-controller-manager 里跑了几十个独立的 controller，每个 controller 负责一类资源的 reconcile 循环：

Reconcile 循环（核心模式）

while true:
    desired = 从 etcd 读取用户声明的期望状态
    actual  = 从 etcd 读取当前实际状态
    if actual != desired:
        执行操作使 actual → desired
    sleep / wait for next event

常见的内置 Controller

Controllerwatch 什么做什么
Deployment ControllerDeployment 对象创建/更新 ReplicaSet，管理滚动升级
ReplicaSet ControllerReplicaSet 对象确保 Pod 数量 = replicas 声明值
Node ControllerNode 心跳心跳超时 → 标记 NotReady → 驱逐 Pod
Job ControllerJob 对象创建 Pod 执行任务，跟踪完成/失败
Endpoint ControllerService + Pod维护 Service 后端 Pod 列表（Endpoints）
ServiceAccount ControllerNamespace为新 namespace 自动创建 default SA
理解 Controller 的关键：它不是一次性执行的脚本，而是持续运行的循环。哪怕你半夜手动删了一个 Pod，ReplicaSet Controller 几秒内就会发现"实际 2 个 < 期望 3 个"，然后创建一个新的补齐。这就是 K8S "自愈能力"的本质。
实战锚点
当你用 LWS（LeaderWorkerSet）部署多机推理时，LWS 本质上就是一个自定义 Controller：它 watch 自己的 CRD 对象，reconcile 循环里创建/管理一组有序的 Pod。理解 controller-manager 里内置 Controller 的行为模式，后面读任何 Operator 代码都不慌。

§6Kubelet · 每个节点上的"工头"

kubelet 跑在每个 Worker Node 上，它是节点侧唯一与控制平面通信的组件。职责：

核心职责

  • Watch Pod：watch apiserver 上分配给本节点的 Pod（通过 spec.nodeName 过滤）
  • 管理容器生命周期：通过 CRI（Container Runtime Interface）调用 containerd 创建/启动/停止容器
  • 上报节点状态：定期（默认 10s）向 apiserver 上报节点 CPU/Mem/磁盘/GPU 等资源容量和已分配量
  • 执行健康检查：按 Pod spec 中定义的 liveness/readiness probe 执行检查，异常时重启或摘除
  • 管理 Volume 挂载：调用 CSI 驱动挂载 PVC 对应的存储卷到 Pod
  • 注册 Device Plugin：接收 GPU 等设备插件的注册，上报 extended resource 给 apiserver

kubelet 与其他组件的关系

kubelet 不是容器运行时——它只是一个 Go 写的管理程序。真正创建 Linux namespace、cgroup、启动进程的是 containerd。kubelet 通过 gRPC 调用 CRI 接口指挥 containerd。
实战锚点
GPU 推理节点上，kubelet 还负责接收 NVIDIA device-plugin 的注册。当 device-plugin 报告"本节点有 8 块 A100"时，kubelet 把这个信息上报给 apiserver，scheduler 才能看到 nvidia.com/gpu: 8。如果 device-plugin 进程挂了，节点上的 GPU 资源就"消失了"——新 Pod 不会调度过来。

§7完整链路 · 一次 kubectl apply 背后发生了什么

把上面所有组件串起来——你执行 kubectl apply -f deploy.yaml 后发生的完整链路：

关键观察

  • 整个过程是事件驱动 + 最终一致的——没有任何一个"中心调度器"在一步完成所有事
  • 每个组件只做自己的本职：controller 只管"对象应该长什么样"，scheduler 只管"放哪"，kubelet 只管"跑起来"
  • apiserver 是所有通信的中转站——scheduler 不直接跟 kubelet 说话
  • 如果步骤 ⑥ 找不到合适 Node，Pod 会一直 Pending，直到有 Node 释放资源或新 Node 加入
延迟参考：从 kubectl apply 到 Pod Running，理想情况（镜像已缓存）约 3-5 秒。主要耗时：① etcd 写入 ~2ms ② scheduler 决策 ~10ms ③ kubelet 拉镜像 0-30s ④ 容器启动 ~1s。所以镜像预热是最影响首次部署速度的因素。

§8带走这些 · 后面章节一通百通

① 两个平面
控制平面做决策（apiserver/etcd/scheduler/controller），数据平面跑容器（kubelet/runtime/proxy）
② 唯一入口
API Server 是集群的唯一通信枢纽，所有组件只跟它交互，彼此不直连
③ 唯一状态
etcd 是唯一真相来源，其余组件全是无状态的——这让控制平面可以随意水平扩展
④ Watch + Reconcile
所有组件通过 watch 事件驱动 + 持续 reconcile 对齐状态——这是 K8S "自愈"的根
⑤ 职责分离
Controller 管"应该有几个 Pod" · Scheduler 管"放哪台机器" · Kubelet 管"怎么跑起来"
⑥ 扩展点
准入控制（webhook）扩展 apiserver · 调度插件扩展 scheduler · device-plugin 扩展 kubelet · CRD 扩展资源模型
