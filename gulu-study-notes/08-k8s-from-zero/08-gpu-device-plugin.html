§0为什么 K8S 不原生认识 GPU

K8S 内置只认识三种资源：cpu、memory、ephemeral-storage。为什么不把 GPU 也做进去？

设计哲学：核心精简 + 插件扩展

  • 硬件厂商太多：NVIDIA、AMD、Intel、华为昇腾、寒武纪……每家的设备发现/分配/隔离逻辑完全不同
  • 迭代速度不同步：GPU 驱动一年更新几十次，K8S 一年发 3 个版本——耦合在一起必然拖慢双方
  • 资源类型无限扩展：除了 GPU 还有 FPGA、RDMA NIC、TPU、NPU……不可能全写进核心

所以 K8S 设计了 Extended Resource + Device Plugin 框架：

  • Extended Resource：在 Node 对象的 status.capacity 中注册自定义资源名，如 nvidia.com/gpu: 8
  • Device Plugin：一个 gRPC 服务，负责告诉 kubelet "本节点有哪些设备、怎么分配给容器"
类比：K8S 核心就像操作系统内核，Device Plugin 就像设备驱动程序。内核不需要知道每块显卡的细节，只需要定义好驱动接口，由厂商实现具体驱动。

§1Device Plugin 协议

Device Plugin 框架在 K8S 1.10 进入 Beta（至今仍是 Beta，接口已非常稳定）。核心是一套 gRPC 协议，plugin 以 Unix Domain Socket 方式跟 kubelet 通信。

注册机制

kubelet 监听目录 /var/lib/kubelet/device-plugins/ 下的 socket 文件。Plugin 启动时在该目录创建 socket，然后向 kubelet 的 Registration 服务注册自己。

三个核心 RPC

RPC 方法方向职责
ListAndWatch kubelet → plugin（stream） plugin 通过 stream 持续上报设备列表和健康状态。设备掉线/恢复时推新消息。
Allocate kubelet → plugin Pod 被调度到本节点，kubelet 调用 Allocate 要求分配指定数量的设备。Plugin 返回环境变量、挂载路径、设备文件。
GetPreferredAllocation kubelet → plugin （可选）当多个设备可选时，plugin 建议优先分配哪些设备（如同一 NVLink 域内的 GPU）。

gRPC proto 定义（简化）

service DevicePlugin {
  // 持续上报设备列表（stream）
  rpc ListAndWatch(Empty) returns (stream ListAndWatchResponse) {}

  // kubelet 请求分配 N 个设备给一个容器
  rpc Allocate(AllocateRequest) returns (AllocateResponse) {}

  // 可选：建议分配哪些设备（拓扑感知）
  rpc GetPreferredAllocation(PreferredAllocationRequest)
      returns (PreferredAllocationResponse) {}
}

message Device {
  string ID = 1;          // 设备唯一 ID，如 "GPU-abc123"
  DeviceHealth health = 2; // HEALTHY / UNHEALTHY
}

message AllocateResponse {
  repeated ContainerAllocateResponse container_responses = 1;
}

message ContainerAllocateResponse {
  map<string, string> envs = 1;    // 注入容器的环境变量
  repeated Mount mounts = 2;        // 挂载到容器的路径
  repeated DeviceSpec devices = 3;  // 设备文件（/dev/nvidia0）
}
socket 路径约定：Plugin 的 socket 必须放在 /var/lib/kubelet/device-plugins/ 下。kubelet 注册服务的 socket 固定为 /var/lib/kubelet/device-plugins/kubelet.sock。Plugin 重启后需要重新注册——所以 DaemonSet 的 restartPolicy: Always 至关重要。
  1. Plugin 进程启动，扫描本地设备（如 /dev/nvidia*）
  2. 在 /var/lib/kubelet/device-plugins/nvidia.sock 创建 gRPC 服务
  3. Plugin 作为 gRPC client 连接 kubelet.sock，调用 Registration.Register()，传入：
    • resource_name: "nvidia.com/gpu"
    • endpoint: "nvidia.sock"
    • version: "v1beta1"
  4. kubelet 收到注册，连接 nvidia.sock，调用 ListAndWatch()
  5. Plugin 通过 stream 返回设备列表：[{ID:"GPU-0",health:HEALTHY}, {ID:"GPU-1",health:HEALTHY}, ...]
  6. kubelet 将 nvidia.com/gpu: 8 patch 到 Node.status.capacity 和 Node.status.allocatable
  7. Scheduler 看到该 Node 有 GPU 资源，开始调度 GPU Pod 过来

§2NVIDIA Device Plugin 工作流

NVIDIA 官方的 k8s-device-plugin 是目前最广泛使用的 GPU device plugin 实现。它以 DaemonSet 方式部署在所有 GPU 节点上。

部署方式

# 一行搞定部署（生产环境建议用 Helm chart 或 GPU Operator）
kubectl apply -f https://raw.githubusercontent.com/NVIDIA/k8s-device-plugin/v0.17.0/deployments/static/nvidia-device-plugin.yml

DaemonSet YAML 核心片段

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: nvidia-device-plugin-daemonset
  namespace: kube-system
spec:
  selector:
    matchLabels:
      name: nvidia-device-plugin-ds
  template:
    spec:
      tolerations:
      - key: nvidia.com/gpu        # 容忍 GPU 节点的 taint
        operator: Exists
        effect: NoSchedule
      containers:
      - name: nvidia-device-plugin-ctr
        image: nvcr.io/nvidia/k8s-device-plugin:v0.17.0
        securityContext:
          privileged: true          # 需要访问 /dev/nvidia*
        volumeMounts:
        - name: device-plugin       # 挂载 kubelet 的 device-plugins 目录
          mountPath: /var/lib/kubelet/device-plugins
      volumes:
      - name: device-plugin
        hostPath:
          path: /var/lib/kubelet/device-plugins

Allocate 时做了什么

当一个请求 nvidia.com/gpu: 2 的 Pod 被调度到本节点，kubelet 调用 plugin 的 Allocate()：

Pod 视角：看到的 GPU 环境

# 进入 Pod 后
$ echo $NVIDIA_VISIBLE_DEVICES
GPU-0,GPU-1

$ nvidia-smi
+---------------------------+
| GPU  Name      | Bus-Id   |
|  0   A100 80GB | 00:3B:00 |  # 只看到被分配的 2 块
|  1   A100 80GB | 00:86:00 |
+---------------------------+

# nvidia-container-runtime 利用 NVIDIA_VISIBLE_DEVICES 做隔离
# Pod 内看不到其他 6 块 GPU
陷阱：Device Plugin crash = GPU "消失"
如果 nvidia-device-plugin Pod 崩溃或被驱逐：
  • kubelet 检测到 socket 断开 → 标记所有设备为 Unhealthy
  • Node 的 allocatable 中 GPU 数量变为 0
  • 已经在运行的 Pod 不受影响（设备已挂载），但新 Pod 不会再调度过来
  • plugin 恢复后重新注册，GPU 资源恢复
实战锚点
8 块 A100 节点，4 块给在线推理（独占），4 块切 MIG 给开发调试。实现方式：给节点打不同 label，在线推理 Pod 通过 nodeSelector + resources.limits: nvidia.com/gpu: 4 独占；开发调试走 MIG 切分后的资源名（§4 详述）。

§3GPU Operator · 一键搞定 GPU 全栈

手动管理 GPU 节点需要装一堆东西：内核驱动、CUDA toolkit、container-toolkit、device-plugin、DCGM 监控……新节点加入时全要重做。GPU Operator 把这些全自动化了。

解决的核心痛点

  • 新 GPU 节点加入 → 自动安装驱动 + 配置 runtime + 部署 device-plugin
  • 驱动升级 → 修改 Operator CR 字段，自动滚动升级所有节点
  • MIG 切换 → 通过 ConfigMap 声明 MIG profile，Operator 自动配置
  • 监控 → 自动部署 DCGM-exporter，暴露 GPU 利用率/温度/显存到 Prometheus

组件拓扑图

安装 GPU Operator

# Helm 安装（推荐）
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update

helm install gpu-operator nvidia/gpu-operator \
  --namespace gpu-operator \
  --create-namespace \
  --set driver.version="550.127.05"    # 指定驱动版本
  --set mig.strategy="mixed"           # MIG 策略：single/mixed/none
  --set devicePlugin.config.name="device-plugin-config"  # 引用 ConfigMap
GFD（GPU Feature Discovery）会自动给节点打上细粒度 label：
nvidia.com/gpu.product=NVIDIA-A100-SXM4-80GB
nvidia.com/gpu.memory=81920
nvidia.com/mig.capable=true
你可以直接用这些 label 做 nodeAffinity，不需要手动维护。

§4MIG（Multi-Instance GPU）· 硬件级 GPU 切分

A100 / H100 / H200 支持 Multi-Instance GPU——在硬件层面把一块物理 GPU 切成多个独立实例，每个实例有自己的 SM（流处理器）、显存和显存控制器。

MIG 的硬件本质

常见 MIG Profile（A100 80GB）

ProfileSM 数显存Memory Slices最大实例数/卡典型用途
1g.10gb1410 GB17开发调试 / 极小模型
2g.20gb2820 GB23Embedding / 小模型推理
3g.40gb4240 GB42中等模型推理
4g.40gb5640 GB41较大模型 / 更多算力
7g.80gb9880 GB81全卡（等效不切分）

K8S 中 MIG 资源的呈现

启用 MIG 后，device-plugin 不再上报 nvidia.com/gpu，而是上报更细粒度的资源名：

# Node status.capacity（mixed strategy 模式）
nvidia.com/mig-1g.10gb: 4    # 4 个 1g.10gb 实例可用
nvidia.com/mig-3g.40gb: 2    # 2 个 3g.40gb 实例可用

# Pod 请求 MIG 实例（就像请求普通 GPU 一样）
resources:
  limits:
    nvidia.com/mig-1g.10gb: 1   # 请求 1 个 1g.10gb MIG 实例

配置 MIG：nvidia-mig-parted

# mig-config.yaml - 声明式 MIG 配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: mig-parted-config
  namespace: gpu-operator
data:
  config.yaml: |
    version: v1
    mig-configs:
      all-1g.10gb:            # 配置名称
        - devices: all        # 应用于所有 GPU
          mig-enabled: true
          mig-devices:
            "1g.10gb": 7      # 每块 GPU 切 7 个 1g.10gb

      mixed-inference:        # 混合切法
        - devices: [0,1,2,3]  # 前 4 块不切（独占给在线推理）
          mig-enabled: false
        - devices: [4,5,6,7]  # 后 4 块切 MIG
          mig-enabled: true
          mig-devices:
            "3g.40gb": 1      # 每块切 1 个 3g + 若干 1g
            "1g.10gb": 3

# 应用配置到节点（通过 label 触发）
kubectl label node gpu-node-01 nvidia.com/mig.config=mixed-inference --overwrite
MIG 切换需要重启 GPU：修改 MIG 配置时，相关 GPU 上的所有进程必须先停止。GPU Operator 的 MIG Manager 会自动 drain 节点 → 重配 MIG → uncordon 节点。生产环境切换 MIG 要在维护窗口进行。
实战锚点
场景：8 块 A100 节点，4 块给在线推理（独占），4 块切 MIG 给开发调试。

实现步骤：
  1. 配置 mig-parted-config 的 mixed-inference profile
  2. 给节点打 label nvidia.com/mig.config=mixed-inference
  3. MIG Manager 自动把 GPU 4-7 切成 MIG 实例
  4. Node capacity 同时呈现：nvidia.com/gpu: 4（未切的）+ nvidia.com/mig-3g.40gb: 4 + nvidia.com/mig-1g.10gb: 12
  5. 在线推理 Pod 请求 nvidia.com/gpu，开发 Pod 请求 nvidia.com/mig-1g.10gb

适用场景

  • 小模型推理：7B 参数模型 FP16 只需 14GB 显存，1 块 A100 可以跑 5 个独立实例
  • 开发调试：开发者只需要少量 GPU 算力验证代码逻辑
  • 多租户共享：每个团队分到独立 MIG 实例，硬件级隔离互不影响
  • Embedding / 向量化：小模型高并发，MIG 切分可以最大化利用率

§5Time-Slicing · 时间片共享

Time-Slicing 是一种软件级 GPU 共享方案：多个 Pod "看到同一块 GPU"，通过 CUDA Time-Slicing 机制轮转使用算力。没有硬件隔离。

工作原理

  • device-plugin 对外声称一块 GPU 有 N 个"副本"（replicas）
  • 每个 Pod 请求 1 个 nvidia.com/gpu，实际上多个 Pod 共享同一物理卡
  • NVIDIA GPU 硬件的时间片调度器在多个 CUDA context 间轮转
  • 每个 Pod 内 nvidia-smi 看到的是同一块完整的 GPU（不像 MIG 那样只看到切片）

配置方式

# device-plugin ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: device-plugin-config
  namespace: gpu-operator
data:
  any: |
    version: v1
    sharing:
      timeSlicing:
        renameByDefault: false   # true 时资源名变为 nvidia.com/gpu.shared
        failRequestsGreaterThanOne: true  # 禁止单 Pod 请求 >1 个共享 GPU
        resources:
        - name: nvidia.com/gpu
          replicas: 4            # 每块物理 GPU "变成" 4 个逻辑 GPU

# 应用配置（通过 label 选择使用此配置的节点）
kubectl label node dev-gpu-node nvidia.com/device-plugin.config=any

效果

# 节点原来有 2 块 GPU，配置 replicas=4 后：
$ kubectl describe node dev-gpu-node | grep nvidia
  nvidia.com/gpu:     8    # 2 块 × 4 replicas = 8 个逻辑 GPU

# 8 个 Pod 都请求 nvidia.com/gpu: 1，全部能调度成功
# 每 4 个 Pod 共享一块物理 GPU

Pod 内看到什么

# Pod A（和 Pod B、C、D 共享 GPU-0）
$ nvidia-smi
+-------------+
| GPU 0       |        # 看到完整的一块 GPU
| A100 80GB   |        # 显存显示 80GB（不是 20GB！）
+-------------+
| Processes:            |
| PID   Mem   GPU-Util |
| 1234  12GB  25%      |  # 自己的进程
| 5678  15GB  30%      |  # 别人的进程也能看到！
+-------------+
Time-Slicing 的致命风险：显存不隔离
  • 所有共享 Pod 的显存使用叠加在同一块 GPU 上
  • 如果 4 个 Pod 各用 25GB，总共 100GB > 80GB → CUDA OOM
  • 一个 Pod OOM 可能导致所有共享该 GPU 的 Pod 全部崩溃
  • 没有任何机制阻止一个 Pod 吃掉全部 80GB 显存
性能损耗：Time-Slicing 的上下文切换有开销。当并发 Pod 多且都是计算密集型时：
  • 上下文切换延迟：每次切换约 10-100μs
  • 显存带宽竞争：多个模型的 weight 无法同时常驻 HBM
  • 实际吞吐 < 独占吞吐 × Pod 数的倒数（不是线性切分）

适用场景

  • 开发测试：开发者只需要少量算力跑测试，显存用量可控
  • 低利用率工作负载：Jupyter notebook、间歇性推理请求
  • 不支持 MIG 的老卡：V100、T4 等无法用 MIG，Time-Slicing 是唯一的超卖方案
  • 快速原型验证：不需要性能保证，只要能跑
实战锚点
绝对不要在生产推理环境用 Time-Slicing。一个用户的 batch 推理吃满显存 → 其他人的在线推理全部 OOM。正确做法：生产推理用独占 GPU 或 MIG，开发测试环境才用 Time-Slicing（并设好 Pod memory limit 做软约束）。

§6MIG vs Time-Slicing vs vGPU 对比

维度MIGTime-SlicingvGPU（NVIDIA vCS/vWS）
隔离级别 硬件级（独立 SM + 显存控制器） 无隔离（共享一切） 驱动级（Hypervisor mediated）
显存隔离 完全隔离，互不影响 无隔离，可互相 OOM 驱动强制限额
算力隔离 完全隔离（独享 SM） 时间片轮转，互相影响延迟 可配置算力比例
性能损耗 接近零（硬件原生） 中等（上下文切换 + 缓存失效） 5-10%（Hypervisor 开销）
灵活性 低（切换需重启 GPU，profile 有限） 高（改 ConfigMap 即可，秒级生效） 中（需要 vGPU License Manager）
支持的 GPU A100 / H100 / H200 / B200 所有 NVIDIA GPU 支持 vGPU 的 Datacenter GPU
最大实例数/卡 7（A100/H100） 无硬限制（replicas 可设任意值） 取决于 license 和配置
成本 免费（GPU 硬件特性） 免费（device-plugin 配置） 需要 vGPU License（按 GPU 计费）
适用场景 生产多租户 / 小模型推理 开发测试 / 低利用率 企业 VDI / 严格 SLA 多租户

决策树

需要 GPU 共享？
├─ 否 → 独占（nvidia.com/gpu: N）
└─ 是 → 需要硬件级隔离？
         ├─ 是 → GPU 支持 MIG？
         │       ├─ 是 → 用 MIG
         │       └─ 否 → 用 vGPU（需 License）
         └─ 否 → 是否容忍 OOM 风险？
                  ├─ 是（开发测试）→ 用 Time-Slicing
                  └─ 否 → 用 vGPU 或回到 MIG
混合部署是最佳实践：同一集群内不同 Node Pool 可以用不同策略。在线推理 Pool 用独占/MIG，开发 Pool 用 Time-Slicing，通过 nodeSelector / taint 隔离。

§7带走这些

① Extended Resource
K8S 通过 Device Plugin 框架扩展硬件支持，核心不内置任何加速器逻辑

ListAndWatch（上报设备）→ Allocate（分配设备）→ GetPreferredAllocation（拓扑亲和）

DaemonSet 部署 · 发现 /dev/nvidia* · Allocate 时注入 NVIDIA_VISIBLE_DEVICES + 设备挂载

A100/H100 独有 · 完全隔离 · 切换需重启 · 适合生产多租户和小模型推理

device-plugin Pod 挂了新 Pod 无法调度，但已运行 Pod 不受影响 · 监控要覆盖
