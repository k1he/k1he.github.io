§0为什么需要七层路由

你的推理集群里同时跑了多个模型：

  • qwen3-72b — 通用对话
  • qwen3-8b — 轻量快速
  • deepseek-r1 — 深度推理
  • embedding-v3 — 向量化
  • reranker-v2 — 重排序

每个模型背后是独立的 Deployment + Service。如果每个 Service 都用 type: LoadBalancer，你就需要 5 个公网 IP、5 个 DNS 记录、5 份 TLS 证书——成本爆炸，管理地狱。

七层路由的核心价值

一个入口 → 多个后端：用 HTTP Host / Path 把请求分发到不同 Service。所有模型共享一个公网 IP、一张通配符证书、一套限流策略。这就是 Ingress 的本质——HTTP 层的反向代理规则。

想象你要实现这样的路由表：

请求路由到
api.myinfer.com/v1/chat/completions + Header X-Model: qwen3-72bsglang-qwen72b-svc:8000
api.myinfer.com/v1/chat/completions + Header X-Model: qwen3-8bsglang-qwen8b-svc:8000
api.myinfer.com/v1/embeddingsembedding-svc:8000
api.myinfer.com/v1/rerankreranker-svc:8000

四层 vs 七层

维度四层（Service type=LoadBalancer）七层（Ingress / Gateway API）
路由依据IP + Port（看不到 HTTP 内容）Host + Path + Header + Method
TLS 终止每个 Service 各自处理在入口统一终止，后端只跑 HTTP
一个 IP 服务几个模型一个 LB = 一个 Service一个 Ingress = N 个 Service
成本N 个公网 IP1 个公网 IP
四层做不到按 URL 分发流量——四层只看 IP:Port，看不到 HTTP 的 Host、Path、Header。所以多模型推理路由必须七层。

§1Ingress 资源 + Ingress Controller 模型

Ingress 体系有两个角色，理解这个分离是关键：

Ingress 只是规则定义（像 nginx.conf）

  • 一段 YAML，声明"什么 Host + 什么 Path → 转发到哪个 Service"
  • 存在 etcd 里，本身不做任何网络转发
  • 你可以创建 100 个 Ingress 资源，但没有 Controller 就没有任何效果

Ingress Controller 是真正的反向代理（像 nginx 进程）

  • 以 Pod 形态运行在集群内（通常是 Deployment 或 DaemonSet）
  • 持续 watch apiserver 上的 Ingress 资源，变更时自动 reload 配置
  • 监听 80/443 端口，接收外部流量并执行路由
  • 需要被外部访问到——所以它的 Service 通常是 LoadBalancer 或 NodePort

常见 Ingress Controller

Controller底层代理适用场景特点
Nginx IngressNginx / OpenResty通用场景首选注解最丰富、社区最大、排障资料多
TraefikGo 原生代理云原生优先、自动发现热更新零停顿、内置 Let's Encrypt、Dashboard 美观
Kong IngressNginx + Lua需要 API 管理认证/限流/计费插件开箱即用
CLB Ingress腾讯云 CLBTKE 环境直接使用云 LB 做七层，Pod 直连模式
常见误区：很多人以为 kubectl apply -f ingress.yaml 就能路由了。实际上如果集群里没有部署任何 Ingress Controller，这个 Ingress 对象只是安静地躺在 etcd 里——没有任何效果。排障第一步：kubectl get pods -n ingress-nginx 确认 Controller 在跑。

§2Ingress 配置详解

基于 Host 的路由

不同域名分发到不同后端——适合多租户或多产品线：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-model-host-routing
  namespace: inference
spec:
  ingressClassName: nginx          # 指定用哪个 Controller
  rules:
  - host: chat.myinfer.com          # 对话模型入口
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: sglang-chat-svc
            port:
              number: 8000
  - host: embed.myinfer.com         # Embedding 入口
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: embedding-svc
            port:
              number: 8000

基于 Path 的路由（推理平台最常用）

同一域名下，不同路径分发到不同后端：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-model-path-routing
  namespace: inference
  annotations:
    # 重写路径：去掉模型名前缀，让后端收到标准的 /v1/... 路径
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
  - host: api.myinfer.com
    http:
      paths:
      # /qwen72b/v1/chat/completions → 转发到 sglang-qwen72b-svc
      # 后端收到的路径变为 /v1/chat/completions（标准 OpenAI 格式）
      - path: /qwen72b(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: sglang-qwen72b-svc
            port:
              number: 8000
      # /qwen8b/v1/chat/completions → sglang-qwen8b-svc
      - path: /qwen8b(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: sglang-qwen8b-svc
            port:
              number: 8000
      # /embeddings/... → embedding-svc
      - path: /embeddings(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: embedding-svc
            port:
              number: 8000
      # /rerank/... → reranker-svc
      - path: /rerank(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: reranker-svc
            port:
              number: 8000

pathType 三种模式

pathType匹配规则示例
Prefix前缀匹配，按 / 分段/v1 匹配 /v1/chat、/v1/models，但不匹配 /v1chat
Exact精确匹配，末尾 / 敏感/v1/models 只匹配 /v1/models，不匹配 /v1/models/
ImplementationSpecific由 Controller 定义Nginx Ingress 支持正则捕获组（如上面的 rewrite 示例）
Prefix 匹配的坑：Prefix 是按 / 分段匹配的，不是字符串前缀！/v1/chat 会匹配 /v1/chat/xxx，但不会匹配 /v1/chatbot（因为 chatbot 和 chat 不是同一个 path segment）。

TLS 终止：Secret 存证书 + Ingress 引用

Ingress 在入口处终止 HTTPS，后端 Pod 只需处理 HTTP——简化证书管理：

# 1. 创建 Secret 存放证书和私钥
apiVersion: v1
kind: Secret
metadata:
  name: myinfer-tls
  namespace: inference
type: kubernetes.io/tls
data:
  tls.crt: LS0tLS1CRUdJTi...    # base64 编码的证书链
  tls.key: LS0tLS1CRUdJTi...    # base64 编码的私钥
---
# 2. Ingress 中引用 Secret
spec:
  tls:
  - hosts:
    - api.myinfer.com
    - "*.myinfer.com"           # 通配符证书覆盖所有子域
    secretName: myinfer-tls     # 引用上面的 Secret

注解控制：超时 / 限流 / 重写 / WebSocket

注解（nginx.ingress.kubernetes.io/ 前缀省略）作用推理场景建议值
proxy-read-timeout等待后端响应的超时（秒）"300"（长推理可能 5 分钟）
proxy-send-timeout向后端发送请求体的超时"60"
proxy-body-size允许的请求体大小上限"50m"（大 prompt / 音频文件）
proxy-buffering是否缓冲后端响应"off"（SSE 流式必须关）
proxy-http-version后端 HTTP 版本"1.1"（WebSocket/SSE 需要）
upstream-hash-by一致性 hash（会话亲和）"$http_x_session_id"（KV Cache 亲和）
rewrite-targetURL 重写目标/$2（配合正则去前缀）
踩坑警告：流式推理（SSE）必须关闭 proxy-buffering
Nginx 默认缓冲后端响应。推理服务逐 token 输出，但客户端要等整个响应完成才收到第一个字——用户体验极差。加上 nginx.ingress.kubernetes.io/proxy-buffering: "off" 才能实现真正的流式输出。

YAML 完整示例：多模型推理路由

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: inference-gateway
  namespace: inference
  annotations:
    # URL 重写：去掉模型名前缀
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    # 超时：推理可能很慢
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"
    # 请求体：大 prompt + 音频文件
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    # 流式输出：关闭缓冲
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
    nginx.ingress.kubernetes.io/proxy-http-version: "1.1"
    # HTTPS 强制跳转
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    # CORS 跨域（前端直调推理 API）
    nginx.ingress.kubernetes.io/enable-cors: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts: ["api.myinfer.com"]
    secretName: myinfer-tls
  rules:
  - host: api.myinfer.com
    http:
      paths:
      - path: /qwen72b(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: sglang-qwen72b-svc
            port: {number: 8000}
      - path: /qwen8b(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: sglang-qwen8b-svc
            port: {number: 8000}
      - path: /deepseek-r1(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: sglang-deepseek-svc
            port: {number: 8000}
      - path: /embeddings(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: embedding-svc
            port: {number: 8000}
      - path: /rerank(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: reranker-svc
            port: {number: 8000}
实战锚点
多模型推理统一入口：一个 Ingress + 多条 path 规则，所有模型共享一个域名 api.myinfer.com。客户端通过路径区分模型（/qwen72b/v1/chat/completions），配合 rewrite-target 注解去掉前缀，让后端 SGLang 收到标准的 OpenAI 格式请求 /v1/chat/completions。这是推理平台最常见的 Ingress 用法。

§3Gateway API（Ingress 的继任者）

Ingress API 从 K8S 1.1 引入，设计时妥协很多（只能 Host+Path、全靠注解扩展、不同 Controller 注解互不兼容）。Gateway API（2023 年 GA）是官方推荐的下一代方案。

三层模型：GatewayClass → Gateway → HTTPRoute

比 Ingress 好在哪

维度Ingress 的问题Gateway API 的解法
角色分离所有配置堆在一个 Ingress 对象三层分离：平台管 Class，运维管 Gateway，开发管 Route
跨 namespaceIngress 只能引用同 namespace 的 ServiceHTTPRoute 可跨 namespace 引用 Gateway 和 Service
匹配规则只有 Host + PathHost + Path + Header + QueryParam + Method
流量管理靠注解（不同 Controller 不兼容）标准化的 backendRefs.weight 流量拆分
协议覆盖只有 HTTP/HTTPSHTTP / gRPC / TCP / TLS / UDP 全覆盖
可移植性注解 = 厂商锁定统一 spec，换 GatewayClass 即换底层实现

Gateway API YAML 示例

# 1. GatewayClass — 平台管理员创建一次
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx
spec:
  controllerName: k8s.nginx.org/nginx-gateway-controller
---
# 2. Gateway — 运维团队创建，定义监听器
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: inference-gw
  namespace: infra               # 运维 namespace
spec:
  gatewayClassName: nginx
  listeners:
  - name: https
    port: 443
    protocol: HTTPS
    hostname: "*.myinfer.com"
    tls:
      certificateRefs:
      - name: myinfer-tls
    allowedRoutes:
      namespaces:
        from: Selector            # 只允许带特定 label 的 namespace
        selector:
          matchLabels:
            gateway-access: "true"
---
# 3. HTTPRoute — 开发者在自己 namespace 创建路由规则
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: qwen72b-route
  namespace: inference            # 开发者的 namespace
spec:
  parentRefs:
  - name: inference-gw
    namespace: infra              # 跨 namespace 引用 Gateway！
  hostnames: ["api.myinfer.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /v1/chat
      headers:                   # 基于 Header 匹配——Ingress 做不到！
      - name: X-Model
        value: qwen3-72b
    backendRefs:
    - name: sglang-qwen72b-svc
      port: 8000
什么时候该用 Gateway API：① 新集群新项目 → 直接上 Gateway API。② 多团队共享入口 → Gateway API 的角色分离能力是杀手级特性。③ 现有 Nginx Ingress 用得好好的 → 不必急迁，Ingress 短期内不废弃，只是冻结不再新增功能。

§4金丝雀发布 / 灰度路由

上线新模型版本时，不想一次性全量切换——需要先灰度 10% 验证效果。七层路由天然支持这个能力。

方式一：基于 Header 的流量切分

只有带特定 Header 的请求路由到新版本——适合内部测试人员验证：

# 主 Ingress（生产流量 → 稳定版 v1.0）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: qwen72b-stable
  namespace: inference
spec:
  ingressClassName: nginx
  rules:
  - host: api.myinfer.com
    http:
      paths:
      - path: /qwen72b
        pathType: Prefix
        backend:
          service:
            name: sglang-qwen72b-stable    # 稳定版 checkpoint
            port: {number: 8000}
---
# 金丝雀 Ingress（只有带 Header 的请求 → 新版本）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: qwen72b-canary
  namespace: inference
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"               # 声明为金丝雀
    nginx.ingress.kubernetes.io/canary-by-header: "X-Canary" # Header 名
    nginx.ingress.kubernetes.io/canary-by-header-value: "true"
spec:
  ingressClassName: nginx
  rules:
  - host: api.myinfer.com
    http:
      paths:
      - path: /qwen72b
        pathType: Prefix
        backend:
          service:
            name: sglang-qwen72b-canary    # 新版本（新 checkpoint）
            port: {number: 8000}

测试方法：curl -H "X-Canary: true" https://api.myinfer.com/qwen72b/v1/chat/completions -d '...'

方式二：基于权重的流量切分

按比例随机分配流量给新版本——适合线上灰度验证：

# 金丝雀 Ingress 改用 canary-weight（其他不变）
metadata:
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"  # 10% 随机流量到新版本

推理场景：新模型版本灰度 10% 流量验证

注意：Nginx Ingress 的 canary 注解要求金丝雀 Ingress 和主 Ingress 使用相同的 host + path，否则不生效。另外同一个 host+path 只能有一个 canary Ingress。

Gateway API 的流量拆分（更优雅）

# Gateway API 原生支持 backendRefs 权重——不需要创建两个 Ingress
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: qwen72b-canary-route
spec:
  parentRefs:
  - name: inference-gw
    namespace: infra
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /v1/chat
    backendRefs:
    - name: sglang-qwen72b-stable
      port: 8000
      weight: 90                   # 标准化的流量拆分
    - name: sglang-qwen72b-canary
      port: 8000
      weight: 10                   # 不需要注解 hack
实战锚点
推理模型灰度时的特别注意：新版本 Pod 刚启动时 KV Cache 是冷的，前几分钟延迟会偏高。建议灰度初期至少观察 10 分钟（让 Cache 热起来），而不是看到延迟升高就立刻回滚。同时关注输出质量——延迟正常但回答质量下降也是回滚信号。

§5限流与熔断

GPU 推理服务的并发能力极其有限——一块 A100 跑 72B 模型同时处理不了几个请求。不限流的后果：OOM、队列爆满、延迟飙升、全部用户受影响。

Nginx Ingress 的 rate-limiting 注解

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: inference-ratelimit
  namespace: inference
  annotations:
    # 每个客户端 IP 限 100 QPS
    nginx.ingress.kubernetes.io/limit-rps: "100"
    # 允许突发 3 倍（300 个请求进入排队）
    nginx.ingress.kubernetes.io/limit-burst-multiplier: "3"
    # 每个 IP 最多 50 个并发连接
    nginx.ingress.kubernetes.io/limit-connections: "50"
    # 超限返回 429 Too Many Requests
    nginx.ingress.kubernetes.io/server-snippet: |
      limit_req_status 429;
    # 内部监控系统 IP 段不限流
    nginx.ingress.kubernetes.io/limit-whitelist-source-range: "10.0.0.0/8"
spec:
  ingressClassName: nginx
  rules:
  - host: api.myinfer.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: sglang-router-svc
            port: {number: 8000}

推理场景：每个 API Key 限 100 QPS

按 IP 限流粒度太粗——多个用户可能共用代理 IP。更精细的做法是按 X-API-Key Header 限流：

metadata:
  annotations:
    # 用自定义 Lua snippet 实现按 Header 限流
    nginx.ingress.kubernetes.io/configuration-snippet: |
      set $limit_key $http_x_api_key;
      if ($limit_key = "") {
        set $limit_key $binary_remote_addr;   # 没有 Key 退回 IP 限流
      }
    nginx.ingress.kubernetes.io/limit-rps: "100"          # 每个 Key 100 QPS
    nginx.ingress.kubernetes.io/limit-connections: "50"   # 每个 Key 50 并发

连接数限制保护后端 GPU 不被打爆

为什么必须限制并发连接数：SGLang/vLLM 使用 continuous batching，一个请求占一个 KV Cache slot。如果并发请求超过 GPU 显存能支撑的 batch size（比如 72B 模型 4xA100 只能同时处理 ~60 个请求），新请求排队 → 延迟飙升，或直接 OOM → 服务崩溃。Ingress 层的 limit-connections 是最外层保护伞。

分层防护架构

层次限流机制作用
L1 · Ingress 层limit-rps + limit-connections粗粒度：防 DDoS、限客户端 QPS 和并发
L2 · API Gateway 层按 API Key 的 token/分钟配额细粒度：计费、配额管理、多租户隔离
L3 · 推理引擎层max_num_seqs / max_batch_size保底：SGLang/vLLM 内部的 batch 上限
注意：Nginx Ingress 的限流注解是每个 Controller Pod 独立计算的。如果你有 3 个 Nginx Pod，实际限流阈值约为配置值的 3 倍。需要全局精确限流时，用 Kong（内置 Redis 分布式计数）或外置 Ratelimit Service（如 Envoy ratelimit）。
实战锚点
推理平台的限流建议分级：免费用户 5 QPS / 10 并发，付费用户 100 QPS / 50 并发，内部服务 不限。Ingress 层做 L1 粗粒度保护（单 IP 不超过 200 QPS），API Gateway 层做 L2 按 Key 精细限流。两层互补，缺一不可。

§6带走这些

① 七层路由价值
一个公网 IP + 一张证书 → 按 Host/Path/Header 分发到 N 个模型后端——多模型推理的标配
② 两个概念分清
Ingress 资源 = 路由规则声明（nginx.conf）· Ingress Controller = 反向代理进程（nginx 主进程）
③ SSE 流式必须
proxy-buffering: "off" + proxy-http-version: "1.1"，否则 token-by-token 输出失效
④ pathType 陷阱
Prefix 按 / 分段匹配：/v1/chat 匹配 /v1/chat/xxx 但不匹配 /v1/chatbot
⑤ Gateway API 三层
GatewayClass（平台）→ Gateway（运维）→ HTTPRoute（开发）· 角色分离 + 跨 ns + 原生流量拆分
⑥ 金丝雀两步走
Header 灰度做内部验证 → Weight 灰度做线上放量 → 观察延迟+质量 → 全量切换
⑦ 限流是底线
