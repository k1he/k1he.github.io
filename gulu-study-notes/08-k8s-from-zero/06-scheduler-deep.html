§0为什么要深入理解调度

场景：你申请了一个 8 卡 A100 的推理 Pod，kubectl apply 之后——Pending 了 30 分钟。

  • kubectl describe pod 提示 0/12 nodes are available: 4 Insufficient nvidia.com/gpu, 3 node(s) had taints that the pod didn't tolerate, 5 node(s) didn't match Pod's node affinity
  • 你明明看到集群里有空闲 GPU 节点——为什么 scheduler 就是不选？
  • 终于调度上去了，却跑到了一台"碎片 GPU"节点——4 卡 A100 + 4 卡被其他 Pod 占用，凑不出完整的 TP8
  • 多个推理副本全部被调度到同一个机架——NVSwitch 交换机 down 了，所有副本一起挂
这些问题的根源都是不理解 scheduler 的决策逻辑。当你知道 Filter 阶段检查哪些硬约束、Score 阶段偏好什么——就能主动设计调度策略，而不是被动等待和排障。

GPU 推理 Pod Pending 的常见原因速查

describe 看到的消息卡在哪个阶段/插件解法方向
Insufficient nvidia.com/gpuFilter → NodeResourcesFit等旧 Pod 释放 / 扩节点 / 抢占低优先级
node(s) had taints that pod didn't tolerateFilter → TaintToleration给 Pod 加 toleration 或去掉节点 taint
didn't match Pod's node affinity/selectorFilter → NodeAffinity检查 label 拼写 / 节点是否有该 label
doesn't satisfy topology spreadFilter → PodTopologySpread放宽 maxSkew / 加节点到缺少 Pod 的域
pod has unbound immediate PersistentVolumeClaimsReserve → VolumeBinding检查 PVC 绑定状态和 StorageClass
Preempting + NominatedNode 设了但没绑PostFilter → Preemption 等待中等被抢占 Pod 退出 / 缩短其 gracePeriod

为什么这很重要？当 Pod 在 unschedulableQ 时，它不会被主动重试——除非集群状态发生变化（比如新节点加入、其他 Pod 被删除释放资源）。这就是为什么有时候 Pod Pending 半小时后突然调度成功——因为另一个 Pod 结束了。

Scheduling Framework · 八大扩展点

从 K8S 1.19 开始，调度器采用插件框架（Scheduling Framework）。一次调度经过以下扩展点：

关键理解：Scheduling Cycle（PreFilter → Reserve）是同步串行的——同一时间只处理一个 Pod。Binding Cycle（Permit → Bind）是异步的——写 nodeName 到 etcd 不阻塞下一个 Pod 的调度。这就是为什么 scheduler 每秒能处理几百个 Pod 的调度决策。

K8S 原生 scheduler 支持 out-of-tree 插件开发。你可以：

  • 方式 1：修改 KubeSchedulerConfiguration 调整内置插件的权重和参数（最简单）
  • 方式 2：编写自定义 plugin 编译到 scheduler binary 中（需要 Go 开发）
  • 方式 3：部署第二个 scheduler（schedulerName: my-scheduler）专门服务 GPU Pod

GPU 集群常见的自定义 scheduler 插件场景：

  • GPU 拓扑感知调度（如 NVIDIA GPU Operator 的 topology-aware placement）
  • Gang scheduling（等所有 Pod 都能调度后才一起绑定——Pipeline Parallel 场景）
  • 碎片化感知调度（避免把 4 卡 Pod 放到只剩 4 卡但分属不同 NVLink 域的节点）

§2Filter 阶段 · 硬约束淘汰

Filter 阶段对每个 Node 逐一执行所有 Filter 插件。任何一个插件返回 Unschedulable → 该 Node 直接淘汰。以下是最重要的 5 个 Filter 插件：

① NodeResourcesFit · CPU / Mem / GPU 资源够不够

对比 Pod 的 requests 与 Node 的 Allocatable - 已分配 requests 总和：

# Pod 请求
resources:
  requests:
    cpu: "32"                      # 32 核
    memory: "320Gi"                # 320GB 内存
    nvidia.com/gpu: "8"            # 8 块 GPU

# Node 状态（8 卡 A100 节点，96 核 / 768Gi / 8 GPU）
# 已有另一个 Pod 占了 8 卡 GPU：
#   剩余 GPU = 8 - 8 = 0
#   → 不满足 Pod 的 gpu requests → 此 Node 被淘汰
最常见的误解：kubectl top node 显示 GPU 利用率只有 20%——但 scheduler 不看利用率，它看的是 requests 累计值。即使 GPU 实际空闲（模型没在推理），只要其他 Pod 已经 request 了那些 GPU，scheduler 就认为资源不足。这是"声明式资源管理"的设计——保证已声明的资源不会被超卖。

② NodeAffinity · 标签选择器

检查 Pod 的 nodeAffinity.requiredDuringSchedulingIgnoredDuringExecution 是否与 Node labels 匹配：

# Pod 要求：节点必须有标签 nvidia.com/gpu.product=NVIDIA-A100-SXM4-80GB
#
# Node-A labels: {nvidia.com/gpu.product: NVIDIA-A100-SXM4-80GB}  → 匹配 ✓
# Node-B labels: {nvidia.com/gpu.product: NVIDIA-V100-SXM2-32GB}  → 不匹配 ✗ → 淘汰
# Node-C labels: {无此 key}                                       → 不匹配 ✗ → 淘汰

③ TaintToleration · 污点容忍

Node 上的 NoSchedule / NoExecute Taint 必须被 Pod 的 Toleration 精确匹配，否则淘汰：

# Node taint:  nvidia.com/gpu=present:NoSchedule
#
# Pod A（有 toleration {key:nvidia.com/gpu, operator:Exists, effect:NoSchedule}）
#   → 匹配 → 通过 ✓
#
# Pod B（普通 CPU 服务，没有任何 GPU toleration）
#   → 不匹配 → 淘汰 ✗  ← 这就是 GPU 节点"专用化"的原理

④ PodTopologySpread · 拓扑分散约束

当 whenUnsatisfiable: DoNotSchedule 时，Filter 阶段检查把 Pod 放到该 Node 后，拓扑域间的 Pod 数差是否超出 maxSkew：

# maxSkew=1, topologyKey=topology.kubernetes.io/zone
# zone-a: 3 个推理 Pod     zone-b: 2 个推理 Pod
#
# 新 Pod 放 zone-a 的某 Node → skew = (3+1) - 2 = 2 > maxSkew → 淘汰 zone-a 所有 Node ✗
# 新 Pod 放 zone-b 的某 Node → skew = 3 - (2+1) = 0 ≤ 1     → 通过 ✓

⑤ InterPodAffinity / AntiAffinity · Pod 间亲和

requiredDuringSchedulingIgnoredDuringExecution 的 podAntiAffinity 会在 Filter 阶段检查：

# Pod 声明：不能跟 label app=sglang-inference 的 Pod 在同一个 hostname
# Node 上已有一个 app=sglang-inference 的 Pod → 淘汰 ✗
#
# 常用于：同一模型的多个 TP8 副本不能跑在同一台机器
# （因为单台最多 8 卡，不可能装两个 8 卡 Pod）
常见坑：Pod 硬反亲和 + replicas 数 > 合格 Node 数 → 必然有 Pod 永远 Pending。例如你有 3 台 A100 节点，Deployment 设了 4 replicas + 硬反亲和（每个 hostname 最多一个 Pod），第 4 个 Pod 永远调度不上。

如果集群有 5000 个 Node，每次调度要对每个 Node 执行所有 Filter 插件，性能开销巨大。K8S 的优化：

  • percentageOfNodesToScore：默认只筛选 50%（≥100 Node）或 10%（≥5000 Node）的 Node。找到足够多可调度 Node 后提前停止 Filter。
  • 并行 Filter：对不同 Node 的 Filter 检查是并行执行的（goroutine 池）。
  • PreFilter 预计算：一些复杂信息（如 Inter-Pod Affinity 的拓扑计算）在 PreFilter 阶段一次算好，避免 Filter 中重复计算。

这意味着在大集群中，scheduler 不一定选到"全局最优 Node"——它选的是"在采样的 Node 中最优的"。对 GPU 集群（通常 <100 台 GPU Node），这个近似影响很小。

实战锚点
GPU 推理 Pod Pending 的排障三步法：
① kubectl describe pod <name> 看 Events 中 FailedScheduling 消息 → 分类统计各原因淘汰了多少节点
② 从淘汰数最多的原因入手。如果是 Insufficient nvidia.com/gpu，执行 kubectl describe node <gpu-node> 查看 Allocated resources 里 GPU 被哪些 Pod 占了
③ 如果是 NodeAffinity/TaintToleration 问题，对比 Pod spec 中的 affinity/toleration 与节点的 labels/taints 是否字符串完全匹配（大小写、连字符都要一致）

§3Score 阶段 · 软偏好打分

通过 Filter 的 Node 进入 Score 阶段。每个 Score 插件对每个候选 Node 打 0-100 分，最终加权求和取最高分的 Node。

LeastAllocated vs MostAllocated（Spread vs Binpack）

LeastAllocated（默认 · 打散策略）

优先选资源剩余最多的 Node → Pod 均匀打散到各节点

score = (allocatable - requested) / allocatable × 100

# Node A: GPU 剩余 6/8 → score = 75
# Node B: GPU 剩余 2/8 → score = 25
# → 选 Node A（更空的）

适合：通用服务、高可用优先、容灾

MostAllocated（Binpack · 装箱策略）

优先选资源剩余最少的 Node → Pod 集中塞满一台再用下一台

score = requested / allocatable × 100

# Node A: GPU 已用 6/8 → score = 75
# Node B: GPU 已用 2/8 → score = 25
# → 选 Node A（更满的）

适合：节省成本、弹性缩容、GPU 碎片整理

GPU 推理集群为什么推荐 MostAllocated（Binpack）？
场景：10 台 8 卡 A100 节点，跑了 10 个单卡推理 Pod。
• LeastAllocated（默认）：每台 1 卡 Pod → 10 台机器各用 1 卡，剩余 7 卡 → 没有一台能放下 8 卡大模型！
• MostAllocated（Binpack）：把 10 个单卡 Pod 塞到 2 台机器 → 剩余 8 台完全空闲 → 大模型随时可用。
一个调度策略的调整 = 省出 8 台 A100 机器的可用性。

BalancedAllocation · CPU/Mem 使用比例均衡

偏好 CPU 和 Memory 使用率接近的节点。避免"CPU 用满了内存还大量空闲"的浪费。

# Node A: CPU 利用率 60%, Memory 利用率 55% → 差值 5%  → 得分高（均衡）
# Node B: CPU 利用率 90%, Memory 利用率 20% → 差值 70% → 得分低（失衡）

NodeAffinity preferred 加分

preferredDuringSchedulingIgnoredDuringExecution 在 Score 阶段给匹配的 Node 加分，权重（weight 1-100）控制偏好强度：

# Pod preferred: weight=80, 希望 gpu-interconnect=nvswitch 的节点
# Node-A 有 nvswitch 标签 → 加 80 分
# Node-B 没有 nvswitch 标签 → 不加分（但也不淘汰——因为是"preferred"不是"required"）

TopologySpreadConstraint 的打分逻辑

当 whenUnsatisfiable: ScheduleAnyway 时，Score 阶段给"放上去后 skew 更小"的 Node 更高分。Pod 数量少的拓扑域中的 Node 得分更高——尽力打散，但不强制。

配置 Binpack 策略的 KubeSchedulerConfiguration

# /etc/kubernetes/scheduler-config.yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler      # 直接修改默认 scheduler
  pluginConfig:
  - name: NodeResourcesFit
    args:
      scoringStrategy:
        type: MostAllocated             # 切换为 binpack 模式
        resources:
        - name: nvidia.com/gpu
          weight: 10                    # GPU 权重最高——优先填满 GPU 维度
        - name: cpu
          weight: 1
        - name: memory
          weight: 1
注意：修改 scheduler 配置会影响整个集群的所有 Pod。如果你同时有 CPU 服务和 GPU 服务，建议用 schedulerName 部署第二个 scheduler 专门服务 GPU Pod，避免影响 CPU 服务的调度。

§4NodeAffinity 和 Taint-Toleration 详解

NodeAffinity · requiredDuringScheduling vs preferredDuringScheduling

类型作用阶段行为用途
requiredDuringScheduling
IgnoredDuringExecution		 Filter（硬约束） 不满足 → Node 被淘汰，Pod 绝不会调度过去 必须是 A100 节点 / 必须在某个 zone
preferredDuringScheduling
IgnoredDuringExecution		 Score（软偏好） 满足 → 加分，不满足 → 不加分但也不淘汰 尽量选 80GB 版本 / 尽量选 NVSwitch 节点
IgnoredDuringExecution 的含义：调度完成后，即使 Node 的 label 被改了（不再满足条件），已经跑着的 Pod 不会被驱逐。这是目前唯一实现的语义。（K8S 社区在讨论 RequiredDuringExecution——label 变了就驱逐）

Taint Effect · 三种级别

Effect对调度的影响对已有 Pod 的影响典型场景
NoSchedule 不容忍的 Pod 不会调度到此 Node 不影响已在运行的 Pod GPU 节点专用隔离
PreferNoSchedule 尽量不调度，但没有其他选择时可以 不影响已在运行的 Pod 非关键节点的软隔离
NoExecute 不容忍的 Pod 不会调度到此 Node 已在运行且不容忍的 Pod 会被驱逐 节点故障、维护模式

常见 Taint 清单

Taint Key何时自动添加Effect你需要做什么
node.kubernetes.io/not-readyNode 状态变为 NotReadyNoExecute系统自动管理；Pod 有默认 tolerationSeconds=300
node.kubernetes.io/unreachableNode 与 apiserver 失联NoExecute同上；失联超时后 Pod 被驱逐到其他 Node
node.kubernetes.io/memory-pressure节点内存不足NoSchedulekubelet 自动加减；根因是节点内存不够用
node.kubernetes.io/disk-pressure节点磁盘不足NoSchedule清理磁盘或扩容
nvidia.com/gpu=present:NoScheduleNVIDIA GPU Operator 配置NoScheduleGPU Pod 需配 toleration；非 GPU Pod 自动被挡

YAML 示例：GPU 节点专用调度

# ===== 完整的 GPU 推理 Pod spec =====
apiVersion: v1
kind: Pod
metadata:
  name: sglang-qwen3-72b
  labels:
    app: sglang-qwen3-72b
spec:
  # --- NodeAffinity：硬约束 + 软偏好 ---
  affinity:
    nodeAffinity:
      # 硬约束：必须是 A100 或 H100 节点
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: nvidia.com/gpu.product          # NVIDIA device plugin 自动打的标签
            operator: In
            values:
            - NVIDIA-A100-SXM4-80GB              # A100 80GB
            - NVIDIA-H100-SXM5-80GB              # H100 80GB
      # 软偏好：尽量选 NVSwitch 互联的节点（weight 80/100）
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: nvidia.com/gpu.interconnect
            operator: In
            values: ["nvswitch"]

  # --- Toleration：容忍 GPU 节点的 taint ---
  tolerations:
  - key: nvidia.com/gpu                          # 匹配 GPU taint
    operator: Exists                             # 不管 value 是什么都容忍
    effect: NoSchedule
  - key: node.kubernetes.io/not-ready            # 容忍短暂的 NotReady（5 分钟）
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300                       # 超过 300s 才驱逐

  containers:
  - name: sglang
    image: lmsysorg/sglang:latest
    command: ["python3", "-m", "sglang.launch_server"]
    args:
    - "--model-path=/models/Qwen3-72B"
    - "--tp=8"                                   # Tensor Parallel = 8 卡
    resources:
      requests:
        nvidia.com/gpu: "8"                      # 声明请求 8 块 GPU
        cpu: "32"
        memory: "320Gi"
      limits:
        nvidia.com/gpu: "8"                      # GPU 的 limit 必须等于 request
        memory: "320Gi"
operator: Exists vs Equal
• Exists：只匹配 key，不看 value → 适合"只要有 GPU taint 就容忍"
• Equal：key + value + effect 全部精确匹配 → 适合区分不同类型 GPU 节点的 taint（如 gpu-type=a100:NoSchedule vs gpu-type=h100:NoSchedule）
实战锚点
最佳实践：Taint + NodeAffinity 双重保护
• Taint：GPU 节点加 nvidia.com/gpu=present:NoSchedule → 防止 CPU Pod 意外跑到 GPU 节点浪费资源
• NodeAffinity required：GPU Pod 声明 nvidia.com/gpu.product In [A100, H100] → 防止 GPU Pod 跑到错误的 GPU 型号节点
两者配合 = 双向隔离：CPU Pod 进不去 GPU 节点，GPU Pod 也不会跑到错误的地方。

§5TopologySpreadConstraints

topologyKey 的含义

topologyKey 是一个 Node label 的 key——拥有相同 value 的 Node 被视为同一个"拓扑域"：

maxSkew / whenUnsatisfiable 详解

字段含义示例
topologyKey 用哪个 Node label 的 key 划分拓扑域 kubernetes.io/hostname → 每个 Node 一个域
topology.kubernetes.io/zone → 每个 AZ 一个域
rack → 每个机架一个域（自定义标签）
maxSkew 各拓扑域中匹配 Pod 数量的最大差值 1 → 最严格均匀
2 → 允许域间差 2 个 Pod
whenUnsatisfiable 无法满足 maxSkew 约束时的行为 DoNotSchedule → Filter 阶段淘汰（硬约束）
ScheduleAnyway → Score 阶段降分（软约束）
labelSelector 统计哪些 Pod 参与分散计算 匹配同一 Deployment 的 Pod labels
minDomains（1.25+） 至少使用多少个拓扑域 3 → 至少分散到 3 个域

推理场景：两种相反的需求

场景 A：多副本推理 · 跨机架打散

同一模型 4 个推理副本（每个 TP8）分散到不同机架 → 一个机架 ToR 交换机故障只丢 1/4 流量

topologySpreadConstraints:
- topologyKey: rack           # 按机架分散
  maxSkew: 1                  # 机架间最多差 1
  whenUnsatisfiable: DoNotSchedule  # 硬约束
  labelSelector:
    matchLabels:
      app: sglang-qwen3-72b

场景 B：多卡推理 · 集中到同一 NVSwitch 域

单个 TP8 Pod 的 8 张 GPU 必须在同一 NVSwitch 域内 → 不用 TopologySpread 解决

# 单 Pod 8 卡 → scheduler 天然保证
# 同一 Pod 的资源来自同一 Node
resources:
  limits:
    nvidia.com/gpu: 8   # 整机分配

# 如果是多机 TP/PP，需要
# nodeAffinity 限定同一 IB 网段
affinity:
  nodeAffinity:
    requiredDuringScheduling...:
      nodeSelectorTerms:
      - matchExpressions:
        - key: network-domain
          operator: In
          values: ["ib-domain-1"]

完整 YAML 示例：跨 Zone + 跨机架双层分散

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-inference
spec:
  replicas: 6                                  # 6 个 TP8 推理副本
  selector:
    matchLabels:
      app: sglang-inference
  template:
    metadata:
      labels:
        app: sglang-inference
    spec:
      topologySpreadConstraints:
      # 第一层（硬约束）：跨 Zone 均匀分布
      - topologyKey: topology.kubernetes.io/zone
        maxSkew: 1                             # Zone 间最多差 1 个 Pod
        whenUnsatisfiable: DoNotSchedule       # 不满足就不调度
        labelSelector:
          matchLabels:
            app: sglang-inference
      # 第二层（软约束）：同 Zone 内跨机架尽量打散
      - topologyKey: rack
        maxSkew: 1                             # 机架间尽量差不超过 1
        whenUnsatisfiable: ScheduleAnyway      # 尽力而为，不强制
        labelSelector:
          matchLabels:
            app: sglang-inference

      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: nvidia.com/gpu.product
                operator: In
                values: ["NVIDIA-A100-SXM4-80GB"]
      tolerations:
      - key: nvidia.com/gpu
        operator: Exists
        effect: NoSchedule

      containers:
      - name: sglang
        image: lmsysorg/sglang:latest
        resources:
          requests:
            nvidia.com/gpu: "8"
            cpu: "32"
            memory: "320Gi"
          limits:
            nvidia.com/gpu: "8"
            memory: "320Gi"
踩坑：如果某些 Node 没有 topologyKey 对应的标签（比如没打 rack 标签），这些 Node 会被直接跳过——视为不属于任何拓扑域。部署前务必用 kubectl get nodes --show-labels | grep rack 确认所有 GPU 节点都有该标签。
另一个坑：labelSelector 必须与 Pod 自己的 label 匹配。如果写错了（比如漏了一个 label key），每个域都会被统计为 0 个 Pod → 约束形同虚设 → Pod 不会被打散。
实战锚点
多机推理（Pipeline Parallel 跨 2-4 台机器）的调度挑战：
• 需求：4 个 TP8 Pod 分布在 4 台不同机器上，但这 4 台必须在同一个 IB 网段（高带宽通信）
• 解法：① topologyKey: kubernetes.io/hostname + maxSkew: 1 + DoNotSchedule 保证分散到不同机器 ② nodeAffinity required 限定 network-domain=ib-domain-1 保证同一网段 ③ 考虑用 Gang Scheduling（Volcano / Coscheduling）确保 4 个 Pod 同时调度成功或全部不调度

§6抢占（Preemption）

PriorityClass 定义

抢占的前提是 Pod 有不同优先级。通过 PriorityClass 声明：

# ===== 推理集群的三级优先级 =====

# 最高优先级：在线推理服务
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: online-inference
value: 1000000                         # 值越大优先级越高（int32 范围）
globalDefault: false
preemptionPolicy: PreemptLowerPriority  # 允许抢占比自己低的 Pod
description: "在线推理服务 — 面向终端用户，不可中断"
---
# 中等优先级：离线批量推理 / 评测
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch-inference
value: 100000
globalDefault: false
preemptionPolicy: PreemptLowerPriority  # 可以抢占开发 Pod
description: "离线批推理 — 无实时要求，可被在线服务抢占"
---
# 最低优先级：开发调试
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: dev-workload
value: 1000
globalDefault: true                     # 没指定 priorityClassName 的 Pod 用这个
preemptionPolicy: Never                 # 自己不会去抢占任何人
description: "开发调试 — 随时可被正式负载抢占"

抢占流程详解

抢占不是"立即生效"——从触发到高优 Pod 真正运行，需要等被驱逐 Pod 的 terminationGracePeriodSeconds 走完。如果被驱逐的离线推理 Pod 设了 grace=600s（排空长推理请求），高优 Pod 可能要等 10 分钟才能调度上去。
优化：离线批推理 Pod 的 grace period 设短一点（如 30s），定期做 checkpoint，被抢占后从 checkpoint 恢复。

推理场景的优先级设计

负载类型PriorityClassvalue抢占策略被抢占后的处理
在线推理 online-inference 1000000 可抢占离线和开发 不应被抢占（最高优先级）
离线批推理 batch-inference 100000 可抢占开发 从 checkpoint 恢复继续
开发调试 dev-workload 1000 Never（不抢占任何人） 重新提交即可 
# 在 Pod spec 中引用 PriorityClass
apiVersion: v1
kind: Pod
metadata:
  name: sglang-online
spec:
  priorityClassName: online-inference    # 使用高优先级
  terminationGracePeriodSeconds: 90      # 排空长推理请求
  containers:
  - name: sglang
    image: lmsysorg/sglang:latest
    resources:
      limits:
        nvidia.com/gpu: 8
抢占的代价：被驱逐的低优先级 Pod 如果正在处理请求，已执行的计算全部丢失。
• 离线批推理：必须实现 checkpoint + 幂等重试，否则被抢占 = 几小时白跑
• 在线推理：如果被不合理地设为低优先级，被抢占意味着线上故障——响应中断、用户看到 5xx
• 开发调试：无所谓，重新提交就行

preemptionPolicy: Never 表示：这个 PriorityClass 的 Pod 不会去抢占别人，但自己可以被更高优先级的 Pod 抢占。

用途：

  • 开发调试 Pod 虽然优先级最低，但你不希望它去抢占更低优先级的系统 DaemonSet Pod
  • 某些"可抢占但不抢占别人"的 workload，如低优先级的数据预处理任务

设了 Never 的 Pod，当 Filter 全失败时不会触发 Preemption → 直接进 unschedulableQ 等待资源释放。

实战锚点
典型 GPU 集群优先级金字塔：
system-node-critical (2000001000) → K8S 系统组件（kube-proxy, device-plugin）
online-inference (1000000) → 在线推理服务（不可中断）
batch-inference (100000) → 离线批量推理 / 训练 / 评测
dev-workload (1000, preemptionPolicy:Never) → 开发调试

流量突增场景：Autoscaler 扩出新的在线推理 Pod → 集群资源不足 → Preemption 自动驱逐离线批推理 Pod 腾出 GPU → 在线服务扩容成功 → 流量回落后离线任务从 checkpoint 恢复。整个过程无需人工干预。

§7带走这些

① 三个队列
activeQ → backoffQ → unschedulableQ · Pod Pending 时先确认它在哪个队列 · unschedulableQ 需要集群状态变化才能激活
② 八大扩展点
PreFilter → Filter → PostFilter → PreScore → Score → Reserve → Permit → Bind · 插件化架构，每个阶段可定制
③ Filter = 一票否决
NodeResourcesFit / NodeAffinity / TaintToleration / PodTopologySpread / InterPodAffinity · 任何一个说 No 就淘汰
④ Score = 加权偏好
LeastAllocated(打散) vs MostAllocated(binpack) · preferred affinity 加分 · topology 打散加分 · 权重可配置
⑤ GPU 推荐 Binpack
MostAllocated 填满少数节点 → 腾出完整 8 卡节点给大模型 · 配合 GPU weight=10 强化 GPU 维度 binpack
⑥ Taint 双向隔离
GPU 节点加 NoSchedule taint → CPU Pod 进不来 · GPU Pod 加 nodeAffinity → 不会跑到错误节点
⑦ Topology 两层
硬约束跨 Zone 打散（DoNotSchedule）+ 软约束跨机架尽力打散（ScheduleAnyway）
⑧ 抢占金字塔
online > batch > dev · 离线任务做 checkpoint · preemptionPolicy:Never 防误伤
实战锚点 · 综合配置：8 卡节点优先 binpack + 跨机架打散
# ===== KubeSchedulerConfiguration =====
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler
  pluginConfig:
  - name: NodeResourcesFit
    args:
      scoringStrategy:
        type: MostAllocated              # GPU binpack
        resources:
        - name: nvidia.com/gpu
          weight: 10
        - name: cpu
          weight: 1
        - name: memory
          weight: 1
---
# ===== Deployment =====
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-qwen3-72b
spec:
  replicas: 4
  selector:
    matchLabels:
      app: sglang-qwen3-72b
  template:
    metadata:
      labels:
        app: sglang-qwen3-72b
    spec:
      priorityClassName: online-inference       # 高优先级
      terminationGracePeriodSeconds: 90         # 排空推理请求
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: nvidia.com/gpu.product
                operator: In
                values: ["NVIDIA-A100-SXM4-80GB"]
      tolerations:
      - key: nvidia.com/gpu
        operator: Exists
        effect: NoSchedule
      topologySpreadConstraints:
      - topologyKey: rack
        maxSkew: 1
        whenUnsatisfiable: ScheduleAnyway       # 跨机架尽力打散
        labelSelector:
          matchLabels:
            app: sglang-qwen3-72b
      containers:
      - name: sglang
        image: lmsysorg/sglang:latest
        resources:
          requests:
            nvidia.com/gpu: "8"
            cpu: "32"
            memory: "320Gi"
          limits:
            nvidia.com/gpu: "8"
            memory: "320Gi"

效果：4 个 8 卡推理副本优先填满 A100 节点（GPU binpack），同时跨机架尽力打散（topology spread），被 Taint + NodeAffinity 双重保护不受 CPU Pod 干扰，优先级最高可抢占离线任务。
