§0为什么推理 Pod 老是被 OOM Kill

你一定见过这些场景：

  • 推理服务跑了几个小时突然被杀——kubectl describe pod 显示 OOMKilled，但 nvidia-smi 看 GPU 显存并没有超
  • 明明节点有 256GB 内存，你的 Pod 只用了 50GB 就被杀——因为你设了 limits.memory: 48Gi
  • Pod 一直 Pending，describe 显示 Insufficient memory——但 kubectl top node 显示节点只用了 60%
  • 两个推理 Pod 同时跑，节点内存不够时，QoS 等级低的那个先被杀
核心问题：K8S 的资源管理有两个完全不同的维度——调度时和运行时。scheduler 看 requests 决定 Pod 放哪，kubelet 看 limits 决定何时杀 Pod。搞混这两个，就是 OOM Kill 和 Pending 的根源。
实战锚点
一个典型的 LLM 推理服务（如 Qwen3-72B，8×A100-80G）：GPU 显存 640GB 由 vLLM/SGLang 精确管理不会超，但Host 内存才是 OOM 的元凶——KV Cache 管理结构、tokenizer 词表、请求 batch buffer、NCCL 通信 buffer 全在 Host 内存里。实际占用可能从启动时的 30GB 涨到高并发时的 55GB。如果 limits.memory 只设了 48Gi，高并发时就会被 OOM Kill。

§1requests 和 limits 的本质区别

一句话：requests = 调度保证，limits = 运行天花板

CPU vs Memory 的限制机制完全不同

维度CPU（可压缩资源）Memory（不可压缩资源）
限制机制CFS（Completely Fair Scheduler）quotacgroup memory.max
超限后果Throttle——降速，进程暂停等待下个周期OOM Kill——SIGKILL 直接杀进程
单位1 = 1 vCPU = 1000m1Gi = 10243 bytes
可压缩？是（CPU 时间片可以"挤一挤"）否（内存用了就是用了，无法暂停）
overcommit 安全性比较安全（最多变慢）非常危险（可能被杀）

CPU limits：CFS quota 实现（throttle 不杀）

# 假设 limits.cpu = 4，CFS period = 100ms（默认）
# kubelet 设置 cgroup 参数：
cpu.max = "400000 100000"
#           quota   period
#
# 含义：每 100ms 时间窗口内，这个 cgroup 最多用 400ms CPU 时间
# 等效于最多跑满 4 个核
# 用完 400ms 后，本周期内所有线程被挂起（throttle），下个周期恢复

# 查看容器的 CFS 配置：
$ cat /sys/fs/cgroup/cpu.max
400000 100000

# 查看被 throttle 的统计：
$ cat /sys/fs/cgroup/cpu.stat | grep throttled
nr_throttled 12345         # 被限速的总次数
throttled_usec 987654321   # 总共被限速的微秒数
CPU throttle 对推理延迟的隐蔽影响：推理服务的 prefill 阶段需要 CPU 做 tokenize 编码，如果 CPU 被 throttle，TTFT（首 token 延迟）会飙升。现象是 P99 延迟周期性升高但 Pod 还活着。排查方法：查看 nr_throttled 是否持续增长。

Memory limits：cgroup memory.max 实现（超了就 OOM Kill）

# 查看容器的内存限制：
$ cat /sys/fs/cgroup/memory.max
53687091200                # = 50Gi 的字节数

# 查看当前使用：
$ cat /sys/fs/cgroup/memory.current
48318382080                # ≈ 45Gi

# 当 memory.current >= memory.max 时的内核行为：
# 1. 内核尝试回收页面缓存（page cache）和可回收 slab
# 2. 回收不够 → 触发 cgroup OOM Killer
# 3. OOM Killer 选择 cgroup 内 oom_score 最高的进程发 SIGKILL
# 4. 容器主进程被杀 → kubelet 检测退出码 137 → 上报 OOMKilled
# 5. 按 restartPolicy 决定是否在原节点重启
常见误区：以为 OOM Kill 是 kubelet 做的。实际上是 Linux 内核的 cgroup OOM Killer 直接发 SIGKILL——无法捕获、无法优雅处理、没有任何预警。kubelet 只是事后从容器退出码（137）得知发生了 OOM。

requests 和 limits 的关系总结

维度requestslimits
作用时机调度时（scheduler 决策）运行时（cgroup 强制执行）
语义最低保证量——"我至少需要这么多"绝对上限——"我绝不能超过这么多"
不设的后果scheduler 当作 0 → 可能在一个节点上塞太多 Pod无上限 → 容器可以吃光整个节点的资源
CPU 超限—Throttle（进程被暂停，不杀）
Memory 超限—OOM Kill（进程被杀，SIGKILL）
配置后果QoS
只设 limits，不设 requestsK8S 自动把 requests 设为 = limitsGuaranteed（如果 CPU+Memory 都这样）
只设 requests，不设 limits容器可以无限使用资源，直到节点耗尽Burstable
两个都不设零保证 + 无上限 = 最危险的状态BestEffort
requests > limitsAPI Server 直接拒绝，创建失败—
requests = limits最稳定：调度精确 + 运行时有保证Guaranteed
实战锚点
推理服务的经典翻车：requests.memory = 16Gi，limits.memory = 64Gi。Scheduler 认为这个 Pod 只需要 16Gi 内存，于是在 256Gi 的节点上调度了 12 个（12×16=192 < 256）。但运行时每个 Pod 实际用 50Gi → 总量 600Gi → 节点内存耗尽 → 连环 OOM Kill。教训：推理服务的 memory requests 应该接近 limits。

§2三种 QoS 等级

K8S 根据 Pod 中所有容器的 requests/limits 配置自动计算 QoS 等级。QoS 决定了节点资源紧张时谁先被杀。

QoS 分类规则

QoS Class条件保护等级
Guaranteed Pod 内每个容器的 CPU 和 Memory 都设了 requests 且 requests == limits 最高保护，最后被杀
Burstable 至少一个容器设了 requests 或 limits，但不满足 Guaranteed 条件 中等保护
BestEffort 所有容器都没有设任何 requests 和 limits 零保护，最先被杀

OOM Kill 顺序

1000（最高分） 典型场景：开发者忘记设 resources 的测试 Pod · 生产环境绝对禁止 Burstable — 按比例计算，中间被杀 oom_score_adj = 2 ~ 999（公式：1000 - 1000 × memoryRequest / nodeCapacity） 同为 Burstable 时，实际内存使用超出 requests 比例越大的越先被杀 Guaranteed — 最后被杀 oom_score_adj = -997（接近最低分） 除非它自己超过了自己的 limits（那是 cgroup 级 OOM，跟节点级驱逐无关） 完整顺序：BestEffort → Burstable（oom_score 高的先）→ Guaranteed · kubelet eviction 先于内核 OOM Killer

oom_score_adj 的设置

# Guaranteed Pod：固定值
oom_score_adj = -997

# BestEffort Pod：固定值
oom_score_adj = 1000

# Burstable Pod：按公式计算
oom_score_adj = max(2, 1000 - 1000 × (memoryRequest / machineMemory))

# 例：节点 256Gi 内存，Pod requests.memory = 50Gi
# oom_score_adj = max(2, 1000 - 1000 × 50/256) = max(2, 805) = 805
# → requests 占节点比例越大，score 越低，越不容易被杀

# 最终 OOM score = oom_score_adj + (进程 RSS / 总内存) × 1000
# 所以即使 oom_score_adj 一样，实际用得多的进程也会先被杀
kubelet eviction vs kernel OOM Kill：kubelet 有一套独立的驱逐机制（eviction），在节点 memory.available 低于阈值（默认 100Mi）时按 QoS 顺序驱逐 Pod。这比内核 OOM Killer 更温和——Pod 状态变为 Evicted 而非 OOMKilled，且 Pod 不会在原节点重启，而是由上层 controller 在其他节点重建。
实战锚点
场景：一台 8×A100 节点（768GB 内存）上跑了两个推理 Pod：
  • Pod A（Burstable）：requests.memory=50Gi，limits.memory=100Gi → oom_score_adj ≈ 935
  • Pod B（Guaranteed）：requests.memory=200Gi，limits.memory=200Gi → oom_score_adj = -997
节点内存压力触发时，Pod A 一定先被杀——哪怕 Pod B 实际用了更多内存。结论：生产推理服务必须用 Guaranteed QoS。
维度kubelet Eviction（驱逐）Kernel OOM Kill
触发者kubelet（用户空间进程）Linux 内核
触发条件节点可用资源低于 eviction thresholdcgroup memory.max 被突破 或 系统内存完全耗尽
选择逻辑QoS → Priority → 资源使用超出 requests 的程度oom_score（oom_score_adj + 实际内存占比）
Pod 状态Failed + reason: EvictedOOMKilled（exitCode=137）
后续行为Pod 不在原节点重启，由 controller 重建按 restartPolicy 可能在原节点重启

§3Extended Resources（GPU 等）

CPU 和 Memory 是 K8S 内置资源（native resources）。GPU、FPGA、RDMA 网卡等设备通过 Extended Resources 机制扩展，由 device-plugin 注册到 kubelet。最常见的就是 nvidia.com/gpu。

nvidia.com/gpu 的特殊规则

特性CPU / Memorynvidia.com/gpu
单位可以是小数（如 500m = 0.5 核）只能是正整数（1, 2, 4, 8）
requests 与 limitsrequests ≤ limits，可以不等必须相等（apiserver 强制校验）
overcommitCPU 可以超分绝对禁止（GPU 显存无法共享）
分割性可以按毫核/字节粒度分配不可分割（一整块卡给你）
跨节点不涉及不能跨节点拼凑（请求 4 卡 = 单节点 4 卡）
限制执行者cgroup（内核级）device-plugin（通过环境变量 + 设备挂载）

GPU 分配的完整链路

单个节点（不能跨节点！） ② Kubelet 调用 device-plugin Allocate()，从节点 GPU 池中取出 4 块，通过环境变量和设备挂载传给容器

YAML 示例

# 正确：请求 8 块 GPU（单机 Tensor Parallel）
apiVersion: v1
kind: Pod
metadata:
  name: sglang-qwen3-72b
spec:
  containers:
  - name: sglang
    image: lmsysorg/sglang:v0.4.5-cu124
    resources:
      requests:
        nvidia.com/gpu: 8          # 必须是正整数
      limits:
        nvidia.com/gpu: 8          # 必须跟 requests 相等

# 错误示例 ——
resources:
  requests:
    nvidia.com/gpu: 4              # ✗ requests != limits → apiserver 拒绝
  limits:
    nvidia.com/gpu: 8

resources:
  requests:
    nvidia.com/gpu: 0.5            # ✗ 不能是小数 → apiserver 拒绝
  limits:
    nvidia.com/gpu: 0.5
GPU 不支持 overcommit 的根本原因：GPU 显存没有 swap 机制、没有 page cache 可回收、没有 CFS 时间片可切分。一旦显存被一个进程占用，其他进程无法透明地使用同一块空间。强制共享会导致 CUDA OOM error 或计算结果错误。
GPU 拓扑感知：默认 device-plugin 不保证分配的 4 卡之间有 NVLink 高速互连。如果推理服务需要卡间高速通信（Tensor Parallelism），需要配合 topology-aware scheduling（如 NVIDIA GPU Operator 的 topology manager 策略）。下一章详述。
实战锚点
多机推理（如 Qwen3-235B 需要 4 机 32 卡）时，你不能写 nvidia.com/gpu: 32——因为单节点最多 8 卡。正确做法是创建 4 个 Pod 各请求 8 卡，通过 LWS（LeaderWorkerSet）或 PyTorchJob 编排它们的启动顺序和 NCCL 通信。GPU 资源模型只管"单 Pod 单节点"——跨节点的编排是上层 controller 的事。

§4LimitRange · 给 namespace 设默认 requests/limits

LimitRange 解决三个问题：

  • 防忘记：给没设 resources 的容器自动注入默认 requests/limits
  • 防超大：限制单个 Pod/Container 的最大资源请求
  • 防超小：确保每个容器至少请求一定资源（避免饥饿）

YAML 示例

# 给推理 namespace 设置资源约束
apiVersion: v1
kind: LimitRange
metadata:
  name: inference-limits
  namespace: inference
spec:
  limits:
  - type: Container
    default:                       # 没设 limits 时自动注入
      cpu: "8"
      memory: 32Gi
    defaultRequest:                # 没设 requests 时自动注入
      cpu: "4"
      memory: 16Gi
    max:                           # 单个容器的 limits 上限
      cpu: "64"
      memory: 512Gi
      nvidia.com/gpu: "8"          # 单容器最多 8 卡（单机上限）
    min:                           # 单个容器的 requests 下限
      cpu: "500m"
      memory: 1Gi
  - type: Pod                      # Pod 级限制（所有容器之和）
    max:
      cpu: "128"
      memory: 768Gi
      nvidia.com/gpu: "8"

LimitRange 的行为

场景LimitRange 行为
容器没设 limits自动注入 default 值
容器没设 requests自动注入 defaultRequest 值
容器 limits 超过 maxapiserver 拒绝创建 Pod（准入控制阶段报错）
容器 requests 低于 minapiserver 拒绝创建 Pod
已经在运行的 Pod不受影响——LimitRange 只在 Pod 创建时生效
LimitRange 是准入控制器：它在 Pod 创建时注入/校验，对已运行的 Pod 无效。修改 LimitRange 后，需要 kubectl rollout restart 或重新创建 Pod 才能应用新规则。
实战锚点
GPU 集群最佳实践：给推理 namespace 设 LimitRange，确保不会有人创建 BestEffort Pod 偷偷占用 GPU 节点的 CPU/Memory 资源。关键配置：① defaultRequest.cpu 至少 1 核 ② defaultRequest.memory 至少 2Gi ③ max.nvidia.com/gpu = 8 防止请求超过单节点 GPU 数。

§5ResourceQuota · 给 namespace 设资源总量上限

如果说 LimitRange 是"单人限购"（限制单个 Pod），那 ResourceQuota 就是"团队预算"——限制整个 namespace 内所有 Pod 的资源总和。

计算型配额

# 团队 A 的推理 namespace：最多用 32 块 GPU
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: inference-team-a
spec:
  hard:
    requests.cpu: "128"            # 所有 Pod requests.cpu 之和 ≤ 128 核
    requests.memory: 512Gi         # 所有 Pod requests.memory 之和 ≤ 512Gi
    limits.cpu: "256"              # 所有 Pod limits.cpu 之和 ≤ 256 核
    limits.memory: 1Ti             # 所有 Pod limits.memory 之和 ≤ 1TiB
    requests.nvidia.com/gpu: "32"  # 团队 A 最多使用 32 块 GPU

对象数配额

# 限制 namespace 内的对象数量，防止资源泄露
apiVersion: v1
kind: ResourceQuota
metadata:
  name: object-quota
  namespace: inference-team-a
spec:
  hard:
    pods: "50"                     # 最多 50 个 Pod
    services: "10"                 # 最多 10 个 Service
    configmaps: "50"               # 最多 50 个 ConfigMap
    persistentvolumeclaims: "20"   # 最多 20 个 PVC
    services.loadbalancers: "2"    # LB 类型 Service 最多 2 个（贵）

配合 PriorityClass 的 scopeSelector

# 按优先级分别限配额——高优先级推理服务不受低优先级的配额限制
apiVersion: v1
kind: ResourceQuota
metadata:
  name: low-priority-gpu-limit
  namespace: shared-inference
spec:
  hard:
    requests.nvidia.com/gpu: "8"   # 低优先级任务最多只能用 8 卡
  scopeSelector:
    matchExpressions:
    - scopeName: PriorityClass
      operator: In
      values:
      - low-priority               # 只匹配 priorityClassName=low-priority 的 Pod
      - batch-job
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: high-priority-gpu-limit
  namespace: shared-inference
spec:
  hard:
    requests.nvidia.com/gpu: "64"  # 高优先级推理服务可以用 64 卡
  scopeSelector:
    matchExpressions:
    - scopeName: PriorityClass
      operator: In
      values:
      - high-priority
ResourceQuota 的强制副作用：当 namespace 存在 ResourceQuota 且包含计算资源配额（如 requests.cpu）时，该 namespace 下所有新建的 Pod 都必须设 resources。否则 apiserver 无法计算配额用量，会直接拒绝：must specify requests.cpu, requests.memory。所以 ResourceQuota 通常配合 LimitRange 使用（提供默认值兜底）。

查看配额使用情况

$ kubectl describe resourcequota team-a-quota -n inference-team-a

Name:                    team-a-quota
Namespace:               inference-team-a
Resource                 Used     Hard
--------                 ----     ----
limits.cpu               96       256
limits.memory            384Gi    1Ti
requests.cpu             48       128
requests.memory          384Gi    512Gi
requests.nvidia.com/gpu  24       32    ← 还能再申请 8 块 GPU
实战锚点
GPU 集群多团队共享的标准模式：每个团队一个 namespace + 一个 ResourceQuota（限制 GPU 总量）+ 一个 LimitRange（提供默认值 + 限制单 Pod 上限）。这样既能防止一个团队把所有 GPU 吃光，也能防止单个 Pod 请求过多资源阻塞调度。

§6资源设置最佳实践

推理服务的 resources 配置范例

# 8×A100-80GB 单机部署 Qwen3-72B（SGLang Tensor Parallel 8）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-qwen3-72b
  namespace: inference
spec:
  replicas: 2
  template:
    spec:
      containers:
      - name: sglang
        image: lmsysorg/sglang:v0.4.5-cu124
        command: ["python3", "-m", "sglang.launch_server"]
        args:
        - "--model-path=/models/Qwen3-72B"
        - "--tp=8"
        - "--mem-fraction-static=0.88"      # 控制 GPU 显存使用比例
        resources:
          requests:
            cpu: "4"                         # 推理主要用 GPU，CPU 做 tokenize/网络
            memory: 50Gi                     # = limits，让 memory 成为 Guaranteed 级别
            nvidia.com/gpu: 8                # 8 卡 Tensor Parallel
          limits:
            cpu: "16"                        # 允许 burst（prefill 高并发时 CPU 密集）
            memory: 50Gi                     # = requests！推理内存稳定，不允许超
            nvidia.com/gpu: 8                # GPU 强制 requests == limits
注意：上面 CPU requests(4) ≠ limits(16)，严格来说 QoS 是 Burstable 而非 Guaranteed。但因为 memory 的 requests == limits 且 GPU 也相等，这个 Pod 的 oom_score_adj 会比较低。如果需要绝对的 Guaranteed QoS（生产环境推荐），把 CPU 也设为 requests == limits == 16。

三种资源的设置思路

CPU: requests=4, limits=16

  • 推理 90% 算力在 GPU
  • CPU 负责 tokenize、HTTP、调度
  • prefill 阶段 CPU burst 需求高
  • 超 limits 只 throttle 不杀
  • requests 设低可节省调度资源

Memory: requests=limits=50Gi

  • 推理服务内存使用模式稳定
  • 模型加载后基本恒定
  • KV Cache 有上限（mem_fraction）
  • 超了就 OOM Kill，不可恢复
  • 必须 Guaranteed 保护

GPU: requests=limits=8

  • 强制要求 requests == limits
  • 只能正整数
  • 不可超分、不可共享
  • 8 卡 = TP-8 单机推理
  • 没有任何灵活空间

Memory 设多少？先压测再定

# 推理服务 Host Memory 构成（以 8×A100 Qwen3-72B 为例）
# ┌────────────────────────────────────────────────────────┐
# │ Tokenizer 词表 + 映射表          ~2-4 GB               │
# │ KV Cache 管理结构（host 端）      ~1-3 GB               │
# │ 请求队列 / batch scheduler       ~2-5 GB               │
# │ NCCL 通信 buffer（每卡 0.5-1G）  ~4-8 GB               │
# │ Python runtime + 框架开销        ~3-5 GB               │
# │ 峰值 batch 处理临时内存          ~5-15 GB              │
# ├────────────────────────────────────────────────────────┤
# │ 总计：稳态 ~20-30 GB，峰值可达 ~40-50 GB               │
# └────────────────────────────────────────────────────────┘

# 正确做法：压测观察峰值，再加余量
# Step 1: 先不设 limits.memory，跑满负载压测 1 小时
# Step 2: 查 cgroup 历史峰值
$ cat /sys/fs/cgroup/memory.peak        # cgroup v2 的历史最高水位
$ cat /sys/fs/cgroup/memory.max_usage_in_bytes  # cgroup v1

# Step 3: limits = peak × 1.2（留 20% buffer）
# Step 4: requests = limits（保证 Guaranteed QoS）

常见错误配置及后果

错误配置后果正确做法
完全不设 resources BestEffort QoS → 一有压力就被杀 · 无调度约束可能超卖 永远设 requests + limits
memory requests << limits（如 16Gi / 64Gi） scheduler 超卖内存 → 运行时集体 OOM Kill 推理服务 memory requests = limits
CPU limits 设太低（如 2 核） tokenize/prefill 被 throttle → TTFT 飙升 CPU limits = 2~4× requests
memory limits 只看空载值 高并发时 KV Cache 增长超限 → OOMKilled 用压测峰值 × 1.2
GPU requests ≠ limits apiserver 直接拒绝创建 GPU 始终 requests == limits

完整 Guaranteed QoS 推理 Pod

# 如果追求最高保护（生产环境推荐）：全部 requests == limits
apiVersion: v1
kind: Pod
metadata:
  name: sglang-guaranteed
  namespace: inference
spec:
  containers:
  - name: sglang
    image: lmsysorg/sglang:v0.4.5-cu124
    resources:
      requests:                    # requests == limits → QoS = Guaranteed
        cpu: "16"                  # 独占 16 核（代价：scheduler 要扣 16 核）
        memory: 50Gi
        nvidia.com/gpu: 8
      limits:                      # 完全等于 requests
        cpu: "16"
        memory: 50Gi
        nvidia.com/gpu: 8
# 此 Pod：
# - QoS = Guaranteed
# - oom_score_adj = -997
# - 节点内存紧张时最后被驱逐
# - 代价：CPU 独占 16 核，即使平时只用 4 核（利用率 vs 稳定性的取舍）
实战锚点
Guaranteed 的代价与取舍：CPU requests=16 意味着 scheduler 从节点 allocatable 中扣除 16 核。如果推理服务平时只用 4 核，这 12 核就"浪费"了。但对于生产推理服务，这个代价完全值得——被 OOM Kill 一次的损失（请求丢失、模型重加载 2 分钟、GPU 闲置）远大于多占 12 核 CPU 的成本。稳定性 > 利用率。

§7带走这些

① requests
Scheduler 的调度依据 · 决定 Pod 放哪台节点 · 所有 Pod requests 总和 ≤ Node Allocatable
② limits
运行时天花板 · kubelet/cgroup 强制执行 · CPU 超了 throttle（不杀）· Memory 超了 OOM Kill
③ QoS 三等级
Guaranteed（-997）→ Burstable（2~999）→ BestEffort（1000）· 数字越大越先被杀
④ OOM Kill 顺序
BestEffort 最先 → Burstable 按比例 → Guaranteed 最后 · 推理服务用 Guaranteed
⑤ GPU 特殊规则
只能整数 · requests == limits · 不可超分 · 不跨节点 · device-plugin 管理
⑥ LimitRange
namespace 级 · 注入默认值 + 限制单 Pod 上下限 · 准入时生效
⑦ ResourceQuota
namespace 级 · 限制所有 Pod 的资源总量 + 对象数 · 配合 PriorityClass 精细控制
⑧ 推理黄金法则
Memory: requests=limits（Guaranteed 保护）· CPU: 可 burst · GPU: 天然 Guaranteed
