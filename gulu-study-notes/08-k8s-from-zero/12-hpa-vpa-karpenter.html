§0为什么推理服务需要弹性

大模型推理服务的流量模式极不均匀：

  • 波峰波谷 10 倍差异：工作日 10:00-12:00、20:00-22:00 流量是凌晨的 10 倍以上
  • 突发事件：营销活动、热点新闻导致流量在几分钟内暴涨 5-10x
  • GPU 极贵：A100 / H100 单卡月成本 $2000+，闲置一天 = 烧掉几千块
  • 冷启动慢：模型加载 30-120 秒，不可能等流量来了再手动扩容
弹性的本质：让资源供给自动跟随流量曲线。不多（浪费 GPU 钱），不少（用户排队/超时），刚刚好。K8S 给了三个层次的弹性工具——Pod 水平扩缩（HPA）、Pod 垂直调整（VPA）、节点自动扩缩（Karpenter/CA）。

§1HPA · Horizontal Pod Autoscaler

HPA 是最常用的弹性手段：根据指标自动调整 Deployment/StatefulSet 的副本数。

核心公式

desiredReplicas = ceil( currentMetricValue / targetMetricValue × currentReplicas )

# 例：当前 QPS 平均 80/Pod，目标 50/Pod，当前 3 副本
desiredReplicas = ceil( 80 / 50 × 3 ) = ceil(4.8) = 5

# 例：当前 QPS 平均 30/Pod，目标 50/Pod，当前 5 副本
desiredReplicas = ceil( 30 / 50 × 5 ) = ceil(3.0) = 3  ← 缩容
HPA Controller 每 15 秒（--horizontal-pod-autoscaler-sync-period）执行一次计算。当有多个指标时，分别计算每个指标的 desiredReplicas，取最大值。

CPU 指标对推理服务几乎无用：GPU 推理瓶颈在显卡而非 CPU。CPU 利用率可能只有 20% 但 GPU 已跑满。推理场景必须用自定义指标。

完整 HPA YAML（自定义指标 + behavior 控制）

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: sglang-custom-hpa
  namespace: inference
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sglang-server
  minReplicas: 2
  maxReplicas: 20
  metrics:
  # 指标 1：每个 Pod 的 QPS 不超过 50
  - type: Pods
    pods:
      metric:
        name: sglang_requests_per_second
      target:
        type: AverageValue
        averageValue: "50"         # 当平均 QPS > 50 时扩容
  # 指标 2：首 Token 延迟不超过 200ms
  - type: Pods
    pods:
      metric:
        name: sglang_avg_ttft_ms
      target:
        type: AverageValue
        averageValue: "200"        # TTFT > 200ms = 用户体感差，需扩容
  # 多指标时取"要求副本数最大的那个"确保所有 SLO 都满足

  # ========== behavior：精细控制扩缩速度 ==========
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30   # 扩容防抖：30s 内取建议值最大的
      policies:
      - type: Percent
        value: 100                     # 每次最多翻倍（2→4→8）
        periodSeconds: 30
      - type: Pods
        value: 4                       # 或者每次最多加 4 个
        periodSeconds: 30
      selectPolicy: Max                # 取两个策略中更激进的

    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容防抖：5 分钟内取建议值最小的
      policies:
      - type: Percent
        value: 25                      # 每次最多缩 25%（8→6→5→4）
        periodSeconds: 60
      selectPolicy: Min                # 取更保守的策略

scaleDown stabilizationWindow（防抖）详解

behavior 关键参数总结

参数scaleUp 推荐值scaleDown 推荐值作用
stabilizationWindowSeconds30s300s（5min）在窗口内取最大/最小建议值
policies.typePercent: 100Percent: 25每次扩缩的上限
policies.periodSeconds30s60s每次评估的间隔
selectPolicyMax（激进）Min（保守）多策略时如何选择
扩缩容抖动（flapping）：如果缩容 stabilizationWindow 太短，流量一小幅波动就触发扩→缩→扩→缩。对推理服务来说，每次扩容都意味着冷启动（模型加载 60s+），抖动 = 持续处于不可用状态。缩容窗口建议 5-10 分钟。
实战锚点
推理 QPS > 阈值时自动扩 Pod：Prometheus 每 15s 抓一次 SGLang /metrics → Prometheus Adapter 聚合为 custom metric → HPA 每 15s 查一次 → 计算 desiredReplicas → patch Deployment replicas → 新 Pod 创建 → 如果当前节点有 GPU 空余则调度，否则触发 Karpenter 扩节点（§3）。整条链路全自动。

§2VPA · Vertical Pod Autoscaler

VPA 不调副本数，而是调单个 Pod 的 requests / limits——让每个 Pod 拿到"刚好够"的资源量。

三种模式

模式行为是否重启 Pod适用场景
Off只计算推荐值，不自动修改否观察阶段 / 手动调优（推理服务首选）
Initial仅在新 Pod 创建时设置推荐值否（已有 Pod 不动）滚动更新时自动生效
Auto运行时自动调整（超出范围就驱逐重建）是（驱逐+重建）无状态轻量服务

工作原理：三个组件协作

VPA 配置示例（Off 模式 — 只推荐不动手）

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: sglang-vpa
  namespace: inference
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sglang-server
  updatePolicy:
    updateMode: "Off"            # 只推荐，不自动修改 Pod
  resourcePolicy:
    containerPolicies:
    - containerName: sglang
      minAllowed:
        cpu: "4"                 # 推荐值下界：最少 4 核
        memory: "16Gi"
      maxAllowed:
        cpu: "32"                # 推荐值上界：最多 32 核
        memory: "128Gi"
      controlledResources: ["cpu", "memory"]  # 只管 CPU/内存，不管 GPU

# 查看 VPA 推荐值
$ kubectl describe vpa sglang-vpa -n inference

Recommendation:
  Container Recommendations:
  - Container Name: sglang
    Lower Bound:  Cpu: 6,  Memory: 24Gi   # 最低估计
    Target:       Cpu: 12, Memory: 48Gi   # ← 推荐值：用这个设 requests
    Upper Bound:  Cpu: 20, Memory: 80Gi   # 极端峰值估计
    Uncapped Target: Cpu: 12, Memory: 48Gi

VPA 在推理场景的局限性

Auto 模式 = 驱逐 Pod = 中断推理服务：
  • 驱逐 = 杀 Pod → 重建 → 模型重新加载 60-120s → 这段时间该副本不可用
  • KV Cache 全部丢失，正在处理的请求被中断
  • VPA Updater 可能同时驱逐多个 Pod → 容量骤降
  • GPU 资源（nvidia.com/gpu）根本不适合动态调整——你要么占 1 张卡要么不占
推理场景 VPA 最佳实践：
  • 使用 Off 模式定期查看推荐值，人工调整 Deployment 的 CPU/Memory requests
  • 配合 HPA 使用——VPA 调单 Pod 资源大小，HPA 调副本数
  • VPA 和 HPA 不要同时基于相同指标：让 HPA 基于自定义指标（QPS/TTFT），VPA 只管 CPU/Memory
实战锚点
VPA Off 模式的典型用法：每周查一次推荐值。发现 SGLang 的 CPU requests 从 8 核可以降到 6 核（推理主要用 GPU，CPU 只做 tokenizer 和请求调度）。降低 CPU requests 后，同一台机器能多放一个 Pod——提高装箱率（bin packing），同样的节点跑更多副本。

§3Karpenter / Cluster Autoscaler · 节点级弹性

当 HPA 扩出新 Pod 但集群没有足够的 GPU 资源放置时，需要自动创建新节点。两种方案：

Cluster Autoscaler vs Karpenter

维度Cluster Autoscaler (CA)Karpenter
扩容逻辑从预定义的 NodeGroup 选一个+1分析 pending Pod 需求，直接选最合适的实例
扩容速度慢：10-15 分钟（ASG → 创建 VM → 就绪）快：2-3 分钟（直接调云 API）
实例选择固定在 NodeGroup 预设的机型从候选列表中动态选最优（成本/可用性）
缩容逻辑节点空闲 N 分钟后删除整合（Consolidation）：主动合并 Pod 到更少节点
配置负担需要为每种规格创建 NodeGroup一个 NodePool 覆盖多种实例
云厂商所有主流云AWS 原生 / Azure 预览 / 社区适配中

Cluster Autoscaler 工作流

Karpenter 核心概念

NodePool YAML（GPU 推理场景）

apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: gpu-inference
spec:
  template:
    metadata:
      labels:
        workload-type: gpu-inference      # Pod 的 nodeSelector 匹配这个标签
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: gpu-nodeclass               # 引用下面的节点模板
      requirements:
      - key: "node.kubernetes.io/instance-type"
        operator: In
        values:                           # 允许的 GPU 实例类型
        - "p4d.24xlarge"                  # 8x A100-40G · $32/hr
        - "p4de.24xlarge"                 # 8x A100-80G · $40/hr
        - "p5.48xlarge"                   # 8x H100     · $98/hr
      - key: "karpenter.sh/capacity-type"
        operator: In
        values: ["on-demand"]             # 推理服务用按量（Spot 有中断风险）
      - key: "topology.kubernetes.io/zone"
        operator: In
        values: ["us-east-1a", "us-east-1b"]

  limits:
    cpu: "1000"                           # NodePool 级别资源上限
    memory: "4000Gi"
    nvidia.com/gpu: "64"                  # 最多管理 64 张 GPU（防失控）

  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 60s                 # 节点空闲 60s 后开始整合
    budgets:
    - nodes: "20%"                        # 同一时间最多中断 20% 节点

推理场景：GPU 节点按需供给，闲置时回收

GPU 节点扩缩的特殊挑战

挑战原因缓解策略
启动极慢GPU 驱动初始化 30s + 拉大镜像 30-60s + 模型加载 60-120s预装 AMI · 镜像缓存 · 模型预热
库存紧张热门 GPU 实例经常没货（H100 尤其）配置多候选实例类型 · 多 AZ
Spot 中断竞价实例可能被回收（2min 通知）推理服务建议用 on-demand
资源碎片Pod 要 4 GPU 但节点只剩 2 块空闲Consolidation 合并 + 合理选机型
GPU 节点 ≠ CPU 节点：CPU 节点 1-2 分钟就绪，GPU 节点需要 3-5 分钟（包含 NVIDIA 驱动初始化 + 大镜像拉取）。这意味着推理服务不可能做到"秒级扩容"，必须配合预热策略。
实战锚点
GPU 节点不够时自动扩节点：HPA 把 replicas 改为 6 → 新 Pod 进入 Pending（需要 2x GPU 但没有节点有空余）→ Karpenter watch 到 pending Pod → 分析需求找到最合适的实例 → 调云 API 创建 p4d.24xlarge → 2-3 分钟后 Node Ready → Pod 调度上去 → 模型加载 → 开始服务。整条链路 Karpenter 全自动，你只需配置好 NodePool。

指标来源：SGLang /metrics 端点

kind: ServiceMonitor

  name: sglang-metrics
  namespace: inference
spec:
  selector:
    matchLabels:
      app: sglang-server
  endpoints:
  - port: http

扩容链路延迟分析

4 分钟的 "裸奔" 窗口：从感知到新 Pod Ready 需要 ~4 分钟。这段时间只有已有 Pod 承接流量（可能过载）。如果 minReplicas 设得太低，突发流量会导致所有 Pod TTFT 飙升 → 用户体验崩溃。

缓解冷启动的三大策略

① Buffer Pod（预留缓冲）

部署低优先级 "占位" Pod。正式 Pod 到来时抢占它。

# 低优先级 PriorityClass
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: buffer
value: -1
---
# Buffer Pod 占着 GPU + 已加载模型
spec:
  priorityClassName: buffer
  containers:
  - name: sglang
    resources:
      requests:
        nvidia.com/gpu: "2"

效果：正式 Pod 抢占 → 拿到热节点 → 省去 2min 创建节点

② 节点预热（OverProvisioning）

通过 Buffer Pod + PDB 确保始终有 N 个空闲 GPU 节点待命。

# PDB 保护 buffer 不被整合掉
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: buffer-pdb
spec:
  minAvailable: 1
  selector:
    matchLabels:
      role: gpu-buffer

效果：Karpenter 提前创建节点 → 扩容时直接用

③ 镜像缓存（Warm AMI）

在节点模板中预装 GPU 驱动 + 预拉推理镜像。

# EC2NodeClass 使用自定义 AMI
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: gpu-nodeclass
spec:
  amiFamily: Custom
  amiSelectorTerms:
  - id: "ami-0abc123"
  # AMI 已包含：
  # - NVIDIA 535 驱动
  # - 预拉的推理镜像

效果：省去驱动安装 30s + 镜像拉取 30-60s

三策略组合效果：
  • 无缓解：感知 15s + 创建节点 120s + 驱动 30s + 镜像 30s + 模型 60s = ~4min
  • Buffer Pod：感知 15s + 抢占 5s + 模型已加载 0s = ~20s（如果 Buffer 已加载模型）
  • 三策略齐用：新 Pod 抢占 Buffer（已在热节点上+模型已加载）→ < 30s
Buffer Pod 被抢后变 Pending → Karpenter 异步补充新节点 → 新 Buffer 就位 → 准备下一轮。

推荐的扩缩指标选择

指标推荐度选择原因
sglang_waiting_requests★★★排队 > 0 = 容量一定不足，最直接的扩容信号
sglang_avg_ttft_ms★★★直接反映用户体感 SLO，超标说明需要扩
sglang_kv_cache_usage_ratio★★☆KV Cache > 80% 说明显存即将耗尽，需要提前扩
gpu_utilization_percent★★☆GPU > 90% 已接近饱和，留一点余量应对突发
cpu utilization★☆☆GPU 推理瓶颈不在 CPU，参考价值低
实战锚点
推理 QPS > 阈值时自动扩 Pod + GPU 节点不够时自动扩节点——完整链路：
① Prometheus 每 15s 采集 SGLang /metrics
② Prometheus Adapter 聚合为 custom.metrics.k8s.io 指标
③ HPA 每 15s 查询，计算 desiredReplicas = ceil(当前QPS/目标QPS × 当前副本)
④ HPA patch Deployment replicas → 新 Pod 创建
⑤ 新 Pod 抢占 Buffer Pod（如有）→ 立即调度到热节点
⑥ 若无热节点：Pod Pending → Karpenter 2min 创建 GPU Node → Pod 调度
⑦ 模型加载完 → readinessProbe 通过 → Service Endpoints 纳入 → 接流量
反向：流量降低 → HPA 等 5min 防抖后缩 Pod → 节点空闲 → Karpenter Consolidation 回收 → 停止 GPU 计费。全程自动化。

§5带走这些

① HPA 核心公式
desiredReplicas = ceil(currentMetric / targetMetric × currentReplicas) · 每 15s 计算一次，多指标取最大值
② 推理必须自定义指标
CPU 指标对 GPU 推理无用；用 QPS / TTFT / waiting_requests / kv_cache_ratio 驱动扩缩
③ behavior 防抖
scaleUp stabilization 30s（快速响应）· scaleDown stabilization 300s（避免抖动）· policies 限制单次幅度
④ VPA 用 Off 模式
Auto 模式重启 Pod 中断推理不可接受；Off 模式做 CPU/Memory 推荐值参考，手动调整提高装箱率
⑤ Karpenter > CA
直接根据 pending Pod 选最优实例类型 · 2-3min 扩节点 vs CA 的 10-15min · Consolidation 主动合并碎片
⑥ GPU 冷启动 ~4min
Buffer Pod + OverProvisioning + 镜像缓存三管齐下 → 扩容延迟从 4min 降到 < 30s
