§0为什么要理解 Pod 生命周期

你一定遇到过这些情况：

  • Pod 状态 CrashLoopBackOff——是容器挂了还是健康检查配错了？
  • 滚动更新时偶发 502——是新 Pod 没 ready 就接流量了，还是旧 Pod 下线太快？
  • 推理服务启动要 60 秒加载模型，但 30 秒就被 kubelet 杀了——是哪个探针的锅？
  • 需要在推理容器启动前先从对象存储拉模型权重——用 initContainer 还是 sidecar？
Pod 生命周期的每个细节都直接影响服务可用性。特别是推理服务这种启动慢、下线要排空连接的场景，配错一个参数就是线上事故。

§2initContainer · 启动前的准备工作

initContainers 是在主容器启动之前顺序执行的容器。全部成功后，主容器才会启动。

执行规则

  • 顺序执行：initContainer[0] 成功 → initContainer[1] → ... → 全部完成 → 主容器启动
  • 失败重试：任何一个 initContainer 失败，整个 Pod 重启（受 restartPolicy 控制）
  • 资源独立计算：init 阶段的资源 = max(各 initContainer requests)，不叠加
  • 完成即退出：initContainer 跑完就销毁，不占运行时资源

典型场景

# 推理服务：先从对象存储拉模型权重到本地 NVMe
initContainers:
- name: model-downloader
  image: goosefs-client:v2
  command: ["/bin/sh", "-c"]
  args:
  - |
    goosefs fs copyToLocal /models/qwen3-72b /local-nvme/models/qwen3-72b
  volumeMounts:
  - name: local-nvme
    mountPath: /local-nvme

# 等数据库就绪（简单场景用 nslookup 探测）
- name: wait-for-db
  image: busybox:1.36
  command: ['sh', '-c', 'until nslookup mysql-svc; do sleep 2; done']
initContainer vs Sidecar 的选择：
  • 需要"做完一件事再启动主容器"→ initContainer（如拉模型、等依赖）
  • 需要"跟主容器一起持续运行"→ Sidecar（如日志收集、Envoy 代理）
实战锚点
70GB 的推理模型从 GooseFS 拉到本地 NVMe 需要约 40 秒（~1.8GB/s）。如果放在 initContainer 里，主容器的 startupProbe 不需要为此预留时间。拉完才启动，逻辑清晰。但如果模型已经预热到节点 NVMe 了，initContainer 里只需要做一个 ls /models/qwen3-72b/config.json 校验即可，2 秒完成。

§3三种探针 · 被 kubelet 杀 Pod 的罪魁祸首

kubelet 通过三种探针监控容器健康状态。配错了就是线上事故。

探针作用失败后果何时执行
startupProbe 确认容器已启动完成 超过 failureThreshold × periodSeconds → 杀容器重启 容器启动后立刻开始，成功一次后停止，交给 liveness
livenessProbe 确认容器还活着 连续失败 failureThreshold 次 → 杀容器重启 startupProbe 成功后持续执行
readinessProbe 确认容器能接流量 失败 → 从 Service Endpoints 摘除（不杀容器） startupProbe 成功后持续执行

探针类型

  • httpGet：GET 请求，2xx/3xx 为成功
  • tcpSocket：TCP 连接成功即成功
  • exec：在容器内执行命令，exit 0 为成功
  • grpc（K8S 1.24+）：gRPC Health Check 协议

推理服务的探针设计范例

# SGLang 推理服务 —— 启动加载模型可能要 60-120 秒
startupProbe:
  httpGet:
    path: /health          # SGLang 内置健康端点
    port: 30000
  initialDelaySeconds: 10  # 容器启动后等 10s 再检
  periodSeconds: 5         # 每 5s 检一次
  failureThreshold: 30     # 最多容忍 30 次失败 = 10 + 30×5 = 160s 启动窗口

livenessProbe:
  httpGet:
    path: /health
    port: 30000
  periodSeconds: 10
  failureThreshold: 3      # 连续 30s 不健康 → 重启

readinessProbe:
  httpGet:
    path: /health_generate  # 真正能推理才算 ready
    port: 30000
  periodSeconds: 5
  failureThreshold: 2      # 10s 不能推理 → 从 Service 摘除
最常见的错误：没配 startupProbe，直接上 livenessProbe。如果 liveness 的 initialDelaySeconds 设得比模型加载时间短，kubelet 会在模型还没加载完时就判定"容器死了"→ 杀掉 → 重启 → 又没加载完 → 又杀掉 → CrashLoopBackOff。
startupProbe 存在的意义：它给了一个"启动宽限期"。在 startupProbe 成功之前，liveness 和 readiness 都不会执行。这样你可以给 startup 一个很大的窗口（如 160s），而 liveness 的周期可以设得很短（如 10s）——两全其美。

§4重启策略 · CrashLoopBackOff 的根源

Pod spec 中的 restartPolicy 控制容器退出后 kubelet 的行为：

策略行为适用对象
Always（默认）容器退出后总是重启长期运行的服务（Deployment / StatefulSet）
OnFailure退出码非 0 时重启Job（任务跑完就结束，失败才重试）
Never永不重启调试 / 一次性脚本

CrashLoopBackOff 的退避机制

当容器反复崩溃时，kubelet 不会立刻重启，而是指数退避：

第 1 次重启：等 10s
第 2 次：等 20s
第 3 次：等 40s
第 4 次：等 80s
第 5 次：等 160s
第 6 次及以后：等 300s（上限 5 分钟）

# 成功运行超过 10 分钟后，退避计数器清零
当你看到 CrashLoopBackOff 时，Pod 并没有"卡死"——它只是在等下一次重启。用 kubectl logs --previous 查看上一次容器的退出日志，才能找到真正的崩溃原因。

§5优雅下线 · 为什么滚动更新时会 502

当 Pod 被删除（手动删除、滚动更新、节点驱逐），kubelet 执行以下步骤：

502 的经典原因

时序竞态：SIGTERM 发给容器后，容器立刻退出。但此时 kube-proxy 的 iptables 规则还没更新完（因为需要 apiserver → Endpoints Controller → kube-proxy 这条链路，通常要 1-3 秒）。在这 1-3 秒内，流量仍然被转发到已经退出的 Pod → 502。

解法：preStop + sleep

lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]  # 等 5 秒让网络侧摘除完成

terminationGracePeriodSeconds: 60  # 给足时间：5s preStop + 推理请求排空

逻辑：

  • preStop sleep 5：容器收到 SIGTERM 前先等 5 秒，让网络侧有时间从 Endpoints 摘除
  • 5 秒后 SIGTERM 到达，推理服务收到信号 → 停止接新请求 → 排空进行中的请求
  • 最终在 terminationGracePeriodSeconds 内正常退出
实战锚点
推理服务的单次推理可能持续 10-60 秒（长 prompt + 长输出）。如果 terminationGracePeriodSeconds 只有默认的 30 秒，长推理请求会被强杀。建议设为 max(预期最长推理时间) + preStop 时间 + 10s 余量，例如 90 秒。

§6带走这些

① 五阶段
Pending → Running → Succeeded/Failed/Unknown · Pending 时查 describe events 定位原因
② initContainer
顺序执行、完成即退出 · 用来做"主容器启动前的准备"（拉模型、等依赖）
③ 三种探针
startup（启动宽限）→ liveness（活着吗→杀）→ readiness（能服务吗→摘流量）
④ 启动慢服务必配 startupProbe
否则 liveness 会在模型加载期间误杀容器 → CrashLoopBackOff
⑤ 优雅下线
preStop + terminationGracePeriod · 路径 A（容器退出）和路径 B（网络摘除）是并行的
⑥ 防 502
preStop sleep 几秒让 iptables 规则收敛 · grace period 要覆盖最长请求时间
