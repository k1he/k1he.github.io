§0为什么要用 Operator——把运维知识编码成软件

K8S 内置的 Deployment / StatefulSet 能搞定无状态服务和简单有状态服务。但当你遇到下面这些场景时，内置资源就不够了：

  • 多机 Tensor Parallel 推理——需要一组 Pod 同时启动，leader 要先拿到所有 worker 的地址
  • MySQL 主从——新建副本时要自动从主库做 clone，failover 时要选举新主并切 VIP
  • Prometheus 监控——每加一个服务就要自动生成 scrape config、创建 ServiceMonitor
  • 模型灰度发布——旧模型不能直接下线，要等流量切完、缓存清空后才能释放 GPU
这些"运维操作"如果靠人写 shell 脚本 + crontab，迟早出事。Operator 模式的核心思想：
把领域专家的运维知识（"如何部署、扩缩、故障恢复"）编码成一个 Controller 程序，让 K8S 7×24 自动执行。

Operator 模式 = 声明式 + 自动化

你不再告诉 K8S "先做 A，再做 B，然后做 C"（命令式），而是声明 "我要一个 3 副本的推理集群"（声明式），Operator 自动算出当前状态和目标状态的差异，然后执行必要的操作。

一句话定义：Operator = 自定义资源类型（CRD） + 自定义控制器（Controller）。CRD 告诉 K8S "我发明了一种新资源"；Controller 持续 watch 这个新资源并执行运维逻辑。

§1CRD · 给 K8S 注册新的资源类型

CRD 是什么

Custom Resource Definition（CRD）是 K8S 的扩展机制——它让你在不修改 K8S 源码的情况下，往 API Server 里注册一种全新的资源类型。注册完后，你就能像使用 Pod、Service 一样用 kubectl get/create/delete 操作你自定义的资源。

CRD 的四大要素

要素含义示例
groupAPI 组，类似"命名空间"避免命名冲突inference.example.com
version版本号，支持多版本共存 + 平滑迁移v1alpha1, v1
scopeNamespaced 或 Cluster 级别大部分用 Namespaced
schemaOpenAPI V3 格式定义 spec/status 的字段和校验规则类型、必填、枚举、最小值等

完整示例：定义一个 InferenceService CRD

# 告诉 K8S："我要注册一种新资源叫 InferenceService"
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: inferenceservices.inference.example.com   # 格式：plural.group
spec:
  group: inference.example.com                    # API 组
  versions:
  - name: v1alpha1                                # 版本号
    served: true                                  # 是否通过 API 提供服务
    storage: true                                 # 是否作为 etcd 存储版本
    schema:
      openAPIV3Schema:                            # 字段校验规则
        type: object
        properties:
          spec:
            type: object
            properties:
              modelName:
                type: string
                description: "模型名称，如 Qwen3-72B"
              replicas:
                type: integer
                minimum: 1
                description: "推理实例副本数"
              gpuPerReplica:
                type: integer
                enum: [1, 2, 4, 8]
                description: "每个副本使用的 GPU 数量"
              tensorParallelSize:
                type: integer
                minimum: 1
                description: "TP 并行度"
            required: ["modelName", "replicas", "gpuPerReplica"]
          status:
            type: object
            properties:
              readyReplicas:
                type: integer
              endpoint:
                type: string
              conditions:
                type: array
                items:
                  type: object
                  properties:
                    type: {type: string}
                    status: {type: string}
                    lastTransitionTime: {type: string, format: date-time}
    subresources:
      status: {}                                  # 启用 status 子资源（spec 和 status 独立更新）
  scope: Namespaced                               # 每个 namespace 独立
  names:
    plural: inferenceservices                     # kubectl get inferenceservices
    singular: inferenceservice
    kind: InferenceService                        # YAML 里的 kind
    shortNames:
    - isvc                                        # kubectl get isvc

CR（Custom Resource）——CRD 的实例

CRD 注册完后，你就能创建它的实例（CR）——跟写 Deployment YAML 一样自然：

# 这就是一个 CR 实例
apiVersion: inference.example.com/v1alpha1
kind: InferenceService
metadata:
  name: qwen3-72b-service
  namespace: production
spec:
  modelName: Qwen3-72B
  replicas: 2
  gpuPerReplica: 8
  tensorParallelSize: 8
注册完 CRD 后，你立刻就能执行：
kubectl get inferenceservices 或 kubectl get isvc
kubectl describe isvc qwen3-72b-service
API Server 已经知道这种资源的存在了，会帮你做 schema 校验、存储到 etcd、支持 watch。
但是！光有 CRD 和 CR，什么也不会发生。CR 只是一条"数据"存在 etcd 里——没有人来读它、没有人来执行任何操作。你还需要一个 Controller 来 watch 这些 CR，并做出实际动作（创建 Pod、配置网络等）。

§2Controller 的 Reconcile 模式

Watch → Queue → Reconcile 循环

Controller 的核心运行模式只有三步，永远循环：

// 1. 读 CR 对象 actualPods := listPodsOwnedBy(cr) // 2. 查实际子资源 if len(actualPods) != cr.Spec.Replicas → fix() // 3. 对比并修复差异 cr.Status.ReadyReplicas = countReady(actualPods) // 4. 更新 status }

幂等性要求

Reconcile 函数必须是幂等的：同一个事件执行一次和执行十次，最终结果必须完全一样。

为什么？因为 K8S 不保证事件只送达一次。网络抖动、Controller 重启、队列重试——都可能导致同一个 CR 被 Reconcile 多次。如果你的逻辑是"每次都创建一个新 Pod"，那重试三次就会多出两个 Pod。

正确做法：先查再做——"如果 Pod 不存在才创建"而不是"无脑创建"。

Owner Reference · 级联清理

Controller 创建子资源（Pod、Service、ConfigMap）时，必须设置 ownerReferences 指向 CR：

# Controller 创建的 Pod 会自动带上这个字段
metadata:
  ownerReferences:
  - apiVersion: inference.example.com/v1alpha1
    kind: InferenceService
    name: qwen3-72b-service
    uid: a1b2c3d4-...
    controller: true                   # 标记为"控制者"
    blockOwnerDeletion: true           # 删 CR 前先删子资源

效果：当你 kubectl delete isvc qwen3-72b-service 时，K8S 的垃圾回收器会自动级联删除所有 ownerReferences 指向它的 Pod、Service——无需 Controller 手动清理。这就是为什么删一个 Deployment 会连带删掉所有 Pod 的原因。

实战锚点
如果你发现删了 CR 后子资源没被清理（orphan），通常是 Controller 创建子资源时忘了设 ownerReference。用 kubectl get pods -o yaml | grep ownerReferences -A5 检查。

§3Operator = CRD + Controller

把 §1 和 §2 合在一起：Operator = CRD（定义"长什么样"）+ Controller（确保"变成那样"）。

经典 Operator 示例

Operator管理什么自动化了哪些运维操作
MySQL OperatorMySQL 主从集群自动初始化从库、配 GTID 复制、故障选举新主、定时备份到 S3
Prometheus Operator监控系统根据 ServiceMonitor 自动生成 scrape config、热加载配置、管理 HA 副本
Cert-ManagerTLS 证书自动申请 Let's Encrypt 证书、到期前自动续签、注入 Secret 到 Ingress
LWS分布式推理集群编排 leader+workers、注入发现地址、整组原子操作、滚动更新

Level-Triggered vs Edge-Triggered

K8S Controller 采用 Level-Triggered（水平触发）模式——这是理解 Operator 容错能力的关键：

Edge-Triggered（边沿触发）：基于"发生了什么事件"来决策。如果你漏掉一个事件（网络抖、Controller 重启），状态就会不一致。

Level-Triggered（水平触发）：基于"当前状态是什么"来决策。不管中间发生过多少事件、漏掉了几个——每次 Reconcile 都重新对比 desired vs actual，计算差异。

好处：天然容错。Controller 重启后不需要"回放历史事件"，只需要看当前状态就能做出正确决策。这也是为什么 Reconcile 必须幂等——它不关心"之前发生了什么"，只关心"现在差多少"。
Operator 的本质：把"SRE/DBA 脑子里的运维 runbook"变成代码。以前半夜收到告警要人手动处理的事，现在 Controller 自动处理——而且更快、更可靠、不会犯困。

§4LWS（LeaderWorkerSet）深度解读

LWS 是什么

LeaderWorkerSet（LWS）是 Google 开源的 CRD，专门为"1 个 leader + N 个 workers"的分布式工作负载设计。它完美匹配多机推理场景：leader 负责接收请求和协调，workers 负责参与计算。

为什么不能用 Deployment / StatefulSet？
多机 TP/PP 推理需要：① 所有 Pod 同时就绪才能工作 ② Leader 需要知道所有 Worker 的地址 ③ 更新时必须整组一起更新 ④ 一个 Pod 挂了整组要重建。Deployment 做不到"组"的概念，StatefulSet 的滚动更新是逐个 Pod 的——不满足"一组 Pod 是一个原子单元"的需求。

CRD 核心字段

字段含义推理场景示例
replicas多少"组"（每组是一个独立推理实例）2 = 两个独立的推理服务可负载均衡
leaderWorkerTemplate.size每组的 Pod 总数（1 leader + N-1 workers）2 = 1 leader + 1 worker（2 机）
leaderTemplateLeader Pod 的模板（可选，不设则与 worker 相同）rank=0，开放推理端口
workerTemplateWorker Pod 的模板rank=1+，只参与计算
restartPolicyPod 异常时的恢复策略RecreateGroupOnPodRestart
rolloutStrategy滚动更新策略按组滚动，maxUnavailable=1

LWS Controller 逻辑架构

推理场景：多机 TP/PP 的完美匹配

2 台 8 卡 A100 机器做 Qwen3-72B 的 16 卡 TP 推理：

  • Group = 一个完整推理实例：Leader（rank 0）启动 SGLang server 接收请求，Worker（rank 1）参与 tensor parallel 计算
  • replicas = 推理实例数：2 个 replicas = 2 个独立的 16 卡推理服务，前面挂 Service 负载均衡
  • 组内通信：Worker 通过 LWS_LEADER_ADDRESS 找到 Leader，NCCL 通过 RDMA/InfiniBand 直连
  • 故障恢复：任何一个 Pod OOM 或 GPU 故障，整组重建（因为分布式推理 rank 缺一不可）
  • 组间独立：Group 0 出问题不影响 Group 1——用户请求只需切流到健康的 Group

YAML 示例：用 LWS 部署 2 机 8 卡 SGLang

# LeaderWorkerSet：2 机 16 卡 TP 推理（Qwen3-72B）
apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata:
  name: sglang-qwen3-72b
  namespace: inference
spec:
  replicas: 1                                     # 1 个推理组（可按需增加做负载均衡）
  leaderWorkerTemplate:
    size: 2                                       # 每组 2 个 Pod：1 leader + 1 worker
    restartPolicy: RecreateGroupOnPodRestart      # 一个挂了整组重建
    leaderTemplate:                               # Leader Pod 模板
      metadata:
        labels:
          role: leader
      spec:
        containers:
        - name: sglang
          image: lmsysorg/sglang:latest
          command: ["python3", "-m", "sglang.launch_server"]
          args:
          - "--model-path=/models/Qwen3-72B"
          - "--tp=16"                             # 跨 2 机共 16 卡 TP
          - "--nnodes=2"                          # 2 个节点
          - "--node-rank=0"                       # Leader 是 rank 0
          - "--nccl-init-addr=0.0.0.0:29500"      # NCCL rendezvous 地址
          - "--host=0.0.0.0"
          - "--port=30000"
          ports:
          - containerPort: 30000                  # 推理服务端口
            name: http
          - containerPort: 29500                  # NCCL 初始化端口
            name: nccl
          resources:
            limits:
              nvidia.com/gpu: 8                   # 每台机器 8 卡 A100
            requests:
              cpu: "32"
              memory: "200Gi"
          volumeMounts:
          - name: model-storage
            mountPath: /models
          - name: shm                             # NCCL AllReduce 需要大 shared memory
            mountPath: /dev/shm
        volumes:
        - name: model-storage
          hostPath:
            path: /nvme/models                    # 模型预热到本地 NVMe
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: "64Gi"                     # 不够会 NCCL segfault
        tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
    workerTemplate:                               # Worker Pod 模板
      spec:
        containers:
        - name: sglang
          image: lmsysorg/sglang:latest
          command: ["python3", "-m", "sglang.launch_server"]
          args:
          - "--model-path=/models/Qwen3-72B"
          - "--tp=16"
          - "--nnodes=2"
          - "--node-rank=1"                       # Worker 是 rank 1
          - "--nccl-init-addr=$(LWS_LEADER_ADDRESS):29500"  # LWS 自动注入
          resources:
            limits:
              nvidia.com/gpu: 8
            requests:
              cpu: "32"
              memory: "200Gi"
          volumeMounts:
          - name: model-storage
            mountPath: /models
          - name: shm
            mountPath: /dev/shm
        volumes:
        - name: model-storage
          hostPath:
            path: /nvme/models
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: "64Gi"
        tolerations:
        - key: nvidia.com/gpu
          operator: Exists
          effect: NoSchedule
  rolloutStrategy:
    type: RollingUpdate
    rollingUpdateConfiguration:
      maxUnavailable: 1                           # 滚动更新时最多 1 组不可用
      maxSurge: 0
实战锚点
LWS 部署多机 SGLang 推理的关键注意事项：
  • LWS_LEADER_ADDRESS 环境变量由 LWS Controller 自动注入到每个 Pod——Worker 不需要硬编码 Leader IP
  • /dev/shm 必须设足够大（建议 ≥ 64Gi），NCCL AllReduce 用共享内存通信，不够会直接 segfault
  • 同组 Pod 最好在同一 InfiniBand 子网内——用 topologySpreadConstraints 或 nodeAffinity 控制
  • 任何一个 Pod OOM/GPU 故障，LWS 会重建整个 Group，保证 TP 拓扑完整不会出现"半死不活"
  • 验证命令：kubectl get lws sglang-qwen3-72b -n inference → 看 readyReplicas
环境变量含义示例值
LWS_LEADER_ADDRESS本组 Leader Pod 的 DNS 名称sglang-qwen3-72b-0-0.sglang-qwen3-72b
LWS_GROUP_INDEX当前 Pod 所在组的索引0
LWS_WORKER_INDEX当前 Pod 在组内的索引（0=leader）1（worker）
LWS_GROUP_SIZE组内 Pod 总数2

利用这些变量，你可以在启动脚本里动态确定 --node-rank=$LWS_WORKER_INDEX 和 --nccl-init-addr=$LWS_LEADER_ADDRESS:29500，无需为每个 Pod 写不同的 YAML。

特性LWSJobSetMPI Operator
设计目标长期运行的 leader-worker 服务批量 Job 编排MPI 分布式训练
生命周期持续运行（像 Deployment）完成即退出（像 Job）完成即退出
滚动更新支持，按组原子更新不支持（一次性任务）不支持
Leader 发现自动注入环境变量需自己配置通过 mpirun hostfile
故障恢复整组重建按 Job 重试策略整体重启

§5其他推理相关 Operator

KServe

CRD: InferenceService

  • 模型推理服务的完整生命周期
  • 自动扩缩容（含 scale-to-zero）
  • Canary 灰度发布（流量按比例切分）

NVIDIA GPU Operator

  • 自动安装 GPU 驱动（免预装节点镜像）
  • 部署 device-plugin（注册 nvidia.com/gpu）
  • 部署 GPU Feature Discovery（标签）
  • 管理 DCGM Exporter（GPU 监控指标）
  • MIG 分片配置管理

解决：GPU 节点基础设施自动化

Triton Inference Server

搭配 KServe 使用

  • 多模型多框架动态加载/卸载
  • Model Repository 热更新（S3/GCS）
  • Dynamic batching 优化吞吐
  • Model Analyzer 自动调优并发
  • Ensemble（多模型 Pipeline 串联）

解决：多模型混合部署 + 高吞吐

选型建议：
  • 单模型多机推理（SGLang / vLLM） → LWS 最轻量、最匹配
  • 生产级推理平台（需要 canary + 自动扩缩 + 模型版本管理） → KServe
  • GPU 节点初始化（不想维护自定义 AMI / OS 镜像） → NVIDIA GPU Operator
  • 多模型高吞吐（同一 GPU 上跑多个小模型） → Triton

§6什么时候该用 Operator vs 纯 Deployment

决策标准：是否有复杂的运维逻辑需要自动化

场景推荐方案理由
单卡推理、无状态、简单扩缩 Deployment + HPA Pod 之间互不依赖，内置能力完全足够
需要稳定网络标识的单机推理 StatefulSet Pod 有固定 hostname，方便日志追踪和模型缓存
多机 TP/PP 推理（2+ 节点） LWS Operator 需要"组"的原子性：同时启动、整组替换、Leader 发现
多模型灰度 + 自动扩缩 + SLA KServe Operator Canary 流量切换、基于 QPS 的扩缩、模型版本管理
GPU 节点驱动和 device-plugin GPU Operator 驱动安装/升级本身是复杂的有状态操作
业务特有：故障自愈 + 特殊调度 + 状态机 自研 Operator 没有现成 Operator 满足时，用 kubebuilder 开发
不要为简单场景写 Operator！
Operator 是有维护成本的代码——它可能有 bug、需要升级、要监控它自身的健康。如果 Deployment + 几行 shell 就能搞定，别引入 Operator 增加复杂度。

判断公式：Operator 的维护成本 < 它替代的手动运维成本 → 用 Operator。否则 = 过度设计。

推理团队的典型演进路径

实战锚点
Phase 1：单卡推理 → Deployment + HPA，够用
Phase 2：多卡单机 TP（8 卡） → 还是 Deployment，只需 nvidia.com/gpu: 8
Phase 3：多机推理 + 故障恢复 → LWS，必须用 Operator（Deployment 做不到组级原子操作）
Phase 4：多模型 + 灰度 + SLA + 自动扩缩 → KServe 或自研 Operator

判断信号：如果你发现自己在写"出了 XX 状况就手动执行 YY 脚本"的 runbook——那就是 Operator 该做的事。
