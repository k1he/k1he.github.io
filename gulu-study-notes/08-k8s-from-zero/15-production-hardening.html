§0为什么上生产前必须做加固

默认的 K8S 集群是一个"全信任"环境：

  • 任何 Pod 都能访问集群内任何其他 Pod 的任意端口（网络全通）
  • 默认 ServiceAccount 拥有超出业务需要的权限（权限过大）
  • 容器可以以 root 身份运行、挂载宿主机路径（逃逸风险）
  • 一次误操作的 kubectl delete ns 可以让整个命名空间灰飞烟灭（无保护）
  • 滚动更新时没有最低可用保障，所有副本可能同时下线（服务中断）
真实事故：某团队在推理集群中，一个调试 Pod 的 ServiceAccount 拥有 cluster-admin 权限。实习生误执行了一个清理脚本，删除了整个 inference namespace 下所有资源——包括正在服务的 3 个推理 Deployment 和对应的 PVC。恢复耗时 4 小时。

加固的四个维度

§1RBAC · 基于角色的访问控制

RBAC（Role-Based Access Control）是 K8S 默认的授权机制。核心思想：不直接给用户/SA 权限，而是定义角色、再绑定角色。

四个核心对象

Role vs ClusterRole

对比项RoleClusterRole
作用范围单个 namespace 内的资源集群级资源 + 跨 namespace 资源
典型场景推理服务 SA 只需读本 namespace 的 PodPrometheus 需要读所有 namespace 的 metrics
绑定方式RoleBinding（只能绑到同一 namespace）ClusterRoleBinding（全集群生效）或 RoleBinding（降级到单 namespace）
非 namespace 资源不能授权 nodes、PV 等集群级资源可以

最小权限原则：推理服务需要什么权限？

推理 Pod 本身通常只需要：① get/list 本 namespace 的 Pods（用于服务发现）② get ConfigMaps（读配置）。不需要 create、delete、update 任何资源。如果你的推理 Pod 拥有 cluster-admin 权限，说明权限配置有严重问题。

完整 YAML 示例：为推理服务创建专用 RBAC

# 1. 创建专用 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: inference-sa               # 推理服务专用 SA
  namespace: inference
---
# 2. 定义最小权限 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: inference-reader
  namespace: inference
rules:
- apiGroups: [""]                  # core API 组
  resources: ["pods"]
  verbs: ["get", "list"]           # 只读 Pod 列表（服务发现）
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get"]                   # 读取推理参数配置
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["model-registry-cred"]  # 只能读指定的 secret
  verbs: ["get"]
---
# 3. 绑定 SA 到 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: inference-sa-binding
  namespace: inference
subjects:
- kind: ServiceAccount
  name: inference-sa               # 绑定到推理 SA
  namespace: inference
roleRef:
  kind: Role
  name: inference-reader           # 引用上面定义的 Role
  apiGroup: rbac.authorization.k8s.io
---
# 4. 在 Deployment 中引用该 SA
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-inference
  namespace: inference
spec:
  template:
    spec:
      serviceAccountName: inference-sa  # 使用专用 SA，不用 default
      automountServiceAccountToken: true
      containers:
      - name: sglang
        image: lmsysorg/sglang:latest
常见陷阱：很多人直接用 default ServiceAccount，它默认拥有的权限取决于集群配置。在某些发行版中，default SA 居然有读集群所有 Secret 的权限——这意味着任何 Pod 都能获取其他服务的数据库密码。 
# 查看某个 SA 实际拥有的权限
kubectl auth can-i --list --as=system:serviceaccount:inference:inference-sa

# 查看谁能删除 namespace（找出危险权限）
kubectl auth can-i delete namespaces --all-namespaces --list

# 查看所有 ClusterRoleBinding（谁拥有集群级权限）
kubectl get clusterrolebindings -o wide | grep -v "system:"

# 查看某个 namespace 下所有 RoleBinding
kubectl get rolebindings -n inference -o yaml

§2NetworkPolicy · 网络微隔离

默认行为：全通 = 不安全

K8S 默认网络模型：集群内所有 Pod 之间、Pod 与 Service 之间可以互相通信。这意味着：

  • 一个被入侵的调试 Pod 可以直接扫描推理服务的内部端口
  • 推理 Pod 可以主动连接到集群内的 MySQL、Redis 等任何服务
  • 横向移动没有任何阻碍——一个突破点 = 全集群暴露
NetworkPolicy = 白名单防火墙。一旦某个 Pod 被 NetworkPolicy 选中（通过 podSelector），未被规则显式允许的流量全部拒绝。没有 NetworkPolicy 时流量全通，有了之后默认拒绝。

核心概念

字段含义类比
podSelector这条规则保护谁安全组绑定到哪些实例
ingress允许谁访问我入站规则
egress我能访问谁出站规则
policyTypes控制哪个方向["Ingress"] / ["Egress"] / 两者都有

推理场景：严格限制推理 Pod 的网络访问

# 推理 Pod 只允许：
# 入站：来自 Ingress Controller（带 label ingress=nginx）的流量
# 出站：访问模型存储（COS/S3 + DNS）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: inference-pod-policy
  namespace: inference
spec:
  podSelector:
    matchLabels:
      app: sglang-inference         # 保护所有推理 Pod
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    # 只允许来自 Ingress Controller 的流量
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress-nginx
      podSelector:
        matchLabels:
          app.kubernetes.io/name: ingress-nginx
    ports:
    - protocol: TCP
      port: 30000                   # 推理服务端口
  - from:
    # 允许 Prometheus 抓取 metrics
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: monitoring
      podSelector:
        matchLabels:
          app: prometheus
    ports:
    - protocol: TCP
      port: 30000                   # /metrics 端点同端口
  egress:
  - to:
    # 允许访问集群 DNS（必须！否则域名解析失败）
    - namespaceSelector: {}
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
  - to:
    # 允许访问对象存储（模型下载）— 用 CIDR 指定外部 IP 段
    - ipBlock:
        cidr: 10.0.0.0/8            # 内网 COS endpoint
    ports:
    - protocol: TCP
      port: 443

默认拒绝所有流量的"兜底策略"

# 先用默认拒绝把口子收紧，再逐条开放白名单
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: inference
spec:
  podSelector: {}                   # 空 = 选中本 namespace 所有 Pod
  policyTypes:
  - Ingress
  - Egress
  # 不写 ingress/egress 规则 = 全部拒绝
CNI 兼容性：NetworkPolicy 需要 CNI 插件支持才能生效。Calico 和 Cilium 完整支持；Flannel 不支持（apply 不报错但规则不生效，这是最危险的——你以为有防护其实没有）。生产环境务必用 Calico 或 Cilium。
实战锚点
推理集群中常见的错误：忘记放行 DNS 出站（UDP 53）。Pod 的 egress 被限制后，如果没有显式允许 kube-dns，所有域名解析都会失败——模型下载卡住、日志上报超时、metrics push 失败。排查时 kubectl exec 进去 nslookup google.com 就能确认。

§3PodDisruptionBudget · 维护时的可用性护栏

PDB（PodDisruptionBudget）告诉 K8S：在自愿中断（voluntary disruption）期间，必须保证至少 N 个 Pod 可用。

什么是"自愿中断"？

自愿中断（PDB 能保护）非自愿中断（PDB 管不了）
kubectl drain 节点维护节点硬件故障
集群升级（kube-upgrade）内核崩溃
Cluster Autoscaler 缩容OOM kill
手动删除 Pod容器 crash

两个互斥参数

参数含义示例
minAvailable最少保持几个可用minAvailable: 2 → 3 副本中最多同时下线 1 个
maxUnavailable最多允许几个不可用maxUnavailable: 1 → 同上效果
两者只能二选一。推荐使用 minAvailable——语义更直观："保证至少 N 个在线"。

推理场景：3 副本推理服务的 PDB

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: sglang-pdb
  namespace: inference
spec:
  minAvailable: 2                   # 3 副本中至少保持 2 个在线
  selector:
    matchLabels:
      app: sglang-inference         # 选中推理 Deployment 的 Pod

PDB 的阻塞行为

# 场景：运维对 Node-1 执行 drain
$ kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

# 如果 node-1 上有 1 个推理 Pod，且当前只有 2 个 Pod 是 Ready：
# drain 会被阻塞！输出：
error when evicting pods/"sglang-inference-abc12" -n "inference" (will retry after 5s):
Cannot evict pod as it would violate the pod's disruption budget.

# drain 会持续重试，直到：
# ① 另一个 Node 上新 Pod 变为 Ready（副本数回到 3）
# ② 或者管理员手动 --force（跳过 PDB 保护——危险！）
PDB + 滚动更新的配合：Deployment 的 maxUnavailable 控制"滚动更新时最多下线几个旧 Pod"，PDB 的 minAvailable 控制"外部中断时最少保留几个"。两者共同保障可用性，但它们是独立机制——PDB 不影响 Deployment 自身的滚动更新策略。
实战锚点
GPU 推理 Pod 启动要 60-120 秒加载模型。如果 PDB 设为 minAvailable: 2，drain 时新 Pod 必须在别的 Node 上变为 Ready 之后，旧 Pod 才会被驱逐。这意味着 drain 一个节点可能需要等 2+ 分钟。运维做节点维护时要预留足够的等待时间，不要加 --force。

§4安全上下文 · 运行时加固

securityContext 控制容器的运行时安全属性。分为 Pod 级（对所有容器生效）和 Container 级（覆盖 Pod 级设置）。

关键字段

字段含义推荐值
runAsNonRoot禁止以 root 身份运行容器true
runAsUser指定运行用户 UID1000（非 0 即可）
readOnlyRootFilesystem根文件系统只读true（防止写入恶意文件）
allowPrivilegeEscalation是否允许子进程提权false
capabilities.drop移除 Linux capabilities["ALL"]（先移除全部，再按需添加）
capabilities.add添加所需 capabilities按需添加最少的
seccompProfile限制可用的系统调用RuntimeDefault

GPU 推理的特殊需求

GPU 推理服务（CUDA）需要一些额外权限：
  • SYS_PTRACE：CUDA 多进程通信（MPS）和调试需要 ptrace 能力
  • 设备文件访问：/dev/nvidia* 设备由 device-plugin 自动挂载，不需要额外配置
  • 共享内存：多 GPU 通信需要较大的 /dev/shm，通过 emptyDir 挂载 medium: Memory 实现

完整 YAML：兼顾安全和 GPU 使用的配置

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-inference
  namespace: inference
spec:
  template:
    spec:
      serviceAccountName: inference-sa
      # Pod 级安全上下文
      securityContext:
        runAsNonRoot: true           # 禁止 root 运行
        runAsUser: 1000              # 以 UID 1000 运行
        runAsGroup: 1000
        fsGroup: 1000               # 挂载卷的文件组
        seccompProfile:
          type: RuntimeDefault       # 启用默认 seccomp 配置
      containers:
      - name: sglang
        image: lmsysorg/sglang:latest
        # Container 级安全上下文
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true  # 根文件系统只读
          capabilities:
            drop: ["ALL"]            # 先移除全部 capabilities
            add: ["SYS_PTRACE"]      # CUDA MPS 需要 ptrace
        resources:
          limits:
            nvidia.com/gpu: 1
          requests:
            nvidia.com/gpu: 1
        volumeMounts:
        - name: shm
          mountPath: /dev/shm        # GPU 通信用大共享内存
        - name: tmp
          mountPath: /tmp            # 临时文件写到这里
        - name: cache
          mountPath: /home/user/.cache  # 模型缓存目录
      volumes:
      - name: shm
        emptyDir:
          medium: Memory
          sizeLimit: 8Gi             # 8GB 共享内存
      - name: tmp
        emptyDir:
          sizeLimit: 1Gi
      - name: cache
        persistentVolumeClaim:
          claimName: model-cache-pvc
readOnlyRootFilesystem 的关键：开启后容器不能写根文件系统的任何位置。所以需要为 /tmp、/dev/shm、缓存目录等显式挂载可写卷。这虽然麻烦，但能彻底防止恶意软件写入可执行文件。

默认情况下，Docker/containerd 给容器约 14 种 capabilities（如 NET_BIND_SERVICE、CHOWN、SETUID 等）。其中 SETUID 允许容器内进程设置任意 UID——结合某些内核漏洞可以逃逸到宿主机。

drop: ["ALL"] 先清零，再用 add 只加回业务真正需要的（推理服务通常只需要 SYS_PTRACE）。攻击面从 14 种降到 1 种。

§5优雅下线完整方案

把前面章节（Pod 生命周期）讲的优雅下线与本章的 PDB 结合，形成完整的生产级下线方案：

下线时序全貌

推理服务的连接排空逻辑

推理服务收到 SIGTERM 后应执行：

  • ① 停止接受新请求：关闭 listener 或返回 503
  • ② 等待进行中请求完成：streaming 推理可能持续 30-60 秒
  • ③ 释放 GPU 资源：清理 CUDA context
  • ④ 正常退出：exit 0

完整 YAML 配置

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-inference
  namespace: inference
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                    # 更新时最多多出 1 个 Pod
      maxUnavailable: 0              # 更新时不允许减少可用数
  template:
    spec:
      terminationGracePeriodSeconds: 90  # 5s preStop + 最长 60s 推理 + 25s 余量
      containers:
      - name: sglang
        image: lmsysorg/sglang:latest
        ports:
        - containerPort: 30000
        lifecycle:
          preStop:
            exec:
              command:
              - /bin/sh
              - -c
              - |
                # 1. 等待网络侧摘流完成
                sleep 5
                # 2. 通知推理进程优雅退出（如果支持 graceful shutdown endpoint）
                curl -s http://localhost:30000/shutdown || true
        readinessProbe:
          httpGet:
            path: /health_generate
            port: 30000
          periodSeconds: 5
          failureThreshold: 2
        startupProbe:
          httpGet:
            path: /health
            port: 30000
          initialDelaySeconds: 10
          periodSeconds: 5
          failureThreshold: 30
---
# PDB：确保滚动更新/drain 时至少 2 个副本在线
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: sglang-pdb
  namespace: inference
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: sglang-inference
maxUnavailable: 0 + maxSurge: 1 的含义：滚动更新时先起一个新 Pod（surge），等它 Ready 后再杀一个旧 Pod。全程可用 Pod 数 >= replicas。代价是更新期间需要额外 1 个 GPU 的资源——但对于推理服务，可用性远比资源节约重要。

§7带走这些

① RBAC
最小权限原则：专用 SA + Role + RoleBinding，推理 Pod 只需 get/list pods + get configmaps
② NetworkPolicy
白名单防火墙：先 deny all，再逐条开放。别忘记放行 DNS（UDP 53）
③ PDB
维护时的可用性护栏：minAvailable 保障最低在线数，drain 时自动阻塞直到安全
④ SecurityContext
runAsNonRoot + readOnlyRootFilesystem + drop ALL capabilities，GPU 只加 SYS_PTRACE
⑤ 优雅下线
preStop(sleep 5s) + terminationGracePeriod(90s) + maxUnavailable:0 = 零停机更新
⑥ Checklist
上线前逐条过——资源/探针/安全/网络/可用性/可观测性/灾备，一项不能少
