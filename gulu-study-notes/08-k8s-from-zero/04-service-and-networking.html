§0为什么 Pod IP 不能直接用

每个 Pod 都有自己的 IP，为什么不能直接拿来访问？三个致命问题：

  • Pod 随时会死：被驱逐、OOM、滚动更新——IP 就变了。硬编码 Pod IP = 定时炸弹
  • Pod 可能有多副本：3 个推理 Pod 跑同一个模型，你请求发给谁？需要负载均衡
  • Pod IP 只在集群内可达：集群外的客户端根本访问不到 Pod 的 overlay 网络
  • Pod IP 没有语义：10.244.1.37 是什么服务？DNS 名字 sglang-svc.inference 才有语义
Service 就是解决方案：它提供一个稳定的虚拟 IP（ClusterIP）+ DNS 名，背后自动关联一组 Pod。Pod 死了换了 IP？Endpoints Controller 自动更新后端列表。客户端只认 Service，不认 Pod。
实战锚点
推理集群典型场景：SGLang 部署了 4 个副本跑 Qwen3-72B，每个 Pod 独占 8 卡 A100。上游 router 只需要知道 sglang-svc:80 这一个入口，kube-proxy 自动把请求均匀分发到 4 个 Pod。任何一个 Pod 因 OOM 重启换了 IP，对 router 完全无感。

§1Service 的四种类型

ClusterIP（默认）—— 集群内虚拟 IP + Endpoints

分配一个虚拟 IP（只存在于 iptables/IPVS 规则中，不绑定任何网卡），集群内 Pod 可通过这个 VIP 访问后端 Pod。

apiVersion: v1
kind: Service
metadata:
  name: sglang-svc
  namespace: inference
spec:
  type: ClusterIP              # 默认值，可不写
  selector:
    app: sglang                  # 匹配带这个 label 的 Pod
  ports:
  - name: http
    port: 80                     # Service 暴露的端口（客户端访问用）
    targetPort: 30000            # Pod 实际监听的端口（SGLang 默认 30000）
    protocol: TCP

创建后，K8S 自动维护 Endpoints（或 EndpointSlice）对象：

# kubectl get endpoints sglang-svc -n inference
NAME         ENDPOINTS
sglang-svc   10.244.1.5:30000,10.244.2.8:30000,10.244.3.12:30000

# 只有通过 readinessProbe 的 Pod 才会出现在 Endpoints 里
# Pod 模型没加载完 → readiness 失败 → 不在 Endpoints 里 → 不接流量
核心机制：Endpoints Controller watch 所有 Pod 和 Service。发现 Pod label 匹配某 Service 的 selector 且 Pod 处于 Ready 状态 → 把 Pod IP:port 加入该 Service 的 Endpoints。kube-proxy 再把 Endpoints 翻译成节点上的转发规则。

NodePort —— 节点端口映射

在 ClusterIP 基础上，额外在每个节点的固定端口上打开监听。外部流量可通过 <NodeIP>:<NodePort> 进入。

spec:
  type: NodePort
  selector:
    app: sglang
  ports:
  - port: 80
    targetPort: 30000
    nodePort: 31080             # 范围 30000-32767，不指定则随机分配
NodePort 的局限：端口范围有限（30000-32767 只有 2768 个）、无法做域名路由、每个服务占一个端口、安全性差（直接暴露节点端口）——不适合生产环境直接对外。通常只用于开发测试，或作为 LoadBalancer 的底层实现。

LoadBalancer —— 云厂商 LB 对接

在 NodePort 基础上，自动向云厂商申请一个外部负载均衡器（如腾讯云 CLB / AWS NLB），并把流量导到 NodePort。

spec:
  type: LoadBalancer
  selector:
    app: sglang
  ports:
  - port: 80
    targetPort: 30000
# 创建后 kubectl get svc 会看到 EXTERNAL-IP 列有公网 IP
# 云厂商通过 annotation 传入更多配置：
# metadata:
#   annotations:
#     service.kubernetes.io/tke-existed-lbid: "lb-xxxxxxx"  # 复用已有 CLB
层叠关系：LoadBalancer ⊃ NodePort ⊃ ClusterIP。创建一个 LoadBalancer Service 实际上同时拥有了 ClusterIP 和 NodePort。流量路径：外部 → LB 公网 IP → NodePort → iptables DNAT → Pod。

ExternalName —— CNAME 映射

不创建 ClusterIP，只在 CoreDNS 中注册一条 CNAME 记录。访问 Service DNS 名时返回外部域名。

spec:
  type: ExternalName
  externalName: model-registry.cos.ap-guangzhou.myqcloud.com  # 指向外部服务
# 集群内访问 model-registry.inference.svc.cluster.local
# → 直接 CNAME 到外部对象存储地址

典型场景：集群内服务想用统一 DNS 名访问集群外的模型仓库/数据库。后续迁移到集群内时只需改 Service 类型，客户端代码无需改动。

Headless Service（ClusterIP: None）—— StatefulSet 专用

不分配 VIP，DNS 查询直接返回所有后端 Pod 的 A 记录。每个 Pod 有独立的 DNS 名。

apiVersion: v1
kind: Service
metadata:
  name: sglang-headless
  namespace: inference
spec:
  clusterIP: None              # 关键：设为 None 就是 headless
  selector:
    app: sglang
  ports:
  - port: 30000
    targetPort: 30000
Headless 的 DNS 行为：
  • 查询 sglang-headless.inference.svc.cluster.local → 返回所有 Ready Pod 的 IP 列表（多条 A 记录）
  • 配合 StatefulSet 时，每个 Pod 有独立 DNS：sglang-0.sglang-headless.inference.svc.cluster.local
  • 客户端自己决定连哪个 Pod（或连全部）——没有 kube-proxy 介入
实战锚点
多机推理（tensor parallel 跨节点）时，worker 之间需要点对点通信（NCCL）。Headless Service + StatefulSet 让每个 worker 有稳定的 DNS 名（如 sglang-0.sglang-headless、sglang-1.sglang-headless），master 可以精确指定跟谁通信，而不是被 kube-proxy 随机负载均衡到错误的 Pod。

四种类型 + Headless 对比

类型VIP集群外可达负载均衡典型场景
ClusterIP有否kube-proxy 轮询集群内服务间调用
NodePort有是（节点 IP:端口）kube-proxy开发测试、非云环境
LoadBalancer有是（LB 外网 IP）云 LB + kube-proxy生产环境对外暴露
ExternalName无N/A（CNAME）无访问集群外服务
Headless无否客户端自选StatefulSet、P2P 通信

§2kube-proxy 的三种模式

kube-proxy 以 DaemonSet 形式跑在每个节点上，负责把 Service VIP 的流量转发到实际的后端 Pod。它 watch apiserver 的 Service/Endpoints 变更，然后在节点上配置转发规则。

iptables 模式（最常见 · 默认）

kube-proxy 把 Service → Endpoints 的映射翻译成 iptables 规则。内核直接在网络层做 DNAT，不经过用户态。

规则链路径：PREROUTING → KUBE-SERVICES → KUBE-SVC-xxx → KUBE-SEP-xxx

概率计算：3 个后端的 probability 分别是 1/3、1/2、1（不是三个都 1/3）。逻辑：第一条 33% 概率命中；没命中进入第二条，此时只剩 2 个候选，50% 命中；最后一条兜底 100%。效果等价于均匀分布。

IPVS 模式 —— 大规模集群性能更好

用 Linux IPVS（IP Virtual Server）内核模块做四层负载均衡。规则以 hash 表存储，查找复杂度 O(1)，不随 Service/Endpoints 数量退化。

  • 调度算法丰富：rr（轮询）、lc（最少连接）、dh（目标哈希）、sh（源哈希）、wrr（加权轮询）
  • 增量更新：Endpoints 变更时只改对应条目，不像 iptables 全量刷新
  • 内核原生：性能不随规模退化，10 万 Service 仍然稳定
  • 前置条件：节点内核需加载 ip_vs、ip_vs_rr、ip_vs_wrr、ip_vs_sh、nf_conntrack 模块
# 切换到 IPVS 模式：修改 kube-proxy ConfigMap
kubectl edit cm kube-proxy -n kube-system
# 找到 mode 字段改为：
mode: "ipvs"
ipvs:
  scheduler: "rr"              # 可选 rr/lc/dh/sh/wrr

# 然后重启 kube-proxy DaemonSet
kubectl rollout restart ds kube-proxy -n kube-system

userspace 模式（已废弃）

最初的实现：kube-proxy 在用户态监听端口，收到包后转发到后端 Pod。每个包都要内核态→用户态→内核态两次拷贝，性能极差。仅作历史了解，不会在生产中使用。

三种模式对比

维度iptablesIPVSuserspace（废弃）
转发层内核 netfilter内核 IPVS 模块用户态 kube-proxy 进程
规则查找O(N) 链式匹配O(1) hash 查找N/A
负载算法随机等权（概率）rr / lc / sh / dh / wrr轮询
Service 数量上限<5000 表现良好>10 万仍稳定几百就卡
规则更新方式全量刷新（大规模时慢）增量更新N/A

如何确认当前模式？ 
kubectl get cm kube-proxy -n kube-system -o yaml | grep mode
# 或在节点上直接检查：
iptables -t nat -L KUBE-SERVICES 2>/dev/null | head -3   # 有输出=iptables 模式
ipvsadm -Ln 2>/dev/null | head -5                        # 有输出=IPVS 模式
实战锚点
推理集群通常 Service 数量不多（几十个模型），但单个 Service 的 Endpoints 可能很多（同一模型几十个副本）。iptables 模式下每次 Endpoints 变更都要全量重建规则链——滚动更新 50 个 Pod 时，iptables 规则会被刷新 50 次，期间可能出现短暂的流量黑洞。如果你的集群副本数频繁变动（如用 HPA 自动扩缩），建议切换到 IPVS 模式。

§3DNS 解析链路

CoreDNS 架构

  • 以 Deployment 形式运行在 kube-system namespace，通常 2 副本保证 HA
  • 有自己的 ClusterIP Service（通常是 10.96.0.10），这是集群 DNS 的入口
  • kubelet 启动 Pod 时自动把 /etc/resolv.conf 的 nameserver 指向 CoreDNS
  • CoreDNS watch apiserver 获取 Service/Endpoints/Pod 信息，维护内存中的 DNS 记录

解析格式：<svc>.<ns>.svc.cluster.local

查询目标DNS 格式返回结果
普通 Servicesglang-svc.inference.svc.cluster.localClusterIP（单个 A 记录）
Headless Servicesglang-headless.inference.svc.cluster.local所有 Pod IP（多条 A 记录）
StatefulSet Podsglang-0.sglang-headless.inference.svc.cluster.local该 Pod 的 IP（单条 A 记录）
Pod DNS10-244-1-5.inference.pod.cluster.localPod IP（少用）
Service Port_http._tcp.sglang-svc.inference.svc.cluster.localSRV 记录

Pod 内 /etc/resolv.conf

# Pod 内 cat /etc/resolv.conf
nameserver 10.96.0.10                              # CoreDNS 的 ClusterIP
search inference.svc.cluster.local svc.cluster.local cluster.local  # search 域列表
options ndots:5                                    # ← 这个值是性能陷阱！

DNS 解析流程（SVG）

ndots 配置的坑

ndots:5 的代价：Pod 默认 ndots:5，意味着域名中点的数量 < 5 时，会先拼接 search 后缀查找。对于外部域名（如 huggingface.co 只有 1 个点），系统会先白白尝试 3 次集群后缀（NXDOMAIN），第 4 次才用原始域名查询成功。

影响：一次外部域名解析 = 4 次 DNS 查询 × 2（A + AAAA） = 8 个 UDP 包。高并发调用外部 API 时（如调 embedding 模型、下载 HuggingFace 模型），CoreDNS 压力翻 4 倍。

解决 ndots 问题

# 方案 1：Pod spec 中降低 ndots（推荐）
spec:
  dnsConfig:
    options:
    - name: ndots
      value: "2"                 # 域名含 2+ 个点直接走绝对查询
    - name: single-request-reopen  # 避免 A/AAAA 并发查询互相干扰

# 方案 2：代码中使用 FQDN（末尾加点，跳过 search）
# requests.get("https://api.openai.com./v1/chat")  ← 注意末尾的点

# 方案 3：CoreDNS 启用 autopath 插件（集群级别优化，一次查询尝试所有后缀）
经验法则：如果你的推理服务需要频繁访问外部 API（模型仓库、监控上报、外部 embedding 服务），把 ndots 降到 2。副作用是跨 namespace 的短名需要写两段以上（如 svc.ns），但这本来就是好习惯。 
# kubectl get cm coredns -n kube-system -o yaml
.:53 {
    errors                           # 记录错误到标准错误
    health {
        lameduck 5s                  # 优雅退出时继续服务 5s
    }
    ready                            # /ready 健康检查端点
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure                # 为 Pod 生成 DNS（基于 IP）
        fallthrough in-addr.arpa ip6.arpa
        ttl 30                       # DNS 记录 TTL 30 秒
    }
    prometheus :9153                 # 暴露 Prometheus metrics
    forward . /etc/resolv.conf {     # 非集群域名转发到上游 DNS
        max_concurrent 1000
    }
    cache 30                         # 缓存 30 秒
    loop                             # 检测转发环路
    reload                           # Corefile 变更自动热加载
    loadbalance                      # DNS 响应中 A 记录随机排序
}

kubernetes 插件负责集群内域名；forward 处理集群外域名；cache 30 减少重复查询。如果推理集群有大量外部 DNS 请求，可以加 cache 300 增大缓存时间。

实战锚点
推理服务的 router 组件需要频繁调用多个模型 Service（如 qwen3-svc、deepseek-svc、llama-svc）。如果 router 和模型 Service 在同一个 namespace，直接用短名即可——DNS 一次命中，零额外延迟。但如果 router 在 gateway namespace 而模型在 models namespace，用 qwen3-svc.models 即可（2 段短名在 ndots:5 下也会走 search，但第二个后缀就命中了）。

§4从 Pod A 到 Pod B 的完整网络路径

Pod A（router，在 Node 1）通过 ClusterIP Service 访问 Pod B（SGLang 推理，在 Node 2），数据包经过的每一跳：

每一跳详解

步骤负责组件做了什么
① DNSCoreDNSService 名 → ClusterIP（10.96.100.50）
② vethLinux 网络Pod 内 eth0 通过 veth pair 连到宿主机网络栈
③ DNATiptables / IPVSClusterIP:80 → 选中的 PodIP:30000
④ 路由Linux 路由表根据目标 Pod 子网判断下一跳（同节点 bridge / 跨节点转发）
⑤⑥ 跨节点CNI 插件VXLAN 封装 / VPC 路由 / Calico BGP
⑦ 接收目标节点网卡解封装（如果是 VXLAN）或直接路由接收
⑧ 路由目标节点路由表把包路由到目标 Pod 的 veth pair
⑨ 投递veth pair包到达 Pod B 的 eth0，应用层收到请求
关键设计：
  • DNAT 在源端执行——Service VIP 不是一个真正的代理进程，而是分布在每个节点上的 iptables 规则。没有单点瓶颈。
  • conntrack 管回程——Linux 内核自动记录 NAT 映射，回包时自动做 reverse DNAT，Pod B 看到的 src 是 Pod A 的真实 IP。
  • CNI 决定跨节点方式——K8S 只定义"任何 Pod 能直接通信"的要求，具体实现靠 CNI 插件（Flannel VXLAN / Calico BGP / Cilium eBPF / 云 VPC-CNI）。
性能参考：iptables DNAT + conntrack 纯内核操作，延迟 < 0.1ms。跨节点物理网络通常 0.1-0.5ms（同机房）。VXLAN 封装增加约 50 字节开销。对推理服务来说，这些网络延迟（~1ms 总计）相比模型推理耗时（100ms-60s）完全可忽略。瓶颈永远在 GPU 计算，不在网络。

§5Service 与推理服务的关系

推理服务通常用 ClusterIP + Ingress 暴露

生产环境不会给每个模型一个 LoadBalancer（贵且管理复杂）。标准做法：

  • 每个模型一个 ClusterIP Service（集群内入口）
  • 一个 Ingress 对象统一管外部入口，按 path/host 路由到不同模型 Service
  • Ingress Controller（Nginx/Envoy）本身通过一个 LoadBalancer Service 暴露

多模型路由架构图

Ingress 配置示例（多模型路由）

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: inference-gateway
  namespace: models
  annotations:
    # 推理服务必须加大超时——LLM 生成可能持续数分钟
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    # 多模态请求可能包含大图片
    nginx.ingress.kubernetes.io/proxy-body-size: "100m"
    # streaming（SSE）必须禁用缓冲，否则 token 不会实时返回
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - inference.mycompany.com
    secretName: inference-tls
  rules:
  - host: inference.mycompany.com
    http:
      paths:
      - path: /v1/qwen3                  # Qwen3-72B 对话/补全
        pathType: Prefix
        backend:
          service:
            name: qwen3-72b-svc
            port:
              number: 80
      - path: /v1/deepseek               # DeepSeek-R1 推理
        pathType: Prefix
        backend:
          service:
            name: deepseek-r1-svc
            port:
              number: 80
      - path: /v1/embeddings             # BGE-M3 向量化
        pathType: Prefix
        backend:
          service:
            name: bge-m3-embed-svc
            port:
              number: 80
推理服务 Ingress 的三个必配项：
  • proxy-read-timeout ≥ 300：默认 60s 远远不够，长 prompt 首 token 延迟就可能 30s+
  • proxy-body-size ≥ 50m：多模态请求包含图片/音频，默认 1m 会直接 413
  • proxy-buffering: "off"：SSE streaming 场景必须关闭，否则客户端看不到实时 token 流
不配这三项 = 线上 504/413/streaming 卡死。

进阶：多模型智能路由

方案实现方式适用场景
按 path 路由Ingress rules.paths固定模型列表，最简单
按 header 路由Nginx canary / Envoy header match客户端指定 X-Model-Name header
按权重分流Nginx canary-weight annotation新模型灰度发布，10% 流量到新版

实战锚点
生产推理平台的完整网络链路：
客户端 → CLB(SSL卸载) → Nginx Ingress(路由) → ClusterIP Service → SGLang Pod

关键配置清单：
  • Ingress: timeout ≥ 300s, body-size ≥ 50m, buffering off
  • Service: sessionAffinity 默认关闭（推理通常无状态）；如需 prefix caching 亲和性可开启
  • Pod: readinessProbe 确认模型加载完毕才接流量
  • 多机推理: worker 间用 Headless Service 做 NCCL 通信，对外暴露只走 master 的 Service
