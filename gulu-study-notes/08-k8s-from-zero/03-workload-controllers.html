§0为什么不直接管理 Pod

上一章学了 Pod 的生命周期——你可以直接 kubectl apply 一个裸 Pod。但生产环境里没有人这么做。原因：

  • Pod 死了没人补：裸 Pod 被 OOM Kill、被驱逐、节点挂了，就永远消失了——没有控制器帮你创建新的
  • 扩缩无从谈起：想从 1 个推理实例扩到 8 个，你得手动写 8 份几乎一样的 YAML
  • 更新是全量中断：要升级镜像版本，你得先删旧 Pod 再建新 Pod，中间服务不可用
  • 回滚无迹可寻：新版本出 bug 了，你连上一个版本的 spec 都找不到
控制器 = 高级 reconcile 循环。第一章讲的 Controller Manager 里跑了一堆内置 controller，每种控制器负责一类工作负载的"期望状态 → 实际状态"对齐。你声明"我要 3 个推理 Pod"，controller 持续保证 3 个在跑。

控制器的共同模式

while true:
    desired = 从 etcd 读取用户声明的期望状态
    actual  = 从 etcd 读取当前实际状态
    if actual < desired: 创建新 Pod
    if actual > desired: 删除多余 Pod
    if Pod template 变了: 按策略滚动替换
    wait for next event

K8S 提供了四种内置工作负载控制器，覆盖所有场景：

控制器解决什么问题典型推理场景
Deployment无状态应用的多副本管理 + 滚动更新SGLang / vLLM 无状态推理实例
StatefulSet有状态应用的稳定标识 + 有序管理PD 分离的 Decode Worker、模型分片服务
DaemonSet每个节点跑一个 PodGPU 监控 agent、device-plugin、日志收集
Job / CronJob一次性 / 定时批任务批量离线推理、模型评估、数据预处理
核心观念：你管的是控制器（Deployment / StatefulSet），不是 Pod。Pod 是控制器创建的"执行单元"，随时可以被销毁和重建。不要 kubectl delete pod 去"重启"服务——用 kubectl rollout restart 让控制器帮你做。

§1Deployment · 无状态应用的标准答案

Deployment 是最常用的工作负载控制器，适用于任意副本都等价、可以随时创建销毁的无状态服务。推理服务 90% 的场景用它。

Deployment → ReplicaSet → Pod 的层级关系

为什么中间要多一层 ReplicaSet？

  • 版本追踪：每个 ReplicaSet 对应一个 Pod template 版本（revision），滚动更新 = 新 RS 扩容 + 旧 RS 缩容
  • 回滚能力：旧 ReplicaSet 保留着（replicas=0），回滚只需把旧 RS 扩回来
  • 职责清晰：ReplicaSet 只管"维持 N 个 Pod"，Deployment 管"版本演进策略"
注意：只有 spec.template 的变更才会触发滚动更新并创建新 ReplicaSet。改 replicas 只是在当前 RS 上 scale，不会产生新版本。

滚动更新策略（maxSurge / maxUnavailable）

apiVersion: apps/v1
kind: Deployment
metadata:
  name: sglang-inference
spec:
  replicas: 4                          # 期望 4 个推理实例
  revisionHistoryLimit: 5              # 保留最近 5 个历史 RS（用于回滚）
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                     # 更新时最多多出 1 个 Pod（总数最多 5）
      maxUnavailable: 0               # 更新时不允许少于 4 个可用（零宕机）
  selector:
    matchLabels:
      app: sglang-inference
  template:
    metadata:
      labels:
        app: sglang-inference
    spec:
      containers:
      - name: sglang
        image: lmsys/sglang:v0.4.5-cu124  # 更新此字段触发滚动更新
        ports:
        - containerPort: 30000
        resources:
          limits:
            nvidia.com/gpu: "1"        # 每副本 1 块 GPU
          requests:
            cpu: "4"
            memory: "32Gi"
        startupProbe:                  # 模型加载可能 60-120s
          httpGet:
            path: /health
            port: 30000
          periodSeconds: 5
          failureThreshold: 30         # 最多等 150s
        readinessProbe:
          httpGet:
            path: /health_generate
            port: 30000
          periodSeconds: 5
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 5"]
      terminationGracePeriodSeconds: 90

maxSurge 和 maxUnavailable 的组合效果

组合效果适用场景
maxSurge=1, maxUnavailable=0先建新再删旧，始终不低于期望数GPU 推理服务（推荐）——不能容忍容量下降
maxSurge=0, maxUnavailable=1先删旧再建新，节省资源GPU 紧张时可接受短暂容量下降
maxSurge=25%, maxUnavailable=25%默认值，同时有新旧 Pod 在替换普通 Web 服务，快速更新

滚动更新过程可视化

回滚机制（revision history）

# 查看历史版本
$ kubectl rollout history deployment/sglang-inference
REVISION  CHANGE-CAUSE
1         初始部署 sglang:v0.4.3
2         升级到 sglang:v0.4.4
3         升级到 sglang:v0.4.5（当前）

# 回滚到上一个版本
$ kubectl rollout undo deployment/sglang-inference

# 回滚到指定版本
$ kubectl rollout undo deployment/sglang-inference --to-revision=1

# 查看当前滚动状态
$ kubectl rollout status deployment/sglang-inference
回滚的本质：Deployment 把旧 ReplicaSet 的 replicas 从 0 扩回去，把当前 RS 缩到 0。这也是为什么 revisionHistoryLimit 不能设为 0——设为 0 意味着删除所有旧 RS，无法回滚。
实战锚点
推理服务的滚动更新比普通 Web 服务慢得多：每个新 Pod 要拉镜像（~15GB）+ 加载模型权重到 GPU（60-120s）。建议 maxSurge=1, maxUnavailable=0，搭配 minReadySeconds: 30（新 Pod ready 后再观察 30s 才继续替换下一个），避免新版本有 bug 时一口气替换完才发现。
常见错误：推理 Deployment 用了默认的 maxSurge=25%。4 副本 × 25% = 多创建 1 个 Pod，但 GPU 节点只剩 0 块空闲 GPU → 新 Pod Pending → 旧 Pod 已经开始被删（maxUnavailable=25% = 可以少 1 个）→ 服务容量从 4 降到 3 却没有新 Pod 补上。GPU 场景务必显式配置 maxSurge 和 maxUnavailable。

§2StatefulSet · 有状态应用

StatefulSet 为每个 Pod 提供稳定的网络标识和持久化存储。Pod 不再是"等价可替换的"——每个有唯一身份。

与 Deployment 的核心区别

特性DeploymentStatefulSet
Pod 名称随机后缀 sglang-7f8b4c-x9k2p有序编号 sglang-0, sglang-1, sglang-2
网络标识无稳定 DNS，通过 Service VIP 访问每个 Pod 有固定 DNS：pod-name.headless-svc
存储多副本共享或无持久存储每个 Pod 有独立 PVC（volumeClaimTemplates）
启停顺序并行随机有序：启动 0→1→2，缩容 2→1→0
更新按 maxSurge 并行逐个替换（从最大序号开始）
Pod 重建后新名字、可能新节点同名、绑定同一 PVC

稳定网络标识（ordinal index + headless service）

有序启停

  • 默认 OrderedReady：Pod-0 Ready 后才创建 Pod-1 → Pod-1 Ready 后才创建 Pod-2
  • 缩容反序：先删 Pod-N → 再删 Pod-N-1（保证 0 号是最后被删的）
  • Parallel 模式：设置 podManagementPolicy: Parallel 可并行启停，适合无顺序依赖的场景

volumeClaimTemplates · 每个 Pod 独立 PVC

apiVersion: v1
kind: Service
metadata:
  name: sglang-decode-hl           # Headless Service
spec:
  clusterIP: None                  # 关键! 无 VIP, DNS 直接解析到 Pod IP
  selector:
    app: sglang-decode
  ports:
  - port: 30000
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: sglang-decode
spec:
  serviceName: sglang-decode-hl     # 绑定 Headless Service
  replicas: 4
  podManagementPolicy: Parallel    # 并行启动, 不需要等上一个 Ready
  selector:
    matchLabels:
      app: sglang-decode
  template:
    metadata:
      labels:
        app: sglang-decode
    spec:
      containers:
      - name: decode-worker
        image: lmsys/sglang:v0.4.5-cu124
        env:
        - name: WORKER_ID              # 通过 Pod ordinal 获取身份
          valueFrom:
            fieldRef:
              fieldPath: metadata.labels['apps.kubernetes.io/pod-index']
        volumeMounts:
        - name: kv-cache
          mountPath: /data/kv-cache   # 每个 worker 独立的 KV Cache 目录
        resources:
          limits:
            nvidia.com/gpu: "1"
  volumeClaimTemplates:             # 每个 Pod 自动创建独立 PVC
  - metadata:
      name: kv-cache
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: local-nvme
      resources:
        requests:
          storage: 200Gi             # KV Cache 可能很大
volumeClaimTemplates 的命名规则：自动为每个 Pod 创建 PVC，命名为 {template-name}-{statefulset-name}-{ordinal}。例如 kv-cache-sglang-decode-0、kv-cache-sglang-decode-1。缩容时 PVC 不自动删除，扩容时自动绑定已有 PVC——数据不丢。

什么时候推理服务需要 StatefulSet？

实战锚点

PD 分离（Prefill-Decode disaggregation）场景是 StatefulSet 的典型用例：

  • Prefill 节点要通过固定地址路由 KV Cache 到 "Decode-2" → 需要稳定 DNS
  • 每个 Decode worker 的本地 NVMe 有独立 KV Cache 持久化 → 需要独立 PVC
  • 重启后必须恢复到同一 identity 才能接回自己的 KV Cache → 需要固定 ordinal
  • 多机 Tensor Parallel 中每个 worker 需要知道"我是 rank-N, 加载 shard-N" → 需要固定身份

如果你的推理服务每个副本独立加载完整模型、互不通信——用 Deployment，更简单更灵活。

常见错误：滥用 StatefulSet。如果你的推理副本完全等价、没有持久状态、不需要互相寻址——用 StatefulSet 只会让运维更复杂：更新是逐个串行的（比 Deployment 慢 N 倍）、缩容遗留 PVC 占磁盘、Pod 绑定了特定存储后调度灵活性下降。
策略行为典型用法
RollingUpdate（默认）从最大序号开始逆序替换，每个 Ready 后继续正常升级
RollingUpdate + partition只更新序号 >= partition 的 Pod金丝雀：先更新 Pod-3 验证，再设 partition=0 更新全部
OnDelete不自动更新，手动删 Pod 后才用新模板重建需要精确控制每个实例何时更新
 
# 金丝雀发布：只更新 Pod-3（序号 >= 3），Pod-0/1/2 保持旧版
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    partition: 3

# 验证通过后，设 partition=0 → 全部更新
$ kubectl patch statefulset sglang-decode -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'

§3DaemonSet · 每节点一个

DaemonSet 确保每个匹配的 Node 上恰好运行一个 Pod。新节点加入自动部署，节点移除自动清理。

典型场景

用途例子为什么必须每节点一个
GPU Device Pluginnvidia-device-plugin注册本节点 GPU 到 kubelet，让 scheduler 能分配
监控 Agentnode-exporter, dcgm-exporter采集本机 CPU/Mem/GPU 温度/功耗/显存指标
日志收集Fluent Bit, Filebeat读取本机 /var/log/containers/ 所有容器日志
网络插件Calico node, Cilium agent配置本节点 Pod 网络规则和路由
存储 CSIlocal-path-provisioner管理本节点磁盘作为持久卷

YAML 示例：GPU 监控 DaemonSet

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: dcgm-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: dcgm-exporter
  updateStrategy:
    type: RollingUpdate               # 逐节点滚动更新
    rollingUpdate:
      maxUnavailable: 1                # 每次最多 1 个节点的 Pod 在更新
  template:
    metadata:
      labels:
        app: dcgm-exporter
    spec:
      nodeSelector:
        nvidia.com/gpu.present: "true"  # 只在有 GPU 的节点部署
      tolerations:
      - key: nvidia.com/gpu             # 容忍 GPU taint
        operator: Exists
        effect: NoSchedule
      containers:
      - name: dcgm-exporter
        image: nvcr.io/nvidia/k8s/dcgm-exporter:3.3.0
        ports:
        - containerPort: 9400
          name: metrics
        securityContext:
          privileged: true               # 需要访问 GPU 驱动
        volumeMounts:
        - name: dev
          mountPath: /dev
      volumes:
      - name: dev
        hostPath:
          path: /dev

updateStrategy（RollingUpdate vs OnDelete）

策略行为适用场景
RollingUpdate（默认）自动逐节点删旧建新，maxUnavailable 控制并行度大多数场景——监控、日志收集器升级
OnDelete不自动更新，手动删 Pod 才会用新模板重建device-plugin 等关键组件——更新会短暂导致 GPU 不可用，需配合 drain 节点逐个操作
maxUnavailable 的含义不同：DaemonSet 每节点只有 1 个 Pod，所以 maxUnavailable=1 表示"同时只有 1 个节点在更新"。想加速可设为 maxUnavailable=3（3 个节点并行更新）或 "20%"。
常见错误：忘记给 DaemonSet 加 tolerations。GPU 节点通常有 taint（如 nvidia.com/gpu=present:NoSchedule），DaemonSet 的 Pod 也要配对应 toleration 才能调度上去。否则你会看到部分 GPU 节点没有监控 Pod。
实战锚点
GPU 推理集群中，nvidia-device-plugin DaemonSet 是基础设施的关键。如果它挂了：
① 新 Pod 无法调度到该节点——GPU 资源"消失"（nvidia.com/gpu Allocatable 变 0）
② 已运行的 Pod 不受影响——设备绑定已完成
排障第一步：kubectl get pods -n kube-system -l name=nvidia-device-plugin -o wide 检查对应节点的 Pod 状态。

§4Job / CronJob · 一次性和定时任务

Job 确保一个或多个 Pod 成功运行至完成。Pod 完成后不会被重建——这是与 Deployment 的根本区别。

核心参数

参数含义默认值
completions需要成功完成的 Pod 总数1
parallelism同时运行的最大 Pod 数1
backoffLimit累计失败 Pod 数上限（超过则 Job Failed）6
activeDeadlineSecondsJob 整体超时（超过则强制终止所有 Pod）无限制
ttlSecondsAfterFinished完成后自动清理 Job 对象的时间不清理

completions / parallelism 组合模式

completionsparallelism模式场景
11单任务串行一次性数据迁移、模型格式转换
NM (M<N)固定完成数并行批量推理（50 分片 8 并行）
空M工作队列模式从 Redis/Kafka 消费任务直到队列空

批量离线推理 Job 示例

apiVersion: batch/v1
kind: Job
metadata:
  name: batch-inference-qwen3-72b
spec:
  completionMode: Indexed            # 每个 Pod 获得唯一 JOB_COMPLETION_INDEX
  completions: 50                    # 50 个数据分片需处理
  parallelism: 8                     # 同时跑 8 个（受 GPU 数量限制）
  backoffLimit: 10                   # 允许累计 10 次 Pod 失败
  activeDeadlineSeconds: 7200        # 整个 Job 2 小时超时
  ttlSecondsAfterFinished: 3600      # 完成 1 小时后自动清理
  template:
    spec:
      restartPolicy: OnFailure         # Job Pod 必须是 OnFailure 或 Never
      containers:
      - name: inference
        image: my-registry/batch-inference:v1.2
        command: ["python", "run_batch.py"]
        args:
        - "--shard-index=$(JOB_COMPLETION_INDEX)"  # 用索引确定处理哪个分片
        - "--total-shards=50"
        - "--model=qwen3-72b"
        - "--input=cos://bucket/prompts/"
        - "--output=cos://bucket/results/"
        resources:
          limits:
            nvidia.com/gpu: "1"
          requests:
            cpu: "4"
            memory: "32Gi"
Indexed Job（K8S 1.24+）：设置 completionMode: Indexed 后，每个 Pod 被分配唯一索引（0 到 completions-1），通过环境变量 JOB_COMPLETION_INDEX 获取。天然适合"数据分片并行处理"——不需要额外消息队列，Job 自带去重保证（同一 index 只会成功一次）。

CronJob · 定时触发 Job

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-model-eval
spec:
  schedule: "0 2 * * *"              # 每天凌晨 2 点执行
  concurrencyPolicy: Forbid          # 上一次没跑完就跳过本次
  successfulJobsHistoryLimit: 3      # 保留最近 3 次成功 Job
  failedJobsHistoryLimit: 3          # 保留最近 3 次失败 Job
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: eval
            image: my-registry/model-eval:v2.0
            command: ["python", "eval_benchmark.py"]
            args: ["--model=qwen3-72b", "--benchmarks=mmlu,gsm8k"]
            resources:
              limits:
                nvidia.com/gpu: "1"

concurrencyPolicy 选项

值行为适用场景
Allow（默认）允许并发——上一次没完也启动新的互不影响的任务
Forbid跳过——上一次还在跑就不启动评测任务（不想重复占 GPU）
Replace取消上一次未完成的，启动新的数据始终以最新为准的场景
backoffLimit 的坑：backoffLimit 是整个 Job 的累计失败 Pod 数上限，不是单 Pod 重试次数。如果 completions=50, backoffLimit=6，任意 6 个 Pod 失败（可能是不同 shard）就会导致整个 Job Failed。大批量任务建议设为 backoffLimit = completions × 0.2（容忍 20% 失败率）。
实战锚点
批量离线推理的典型模式：将评测数据集切成 N 个 shard，parallelism 设为可用 GPU 数。每个 Pod 通过 JOB_COMPLETION_INDEX 知道处理哪个 shard。这比手动起 N 个脚本强在：失败自动重试、超时自动终止、完成自动清理、进度一目了然（kubectl get job 看 completions 计数）。

§5选择决策树

面对一个工作负载，用哪种控制器？跟着这棵决策树走：

经验法则：90% 的推理在线服务用 Deployment 就够了。只有当 Pod 之间不等价（需要固定身份、持久卷、有序管理）时，才升级到 StatefulSet。不要为了"感觉更高级"选 StatefulSet——它的运维复杂度显著更高。犹豫不决时先选 Deployment。

§6带走这些

① 不管裸 Pod
永远通过控制器管理工作负载——自愈、扩缩、滚动更新、回滚全靠它
② Deployment
无状态首选 · Deployment → ReplicaSet → Pod 三层 · 版本管理 + 秒级回滚
③ 滚动更新
maxSurge 控"最多多几个" · maxUnavailable 控"最多少几个" · GPU 场景推荐 1/0
④ StatefulSet
稳定 Pod 名 + DNS + PVC · 有序启停 · PD 分离 / 模型分片场景使用
⑤ DaemonSet
每节点一个 Pod · 监控 / 日志 / device-plugin 的标配 · 别忘 toleration
⑥ Job / CronJob
跑完即止 · completions + parallelism 组合出串行 / 并行 / 队列三种模式
⑦ 选择标准
无状态 → Deployment · 有身份 → StatefulSet · 每节点 → DaemonSet · 一次性 → Job
