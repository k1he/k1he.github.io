§0为什么推理服务需要关心存储

传统 Web 服务的容器是无状态的——代码在镜像里，启动就能干活。但 LLM 推理服务不一样：

  • 模型权重巨大：Qwen3-72B 的 safetensors 约 70GB，DeepSeek-V3 更是 600GB+
  • 不能打进镜像：镜像层只适合存几百 MB 的代码和依赖，70GB 镜像拉取要 10 分钟+
  • 启动前必须到位：推理进程需要 mmap 或逐层加载权重文件，文件不在就跑不了
  • 多副本共享：同一个模型可能被 10 个推理 Pod 同时使用，每个都拷一份太浪费
一句话：推理服务的第一性能瓶颈往往不是 GPU 计算，而是模型权重从存储到 GPU 显存的搬运速度。从哪种存储搬、用什么协议搬、能不能预热——这些都是存储子系统的范畴。
实战锚点
一个 70GB 模型权重从不同存储加载的首次启动时间：
  • 本地 NVMe：70GB / 3.2GB/s = ~22 秒（纯 IO，最快）
  • 网络 CephFS：70GB / 800MB/s = ~90 秒（受网络带宽限制）
  • 对象存储 FUSE：70GB / 200MB/s = ~350 秒（FUSE overhead + 小文件随机读）
  • GooseFS 缓存命中：70GB / 1.8GB/s = ~40 秒（内存缓存加速）
选错存储方案，扩容一个推理副本要多等 5 分钟——在流量洪峰时，这是不可接受的。

§1PV 和 PVC 的绑定模型

K8S 的存储抽象分两层：供给侧（PV）和消费侧（PVC）。这种分离让 Pod 不需要知道底层存储的实现细节。

核心概念

概念创建者作用域类比
PersistentVolume (PV)管理员 / Provisioner集群级（无 namespace）物理磁盘
PersistentVolumeClaim (PVC)用户 / Pod specNamespace 级磁盘申请单

绑定流程

accessModes 详解

模式缩写含义典型存储推理场景
ReadWriteOnceRWO单节点读写云磁盘、本地盘单副本推理 / checkpoint
ReadOnlyManyROX多节点只读NFS、CephFS多副本共享模型权重
ReadWriteManyRWX多节点读写NFS、CephFS、Lustre分布式训练 checkpoint
常见误解：RWO 不是"只有一个 Pod 能用"，而是"只能挂载到一个节点"。同一节点上的多个 Pod 可以同时挂载同一个 RWO 的 PV。在推理场景中，如果用 local PV 存模型且同节点部署多个推理 Pod，RWO 就够用。

YAML 示例：PV + PVC

# --- PV：管理员提前创建，对应一块 NVMe 本地盘 ---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: gpu-node-01-nvme         # 命名规范：节点名-存储类型
spec:
  capacity:
    storage: 1800Gi              # 1.8TB NVMe
  accessModes:
    - ReadOnlyMany               # 模型只读，多 Pod 共享
  persistentVolumeReclaimPolicy: Retain  # 释放后保留数据
  storageClassName: local-nvme
  local:
    path: /mnt/nvme0             # 节点上的实际挂载路径
  nodeAffinity:                  # local PV 必须绑定节点
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: ["gpu-node-01"]
---
# --- PVC：用户在 inference namespace 创建 ---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: model-weights-pvc
  namespace: inference
spec:
  accessModes:
    - ReadOnlyMany
  resources:
    requests:
      storage: 100Gi            # 只需要 100Gi 就够放 72B 模型
  storageClassName: local-nvme  # 匹配 PV 的 storageClassName
PVC Pending 常见原因：① storageClassName 不匹配 ② 没有满足容量要求的 Available PV ③ accessModes 不兼容 ④ 用了 WaitForFirstConsumer 但 Pod 还没被调度。用 kubectl describe pvc 看 Events 能快速定位。

§2StorageClass 和动态供给

手动创建 PV 在小集群可行，但 100 个节点 × 4 块 NVMe = 400 个 PV 手动管理？不现实。StorageClass + 动态供给解决这个问题。

静态供给 vs 动态供给

静态供给

  • 管理员手动创建 PV
  • PVC 从已有 PV 中匹配
  • 适合：固定节点的 local 盘
  • 缺点：运维负担重

动态供给

  • PVC 引用 StorageClass
  • Provisioner 自动创建 PV + 底层存储
  • 适合：云磁盘、Ceph RBD
  • 优点：按需创建，用完回收

Provisioner 工作流

StorageClass YAML 示例

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: cbs-premium
provisioner: com.tencent.cloud.csi.cbs    # 腾讯云 CBS CSI 驱动
parameters:
  diskType: CLOUD_PREMIUM                  # 高性能云硬盘
reclaimPolicy: Delete                      # PVC 删除时自动删磁盘
volumeBindingMode: WaitForFirstConsumer    # 等 Pod 调度后再创盘
allowVolumeExpansion: true                 # 允许在线扩容

两个关键策略

参数选项含义推理场景建议
reclaimPolicy Retain PVC 删除后 PV 保留，需手动清理 模型权重盘 — 防止误删 70GB 数据
Delete PVC 删除后 PV 和底层存储一起删 临时 scratch 盘 / 推理缓存
volumeBindingMode Immediate PVC 创建时立刻绑定 PV 网络盘（无拓扑限制）
WaitForFirstConsumer 等 Pod 被调度到节点后再绑定 本地盘必须用这个（否则可能绑到错误节点的盘）
经典事故：StorageClass 用了 Immediate 绑定模式 + local PV。PVC 创建时立刻绑到了 node-A 的 PV，但 scheduler 因为 GPU 亲和把 Pod 调度到 node-B → Pod 永远 Pending（"volume node affinity conflict"）。本地盘的 SC 必须用 WaitForFirstConsumer。

§3本地存储方案

推理服务对存储带宽极度敏感——模型加载是纯顺序读 IO。本地 NVMe 盘能提供最高 3.2GB/s 的读带宽，远超任何网络存储。

三种本地存储对比

方案是否绑节点调度感知生产可用
hostPath 是 无（scheduler 不知道） 危险，仅调试
local PV 是 有（nodeAffinity 强制） 推荐
emptyDir 随 Pod 生灭 N/A 临时缓存可用

hostPath — 简单但危险

# 不推荐用于生产！仅列出供理解
volumes:
- name: model-dir
  hostPath:
    path: /data/models        # 直接挂宿主机路径
    type: Directory
hostPath 的问题：① scheduler 不知道这个路径在哪些节点存在——Pod 调度到没有 /data/models 的节点就挂 ② 没有容量管理 ③ 安全风险（容器可以访问宿主机文件系统） ④ 多租户隔离不了。

local PV — 生产推荐方案

apiVersion: v1
kind: PersistentVolume
metadata:
  name: gpu-node-02-nvme-models
spec:
  capacity:
    storage: 900Gi
  accessModes:
    - ReadOnlyMany            # 多个推理 Pod 只读共享
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-nvme
  local:
    path: /mnt/nvme0/models   # NVMe 盘上的模型目录
  nodeAffinity:               # 关键：把 PV 绑到具体节点
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values: ["gpu-node-02"]
local PV 的核心设计：通过 nodeAffinity 告诉 scheduler "这个 PV 只在 gpu-node-02 上可用"。scheduler 在调度引用此 PVC 的 Pod 时，会自动把 Pod 约束到 gpu-node-02。这就解决了 hostPath 的"调度盲区"问题。

NVMe 本地盘的管理实践

# 节点初始化脚本：格式化并挂载 NVMe
#!/bin/bash
NVME_DEV="/dev/nvme0n1"
MOUNT_POINT="/mnt/nvme0"

# 创建 XFS 文件系统（对大文件顺序读最友好）
mkfs.xfs -f ${NVME_DEV}
mkdir -p ${MOUNT_POINT}
mount -o noatime,nodiratime ${NVME_DEV} ${MOUNT_POINT}

# 写入 fstab 持久化
echo "${NVME_DEV} ${MOUNT_POINT} xfs noatime,nodiratime 0 0" >> /etc/fstab

# 创建模型目录
mkdir -p ${MOUNT_POINT}/models
chmod 755 ${MOUNT_POINT}/models
实战锚点
GPU 节点通常配 2-4 块 NVMe（每块 1.9TB）。最佳实践是：一块盘专门存模型权重（只读，用 local PV），另一块盘做推理中间结果的 scratch 空间（用 emptyDir 的 medium: "" 配合 sizeLimit）。模型盘用 Retain 策略，避免 Pod 删除时误清权重文件。

§4网络存储方案

本地盘快但不灵活——模型更新需要逐节点同步，新节点加入需要预热。网络存储解决的是灵活性和共享的问题。

常见网络存储对比

存储协议带宽accessModes适用场景
NFSNFSv4~500MB/sRWX / ROX简单共享，小规模集群
CephFSCeph RADOS~800MB/sRWX / ROX大规模分布式存储
云磁盘iSCSI / NVMe-oF~350MB/sRWO持久化数据，高可靠
对象存储 + FUSES3 / COS~200MB/sROX海量冷数据，模型归档
GooseFSFUSE / POSIX~1.8GB/sROX缓存加速层，推理热数据

NFS / CephFS — 多副本共享模型

apiVersion: v1
kind: PersistentVolume
metadata:
  name: model-nfs
spec:
  capacity:
    storage: 2Ti
  accessModes:
    - ReadOnlyMany             # 多节点只读 — 推理 Pod 共享
  nfs:
    server: 10.0.1.100         # NFS server 地址
    path: /exports/models      # 模型存储路径
  mountOptions:
    - ro                       # 强制只读挂载
    - nfsvers=4.1
    - rsize=1048576            # 1MB read size，大文件顺序读优化
    - wsize=1048576

对象存储 + FUSE 挂载

# 使用 cosfs / s3fs 把对象存储挂载为 POSIX 文件系统
apiVersion: v1
kind: Pod
metadata:
  name: inference-pod
spec:
  containers:
  - name: sglang
    volumeMounts:
    - name: cos-models
      mountPath: /models
      readOnly: true
  volumes:
  - name: cos-models
    flexVolume:                # 或通过 CSI 驱动挂载
      driver: "cos.csi.cloud"
      options:
        bucket: "model-weights-prod"
        path: "/qwen3-72b"
        additional_args: "-oallow_other -o max_read_ahead=128m"
FUSE 挂载的性能陷阱：对象存储通过 FUSE 虽然提供了 POSIX 兼容接口，但 ① 元数据操作（ls / stat）很慢 ② 随机读性能差 ③ 内核态/用户态切换开销大。不适合直接用于推理服务加载模型——应该作为数据源，配合缓存层使用。

GooseFS — 缓存加速层

GooseFS（腾讯云的分布式缓存系统，类似 Alluxio）在对象存储和推理 Pod 之间加了一层内存/SSD 缓存：

# GooseFS FUSE 挂载 — 透明缓存加速
apiVersion: v1
kind: Pod
metadata:
  name: inference-pod
spec:
  initContainers:
  - name: warm-cache
    image: goosefs-client:v2.5
    command: ["/bin/sh", "-c"]
    args:
    - |
      # 预热：把模型从 COS 加载到 GooseFS 缓存
      goosefs fs load /models/qwen3-72b
      # 校验缓存命中率
      goosefs fs stat /models/qwen3-72b | grep "InCache: 100%"
  containers:
  - name: sglang
    volumeMounts:
    - name: goosefs-fuse
      mountPath: /models       # 推理进程直接读这个路径
      readOnly: true
  volumes:
  - name: goosefs-fuse
    hostPath:
      path: /mnt/goosefs-fuse  # GooseFS FUSE 在节点上的挂载点
实战锚点
GooseFS 在缓存命中时读带宽可达 1.8GB/s（内存缓存）或 1.2GB/s（SSD 缓存），接近本地 NVMe 性能。首次冷启动仍需从 COS 拉取（~200MB/s），但后续同模型的 Pod 启动只需 40 秒。适合"模型版本固定、副本数动态伸缩"的场景。

§5CSI 驱动架构（简述）

CSI（Container Storage Interface）是 K8S 与存储系统之间的标准接口。所有现代存储方案都通过 CSI 驱动接入 K8S。

两侧架构

职责划分

侧部署形式职责关键操作
ControllerDeployment (1 副本)存储资源的生命周期管理CreateVolume / DeleteVolume / Attach / Snapshot
NodeDaemonSet (每节点)节点上的挂载操作NodeStageVolume / NodePublishVolume / NodeUnpublish

常见 CSI 驱动

驱动存储类型适用场景
ceph-csiCeph RBD / CephFS私有云大规模分布式存储
aws-ebs-csi-driverAWS EBSAWS 上的块存储
com.tencent.cloud.csi.cbs腾讯云 CBS腾讯云块存储
local-path-provisioner本地路径开发/测试环境本地盘动态供给
csi-driver-nfsNFSNFS 动态 provisioning
  1. PVC 创建 → Controller 侧 csi-provisioner watch 到 → 调用 CSI Plugin 的 CreateVolume
  2. Pod 调度到节点 → Controller 侧 csi-attacher 调用 ControllerPublishVolume（把磁盘 attach 到节点）
  3. kubelet 发现 Pod 需要 Volume → 调用 Node 侧 Plugin 的 NodeStageVolume（格式化 + mount 到全局目录）
  4. kubelet 调用 NodePublishVolume（bind mount 到 Pod 的目录）
  5. Pod 退出 → kubelet 调用 NodeUnpublishVolume + NodeUnstageVolume
  6. PVC 删除 → csi-attacher 调用 ControllerUnpublishVolume → csi-provisioner 调用 DeleteVolume

§6模型权重加载方案对比

选择模型加载方案时需要权衡：首次启动时间、扩容速度、运维复杂度、成本。以下对比假设模型大小为 70GB（Qwen3-72B 级别）。

方案读带宽首次启动扩容时间灵活性运维复杂度
NVMe local PV
模型预置在节点		 3.2 GB/s ~22s 慢（需预热新节点） 低（绑死节点） 中（需管理节点盘）
网络盘 PVC
CephFS / NFS		 0.5-0.8 GB/s ~90-140s 快（任意节点调度） 高（无节点限制） 低（标准 PVC）
initContainer 拉取
从 COS/S3 下载到 emptyDir		 0.2 GB/s ~350s 中（每次都要下载） 高（无节点限制） 低（纯 Pod 内逻辑）
GooseFS 缓存
缓存命中时		 1.8 GB/s ~40s 快（缓存层透明） 高 高（需维护 GooseFS 集群）
P2P 分发
Dragonfly / 自研方案		 1.5-1.8 GB/s ~40-50s 快（节点间互传） 高 高（需 P2P Agent）

选型决策树

实战锚点
大规模推理集群的混合方案：固定节点用 NVMe local PV（常驻模型，22 秒启动） + 弹性节点用 P2P 分发（新节点加入时从邻近节点拉取，1.8GB/s，40 秒启动）。P2P 分发的关键是种子节点——保证至少有 2-3 个节点持有完整模型副本，其他节点从它们并行拉取分块。实测 10 个节点同时扩容，每个节点都能达到 1.5GB/s+ 的聚合下载速度。
为什么不把模型打进镜像？ 一个 70GB 的镜像层即使用 zstd 压缩也有 50GB+，① 推送/拉取时间极长 ② 镜像仓库带宽打满 ③ 模型版本迭代频繁，每次更新都要 build 新镜像 ④ 无法复用已缓存的模型文件。正确做法是镜像只装推理框架（~5GB），模型权重走存储卷挂载。

§7带走这些

① PV/PVC 分离
PV 是集群级存储资源，PVC 是 namespace 级申请单，1:1 绑定。Pod 只关心 PVC name。
② 动态供给
StorageClass + CSI Provisioner 自动创建 PV。本地盘必须用 WaitForFirstConsumer 避免拓扑错配。
③ accessModes
RWO = 单节点（本地盘/云磁盘）、ROX = 多节点只读（模型共享最常用）、RWX = 多节点读写。
④ 本地盘选 local PV
不要用 hostPath——local PV 有 nodeAffinity 让 scheduler 感知拓扑，避免 Pod 调度到错误节点。
⑤ 网络盘选型
CephFS/NFS 适合共享模型；对象存储适合冷归档；GooseFS 适合缓存加速高频访问模型。
⑥ CSI 两侧
Controller 侧管创建/删除/快照，Node 侧管格式化/挂载。所有存储接入 K8S 都走 CSI 标准接口。
⑦ 推理场景首选
固定节点 → NVMe local PV（22s）；弹性扩缩 → GooseFS/P2P（40s）；简单起步 → CephFS ROX。
