§0为什么要理解容器网络

你可能觉得"网络不就是通了就行吗？"但在多机推理场景下，网络是性能的天花板：

  • 同样 2 台 8×A100 机器跑 Tensor Parallel，Overlay 网络下 NCCL allreduce 带宽只有 3-5 GB/s，而 Underlay/hostNetwork 能跑到 22-24 GB/s
  • 同一个模型、同样的 GPU，换一种 CNI 配置，推理 throughput 差 3-5 倍
  • Pod 间通信偶尔丢包——是 CNI 的 MTU 配错了，VXLAN 封装后超过物理网卡 MTU 导致分片
  • 跨节点的 prefill-decode 分离架构，网络延迟直接影响 TTFT（Time To First Token）
实战锚点
真实案例：某团队用 Flannel（VXLAN）部署 2 机 16 卡 Qwen-72B 推理，NCCL allreduce 带宽只有 3.2 GB/s，推理吞吐量仅为单机的 1.1 倍（GPU 大量时间在等网络）。切换到 Calico BGP + hostNetwork 后，NCCL 带宽升到 22 GB/s，吞吐量达到单机的 1.85 倍。差距全在网络这一层。
理解容器网络不是为了"面试八股"——它直接决定你多机推理的投入产出比。GPU 很贵，因为网络配置问题浪费 50% 算力是最不该犯的错误。

§1K8S 网络模型的三个保证

K8S 定义了一个扁平网络模型，不管底层用什么 CNI 插件实现，必须满足三个保证：

保证一：Pod 间直接通信

任何两个 Pod 之间可以直接通信，无需 NAT 转换。不管它们在同一个 Node 还是不同 Node，发出的包和收到的包源 IP 保持不变。

保证二：Node 和 Pod 互通

Node 上的进程可以和任意 Pod 直接通信（反过来也一样），无需 NAT。kubelet、kube-proxy 等系统组件依赖这一点。

保证三：IP 一致性

Pod 看到自己的 IP 地址 = 别人看到它的 IP 地址（无隐式 NAT）。NCCL 等分布式协议依赖"我声明的地址就是别人能连到我的地址"。

为什么这三个保证对推理很重要？NCCL 初始化时，每个 rank 会广播自己的 IP+port 给其他 rank。如果 Pod 看到的自己的 IP 和别人看到的不一致（NAT 场景），NCCL bootstrap 会直接失败。扁平网络让容器内的 NCCL 程序像在裸机一样工作——零适配。

这意味着什么

# Pod A (10.244.1.5 @ Node1) 想访问 Pod B (10.244.2.8 @ Node2)
# 在 K8S 网络模型下，直接：
curl http://10.244.2.8:8080/generate

# 不需要知道 Pod B 在哪台 Node 上
# 不需要端口映射
# Pod B 收到的 src IP 就是 10.244.1.5（Pod A 的真实 IP）
K8S 只定义了目标（这三个保证），不规定怎么实现——CNI 插件就是"怎么实现"的答案。不同 CNI 用不同方式达成同样的保证，但性能代价天差地别。

§2单节点网络：veth pair + bridge

理解容器网络的第一步：看同一台 Node 上的两个 Pod 怎么通信。

核心组件

  • Network Namespace：每个 Pod 有独立的网络命名空间（独立网卡、路由表、iptables）——Pod 间天然网络隔离
  • veth pair：虚拟网卡对，像一根"虚拟网线"。一端在 Pod 内（叫 eth0），一端在宿主机（叫 vethXXX）
  • bridge（cni0 / cbr0）：宿主机上的虚拟交换机，把所有 Pod 的 veth 宿主机端连在一起

同节点 Pod 间通信路径

关键细节

  • 同节点通信不经过物理网卡——全在内核内存中通过 bridge 二层转发，延迟极低（~10-50μs）
  • veth pair 是一对一的：每创建一个 Pod，CNI 就会创建一对 veth。宿主机上 ip link 能看到一堆 vethXXXXX
  • Bridge 像交换机一样工作：学习 MAC 地址 → 根据目标 MAC 转发到对应端口
  • CNI 还负责给 Pod 分配 IP、设置默认路由、配置 DNS（/etc/resolv.conf）
# 在宿主机上查看 bridge 和它连接的 veth
$ brctl show cni0
bridge name   bridge id          STP enabled   interfaces
cni0          8000.a2b4c6d8e0f1  no            veth3f8a1b2c
                                               veth7d4e5f6a
                                               vethb9c0d1e2

# 查看某个 Pod 的 veth 对应宿主机的哪个网卡
# 先在 Pod 内：
$ kubectl exec my-pod -- cat /sys/class/net/eth0/iflink
15

# 再在宿主机上找编号 15 的网卡：
$ ip link | grep "^15:"
15: veth3f8a1b2c@if14: <BROADCAST,MULTICAST,UP> mtu 1450 ... master cni0

# 确认 MTU（VXLAN 模式下通常是 1450，纯路由模式是 1500）
$ ip link show cni0 | grep mtu
4: cni0: <BROADCAST,MULTICAST,UP> mtu 1450 ...
同节点通信性能极高——两个 Pod 在同一 Node 上交换数据，本质就是内核内存拷贝，跟进程间通信差不多。所以同机多卡推理完全不需要担心 CNI 性能——瓶颈在 PCIe/NVLink，不在网络栈。跨节点才是 CNI 的战场。

§3跨节点网络：Overlay vs Underlay

同节点走 bridge 二层转发就行，但跨节点时目标 Pod 在另一台物理机上。Pod 的 10.244.x.x 地址是集群内部分配的，物理交换机根本不认识——包怎么送过去？

两种根本不同的思路：

方案一：Overlay（VXLAN 封装隧道）

Overlay 优点

  • 部署简单，对底层网络零要求（只要 Node 间 IP 可达即可）
  • 任何云平台、IDC 都能用，不需要找网络团队配路由
  • Pod 网段完全自管理，跟物理网络规划解耦
  • 可跨三层网络（跨机房、跨 AZ）

Overlay 缺点

  • 封装开销 ~50 bytes/包：有效 MTU 降到 1450
  • CPU 开销：每包都要封装/解封装，高带宽时 CPU 占用明显
  • 性能损失 5-15%（小包场景更严重——header 占比大）
  • 排障困难：tcpdump 看到的是封装后的包，内层需要手动解析

方案二：Underlay（BGP 路由 / 直接路由）

另一种思路：不封装，直接告诉物理网络怎么路由 Pod IP。

# 每个 Node 通过 BGP 协议向物理路由器/交换机宣告：
# "10.244.1.0/24 这个网段的包，发给我（Node1 的物理 IP 192.168.1.10）"
# "10.244.2.0/24 这个网段的包，发给 Node2 的物理 IP 192.168.1.11"

# Node1 的路由表：
10.244.1.0/24  dev cni0               # 本地 Pod，走 bridge
10.244.2.0/24  via 192.168.1.11 dev eth0  # Node2 的 Pod，路由过去

# 物理交换机也学到了这些路由（通过 BGP peer）
10.244.1.0/24  → next-hop 192.168.1.10 (Node1)
10.244.2.0/24  → next-hop 192.168.1.11 (Node2)

# 结果：Pod 的包"裸"着走物理网络，零封装！

Underlay 优点

  • 零封装：原始 IP 包直接在物理网络传输，性能接近裸机
  • 无额外 CPU 开销，MTU 不受影响（可以用 Jumbo Frame 9000）
  • 延迟最低：少了封装/解封步骤
  • 排障简单：tcpdump 直接看到 Pod 的真实 IP 包

Underlay 缺点

  • 需要物理网络设备支持 BGP 或允许静态路由配置
  • 需要网络团队配合（BGP peer、路由通告策略）
  • Pod IP 段需要跟物理网络规划不冲突
  • 跨三层网络（跨机房）需要全路径 BGP，配置复杂
核心取舍：Overlay 用"运维便利性"换"性能"，Underlay 用"基础设施复杂度"换"高性能"。对 HTTP API 服务来说 Overlay 足够；对多机 NCCL 通信来说，Overlay 的性能损失是灾难级的。
实战锚点
判断你的集群用的哪种模式： 
# 检查 Pod 网卡的 MTU
$ kubectl exec -it any-pod -- ip link show eth0 | grep mtu
    link/ether ... mtu 1450  # ← 1450 说明是 VXLAN Overlay（被吃了 50B）
    link/ether ... mtu 1500  # ← 1500 说明是直接路由 Underlay
    link/ether ... mtu 9000  # ← 9000 说明开了 Jumbo Frame（高性能集群）

# 看有没有 flannel.1 / vxlan.calico 设备（VTEP）
$ ip link show | grep -E "flannel|vxlan"
5: flannel.1: <BROADCAST,MULTICAST,UP> mtu 1450 ...  # ← Overlay 模式

§4主流 CNI 插件对比

CNI（Container Network Interface）是 K8S 定义的标准接口。kubelet 创建 Pod 时调用 CNI 二进制文件来配置网络。不同 CNI 插件 = 不同的实现策略。

CNI 插件默认网络模式性能NetworkPolicy复杂度最适合场景
Calico BGP 路由（可选 VXLAN fallback） 高 完整支持 中 生产首选，性能与安全兼得
Cilium eBPF 原生路由（可选 VXLAN/Geneve） 极高 完整 + L7 策略 高 大规模集群 / 替代 kube-proxy / 需内核 5.10+
Flannel VXLAN Overlay 中 不支持 低 开发测试 / 不需要 NetworkPolicy 的小集群

三者的本质差异

Calico

  • 默认用 BGP 把 Pod 路由宣告到网络
  • 同子网走直接路由，跨子网可 fallback VXLAN
  • 用 iptables/eBPF 实现 NetworkPolicy
  • 成熟稳定，文档丰富
  • 支持 CrossSubnet 模式（折中方案）

Cilium

  • 用 eBPF 程序在内核中做路由+策略
  • 跳过 iptables 和 bridge，减少包经过的层
  • 可完全替代 kube-proxy（Service→Pod 映射）
  • 支持 WireGuard 透明加密
  • 需要 Linux 5.10+ 内核

Flannel

  • 最简单的 VXLAN 实现，10 分钟部署
  • 不支持 NetworkPolicy（需配合 Calico 策略引擎）
  • 适合学习和理解 Overlay 原理
  • host-gw 模式可在同子网走直接路由
  • 功能最少但坑也最少

选择决策

  • GPU 推理集群（NCCL 多机）：管理网用 Calico BGP，NCCL 走独立网卡的 hostNetwork 或 SR-IOV
  • 普通 API 服务集群：Calico 或 Cilium，性能和安全都够
  • 学习/测试/minikube：Flannel，5 分钟搞定
  • 安全合规要求高：Cilium（L7 策略 + WireGuard 加密）
# 查看当前 Calico 的 IPPool 配置
$ calicoctl get ippool -o yaml
apiVersion: projectcalico.org/v3
kind: IPPool
spec:
  cidr: 10.244.0.0/16
  ipipMode: Never
  vxlanMode: Never         # ← 纯 BGP 路由（最高性能）
  natOutgoing: true

# 如果底层交换机不支持 BGP，改为 CrossSubnet 模式：
# 同子网走直接路由，跨子网 fallback 到 VXLAN
spec:
  vxlanMode: CrossSubnet

# 或者纯 VXLAN（最方便但性能最差）：
spec:
  vxlanMode: Always
实战锚点
在腾讯云 TKE 上，默认 CNI 是 VPC-CNI（类似 AWS VPC CNI），Pod 直接获得 VPC 子网 IP，性能等同裸机——这本质上就是 Underlay 模式。如果你在自建集群上想要同等性能，需要用 Calico BGP 并让网络团队在交换机上配 BGP peer。

把所有组件串起来——看一个跨节点数据包的完整旅程。

路径一：Underlay（BGP 直接路由）

路径二：Overlay（VXLAN 隧道）

两种路径对比总结

环节Underlay（BGP）Overlay（VXLAN）

§6CNI 与推理性能的关系

不同的推理通信模式对 CNI 性能的敏感度完全不同：

场景一：HTTP API 请求（客户端 → 推理服务）

  • 数据量：请求 ~1-10 KB，响应 ~1-100 KB（流式 token）
  • 频率：QPS 几百到几千
  • 带宽需求：几十 MB/s，远低于网卡能力
  • 对延迟敏感度：中等（用户感知级 ~100ms）
结论：CNI 性能差异可忽略。Overlay 的 50 bytes header 和 0.1ms 额外延迟，对 HTTP 场景无感。Flannel VXLAN 也完全够用。

场景二：NCCL 多机通信（Tensor Parallel / Pipeline Parallel）

  • 数据量：每步 allreduce 几十 KB ~ 几 MB
  • 频率：每个 token 生成都要通信（极高频）
  • 带宽需求：数十 GB/s，需要跑满 100Gbps 网卡
  • 对延迟敏感度：极高——每多 1μs，吞吐量可见下降
结论：CNI 是关键瓶颈！Overlay 封装 CPU 开销 + 内核协议栈延迟 = NCCL 带宽大幅下降。必须用 Underlay 或彻底绕过 CNI。

场景三：prefill-decode 分离（跨节点 KV Cache 传输）

  • 数据量：一次 KV Cache 传输 100MB-1GB
  • 频率：每个请求一次（prefill 完成后传给 decode 节点）
  • 对延迟影响：直接影响 TTFT（首 token 延迟）
结论：有影响但不如 NCCL 极端。大块传输中 header 占比小，瓶颈在 MTU（分片）和 TCP 窗口。建议 Underlay + Jumbo Frame。

注意 NCCL busbw 那一列：Overlay vs hostNetwork/RDMA 差了 5-8 倍！这不是 15% 的差异，是"能用 vs 不能用"的差异。原因：NCCL 用高频小消息模式，Overlay 的 per-packet CPU 开销 + 内核路径长度被极度放大。

解法预告

方案原理性能复杂度
hostNetwork: true Pod 直接用宿主机网络栈，跳过 veth/bridge/CNI 接近裸机 低（但端口冲突风险，每节点只能跑一个实例）
SR-IOV 物理网卡虚拟出多个 VF，每个 Pod 独占一个 VF，绕过内核协议栈 裸机级 中（需要 SR-IOV device plugin + 网卡支持）

GPUDirect RDMA RDMA + GPU 显存直通，网卡直接读写 GPU 显存，零拷贝 NCCL 最优路径 极高（Mellanox/NVIDIA 全栈 + GPU Operator）

§7带走这些

① 三个保证
K8S 网络 = Pod 直通无 NAT + Node-Pod 互通 + IP 一致性。CNI 插件负责实现这些保证
② 单节点路径
Pod eth0 → veth pair → cni0 bridge → veth pair → 对端 Pod eth0。内核态完成，不经物理网卡
③ Overlay 原理
VXLAN 把原始包装进 UDP 隧道（+50B header），物理网络不需要认识 Pod IP。简单但有性能代价
④ Underlay 原理
BGP 让交换机直接学到 Pod 网段路由，包裸传无封装。高性能但需要网络设备配合
⑤ CNI 选型
Calico BGP 生产首选 / Cilium eBPF 大规模集群 / Flannel 仅测试环境
⑥ 推理关键结论
HTTP API → CNI 无感。NCCL 多机 → CNI 是 5-8 倍瓶颈！必须 hostNetwork 或 SR-IOV
⑦ 标准架构
管理网（Calico/Cilium）+ NCCL 专网（hostNetwork/SR-IOV/RDMA）双网络分离
