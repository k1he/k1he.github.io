PART 1KV Transfer 模块：四层职责（注意！）

SGLang 把"跨机搬 KV"这件事拆成四层。之前的表少画了 Mooncake 这一层，我们补上——Mooncake 不是 SGLang 的代码，而是一个独立的开源项目（kvcache-ai/Mooncake，清华 MADSys + 月之暗面），SGLang 通过 Python binding 调用它。

层干什么源码属主具体位置
1 · 控制平面P/D 发现彼此（拓扑、dp_rank、ZMQ 端点）SGLangcommon/conn.py BootstrapServer
2 · 元数据平面一个请求级的"我要发去哪、我要从哪收"的对接SGLangcommon/conn.py KVManager + ZMQ
3 · 集成适配层把 SGLang 的 KV 概念翻译成 Mooncake 的 API 调用SGLangmooncake/conn.py（1600+ 行，属于 SGLang）
4 · 数据平面（底层）真实的 RDMA / NVLink 字节搬运Mooncake（外部项目）libmooncake.so + mooncake.engine.TransferEngine

P 和 D 从"各自启动"到"完成一次 KV 交接"，需要穿过这四层。接下来专门讲 Mooncake 的角色。

PART 1.5Mooncake 是谁，和 SGLang 是什么关系

Mooncake 是一个独立项目

  • 开源地址：github.com/kvcache-ai/Mooncake；站内新增 Mooncake 独立深度章节（论文 + 源码 + 动画实验）
  • 出品：清华 MADSys Lab + 月之暗面（Moonshot AI），起源于 Kimi 线上服务
  • 语言：C++ 核心 + Python binding
  • pip install：pip install mooncake-transfer-engine
  • 在 SGLang 之外还服务：vLLM、Dynamo、LMCache 等

Mooncake 提供三个东西（SGLang 用到了前两个）

组件能力SGLang 怎么用
mooncake.engine.TransferEngine一个高性能 RDMA 引擎：注册/去注册显存、session 发现、transfer_sync_write、batch_transfer_sync_writePD 的 KV 跨机搬运
mooncake.allocatorNVLinkAllocator / BarexAllocator：GPU 显存 custom allocator，bypass NCCL 做 peer 直写单机 NVLink 场景
mooncake.store分布式 KV store（Mooncake Store）SGLang 里 hierarchical cache 的可选后端，和 PD 分离无关
关键认知：Mooncake 只负责"把一段 GPU 内存从机器 A 搬到机器 B"，它不知道 KV cache、bootstrap_room、chunked prefill 这些概念。所有"哪段 KV 要搬"、"搬去对方哪个 page"的决策都是 SGLang 做的；Mooncake 只负责完成 (src_ptr, dst_ptr, length) 这种纯字节级的命令。

它为什么比裸 NCCL / GDRCopy 好？

特性NCCLGDRCopyMooncake Transfer Engine

多 QP 并行受限N/A✅ 自动 multi-QP，吞吐打满

对 PD 而言最关键的是 "P/D 数量不对称 + 运行时发现 peer"——你可以跑 2P+3D，随时加 P 加 D，Mooncake 都能即时建立 session 传数据。NCCL 做不到。

边界非常干净：SGLang 所有 "给我把这几段内存发到那台机器" 的请求，最终都穿过这一句 self.engine.batch_transfer_sync(...)。再往下的 multi-QP 调度、RDMA doorbell、ibv completion 都在 libmooncake 里，SGLang 代码库里看不到。

PART 4_resolve_rank_mapping：TP 不一致的组合爆炸

真实生产环境下，P 和 D 的并行度可能完全不同：
P TP=4 + DP=2（4 卡服务器，高算力）
D TP=8 + DP=1（8 卡服务器，高 KV 容量）

这时一条请求的 KV 如何从"P 的 4 个 rank"映射到"D 的 8 个 rank"？_resolve_rank_mapping 负责算这个映射。

// common/conn.py:249-327（只看 TP 分支）
def _resolve_rank_mapping(self, info: PrefillServerInfo):
    if self.attn_tp_size == info.attn_tp_size:
        # 情况 A: P 和 D TP 相同
        target_tp_rank = self.kv_args.engine_rank % self.attn_tp_size
        required_dst_info_num = 1
        required_prefill_response_num = 1
        target_tp_ranks = [target_tp_rank]

    elif self.attn_tp_size > info.attn_tp_size:
        # 情况 B: D TP > P TP。比如 D=8, P=4
        # 1 个 P rank 服务 2 个 D rank。所以每 2 个 D rank 发同一个 P rank
        target_tp_rank = (self.kv_args.engine_rank % self.attn_tp_size) // (
            self.attn_tp_size // info.attn_tp_size
        )
        required_dst_info_num = self.attn_tp_size // info.attn_tp_size  # P 需要等 2 条 D metadata
        required_prefill_response_num = 1

    else:
        # 情况 C: D TP < P TP。比如 D=2, P=8
        # 1 个 D rank 要从 4 个 P rank 各取一份 KV head 切片
        target_tp_ranks = list(range(
            (self.kv_args.engine_rank % self.attn_tp_size) * (info.attn_tp_size // self.attn_tp_size),
            (self.kv_args.engine_rank % self.attn_tp_size + 1) * (info.attn_tp_size // self.attn_tp_size),
        ))
        required_dst_info_num = 1
        required_prefill_response_num = info.attn_tp_size // self.attn_tp_size  # D 要等 4 条 P 成功
量含义
target_tp_ranks对本 D rank 而言，要从哪些 P rank 收 KV
required_dst_info_numP 等几条 D 的 metadata 才能进 WaitingForInput
required_prefill_response_numD 等几条 P 的 sync_status 才能切 Success

PART 5两侧 ZMQ 线程：消息格式大全

P 侧和 D 侧各开了一个 ZMQ PULL socket，在后台线程里循环 recv_multipart。消息都是 multipart bytes，不同 opcode 走不同分支。

D → P 的消息（P 的 bootstrap_thread 处理）

// mooncake/conn.py:1345-1422
def bootstrap_thread():
    while True:
        msg = server_socket.recv_multipart()
        room = msg[0].decode()

        if room == "WATERMARK":
            # staging buffer 反馈水位
            self._handle_watermark(msg); continue

        if room == "STAGING_RSP":
            # staging buffer transfer 响应
            self._handle_staging_rsp(msg); continue

        sid = msg[3].decode()
        if room == "None":
            # 首次握手：D 告诉 P 自己的 KV/aux 指针
            self.decode_kv_args_table[sid] = KVArgsRegisterInfo.from_zmq(msg)
        else:
            # 请求级 metadata
            room = int(room)
            self.transfer_infos[room][sid] = TransferInfo.from_zmq(msg)
            if len(self.transfer_infos[room]) == required_dst_info_num:
                self.update_status(room, KVPoll.WaitingForInput)

P → D 的消息（D 的 decode_thread 处理）

// mooncake/conn.py:1425-1496
def decode_thread():
    while True:
        msg = server_socket.recv_multipart()

        if msg[0] == AUX_DATA_HEADER:
            self._handle_aux_data(msg); continue
        if msg[0] == b"CHUNK_READY":  # staging 反馈
            ...; continue
        if msg[0] == b"STAGING_REQ":
            self._handle_staging_req(msg); continue

        # 正常 sync：room, status, prefill_rank
        room, status, prefill_rank = msg
        if int(status) == KVPoll.Success:
            self.prefill_response_tracker[int(room)].add(int(prefill_rank))
            if len(self.prefill_response_tracker[int(room)]) == required_prefill_response_num:
                self.update_status(int(room), KVPoll.Success)

PART 6MetadataBuffers：KV 之外的首 token 接力棒

P 不仅要把 KV 给 D，还要把首 token（以及首 token 的 logprob、cached_tokens、spec 采样信息）给 D。这一部分不走 KV pool，走独立的 metadata buffer。

// disaggregation/utils.py:135-220
class MetadataBuffers:
    def __init__(self, size, hidden_size, hidden_states_dtype, max_top_logprobs_num=128):
        self.output_ids            = torch.zeros((size, 16), dtype=torch.int32, device=device)
        self.cached_tokens         = torch.zeros((size, 16), dtype=torch.int32, device=device)
        self.output_token_logprobs_val = torch.zeros((size, 16), dtype=torch.float32, device=device)
        self.output_top_logprobs_val   = torch.zeros((size, 128), dtype=torch.float32, device=device)
        self.output_topk_p         = torch.zeros((size, 16), dtype=torch.float32, device=device)
        self.output_topk_index     = torch.zeros((size, 16), dtype=torch.int64, device=device)
        self.output_hidden_states  = torch.zeros((size, hidden_size), dtype=hidden_states_dtype, device=device)
        self.bootstrap_room        = torch.zeros((size, 8),  dtype=bootstrap_room_dtype, device=device) # ★ 校验防串包

size 就是同时在传的请求数上限。每个请求拿一个 slot，用完归还。P 把首 token 写进对应 slot 的 output_ids[slot, 0]，同时把 bootstrap_room 写进 bootstrap_room[slot, 0]。

transfer_worker 在 send_aux 时把 slot 的所有 tensor 都 RDMA 到 D 侧对应的同一 slot；D 的 commit 从 slot 读出来后校验 bootstrap_room 匹配。

PART 7Staging Buffer：异构 TP 的特殊优化

当 P TP=4，D TP=1（D 用 DP attention）时：

  • D 一个 rank 拥有所有 KV head
  • P 4 个 rank 各持 1/4 的 KV head
  • D 一个请求的 KV 需要从 4 个 P rank 各取一份

直接 per-token RDMA 会产生大量小 transfer（每 head slice 一次 RDMA，每 token 一批），带宽利用率极低。

staging buffer 方案

未优化

  • N token × H head × 4 P rank = 4NH 次小 RDMA
  • 每次只传 head_dim 字节
  • RDMA queue 被小包挤爆

开启 staging

  • P 侧先 gather 多个 head 到一个连续 GPU buffer
  • 一次 bulk RDMA 写到 D 的 staging pool
  • D 侧再从 staging pool scatter 到各 KV page
  • 吞吐 2-5x 提升
// 环境变量
export SGLANG_DISAGG_STAGING_BUFFER=1
export SGLANG_DISAGG_STAGING_BUFFER_SIZE_MB=64
export SGLANG_DISAGG_STAGING_POOL_SIZE_MB=4096
不要用于 MLA 模型：DeepSeek-V2/V3 的 MLA 结构每个 slice 就是全部（latent），不存在 gather/scatter 收益，强开 staging 反而有正确性问题。
