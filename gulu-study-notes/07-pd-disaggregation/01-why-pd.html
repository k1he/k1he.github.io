PART 1Prefill 和 Decode：两个完全不同的工作

LLM 推理对每个请求要做两件事：

阶段做什么算的什么瓶颈
Prefill把整段 prompt 一次性算成 KV cacheN 个 token 同时过 attention / MLPcompute-bound（matmul 打满算力）
Decode每次只生成 1 个 token，循环 N 次1 个 token 过 attention，但要读全部 KVmemory-bound（HBM 带宽打满）

一个具体例子：H100 上 70B 模型

Prefill 4096 tokens

  • FLOPS：约 2 · 4096 · 70B ≈ 5.7e14
  • HBM read：权重 140GB（只读一次，因为 4096 token 共享）
  • arithmetic intensity = 5.7e14 / 140e9 ≈ 4100
  • H100 算力 989 TFLOPS，带宽 3.35 TB/s，转折点约 295
  • 远在 roofline 的 compute 侧

Decode 1 个 token

  • FLOPS：约 2 · 1 · 70B = 1.4e11
  • HBM read：权重 140GB（每个 token 都要重读）
  • arithmetic intensity = 1.4e11 / 140e9 = 1.0
  • 带宽 3.35 TB/s → 理论 latency ≈ 42 ms/token
  • 远在 roofline 的 memory 侧
📐 Roofline 可视化：拖动 batch/seq 看 P 和 D 的位置
横轴 arithmetic intensity，纵轴吞吐；两个关键点：Prefill 在 compute ceiling，Decode 紧贴 bandwidth ceiling
Prefill AI: 4096 FLOPs/B Prefill 吞吐: 989 TFLOPS Decode AI: 1.0 FLOPs/B Decode 吞吐: 3.35 TFLOPS
拖动两个滑块：注意无论你怎么调 prefill 长度，Prefill 的点都停在 compute ceiling 上；Decode 无论 batch 多大，都死死贴在 bandwidth 斜线上。这两种工作放在一个 GPU 上，一定会互相拖后腿。

PART 2放在一台 GPU 上会怎样：Prefill Interruption

传统方案：一台 GPU 同时处理 Prefill 和 Decode 请求，调度器从 waiting_queue 中按策略挑选。看起来自然，但会出两个严重问题：

问题 1：Prefill 把 Decode 卡住

假设 GPU 正在 decode 一批请求，每 42ms 出一个 token。此时一个 4096-token 的 prompt 进来，prefill 需要约 120ms。Scheduler 为了效率，会让 prefill 插进来共享一次 forward。结果：

  • 原本每 42ms 一 token 的 decode 节奏被打断
  • 这一步的 forward 变成 prefill+decode 混合，延迟 120ms+
  • 所有正在 decode 的请求都要等这 120ms
  • ITL（inter-token latency）从 42ms 飙到 120ms

问题 2：Chunked Prefill 的半截解法

Chunked Prefill 把长 prompt 切成 512 或 1024 token 小段，每次和 decode 一起跑。但：

  • P 原本是 compute-bound；切成小块反而让 AI 下降，每 token prefill 效率变低
  • 仍有 ITL jitter（小块也占用 forward 时间）
  • 调优复杂：chunk 太小 P 吞吐下降，chunk 太大 ITL 抖动

PART 3PD 的代价：并不是纯净胜利

PD 分离不是免费午餐。分开之后新增的代价：

新增的链路成本

新增环节代价源码体现
Router 选 P+D两次 policy 调用（cache_aware + power_of_two）pd_router.rs:702
P/D 通过 bootstrap_room 认亲一次 ZMQ 控制消息 (D→P: metadata)mooncake/conn.py:1820
KV 跨机传输一次 RDMA write（NVLink 或 IB）mooncake/conn.py:1146
首 token 跨机传输metadata buffer 捎带 output_id / logprobsutils.py:135
D 侧 pre-alloc KV 空间DecodeReqToTokenPool 多一个 pre_alloc_sizedecode.py:96

何时 PD 值得做

  • 长 prompt + 对 ITL 敏感（chatbot、agent 多轮）：unified 的 jitter 无法接受，PD 收益最大
  • 高并发：P 和 D 的最优 batch size 不同，分开让每侧独立调优
  • 异构硬件：P 用大显存卡（算力强），D 用高带宽卡（memory 强）

何时不值得

  • prompt 很短（几十 token）：prefill 本身不到 10ms，打断影响小
  • 低 QPS：unified 下 prefill 不频繁，无 jitter 问题
  • 单机部署：KV transfer 只能走 NVLink / shared memory，收益缩水

问题答案
Prefill 和 Decode 为什么特性不同？P 算 N 个 token 共享权重 → compute-bound；D 每次 1 token 重读权重 → memory-bound
