PART 1为什么要把职责拆成 4 个角色

LLM 推理本来是 "一台 GPU 从头跑到尾" 的单体任务。PD 分离把它拆成 P + D 两个独立进程，自然就暴露出几个新问题：

  • 请求要同时到达 P 和 D → 需要 Router
  • P/D 各自做自己那块 → 需要独立的 P 节点、D 节点
  • P 的 KV 要搬到 D → 跨机搬几十 GB，NCCL 拓扑僵化做不了 → 需要 Mooncake

所以 PD 系统里刚好 4 个角色。再少一个都不行：少 Router 就要 client 自己选 PD 对；少 P/D 就没 PD；少 Mooncake 就无法支持 P/D 数量动态变化。

关键思路：Router 做选择 + 生成 room_id；P/D 对请求无状态，靠 room_id 找对方；Mooncake 负责真把 KV 从 P 搬到 D。接下来逐个拆解。

PART 24 个角色一眼看懂

角色 1 · 入口

🧭 Router

职责：做"选择 + 分派"

  • 从 P 池选一台 P（默认 cache_aware）
  • 从 D 池选一台 D（默认 power_of_two）
  • 生成唯一 bootstrap_room 写进请求 body
  • tokio::join! 同时发给 P 和 D
  • 转发 D 的 SSE 流回 client

语言：Rust · sgl-model-gateway/src/routers/http/pd_router.rs
角色 2 · 算力担当

⚙️ P 节点（Prefill Worker）

职责："把 prompt 嚼成 KV cache"

  • 收到请求进 BootstrapQueue 等 D 通知
  • 收到 D 的 metadata 后才开始 forward
  • 跑完整个 prompt 的 attention + MLP
  • 得到 KV cache + 首个 output token
  • 委托 Mooncake 把 KV 发给 D

语言：Python + CUDA · sglang/srt/disaggregation/prefill.py
角色 3 · 流式输出

💧 D 节点（Decode Worker）

职责："接手 KV 继续生成 token"

  • 收到请求先预分配 KV page（主动）
  • 把目标 page 地址 + room 通过 ZMQ 告诉 P
  • 等 P 的 KV 通过 Mooncake 写进来
  • commit 首 token（从 metadata buffer 读）
  • 进 running_batch 循环 + SSE 输出

语言：Python + CUDA · sglang/srt/disaggregation/decode.py
角色 4 · 搬运工

🚚 Mooncake（独立项目）

职责："把一段显存从 A 搬到 B"

  • 启动时注册 GPU 显存（KV pool + aux）
  • 维护跨机 session（按 hostname 发现 peer）
  • 收到 (src, dst, len) 做 RDMA write
  • 自动 multi-QP 并行打满网卡
  • 完成后 SGLang 通过 ZMQ 通知 D

语言：C++ + Python binding · kvcache-ai/Mooncake (独立仓库)

PART 3角色 1：Router · "选择 + 分派"

核心输入输出

INPUTOUTPUT
client 的 HTTP 请求D 的 SSE token 流（转发给 client）

内部 4 步

  1. 选 P：cache_aware 策略——查 Router 进程内的 radix tree，优先路由到"上次这段前缀去过的 P"
  2. 选 D：power_of_two 策略——随机抽两个 D，取 load 小的
  3. 生成 room_id：rand::random::<u64>() & i64::MAX，本请求的"临时暗号"
  4. 双发：tokio::join!(p.send(), d.send()) 并发打给 P 和 D
Router 的关键设计：P 和 D 是独立选择，不是绑定对。选完 P=p1, D=d2 只是一个"临时组合"，把他们串起来的完全靠 room_id。

PART 4角色 2：P 节点 · "算力担当，被动等通知"

核心输入输出

INPUTOUTPUT
① Router 的 HTTP（带 room_id）
② D 通过 ZMQ 发来的 metadata（KV 写到哪）		① prompt 的 KV cache（通过 Mooncake 发给 D）
② 首个 output token（通过 metadata buffer 发给 D）

P 对请求是无状态的

  • P 不知道哪个 user、哪个 session、哪个对话轮
  • P 只认 room_id：sender / 队列项 / transfer_infos 表项全部用它做 key
  • P 收到 HTTP 后不立即 forward——进 BootstrapQueue 等 D 的 ZMQ，没收到就一直等
  • 收到 metadata 后进 waiting_queue，装箱 → forward → 产出 KV + 首 token

为什么 P 要"被动等通知"

"KV 写到 D 的哪些 page" 这个信息只有 D 自己知道。P 无法预测 D 的 KV pool 状态，只能等 D 分配好后告诉它。这是 PD 架构里看起来"反直觉"但其实必然的设计。

PART 5角色 3：D 节点 · "流式输出 + 主动分配"

核心输入输出

INPUTOUTPUT
① Router 的 HTTP（带 room_id）
② Mooncake 写进来的 KV + metadata
③ Mooncake 完成通知（ZMQ）		① 发给 P 的 metadata（KV 目标地址）
② SSE token 流（通过 Router 发给 client）

D 做 3 件大事

  1. 主动分配 KV：在自己 KV pool 里挖好坑位（_pre_alloc），记录 page 索引
  2. 告诉 P 目标地址：通过 ZMQ 发 (room_id, 目标 page 索引, aux 索引, D 的 endpoint) 给 P
  3. 等货 + commit + decode：KV 到齐 → 校验 room_id → 首 token 进 req.output_ids → 加入 running_batch → 每步生成一个 token，SSE 吐回 Router

D 也是无状态的

  • D 只认 room_id：receiver / PreallocQueue 项 / metadata buffer slot 全部用 room_id 做 key
  • "预分配" 只是给这个 room_id 占坑位，不涉及任何业务语义
  • commit 时最后一道保险：比较 metadata_buffer.bootstrap_room 是否等于本 req 的 room_id，防止串包

PART 6角色 4：Mooncake · "纯粹的字节搬运工"

核心输入输出

INPUTOUTPUT
(session_id, src_ptrs, dst_ptrs, lens) 四元组RDMA write 完成 / 失败（返回码）

Mooncake 完全不懂业务

Mooncake 收到的就是 "从地址 A 搬 len 字节到地址 B"——它不知道 KV cache、room_id、layer、head。所有业务翻译都在 SGLang 的 mooncake/conn.py 里做完，才通过 batch_transfer_sync 扔给 Mooncake。

PART 7核心机制：无状态 + bootstrap_room 认亲

你的总结非常到位：PD 对请求是无状态的，靠 room_id 把 P/D 关联起来。展开三个子结论：

① 为什么必须无状态

  • P 池和 D 池是独立的 worker 数组，Router 每次请求重新选，没有"粘性"
  • 任何一台 P/D 都要能处理任何 room_id
  • 这让水平扩缩容、节点重启、故障切换都非常简单

② room_id 在两侧分别是什么 key

在 P 侧在 D 侧用途
transfer_infos[room]prefill_response_tracker[room]登记对端发来的 metadata / 完成状态
request_status[room]request_status[room]独立维护两侧 KVPoll 状态
MetadataBuffers.bootstrap_room[slot]（写入）MetadataBuffers.bootstrap_room[slot]（读出校验）防 metadata buffer 串包
sender.bootstrap_roomreceiver.bootstrap_room识别"这是哪个请求"

③ room_id 的三次关键旅程

  1. Router 生成：generate_room_id() 产生 64-bit 随机数，写进 request JSON
  2. P/D 收到后登记：P 创建 sender 用它做 key；D 创建 receiver 用它做 key。此时 P 和 D 互相不知道对方存在
  3. D 主动握手：D 通过 ZMQ 把 (room_id, 目标地址) 发给 P；P 的 bootstrap_thread 把它登进 transfer_infos[room_id]——这一刻 P/D 通过 room_id 相认
比喻：Router 就像饭店前台，给你一张"取餐号" (room_id)，同时分别给厨房 (P) 和传菜员 (D) 看了这个号码。厨房只管按号备菜，传菜员只管按号收菜——他们互不认识，但通过号码知道这碗饭的去向。

PART 84 角色之间的 6 条消息

#谁 → 谁通信内容触发
M1Router → PHTTP POST整个请求 + room_id每次请求
M2Router → DHTTP POST整个请求 + room_id（同 M1）和 M1 并发

M6D → Router → ClientHTTP SSEtoken 流D 每步 decode
关键观察：
• 控制面（M3, M5）走 ZMQ，数据小，延迟敏感
• 数据面（M4）走 Mooncake RDMA，数据大，带宽敏感
• 控制面和数据面分离，ZMQ 不会因为 RDMA 拥塞而阻塞
• 每条消息都带 room_id，保证归类到正确请求

PART 10状态机：P/D 两侧独立演化，通过 ZMQ 耦合

P 和 D 各自维护一个 KVPoll（5 状态：Bootstrapping / WaitingForInput / Transferring / Success / Failed），两侧独立推进，通过 ZMQ 消息耦合。

P 侧 sender

状态进入条件
Bootstrappingsender 创建（Router HTTP 刚到）
WaitingForInput★ 收到 D 的 ZMQ metadata
Transferringrun_batch 完，进 InflightQueue
SuccessMooncake 完成全部 chunk + aux
Failed超时 / RDMA 错 / abort

D 侧 receiver

状态进入条件
Bootstrappingreceiver 创建（Router HTTP 刚到）
WaitingForInput查到 P 的 endpoint
Transferringsend_metadata 已发出
Success★ 收齐 P 的 sync_status
Failed超时 / 串包 / P 报 Failed

状态机耦合图

注意：P 从 Bootstrapping 到 WaitingForInput 的跃迁依赖 D 的消息；D 从 Transferring 到 Success 的跃迁依赖 P 的消息。两侧状态机互为触发，任何一方 ZMQ 丢了都会死锁——所以有超时机制。

PART 11要点回顾

问题答案
PD 系统有几个角色？4 个：Router / P 节点 / D 节点 / Mooncake
Router 的职责？选 P + 选 D + 生成 room_id + 双发 + 转发 SSE
P 的职责？被动等 D 的 metadata → forward 算 KV + 首 token → 委托 Mooncake 发
D 的职责？主动预分配 KV + 告诉 P 地址 + 等货 + commit + decode + SSE
Mooncake 的职责？纯粹的跨机显存搬运（RDMA）
P/D 是无状态的吗？是。只通过 bootstrap_room 识别请求
Mooncake 属于 SGLang 吗？不属于。独立开源项目（kvcache-ai/Mooncake），SGLang 通过 Python binding 使用
首 token 谁算的？P 算的，但通过 metadata buffer 经 Mooncake 送给 D，再由 D 吐给 client
