01 / MODEL先分清：你说的 tokenize，其实有五层

一次 OpenAI Chat 请求并不是直接把字符串交给 BPE。真正的 CPU 路径通常是：

01JSON 解析messages / tools / sampling params
02Chat TemplateJinja 渲染角色与特殊标记
03NormalizeUnicode / lowercase / whitespace
04Pre-tokenize按空格、标点或 byte 切初始片段
05ModelBPE / WordPiece / Unigram 合并
06Post-processBOS / EOS / special tokens
07Dispatchinput_ids 经 ZMQ / gRPC 进入 Scheduler
当前阶段 1 / 7
请求首先被解析为结构化对象。别把 JSON、模板渲染和真正 tokenizer 的成本混成一个数字。

Encode

prompt → input_ids。它位于首 token 之前，直接进入 TTFT 临界路径。

Detokenize

每轮生成的 ID → 可打印增量文本。它位于 streaming 热路径，可能影响 ITL 和流式刷新。

Template ≠ Tokenize

长 system prompt、tools JSON 的序列化和 Jinja 模板也吃 CPU；测量时必须拆开。

第一条结论：“tokenizer 很慢”至少可能指四件事：模板渲染慢、Rust tokenizer 编码慢、Python slow tokenizer 慢，或者高并发下单进程排队慢。优化前先分层。

02 / ALGORITHMBPE 到底在做什么：不是查一次字典

以 Byte-level BPE 为例

  1. 文本先按 UTF-8 变成 byte，保证任何字符串都可表示。
  2. 预切分器按空格/标点产生片段，减少跨边界合并。
  3. 每个片段从最细粒度符号开始，反复选择词表中优先级最高的相邻 pair 合并。
  4. 最终 piece 映射成整数 ID，并添加特殊 token。
Llama/Qwen 等模型具体 tokenizer 配置不同。BPE、WordPiece、Unigram 的搜索策略不同，但性能分析方法相同：输入扫描 + 候选维护 + 词表查找 + 输出分配。

复杂度直觉

高质量实现不会每一步都全量扫描。Rust tokenizers 会用紧凑数据结构、优先队列/缓存和并行 batch 路径降低常数。

T_encode ≈ α · input_bytes + β · pieces + γ · allocations

所以成本通常更接近“输入字节数”而非“最终 token 数”；中文、代码、emoji、异常 Unicode 的 bytes/token 不同，不能只按 token 数外推。

BPE 合并显微镜

下面用教学词表演示 tokenizer。真实模型的 merge 表要大得多，但控制流一致。

Fast tokenizer

Hugging Face fast tokenizer 的核心通常在 Rust，Python 只是绑定层；批量 encode 往往能显著摊薄跨语言与分配开销。

Slow tokenizer

纯 Python 实现更容易受解释器、GIL 和对象分配影响。SGLang tokenizer_mode=auto 会优先选择可用的 fast 实现。

词表与正则

复杂 pre-tokenizer 正则、超长无空格字符串、特殊 token 扫描、chat template 都可能改变常数项。

04 / STREAMDetokenize 为什么不能每次只 decode 新 token

UTF-8 与 tokenizer 边界不一致

一个 token 可能只覆盖某个 Unicode 字符的部分 byte；直接 decode 单个 token 可能得到 �。另外某些 tokenizer 的空格、合并规则需要前文上下文。

SGLang 为每个请求保存 DecodeStatus：

  • decode_ids：累计 token IDs
  • surr_offset：保留一段左侧上下文
  • read_offset：当前可安全读取边界
  • sent_offset：已经发给客户端的字符位置

核心公式

new_text = decode(ids[surr_offset:])
　　　　　− decode(ids[surr_offset:read_offset])

用“带上下文的完整 decode”减掉“左侧上下文 decode”，获得稳定的新文本。遇到末尾 � 时只发送可打印前缀，下一轮带更多 token 重试。

HTTP PDRouter 把带 bootstrap 字段的同一请求并发发给 P 与 D；若 payload 仍是 text，两侧各自进入 SRT TokenizerManager，输入 encode 可能发生两次。

切换部署形态，看 token 在哪里产生

HTTP PD：为什么可能重复

当前 Model Gateway 的 HTTP PDRouter::execute_dual_dispatch_internal 构造 prefill 和 decode 两个 POST，并同时 send()。它注入 bootstrap 元数据，但不会替你把 text 改成 input IDs。

let prefill_fut = prefill_request.send();
let decode_fut  = decode_request.send();
tokio::select! { ... }

因此两边是否重复 encode，取决于发送的请求体：raw text 会走各自 TokenizerManager；预先填好的 input_ids 则跳过。

gRPC Gateway PD：中心化一次

gRPC pipeline 的 ChatPreparationStage 在 Gateway 内应用 chat template 并 tokenizer.encode(...)，把 token_ids 放入 PreparationOutput。随后请求构建阶段复用这些 IDs，并对 P/D dual dispatch。

let encoding = tokenizer.encode(&processed_text, false)?;
ctx.state.preparation = Some(PreparationOutput {
    token_ids: encoding.token_ids().to_vec(), ...
});

这能避免 P/D 各做一次输入 tokenization，并让路由层也能复用 token IDs 做 stop decoder / streaming response。

07 / PLAYBOOK一套可落地的评估与优化顺序

Step 1 · 先证明瓶颈

  • 记录 template_ms、tokenize_ms、dispatch_ms，不要只看 TTFT。
  • 看 tokenizer 进程 CPU、run queue、cgroup throttling、RSS、context switches。
  • 按输入 token bucket（0–1K / 1–4K / 4–16K / 16K+）画 P50/P95。
  • 检查 tokenizer.is_fast，确认没有因为 custom tokenizer / trust_remote_code 落到 slow path。
  • 在 PD 两侧分别采样，判断同一 rid 是否 encode 两次。

Step 2 · 再按风险排序优化

  1. 确保 fast tokenizer；避免无必要的 slow/custom Python 路径。
  2. 统一 kwargs，尝试 batch encode / dynamic batch。
  3. 增加 tokenizer_worker_num，同时检查内存与 NUMA。
  4. 缓存稳定 system prompt/tools 的模板或 token 前缀，但必须把 tokenizer revision 与模板 hash 纳入 key。
  5. HTTP PD 改为 Gateway 中心化 tokenize，或可信链路传 input_ids。
  6. 最后才考虑自研 Rust tokenizer service；否则运维复杂度可能大于收益。

推荐 benchmark 代码骨架

from time import perf_counter
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained(MODEL, use_fast=True)
samples = load_real_prompts()              # 保留真实长度与字符分布

# warmup：排除文件 IO、lazy regex、cache cold start
for text in samples[:100]: tok(text, add_special_tokens=False)

t0 = perf_counter()
encoded = tok(samples, add_special_tokens=False)
elapsed = perf_counter() - t0
tokens = sum(map(len, encoded["input_ids"]))

print({
  "requests/s": len(samples) / elapsed,
  "tokens/s": tokens / elapsed,
  "us/token": elapsed * 1e6 / tokens,
})

至少跑：单条 encode、batch encode（1/4/16/32/64）、1/2/4/8 线程、中文/英文/代码/emoji 四类语料、P50/P95/P99 长度。服务级测试再加入 open-loop QPS 扫描。

安全边界

不要接受不可信客户端随意传 input_ids 后假设其与 text 一致；审计、内容过滤、缓存路由可能因此失真。

一致性边界

tokenizer 文件、revision、added tokens、chat template、BOS/EOS 配置任一变化，都可能让相同文本产生不同 IDs。

缓存边界

tokenize cache 的 key 必须覆盖模型/模板/工具定义/规范化参数；前缀缓存要处理 token 边界重新合并问题。

本章带走这六句话

  1. Chat template、encode、detokenize、排队是四段不同成本。
  2. Fast tokenizer 仍然是 CPU 程序；高 QPS 下单进程照样会饱和。
  3. SGLang 输入由 TokenizerManager 负责，输出由独立 DetokenizerManager 增量解码。

  5. 经典 HTTP PD + raw text 可能在 P/D 两侧重复 encode；gRPC Gateway 可中心化一次。
  6. 用真实语料、open-loop QPS 和分阶段打点评估，不要只看单次 microbench。
