PART 1Router 在 PD 系统中的角色

PD 模式下的 Router（SGLang 源码里叫 sgl-model-gateway，二进制叫 smg）是整个系统的唯一入口。它不是普通的反向代理，而是一个同时知道 Prefill 池和 Decode 池、能把一个请求同时分派到 P 和 D的特殊 LB。

它解决的三个问题

问题普通 LB 做不到PD Router 怎么做
同一个请求需要由 P+D 两个 worker 协作普通 LB 只会选一个后端两个独立 worker pool，一次请求两次 dispatch
P/D 之间必须通过 bootstrap_room 认亲LB 不参与 payload 修改生成 bootstrap_room，把 (host,port,room) 写进请求 JSON
P 和 D 需要几乎同时接到请求顺序路由会让 P 或 D 干等tokio::join! 并发双发

Router 内部四大组件

WorkerRegistry

维护 WorkerType::Prefill 和 WorkerType::Decode 两个列表。启动时通过 --prefill / --decode 注入，运行时通过 /workers API 动态 add/remove。

PolicyRegistry

同时持有 prefill_policy 和 decode_policy 两个策略对象。默认：P 用 cache_aware，D 用 power_of_two。

PDRouter

真正执行路由的入口。所有 /v1/chat/completions、/generate 等都经过 execute_dual_dispatch。

RetryExecutor

包一层重试：P 或 D 某个 worker 5xx 时重新 select_pd_pair，新的 room_id、新的 worker 对。

PART 2入口参数：CLI 到 Router 实例

启动命令：

# 2 个 Prefill + 2 个 Decode + cache_aware/power_of_two 双策略
smg launch --pd-disaggregation \
  --prefill http://p1:30001 9001 \
  --prefill http://p2:30002 9002 \
  --decode  http://d1:30003 \
  --decode  http://d2:30004 \
  --prefill-policy cache_aware \
  --decode-policy  power_of_two \
  --port 30000

--prefill URL [bootstrap_port] 的第二个参数是 P 侧另一个端口：HTTP (30001) 处理 client 请求，bootstrap (9001) 专门给 D 的 KV Manager 发控制消息。这两个端口是分开的，不要混淆。

源码：CLI 参数解析

// sgl-model-gateway/src/main.rs:23-52
fn parse_prefill_args() -> Vec<(String, Option<u16>)> {
    let args: Vec<String> = std::env::args().collect();
    let mut prefill_entries = Vec::new();
    let mut i = 0;
    while i < args.len() {
        if args[i] == "--prefill" && i + 1 < args.len() {
            let url = args[i + 1].clone();
            // 可选的第 2 个参数：bootstrap_port
            let bootstrap_port = if i + 2 < args.len() && !args[i + 2].starts_with("--") {
                args[i + 2].parse::<u16>().ok()
            } else { None };
            prefill_entries.push((url, bootstrap_port));
            i += 2;
        } else { i += 1; }
    }
    prefill_entries
}

PART 5select_pd_pair 深读 + 两种策略

// pd_router.rs:702-781
async fn select_pd_pair(&self, request_text, model_id, headers)
    -> Result<(Arc<dyn Worker>, Arc<dyn Worker>), String>
{
    let prefill_workers = self.worker_registry.get_prefill_workers();
    let decode_workers  = self.worker_registry.get_decode_workers();
    let prefill_policy  = self.policy_registry.get_prefill_policy();
    let decode_policy   = self.policy_registry.get_decode_policy();

    let hash_ring = self.worker_registry.get_hash_ring(model_id_or_default);

    // 关键：两次独立的策略调用
    let prefill = pick_worker_by_policy_arc(&prefill_workers, &*prefill_policy,
        request_text, headers, hash_ring.clone(), "prefill").await?;
    let decode  = pick_worker_by_policy_arc(&decode_workers,  &*decode_policy,
        request_text, headers, hash_ring,         "decode").await?;
    Ok((prefill, decode))
}
关键认知：P 和 D 是两次完全独立的 policy 调用。"哪台 P 拿到请求"和"哪台 D 拿到请求"没有绑定关系，它们在后端通过 bootstrap_room 认亲，不是在 Router 里配对。

PART 5.5cache_aware 到底是怎么感知的？——不是查 P 的 KV pool

经常被误解的一点：cache_aware 不会去查每个 P 节点的真实 KV cache 状态。Router 和 P 之间没有任何"当前 prefix cache 占用"的 RPC 或 metric 上报。那它怎么"知道"哪台 P 有哪段前缀的 cache？

不是这么做的：
❌ 遍历每个 P 节点查 prefix cache（没这个 API）
❌ 从 P 上报 cache 状态（没这个 channel）
❌ 让 P 做字符串匹配告诉 Router（P 根本不知道 Router 要送谁来）
实际的做法（sgl-model-gateway/src/policies/tree.rs）：
Router 在自己进程内维护一棵近似 radix tree (approximate prefix tree)，只记录"上次 prefix X 送到了哪台 worker"。不跟 P 做任何通信。根据 "同一个 prefix 我上次发给了 P1，所以 P1 应该还留着它的 KV cache" 这个猜测做路由。

▸ 一次 select_worker 到底做了多少工作

步骤操作复杂度
1求所有 worker 的 min_load / max_load（单次 fold 遍历）O(N_workers)，N 通常 < 50
2判断 imbalanced：max - min > abs && max > min * relO(1)
3关键：沿着 root 按 char 向下走 radix tree，每步查一次 DashMap 的 shardO(prefix 长度)，和 worker 数无关
4拿到命中节点的 tenant（上次去的 worker URL）O(1)（leaf 有 last_tenant 缓存）
5在 worker 数组里找 URL 对应的 indexO(N_workers)
6把本次 text 也插进 tree（异步副作用）O(prefix 长度)

一次路由的成本大约是 "几次 DashMap 查询 + 一点字符串比较"，在现代 CPU 上是 微秒级。基准测试（benches/tree_benchmark.rs）在 100k 节点的 tree 上，prefix_match 单次 < 10µs。

▸ "近似"前缀树长什么样

假设有 2 台 P（P1、P2）和一段请求历史：

请求 1："You are a helpful assistant. Q: What is MLA?"   → 发给 P1
请求 2："You are a helpful assistant. Q: Explain GQA"   → 上次 "You are a..." 命中 → 发给 P1
请求 3："You are a coding expert. Task: fix this bug"   → "You are a " 部分命中，后面分叉 → 落到 "coding" 子树（之前没去过）→ load 最小策略 → P2
请求 4："Translate to French: Hello"                     → 没命中 → load 最小 → P1（假设）

关键性质：

  • 按字符存，不是按 token。这样 Router 不需要做 tokenization（否则要跑 tokenizer，每次 10-50ms）
  • 每个节点存的是该节点的子串（radix tree 压缩特性），不是单个字符
  • 每个节点记录 last_tenant：上次这条 prefix 命中时被发给了哪个 worker URL
  • 这棵树是 Router 进程内存里的一份本地 cache，和 P 上的真实 KV cache 无关

▸ 源码直击：select_worker + 树查询

// sgl-model-gateway/src/policies/cache_aware.rs:351-477（精简）
async fn select_worker(&self, workers, info) -> Option<usize> {
    // ① O(N) 扫一遍 worker 拿 load 极值
    let (min_load, max_load) = workers.iter().fold(..., |(min, max), w| {
        let load = w.load();
        (min.min(load), max.max(load))
    });

    // ② 判断是否 imbalanced（两个阈值同时满足）
    let is_imbalanced = max_load.saturating_sub(min_load) > self.config.balance_abs_threshold
        && (max_load as f32) > (min_load as f32 * self.config.balance_rel_threshold);

    if is_imbalanced {
        // 紧急：放弃 cache 亲和，直接选 load 最小
        return self.select_worker_min_load(...);
    }

    // ③ 关键：查 tree，O(prefix 长度)，不涉及任何 worker RPC
    let tree = self.trees.get(model_id)?;
    let result = tree.prefix_match_with_counts(text);
    let match_rate = result.matched_char_count as f32 / result.input_char_count as f32;

    // ④ 命中 vs 不命中两条路径
    let selected_idx = if match_rate > self.config.cache_threshold {
        // cache hit：跟着 tree 记录的 tenant 走
        let tenant_url: &str = &result.tenant;
        workers.iter().position(|w| w.url() == tenant_url)
    } else {
        // cache miss：选 load 最小的（给新 prefix 一个新家）
        healthy_indices.iter().min_by_key(|&&idx| workers[idx].load()).copied()
    };

    // ⑤ 把这次请求也插进 tree，记录 tenant = 被选中的 worker
    if let Some(idx) = selected_idx {
        tree.insert(text, workers[idx].url());
        return Some(idx);
    }
}
// tree.rs:531-623 · 树查询本体（最核心那部分）
pub fn prefix_match_with_counts(&self, text: &str) -> PrefixMatchResult {
    let mut remaining = text;
    let mut matched_chars = 0;
    let mut prev = Arc::clone(&self.root);

    while !remaining.is_empty() {
        let first_char = remaining.chars().next().unwrap();
        // DashMap 按首字符分 shard → 只锁一个 shard，不锁整表
        let child = prev.children.get(&first_char).map(|e| e.value().clone());

        match child {
            Some(node) => {
                let node_text = node.text.read().unwrap();
                let shared = shared_prefix_count(remaining, node_text.as_str());
                if shared == node_text.char_count() {
                    // 整个节点匹配，继续下钻
                    matched_chars += shared;
                    remaining = advance_by_chars(remaining, shared);
                    prev = node;
                } else { matched_chars += shared; prev = node; break; }
            }
            None => break,   // 到底了
        }
    }
    // 从这个节点的 last_tenant 读出"上次谁接手的"
    let tenant = *prev.last_tenant.read();
    PrefixMatchResult { tenant, matched_char_count: matched_chars, input_char_count: ... }
}
并发优化：DashMap 按 shard 分段加锁（ROOT_SHARD_COUNT 个 shard，每个独立 RwLock），所以多个请求同时查 tree 不会互相阻塞。每个节点还有 last_tenant 的 RwLock 作为 O(1) fast path 避免遍历 tenant_last_access_time。

▸ 常见疑问一次说清

疑问答案
Router 怎么"知道" P1 真的有那段 prefix 的 KV？它不知道。这只是"最近把这段 prefix 送过 P1，P1 极可能还留着"的猜测。如果 P1 的 prefix cache 被挤出去了，P1 收到请求也要重新算，但那是另一个层面的问题，不影响路由正确性。
会不会因为 tree 过时路由错？会，但不是"错误"。最多是"本来能命中的结果没命中"，请求仍能正常完成，只是 P 侧会重新算一遍 prompt。
这棵树会无限膨胀吗？不会。有后台 PeriodicTask 按 eviction_interval_secs 周期做 LRU eviction，超过 max_tree_size 时按 tenant_last_access_time 淘汰 leaf。
为什么按字符不按 token？按 token 要在 Router 做 tokenization（加载 tokenizer 模型，每请求 10-50ms），得不偿失。按字符虽然比 token 粒度粗，但命中率差异很小，速度快 100x 以上。
多副本 Router 怎么同步 tree？看到源码里的 mesh_sync：开 smg-mesh 特性后，insert/remove 操作会广播到集群里其他 Router，保证一致视图。不开 mesh 则每个 Router 独立（tree 会冷启动几次后收敛）。
和 load 不均衡怎么平衡？imbalanced 检查是第一道门：max-min > 5 且 max > min*1.5 时忽略 tree，走 min-load 救火。所以不会出现"某台 P 因为 cache 命中被打爆，其他 P 闲着"的情况。

PART 6bootstrap 注入的精细细节

// pd_router.rs:217-275（精简）
const BOOTSTRAP_HOST_KEY: &str = "bootstrap_host";
const BOOTSTRAP_PORT_KEY: &str = "bootstrap_port";
const BOOTSTRAP_ROOM_KEY: &str = "bootstrap_room";

fn inject_bootstrap_into_value(mut original: Value, p: &dyn Worker, batch_size: Option<usize>)
    -> Result<Value, String>
{
    let obj = original.as_object_mut()...;

    if let Some(n) = batch_size {
        // batch 请求（/generate 里 prompt 是数组）：每个元素一个 room_id
        let mut rooms = Vec::with_capacity(n);
        for _ in 0..n {
            rooms.push(generate_room_id());
        }
        obj.insert(BOOTSTRAP_ROOM_KEY.into(), Value::Array(rooms.into_iter().map(...).collect()));
    } else {
        obj.insert(BOOTSTRAP_HOST_KEY.into(), Value::from(p.bootstrap_host()));
        obj.insert(BOOTSTRAP_PORT_KEY.into(), match p.bootstrap_port() {
            Some(v) => Value::from(v), None => Value::Null,
        });
        obj.insert(BOOTSTRAP_ROOM_KEY.into(), Value::from(generate_room_id()));
    }
    Ok(original)
}
// pd_types.rs:60
pub fn generate_room_id() -> u64 {
    rand::random::<u64>() & (i64::MAX as u64)
}
为什么 mask 到 i64：Python 端某些路径（io_struct.py 的 bootstrap_room: Optional[int]）会把它当 64-bit 有符号整数，如果超过 i64::MAX 会 overflow。Router 生成时 mask 一次，保证两边对齐。

PART 8本章要点回顾

问题答案
Router 是用什么写的？Rust (sgl-model-gateway)，基于 axum + tokio + reqwest
P 和 D 怎么被配对？不配对。两次独立 policy 调用，在后端通过 bootstrap_room 认亲
为什么 P/D 几乎同时收到请求？tokio::join! 并发双发，不是串行
bootstrap_room 是什么？64-bit 随机数，rand::random() & i64::MAX，一请求一生成
为什么注入到 JSON 而不是 header？body 字段在 Python 侧由 TokenizedGenerateReqInput 解析，比 header 好处理；batch 请求时每个元素都能带一个 room
最终 client 看到的 token 是谁生成的？首 token 是 P 生成（prefill 的最后一步采样），但通过 metadata buffer 传到 D，D 再通过自己的 SSE 吐回去。后续 token 由 D 生成
下一章预告：请求到达 P/D worker 后，先经过 TokenizerManager（tokenize + 转 protobuf），再送到 Scheduler 分流到 P 专属队列或 D 专属队列。这个环节是 Python 侧的第一站。
