权重加载全流程 09

.safetensors → GPU 的那段旅程：lazy 流式 + 权重合并 + TP shard 一步到位
总览 safetensors 是啥 主流程 3 步 TP shard 的规则 QKV / gate_up 合并 MoE expert 堆叠 模型注册 实战技巧

PART 1为什么这不是"一行 torch.load 就行"？

朴素方案：

# 想象中
weights = torch.load("model.safetensors")
model.load_state_dict(weights)

但实际情况复杂得多：

问题为啥怎么办
模型太大Llama-70B fp16 是 140 GB，一次全读进 CPU 内存会 OOMlazy 流式读取，一个 tensor 处理完再下一个
TP 切分HF 上权重是完整的，4 卡每卡只要 1/4加载时切，不是加载完再切（避免 CPU 峰值）
权重合并HF 里 q_proj / k_proj / v_proj 是 3 个独立 tensor，mini-sglang 用融合的 qkv_proj攒齐 3 个后 cat
MoE expert 堆叠HF 里 experts.0.gate_proj / experts.1.gate_proj ...，mini-sglang 打包成一个 stacked tensor攒齐所有 expert 后 stack
key 名字不同HF 的 layer 命名可能跟 mini-sglang 内部不一致架构注册表 + 规则化映射
vision / multimodal 头Mistral3 等模型有 vision 部分，推理时不用加载时丢弃
核心设计：weight loading 是一个 generator——每次只产出一个已经 sharded、merged、在 GPU 上的 tensor，model.load_state_dict 拿过来就装上。CPU 峰值内存 = 1 个最大 tensor + 一点 merge buffer。

PART 2safetensors 格式速览

HuggingFace 上的模型权重现在主流是 .safetensors 格式（不是旧的 pytorch_model.bin pickle）。

文件结构

# 一个 .safetensors 文件：
┌──────────────┬─────────────────────────────────────┐
│  8 bytes     │  header_length (u64, little-endian) │
├──────────────┼─────────────────────────────────────┤
│  header JSON │  {"tensor_name": {dtype, shape,     │
│              │     data_offsets: [start, end]}, …} │
├──────────────┼─────────────────────────────────────┤
│  raw tensor  │  连续二进制数据（按 header 描述偏移）│
│  bytes       │                                     │
└──────────────┴─────────────────────────────────────┘

为什么比 pickle 好？

  • 安全：pickle 可以执行任意代码，safetensors 纯数据
  • 零拷贝 lazy 读：header 只描述 offsets，可以 mmap 文件然后用 safetensors.safe_open 逐个读 tensor，不加载全部
  • 跨框架：不依赖 PyTorch

mini-sglang 怎么读

# models/weight.py:90
with safetensors.safe_open(file, framework="pt", device=str(device)) as f:
    for name in f.keys():
        raw = f.get_tensor(name)    # 此刻才从磁盘读, 直接到 GPU
        ...                          # 处理完 raw 就丢
framework="pt" + device="cuda:0" 让它直接产出 PyTorch GPU tensor，跳过 CPU。这是 safetensors + CUDA 的组合优势：磁盘 → GPU 直通，CPU 只做元数据管理。

PART 3主流程：load_weight generator

整个加载逻辑就一个函数（models/weight.py:75），核心结构：

def load_weight(model_path, device) -> Iterator[Tuple[str, torch.Tensor]]:
    """Yields (name, tensor) 已经 sharded, merged, 在 GPU 上"""

    # ① 下载/找到 .safetensors 文件列表
    model_folder = download_hf_weight(model_path)
    files = glob.glob(f"{model_folder}/*.safetensors")

    # ② 准备 merge/expert buffer
    merge_buf = {}       # 攒 q_proj/k_proj/v_proj → qkv_proj
    expert_buf = {}      # 攒 experts.0 / experts.1 / ... → 堆叠

    for file in files:
        with safetensors.safe_open(file, ...) as f:
            for name in f.keys():
                # ③ 过滤 multimodal 前缀
                if name.startswith(("vision_tower.", "multi_modal_projector.")):
                    continue
                raw = f.get_tensor(name)
                name = name.removeprefix("language_model.")

                # ④ TP shard（按规则切 dim 0 / dim 1 / vocab）
                tensor = _shard_tensor(name, raw, rank, world, num_kv_heads)
                del raw

                # ⑤ 如果属于合并组，存 merge_buf 攒齐再 yield
                if (info := _get_merge_info(name)) is None:
                    out = (name, tensor)
                else:
                    merged_key, slot, all_slots = info
                    merge_buf[merged_key][slot] = tensor
                    if not all(s in merge_buf[merged_key] for s in all_slots):
                        continue   # 还没攒齐, 下一个
                    parts = [merge_buf[merged_key][s] for s in all_slots]
                    del merge_buf[merged_key]
                    out = (merged_key, torch.cat(parts, dim=0))

                # ⑥ MoE: 同名 expert 再攒齐一轮 stack
                if config.is_moe and (expert_info := _get_expert_stack_info(out[0])):
                    packed_key, expert_idx = expert_info
                    expert_buf[packed_key][expert_idx] = out[1]
                    if len(expert_buf[packed_key]) != config.num_experts:
                        continue
                    experts = [expert_buf[packed_key][i] for i in range(config.num_experts)]
                    yield packed_key, torch.stack(experts, dim=0)
                else:
                    yield out[0], out[1]

这个函数的 3 个"关卡"

调用入口

# engine/engine.py:139  _load_weight_state_dict
return {k: v.to(self.dtype) for k, v in load_weight(config.model_path, self.device)}

# 然后
self.model.load_state_dict(self._load_weight_state_dict(config))

注意 dict comprehension 在驱动 generator——生成器一个个 yield，字典一个个填充，整个过程是流式的。

PART 4_shard_tensor · TP 切片规则

这是加载时最核心的决策：对于一个给定的权重名字，应该按哪一维切？切哪一段？

# models/weight.py:13
_SPLIT_DIM_0 = [".q_proj", ".k_proj", ".v_proj", ".gate_proj", ".up_proj"]
_SPLIT_DIM_1 = [".o_proj", ".down_proj"]

def _shard_tensor(key, value, r, n, num_kv_heads):
    if any(key.count(sub) for sub in _SPLIT_DIM_0):
        # ① Column parallel: 按输出维 (dim 0) 切
        is_kv_proj = any(key.count(sub) for sub in (".k_proj", ".v_proj"))
        if is_kv_proj and num_kv_heads < n:
            # GQA corner case: kv_heads 不够分 → 复制
            head_dim = value.shape[0] // num_kv_heads
            head_idx = r * num_kv_heads // n
            return value[head_idx * head_dim : (head_idx + 1) * head_dim].clone()
        return value.chunk(n, dim=0)[r].clone()

    elif any(key.count(sub) for sub in _SPLIT_DIM_1):
        # ② Row parallel: 按输入维 (dim 1) 切
        return value.chunk(n, dim=1)[r].clone()

    elif key.count("lm_head") or key.count("embed_tokens"):
        # ③ Vocab parallel: 按词表维切
        num_embeddings_per_partition = div_ceil(value.shape[0], n)
        vocab_start = r * num_embeddings_per_partition
        vocab_end = min((r+1) * num_embeddings_per_partition, value.shape[0])
        return value[vocab_start:vocab_end, :].clone()
    else:
        # ④ 其他（bias、layernorm、rmsnorm weight 等）：复制
        return value

三条规则对照表

权重类型关键词切法对应 Layer
Column Parallelq_proj / k_proj / v_proj / gate_proj / up_proj按 dim=0 切（输出维）LinearQKVMerged / LinearColParallelMerged
Row Parallelo_proj / down_proj按 dim=1 切（输入维）LinearOProj / LinearRowParallel
Vocab Parallellm_head / embed_tokens按 vocab 维切（dim=0）ParallelLMHead / VocabParallelEmbedding
Replicated以上都不匹配不切（全部复制）norm weights、bias 等
为什么 PyTorch 权重 shape 是 [out_dim, in_dim]？
PyTorch 的 nn.Linear(in, out) 内部权重形状是 [out, in]（跟数学公式 Y = X·W 的 W 形状是转置关系，因为 PyTorch 做 F.linear(x, w) = x @ w.T）。所以"按输出维切"对应 dim=0，"按输入维切"对应 dim=1——跟 06 章矩阵 W 的"切列"是同一回事，只是 index 方向相反。

GQA 的 corner case：num_kv_heads < tp_size

比如 Qwen3-0.6B 只有 2 个 KV head 但用户开 --tp 4。2 < 4，不能均分，要复制：

num_kv_heads = 2, tp_size = 4, rank = 0,1,2,3

head_dim = value.shape[0] // num_kv_heads    # K/V 每个 head 的维度
head_idx = r * num_kv_heads // n             # rank 0,1 → head 0;  rank 2,3 → head 1
return value[head_idx * head_dim : (head_idx + 1) * head_dim]

# rank 0, 1 都拿 K_head_0, V_head_0     （复制）
# rank 2, 3 都拿 K_head_1, V_head_1     （复制）

这就对应 06 章说的 allow_replicate=True——KV head 不够切时"跨卡共享"。

_SPLIT_DIM_0 里藏着一个细节：attn_bias

注意关键字用 key.count(sub) 而不是 key.endswith(sub)。这样 q_proj.weight 和 q_proj.bias 都能被匹配到。bias 作为一维张量，chunk(n, dim=0) 依然能正确切（dim=0 就是它唯一的维度）。

PART 5QKV / gate_up 合并

HF 的模型把 Q、K、V 存成 3 个独立权重：

model.layers.0.self_attn.q_proj.weight    [Hq·D, hidden]
model.layers.0.self_attn.k_proj.weight    [Hkv·D, hidden]
model.layers.0.self_attn.v_proj.weight    [Hkv·D, hidden]

mini-sglang 为了一次 matmul 算出 Q、K、V（减少 3 个 kernel launch → 1 个），用融合的 qkv_proj：

model.layers.0.self_attn.qkv_proj.weight    [(Hq+2·Hkv)·D, hidden]

怎么合并？attend-then-cat 模式

# models/weight.py:17
_MERGE_GROUPS = {
    ".q_proj":    (".qkv_proj",     ("q", "k", "v")),
    ".k_proj":    (".qkv_proj",     ("q", "k", "v")),
    ".v_proj":    (".qkv_proj",     ("q", "k", "v")),
    ".gate_proj": (".gate_up_proj", ("gate", "up")),
    ".up_proj":   (".gate_up_proj", ("gate", "up")),
}

流程示意

关键细节：合并发生在 shard 之后
先 _shard_tensor 切好 local 那份，再塞 merge_buf。这样 cat 出来的已经是 local 的 qkv_proj，不需要额外通信。
  • rank 0: cat(local_q₀, local_k₀, local_v₀) → local qkv_proj₀
  • rank 1: cat(local_q₁, local_k₁, local_v₁) → local qkv_proj₁
  • ... 每张卡独立 cat，结果互不相干

合并的顺序保证

safetensors 里同一 layer 的 q/k/v 通常是按字母序出现（k → q → v 或 q → k → v），但代码不依赖顺序——靠 merge_buf[merged_key][slot] = tensor 这种字典键赋值，然后检查 all(s in merge_buf[merged_key] for s in all_slots) 确保三个都到齐了才触发 cat。

同样的逻辑对 MLP 的 gate_proj + up_proj → gate_up_proj 适用。

PART 6MoE · experts 堆叠

MoE 模型（如 Qwen3-MoE）的权重布局：

model.layers.0.mlp.experts.0.gate_proj.weight
model.layers.0.mlp.experts.0.up_proj.weight
model.layers.0.mlp.experts.0.down_proj.weight
model.layers.0.mlp.experts.1.gate_proj.weight
...
model.layers.0.mlp.experts.63.gate_proj.weight     # 64 个 expert

mini-sglang 把所有 expert 同名权重堆叠成一个 tensor（方便 fused MoE kernel 用）：

model.layers.0.mlp.experts.gate_up_proj    shape [num_experts, 2·inter, hidden]
model.layers.0.mlp.experts.down_proj       shape [num_experts, hidden, inter]

代码实现

# models/weight.py:31
_EXPERT_PATTERN = re.compile(r"^(?P<prefix>.+\.experts)\.(?P<idx>\d+)\.(?P<name>.+)$")

def _get_expert_stack_info(key):
    match = _EXPERT_PATTERN.match(key)
    if match is None: return None
    packed_name = match.group("name")
    if packed_name.endswith(".weight"):
        packed_name = packed_name.removesuffix(".weight")
    return f"{match.group('prefix')}.{packed_name}", int(match.group("idx"))
    # 例：
    #   "…experts.5.gate_up_proj.weight" → ("…experts.gate_up_proj", 5)

双重 buffer：先 merge 再 stack

为什么堆叠？ fused MoE kernel（kernel/triton/fused_moe.py）要并行处理多个 expert 的 matmul。如果每个 expert 是独立 tensor，kernel 要 launch 64 次（一次一 expert）。堆成一个 3D tensor 后，kernel 只 launch 1 次，通过 expert_id 在 dim 0 上索引。

mini-sglang 目前的 MoE 做 expert 复制——每张卡都有所有 expert 权重，只切 row/col parallel 那一维。所以没有跨 TP 的 expert 路由（all-to-all），这是简化之处（SGLang 主线支持 Expert Parallel）。

PART 7模型注册：怎么知道用哪个模型类？

HF 的 config.json 里有个字段 "architectures": ["Qwen3ForCausalLM"]。mini-sglang 用这个字符串在注册表里查对应类。

# models/register.py
_MODEL_REGISTRY = {
    "LlamaForCausalLM":                    (".llama",      "LlamaForCausalLM"),
    "Qwen2ForCausalLM":                    (".qwen2",      "Qwen2ForCausalLM"),
    "Qwen3ForCausalLM":                    (".qwen3",      "Qwen3ForCausalLM"),
    "Qwen3MoeForCausalLM":                 (".qwen3_moe",  "Qwen3MoeForCausalLM"),
    "MistralForCausalLM":                  (".mistral",    "MistralForCausalLM"),
    "Mistral3ForConditionalGeneration":    (".mistral",    "MistralForCausalLM"),
}

def get_model_class(model_architecture, model_config):
    module_path, class_name = _MODEL_REGISTRY[model_architecture]
    module = importlib.import_module(module_path, package=__package__)
    model_cls = getattr(module, class_name)
    return model_cls(model_config)

想加新模型？两步

  1. 在 models/ 下写一个新文件（比如 dbrx.py），实现 DbrxForCausalLM(BaseLLMModel)
  2. 在 register.py 加一行 "DbrxForCausalLM": (".dbrx", "DbrxForCausalLM")

如果权重名字跟 mini-sglang 已有模型不一致（比如用 attention.wq 而不是 self_attn.q_proj），还要扩展 _SPLIT_DIM_0/_MERGE_GROUPS。

常见 "key mismatch" 错误

错误原因解法
Missing key: ...qkv_proj.weight权重没合并成功（merge_buf 没攒齐）检查 safetensors 里是否真的有 q/k/v 三个
Unexpected key: vision_tower.*Mistral3 等 VLM 的视觉分支已自动过滤，不会报错。若其他 VLM 报错，加前缀到跳过列表

验证加载是否正确的小技巧

# 在 engine/engine.py 的 load_state_dict 前后打 log
for k, v in state_dict.items():
    print(f"{k}: shape={v.shape}, dtype={v.dtype}, device={v.device}, norm={v.norm().item():.4f}")
# 正常应该看到 norm 在 0.01 ~ 10 之间。如果特别大或特别小，可能切错了

同一份 HF 权重，TP 1/2/4 切出来会一样吗？

不会——切出来的 local tensor 不同，但装进 local Linear 后数学上等价。
  • TP=1: 每卡持有完整 W，output = X·W
  • TP=2: 每卡持有 W/2, 两卡 output 拼接 / 求和后等于 X·W
  • TP=4: 同理
所以同一个模型在 TP=1 和 TP=4 下输出 token 是完全一致的（浮点误差内）。这是验证 TP 实现正确性的最好方法。

总结：权重加载的 4 个关键步骤

  1. 找文件：download_hf_weight → glob 出所有 .safetensors
  2. 流式读 + 当场 shard：safetensors.safe_open 逐个读 tensor，_shard_tensor 按规则切自己那份
  3. 合并：q/k/v → qkv_proj（必须）；gate/up → gate_up_proj；MoE 再做一层 expert 堆叠
  4. yield：给 Engine 装进 model.load_state_dict

整个过程核心优势：CPU 峰值内存 ≈ 最大单个 tensor（几百 MB），而不是全模型大小（几十到一百多 GB）。即使在小内存机器上也能加载超大模型。
