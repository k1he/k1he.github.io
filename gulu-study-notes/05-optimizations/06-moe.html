MoE 架构 · Mixture of Experts 12

DeepSeek / Qwen3-MoE / Mixtral 都在用的"稀疏激活"架构。mini-sglang 怎么实现 + 跟 dense 的区别。
MoE 是啥 vs Dense 对比 forward 流程 Router 与 top-k Fused MoE kernel mini-sglang 的 TP 策略 Expert Parallel（未实现）

PART 1MoE 的核心思想

Dense 模型的 MLP：所有 token 都经过同一个 MLP。

MoE 模型的 MLP：有 N 个"专家 MLP"（experts），每个 token 只经过 top-k 个。其他 expert 不参与这个 token 的计算。

只算 2 个 expert，约 dense 1/32

核心公式

gate_scores = Linear_gate(token)                # [num_experts]
top_k_vals, top_k_ids = topk(softmax(gate_scores), k=2)  # 选 top-2

output = sum(
    top_k_vals[i] * experts[top_k_ids[i]](token)  # 只计算 top-k 个 expert
    for i in range(k)
)
"稀疏激活" 的直观理解：DeepSeek-V3 有 256 个 expert，每 token 只激活 8 个——97% 的参数在每次 forward 里是躺平的。这就是 MoE 能把"总参数量"做到万亿级但每次推理只算几百亿的秘诀。

PART 2关键指标对比

维度Dense (Llama-3-70B)MoE (Qwen3-235B-A22B)
总参数70B235B
每 token 激活参数70B（全部）22B（top-8 exp · ~10%）
显存占用140 GB470 GB（更大！）
计算量/ token~70 GFLOPs~22 GFLOPs
质量基线通常更好（参数多）
吞吐（同等显存下）基线通常更高（算得少）
推理复杂度简单需要 router + 可能的 all-to-all
MoE 的 trade-off：用显存换质量 + 算力效率。 适合有大显存（集群）的场景，不适合单卡部署。Qwen3-MoE 的"A22B"就是说"激活 22B"——推理时算力需求只相当于 22B dense 模型。

PART 3MoEMLP 的 forward 流程（mini-sglang 源码）

# models/utils.py:53  MoEMLP
class MoEMLP(BaseOP):
    def __init__(self, config):
        self.experts = MoELayer(
            num_experts=config.num_experts,
            top_k=config.num_experts_per_tok,
            hidden_size=config.hidden_size,
            intermediate_size=config.moe_intermediate_size,
            renormalize=config.norm_topk_prob,
        )
        self.gate = LinearReplicated(               # ★ router 用 replicated 不切
            config.hidden_size,
            config.num_experts,
            has_bias=False,
        )

    def forward(self, hidden_states):
        num_tokens, hidden_dim = hidden_states.shape
        hidden_states = hidden_states.view(-1, hidden_dim)
        router_logits = self.gate.forward(hidden_states)       #  ① 路由打分
        final = self.experts.forward(hidden_states, router_logits)   ② 实际计算
        return final.view(num_tokens, hidden_dim)

4 个核心步骤（点开每步看细节）

① Router gate

router_logits = gate(hidden_states)
# gate: [hidden, num_experts]
# shape: [T, num_experts]

这是一个普通 Linear 层，不做 TP 切（用 LinearReplicated）——每卡都持有完整 gate 权重。原因：num_experts 通常只有几十，切它开销比省的计算还多。

② topk 选 expert

topk_weights, topk_ids = fused_topk(
    hidden_states, router_logits,
    topk=self.top_k,
    renormalize=self.renormalize,
)
# topk_ids: [T, top_k] int32  每 token 选了哪 k 个 expert
# topk_weights: [T, top_k] fp32  对应权重

用 sgl_kernel.topk_softmax 融合算 softmax + topk。返回每 token 的 top-k expert id 及权重。

③ fused MoE compute

output = fused_experts(
    hidden_states,
    w1=gate_up_proj,   # [E, 2*I, hidden]
    w2=down_proj,       # [E, hidden, I]
    topk_weights, topk_ids,
    activation="silu",
)

核心 kernel。内部做：每个 token 路由到它的 top-k expert，在对应 w1/w2 切片上做 matmul + silu_and_mul + 加权求和。

④ all-reduce（TP > 1 时）

if self.tp_size > 1:
    final = self._comm.all_reduce(final)
return final

expert 内部是 row parallel（intermediate 维被 TP 切了），所以结束要 all-reduce 合并部分和。跟 dense MLP 末尾的 all-reduce 一样。

MoELayer 的权重 shape

# layers/moe.py:34
intermediate_size_per_partition = div_even(intermediate_size, tp_size)

self.gate_up_proj = torch.empty(
    num_experts,
    2 * intermediate_size_per_partition,   # ★ TP 切的是 intermediate 维
    hidden_size,
)
self.down_proj = torch.empty(
    num_experts,
    hidden_size,
    intermediate_size_per_partition,       # ★ 同样切 intermediate
)
每个 expert 的内部结构 = 标准 GatedMLP（跟 dense MLP 一样）
  • gate_up_proj 是 column parallel（按输出维切 2*intermediate）
  • down_proj 是 row parallel（按输入维切 intermediate）
  • TP 在每个 expert 内部切 intermediate，不跨 expert
  • 所有 expert 的权重堆叠在第 0 维：[num_experts, ...]

PART 4Router 的细节

fused_topk kernel 做了什么？

# moe/fused.py:9
def fused_topk(hidden_states, gating_output, topk, renormalize):
    from sgl_kernel import topk_softmax

    topk_weights = torch.empty(M, topk, dtype=torch.float32, ...)
    topk_ids = torch.empty(M, topk, dtype=torch.int32, ...)
    topk_softmax(topk_weights, topk_ids, gating_output.float(), renormalize)

    if renormalize:
        topk_weights = topk_weights / (topk_weights.sum(dim=-1, keepdim=True) + 1e-8)
    return topk_weights, topk_ids

它融合了三个操作：

  1. softmax(gating_output)：把 logits 变成概率
  2. topk：每 token 选最大的 k 个
  3. renormalize（可选）：top-k 被选中的概率再归一化（让它们加起来=1）

举例

gating_output[token 0] = [1.0, 3.0, 0.5, 2.0, ...]     # 64 个 expert
                          ↓ softmax
probs               = [0.10, 0.50, 0.05, 0.25, ...]
                          ↓ topk(k=2)
topk_ids[token 0]   = [1, 3]       # 选 expert 1 和 3
topk_weights[token 0] = [0.50, 0.25]
                          ↓ renormalize
topk_weights[token 0] = [0.67, 0.33]    # 加起来 = 1

PART 5Fused MoE Kernel · 把几百个 matmul 融合成一个

问题：naive 实现会有多惨？

# naive 伪代码
for t in range(num_tokens):           # 1000 token
    for k in range(top_k):              # 2
        expert_id = topk_ids[t, k]
        out = MLP(hidden[t], w1[expert_id], w2[expert_id])
        # → 2000 次 MLP 调用，每次 matmul 超小

每次 matmul 只处理 1 个 token，GPU 严重 under-utilization，launch 开销爆炸。

解决：按 expert 分组批量 matmul

# fused 版本的核心思路
for e in range(num_experts):                # 64
    tokens_for_e = [t for t in tokens if e in topk_ids[t]]
    out_for_e = batched_matmul(hidden[tokens_for_e], w1[e], w2[e])
    # → 64 次 batched MLP，每次处理一个 expert 的所有 token

但 Python 循环 64 次仍然慢。真正的 fused kernel 用一个 CUDA kernel 处理所有 expert。

moe_align_block_size：打散到固定大小的 block

# moe/fused.py:31  moe_align_block_size
def moe_align_block_size(topk_ids, block_size, num_experts):
    """
    把 topk_ids 按 expert 分组，pad 到 block_size 的倍数。
    比如 topk_ids = [[2,3,4],[1,2,4],[1,3,4],[1,2,3]], block=4
    → sorted_ids = [3,6,9,12 | 0,4,10,12 | 1,7,11,12 | 2,5,8,12]
      expert_ids = [1, 2, 3, 4]  (每个 block 对应的 expert)
    """
fused_moe 的本质：把不规则的"每 token 路由"整理成规则的"block-level GEMM"，让 GPU tensor core 能打满。
代价是引入 padding（有些 expert 被选的 token 少，要 pad 到 block_size 整数倍）。但 pad 浪费远小于 kernel launch 开销。

mini-sglang 用的是 Triton 实现的 fused_moe，代码在 kernel/triton/fused_moe.py。参考了 vLLM / sglang / Qwen 的实现。

PART 6mini-sglang 的 TP 策略：expert 复制

MoE + TP 有多种组合方式：

策略说明通信开销显存实现复杂度
Expert 复制 + 内部 TP所有 expert 在每卡都有，内部 intermediate 按 TP 切低（只 all-reduce）高（每卡都占完整 expert）简单
Expert Parallel (EP)每卡只持有 num_experts/TP 个 expert高（all-to-all）低复杂
EP + DPDeepSeek-V3 等超大模型用最高最低最复杂

mini-sglang 选择：Expert 复制 + 内部 TP

# layers/moe.py
self.gate_up_proj = torch.empty(
    num_experts,                                 # ★ 完整数量, 不按 TP 切
    2 * intermediate_size_per_partition,           # intermediate 按 TP 切
    hidden_size,
)

这种策略的优缺点

✅ 优点

  • 实现极其简单——跟 dense MLP 几乎一样，只在外面套一层 router
  • 通信只有 1 次 all-reduce（跟 dense 一样）
  • 没有复杂的 all-to-all 路由逻辑
  • 无 token balancing 问题（每卡都能本地算所有 expert）

❌ 缺点

  • 显存代价高：每卡都要存全部 expert，没有节省
  • 对超大 MoE（256+ expert）不 scalable
  • TP 上限 ≈ intermediate_size（不能切到 intermediate 比 TP 小）
  • Qwen3-MoE 30B-A3B 这种小 MoE 还 OK，DeepSeek-V3 这种 600B 就不行
mini-sglang 的定位决定了这个选择。它是教学实现，目标是把"MoE 推理"这件事讲清楚。Expert 复制策略是最直观的起点——读者看懂之后再去学 EP 会容易很多。

PART 7Expert Parallel（mini-sglang 未实现）

为了完整性，简单讲下 SGLang 主线 / DeepSeek 推理框架是怎么做 EP 的：

EP 的核心：每卡只存 N/TP 个 expert

EP 的两次 all-to-all

  1. Dispatch：每 token 按 topk_ids 切分 → 通过 all-to-all 发到对应 rank
  2. Expert compute：在目标 rank 上用本地 expert 权重算 MLP
  3. Combine：算完的 output 通过第二次 all-to-all 送回原 token 所在 rank

EP 的挑战

  • Token balancing：如果所有 token 都选同一个 expert，对应 rank 算力爆满，其他空闲。实际靠训练时的 auxiliary loss 确保 expert 使用均衡。
  • 通信量：两次 all-to-all，每次通信量 ≈ num_tokens × hidden × dtype。对 DeepSeek-V3 这种大模型，all-to-all 时间可能占 forward 的 30%+。
  • 动态 shape：不同 iter 里 token 分布给 expert 不均匀，CUDA Graph 没法直接录制（需要 padding 到最大可能情况）。

SGLang 主线支持 EP（--enable-ep），配合 DeepEP 等优化库。如果你关心 DeepSeek / Kimi 这种超大 MoE，可以看 SGLang 主线的 python/sglang/srt/layers/moe/。

总结

  • MoE = sparse MLP：N 个 expert 但每 token 只激活 top-k
  • Router：用 gate linear + softmax + topk 选 expert，权重加权输出
  • Fused MoE kernel：把 "每 token 路由到不同 expert" 整理成 block-level GEMM，用 moe_align_block_size + Triton kernel 实现
  • mini-sglang 的 TP 策略：expert 复制 + 每 expert 内部 TP，简单但显存贵
  • Expert Parallel（未实现）：每卡只存部分 expert，用 all-to-all 路由 token——DeepSeek-V3 的必需品
