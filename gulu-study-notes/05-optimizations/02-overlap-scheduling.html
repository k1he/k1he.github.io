PART 1问题：不优化的话 CPU/GPU 是串行的

没有 overlap 时，一个 iteration 内的执行是这样的：

核心痛点：CPU 在准备下一个 batch 时 GPU 在等，GPU 在算时 CPU 在等。
每 iteration 的 CPU 部分（调度 + 结果处理）加起来大概 1-2 ms。GPU decode 部分也就 3-5 ms。CPU 占了总时间的 20-40%，这部分如果能"藏起来"就是纯收益。

PART 2核心思想：让 CPU 和 GPU 并行

关键观察：CPU 和 GPU 做的事其实不依赖对方——

  • CPU 在调度下一个 batch时，用的是自己的数据结构（pending_list、running_reqs 等），不需要 GPU 配合
  • GPU 在算当前 batch时，用的是已经准备好的输入，不需要 CPU 配合

所以可以让它们同时做事——在一个 iteration 里，CPU 同时做两件事：

  1. 为下一批做调度 + launch GPU 计算（异步，立即返回）
  2. 处理上一批的 GPU 结果

这两件事彼此不依赖，CPU 可以一气做完。GPU 则在后台跑 model forward。

PART 3两条 CUDA Stream 的角色分工

要实现 overlap，需要两条独立的 CUDA Stream——stream 是 CUDA 里 "一条命令队列"，同一 stream 内严格顺序执行，不同 stream 可并行。

# scheduler/scheduler.py:52
self.device = self.engine.device
self.stream = torch.cuda.Stream(device=self.device)      # scheduler 自己的 stream
self.engine_stream_ctx = torch.cuda.stream(self.engine.stream)
torch.cuda.set_stream(self.stream)                         # 默认用 scheduler.stream

两条 stream 各管什么

stream干啥典型操作
scheduler.stream调度元数据相关page table 写入、H2D copy（positions、mapping）、attn metadata 准备
engine.stream模型 forward + sampler所有 kernel: embed, QKV, attention, O, MLP, LM head, sample

两条 stream 之间的依赖：wait_stream

# scheduler/scheduler.py:100
with self.engine_stream_ctx:            # 切到 engine.stream 当默认
    self.engine.stream.wait_stream(self.stream)    # engine 等 scheduler 的准备完
    ongoing_data = (forward_input, self._forward(forward_input))
engine.stream.wait_stream(scheduler.stream) 的语义：
在 engine.stream 里插入一个"等待点"，等到 scheduler.stream 到此刻为止提交的所有操作都完成才继续。这保证 model forward 读的 metadata 是已经写好的。
注意这是GPU 侧的同步，不是 CPU 侧——CPU 不会被阻塞，只是 engine.stream 里的新 kernel 要等 scheduler.stream 的前置操作做完才启动。

PART 4overlap_loop 逐行拆解

# scheduler/scheduler.py:83
def overlap_loop(self, last_data: ForwardData | None) -> ForwardData | None:
    blocking = not (
        last_data is not None                    # 有 last 要处理
        or self.prefill_manager.runnable
        or self.decode_manager.runnable
    )
    for msg in self.receive_msg(blocking=blocking):  # ① 收 ZMQ
        self._process_one_msg(msg)

    forward_input = self._schedule_next_batch()       # ② 调度 + 准备 metadata
    ongoing_data = None
    if forward_input is not None:
        with self.engine_stream_ctx:                 # ③ 切到 engine.stream
            self.engine.stream.wait_stream(self.stream)
            ongoing_data = (forward_input, self._forward(forward_input))
            # ↑ launch model.forward + sample, 异步返回

    self._process_last_data(last_data)              # ④ CPU 处理上轮结果
    return ongoing_data                           # 下一轮作为 last_data

5 个阶段的详细时间线

阶段在哪条 stream做什么阻塞 CPU？
① receive_msgCPU only从 ZMQ 拉消息，filter 入队blocking=True 时阻塞
② schedule_next_batchscheduler.streamPrefillAdder 装箱 + allocate_paged + prepare_metadata（触发一堆 H2D copy）不阻塞（copy 是 async）
③ _forward (launch)engine.streamlaunch model.forward + sample + D2H copy不阻塞（launch 返回立即）
④ _process_last_dataCPU onlycopy_done.synchronize 等上轮 D2H 完；然后 cache_req / send reply阻塞，等 copy event
⑤ return—本轮的 ongoing_data 给下一轮做 last_data—
关键：第 ③ 和第 ④ 步是并行的——③ launch 完立刻返回（不等 GPU 算完），④ 在 CPU 上处理上轮的结果。GPU 在后台跑本轮的 forward，与 CPU 的 ④ 并行。

blocking 逻辑

blocking = not (
    last_data is not None
    or self.prefill_manager.runnable
    or self.decode_manager.runnable
)

只有所有三件事都没——没上批要处理、没 pending prefill、没 running decode——才阻塞等 ZMQ。否则非阻塞 drain，有多少收多少。

这样系统忙时不停歇，闲时优雅阻塞不消耗 CPU。

PART 5多 iteration 时序图

把 3 个连续 iteration 画出来，看 "iter N 的 CPU" 和 "iter N-1 的 GPU" 怎么并行：

读这张图的关键点

  • iter 1 特殊：没有 last_data，所以 CPU 最后那段是空闲。这是"启动期"的一次性浪费。
  • iter 2 开始稳态：CPU 在 launch 完 iter 2 之后立刻去处理 iter 1 的结果，GPU 同时在算 iter 2。
  • GPU 几乎不间断：forward 1 → forward 2 → ... 衔接紧密（中间只有 launch 那一小段 gap）。
  • CPU 的 "process last" 被 GPU 吃掉：只要 GPU forward 比 CPU process 长（通常是这样），process 时间完全不影响总 iter 时长。

PART 6细节坑点

坑 1 · copy_done.synchronize() 到底在等什么？

# scheduler/scheduler.py:142
def _process_last_data(self, last_data):
    batch, (_, next_tokens_cpu, copy_done) = last_data[0].batch, last_data[1]
    copy_done.synchronize()   # ★ 在等上轮的 D2H copy 完成
    ...
    for i, req in enumerate(batch.reqs):
        next_token = next_tokens_cpu[i]   # 现在可以读 cpu tensor 了

它等的是上一轮 forward 结束后那个 D2H async copy。如果 GPU 还在算，这里会阻塞 CPU。但正常情况下，当 CPU 走到 _process_last_data 时，上一轮 forward 早就完了（整个 overlap 的加速就靠这个时间差）。

坑 2 · lazy_free_region 为什么要存在？

# scheduler/cache.py:93
@contextmanager
def lazy_free_region(self):
    def lazy_free(indices):
        lazy_free_list.append(indices[:: self.page_size])
    lazy_free_list = []
    try:
        self._free = lazy_free
        yield
    finally:
        del self._free
        self.free_slots = torch.cat([self.free_slots] + lazy_free_list)
在 _process_last_data 里处理多个 req，每个 finish 都要 free 一堆 page。如果每次都 torch.cat，内存分配开销巨大。
lazy_free_region 把所有 free 攒起来，最后一次性 cat。这是个 GPU tensor 内存管理的常见优化。

坑 3 · 为什么 complete_one 在 forward_batch 里（不在 process_last_data）？

# engine/engine.py:200
for req in batch.reqs:
    req.complete_one()     # cached_len ← device_len; device_len += 1

注意这是在 forward_batch 里面调用的，不是 _process_last_data。为什么？

因为 overlap loop 要求 req 的长度状态必须立刻更新，以便下一轮 schedule_next_batch 能正确计算 device_len / extend_len。如果等到 _process_last_data 才更新（已经是下一轮），schedule 就会基于过时的状态，导致错误。

坑 4 · finished_reqs 集合的作用

# scheduler/scheduler.py:165
self.finished_reqs: Set[Req] = set()
# ...
if finished and req not in self.finished_reqs:
    self.decode_manager.remove_req(req)
    self._free_req_resources(req)
    new_finished_reqs.add(req)
# ...
self.finished_reqs = new_finished_reqs
防止 "double free"：overlap loop 下，同一个 req 可能在连续两个 iter 都被判定为 finished（上一轮 forward 出 EOS，这一轮 process_last_data 看到；但同时本轮 forward 又跑了一步，产出同一个 req 的另一个"下一 token"）。
finished_reqs 记住上轮已经 free 过的 req，防止重复调用 _free_req_resources（会导致 table_idx 被 free 两次）。
这是 overlap 引入的微妙并发问题，不做就会偶发 crash。

坑 5 · set_stream 的作用

# scheduler/scheduler.py:55
torch.cuda.set_stream(self.stream)    # 把默认 stream 设成 scheduler.stream

所有不显式指定 stream 的 PyTorch 操作（比如 tensor.to(device, non_blocking=True)）都走默认 stream。set_stream 让这些操作落在 scheduler.stream 上，不会污染 engine.stream。这样 wait_stream 才能精确同步。

坑 6 · normal_loop 作为 ablation

# scheduler/scheduler.py:120
if ENV.DISABLE_OVERLAP_SCHEDULING:
    with self.engine_stream_ctx:
        self.engine.stream.wait_stream(self.stream)
        while True:
            self.normal_loop()
else:
    while True:
        data = self.overlap_loop(data)

normal_loop 是串行版本——没有 last_data 概念，每次调度 → forward → 立刻 process。用 MINISGL_DISABLE_OVERLAP_SCHEDULING=1 启用，方便对比测量 overlap 的收益。

PART 7实测收益与适用场景

什么时候 overlap 有效？

场景CPU 时间GPU 时间overlap 收益
大 batch decode~1.5 ms（多 req 的 process 开销大）~4 ms大 (~30%)
小 batch decode（bs=1）~0.8 ms~2 ms中 (~25%)
prefill~0.5 ms~20 ms小 (< 5%)
有 radix eviction 的复杂调度~2 ms~4 ms大 (~35%)
一般规律：CPU 时间 / GPU 时间 的比值越高，overlap 收益越大。
当 GPU 时间远大于 CPU 时间（prefill 场景），CPU 时间本来就被淹没，overlap 省不了多少。
当 CPU/GPU 比值接近 1:1（大 decode batch），overlap 能把总时间压到 max(CPU, GPU)，近似翻倍吞吐。

实测（mini-sglang benchmark/offline，H200, Qwen3-0.6B）

# 默认 (overlap on)
python benchmark/offline/bench.py --model Qwen/Qwen3-0.6B
# throughput: ~5500 token/s

# overlap off
MINISGL_DISABLE_OVERLAP_SCHEDULING=1 python benchmark/offline/bench.py ...
# throughput: ~4200 token/s

# → overlap 贡献 ~31% 吞吐

跟 CUDA Graph 是什么关系？

两者独立，叠加生效。
  • CUDA Graph 压缩 GPU 侧的 launch 开销（CPU dispatch 时间降到几 µs）
  • Overlap Scheduling 隐藏 CPU 侧的 scheduler 开销（把它藏在 GPU forward 后面）
  • 开 graph 后 CPU launch 只用 5 µs，但 CPU 的 schedule + process_last 仍需 1-2 ms，overlap 仍然有用
  • mini-sglang 默认两者都开

调试时建议关 overlap

因为 overlap 引入的时序复杂性（last_data 跨 iter、finished_reqs 去重）会让 bug 更难定位。调试时用 MINISGL_DISABLE_OVERLAP_SCHEDULING=1 切到 normal_loop 做干净的单步推理，定位清楚后再开回来看。

总结：overlap 的三层机制

  1. 并行：CPU 处理本批 launch + 上批结果，GPU 跑本批 forward，两者时间重叠
  2. 同步：用两条 CUDA stream + wait_stream，保证 metadata 准备和 forward 之间的 happens-before 关系
  3. 缓存：ForwardData（forward_input + forward_output + copy_done event）在迭代间传递，让下一轮能处理上一轮的结果

核心抽象：把每个 iter 从"串行 3 步"（recv → forward → reply）变成"并行 2 路"（CPU: 本批 launch + 上批 reply · GPU: 本批 forward）。
