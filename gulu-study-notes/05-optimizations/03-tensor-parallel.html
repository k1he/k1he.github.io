PART 1为什么要 Tensor Parallel

简单说：大模型权重塞不下一张卡。Llama-3-70B 用 fp16 ≈ 140 GB；H100 80G 一张卡装不下，必须拆开。

为什么是 Tensor Parallel 而不是别的

策略切谁开销适用
Tensor Parallel (TP)每层的权重矩阵横/竖切每层 1-2 次 all-reduce同机多卡（NVLink 高带宽必备）
Pipeline Parallel (PP)把 N 层模型切成 K 段跨段传 activation，bubble 时间跨节点
Data Parallel (DP)请求按 batch 切梯度 all-reduce（推理无）训练 / 多副本扩容
Expert Parallel (EP)MoE 把不同 expert 放不同卡token 重路由MoE 专属

mini-sglang 只实现了 TP（MoE 模型也是 TP+expert 复制）。原因：

  • 推理只有 forward，没有反向，TP 通信量比训练少一半
  • NVLink (~600 GB/s) 让 all-reduce 快到几乎不影响 latency
  • 实现简单——只要替换 Linear 层的实现就行，模型代码几乎不动
TP 的核心思想（一句话）： 把一个大矩阵乘法 Y = X · W，按 W 的列或行切成多份，每张卡算一份，最后通过通信合并结果。本质是把矩阵乘法的并行性显式暴露出来。

PART 2多卡进程拓扑

对比单卡（前 5 章假设）和 TP=4 的进程数：

角色单卡TP=4
API Server (FastAPI)11（不变）
Tokenizer WorkerN（默认 1）N（不变）
De-tokenizer Worker11（不变）
Scheduler Worker14（每 GPU 一个进程）
总进程数3+N6+N
关键观察：
  • 只有 Rank 0 跟外界通信（收 UserMsg、发 DetokenizeMsg）
  • 4 个 Scheduler 跑同一份代码，决策完全一致——靠 ZMQ Pub/Sub 广播原始消息保证它们看到的输入序列相同
  • 每个 Scheduler 拥有 1/4 模型权重 + 1/4 KV cache + 自己的 PrefillManager/DecodeManager/CacheManager（状态相同但物理隔离）
  • 没有共享内存——所有跨进程协同要么走 ZMQ（控制），要么走 NCCL（数据）

PART 2.5📐 数学基础：X · W = Y 与切法的逻辑必然性

在讲 4 种 Linear 之前，必须先把"切的到底是什么、为什么只能这么切"讲透。

第一步 · X / W / Y 在 Transformer 里到底是什么？

Y = X · W 是所有 Linear 层的核心操作。Transformer 一层里它出现 4 次：

位置X 是什么W shapeY 是什么
① QKV proj上一层 hidden state[hidden, (Q+2KV)·head_dim]Q/K/V 拼接
② O projattention 输出[heads·head_dim, hidden]回到 hidden 维
③ MLP gate_uphidden state[hidden, 2·intermediate]门控 + 上投影
④ MLP downsilu_and_mul 输出[intermediate, hidden]回到 hidden 维
结论：整个 Transformer 就是不断 Y = X · W → attention → Y = X · W → MLP → ... 重复几十层。TP 切的就是这些 W。

第二步 · 矩阵乘法的"切片性质"——为什么切法不是任意的

记住矩阵乘法的本质：

Y[i, j] = Σₖ X[i, k] · W[k, j]
        = X[i, 0]·W[0, j] + X[i, 1]·W[1, j] + ... + X[i, K-1]·W[K-1, j]

这个求和的结构决定了 W 只能按两种"维度"切：输入维 K（行）或输出维 N（列）。每种切法对 X 有不同要求。

切法 A · W 按列切 → "Column Parallel"

把 W 切成左右 4 列，每张卡持有一列。X 不切。

切法 B · W 按行切 → "Row Parallel"（X 必须配合切）

把 W 切成上下 4 块。但因为 W 的行数 K 变成 K/4，X 的列数也必须变成 K/4 才能匹配——所以X 也要按列切。

第三步 · 反例：为什么不能"W 按行切但 X 不切"？

试试就知道——维度根本对不上！ 
# W 按行切：W₀ shape = [K/2, N], W₁ shape = [K/2, N]
# X 不切：    X shape  = [T, K]

X · W₀ = ???
[T, K] · [K/2, N] = ???   # ❌ K ≠ K/2，矩阵乘法非法
矩阵乘法硬约束：X 的列数必须 = W 的行数。把 W 按行切了，X 也必须按列切才能匹配。这是数学不允许，不是工程选择。

所以 4 种"想象中的切法"里只有 2 种数学合法：

切法数学上可行？名字代价
W 按列切，X 不切✅Column Parallel无通信，但 Y 是切分的
W 按行切，X 配合按列切✅Row Parallel需要 all-reduce
W 按行切，X 不切❌—shape 不匹配
W 按列切，X 也按列切❌—shape 不匹配

第四步 · "column-then-row" 模式为什么能成对消除通信

仔细看会发现一个巧妙的事：

  • Column Parallel 的输入 X 完整、输出 Y 切列
  • Row Parallel 的输入 X 切列、输出 Y 完整（all-reduce 后）

这正好首尾相接！QKV (col par) 的输出直接喂给 attention（每卡独立算）→ O proj (row par) 的输入正好已经是切列的。中间不需要任何通信！

X[完整]
 │
 ├─→ W_qkv (col par)  ─→  QKV[切列]      # 无通信
 │                         │
 │                         ▼
 │                       attention      # 各卡独立
 │                         │
 │                         ▼
 │                       O_in[切列]      # 天然切列
 │                         │
 ├─→ W_o (row par)    ─→  Y[partial]    # 部分和
 │                         │
 │                         ▼
 │                       ★ all-reduce   # 唯一通信
 │                         │
 ▼                         ▼
完整 Y[完整]             完整 Y
这就是 "column-then-row" 模式的精妙之处（来自 Megatron-LM 论文）：每对 col→row 之间无通信，整个 attention/MLP block 只在末尾 all-reduce 一次。4 次 Linear 只触发 2 次 all-reduce。

PART 34 种 Linear 切法（mini-sglang 的全部秘诀）

整个 TP 的"魔法"就 4 个 Linear 类，全在 layers/linear.py。把它们看懂，TP 就懂了 90%。

① Column Parallel (按列切 W)

# layers/linear.py:71  LinearQKVMerged (column parallel for QKV)
local_num_qo = div_even(num_qo_heads, tp_info.size)
local_num_kv = div_even(num_kv_heads, tp_info.size, allow_replicate=True)
local_osize = (local_num_qo + 2 * local_num_kv) * head_dim   # 本卡持有的 QKV 维度

# forward 跟普通 Linear 没区别，因为不需要通信
def forward(self, x):
    return F.linear(x, self.weight, self.bias)
用途： Q/K/V 投影、MLP up_proj、MLP gate_proj。这些层"前面的输入是相同的、后面的输出是独立的"，正好可以让每张卡只算自己的一份。

② Row Parallel (按行切 W) + all-reduce

部分和 ↓ NCCL all_reduce ↓ 所有 rank 加和，得到完整 Y = ΣᵢYᵢ 
# layers/linear.py:91  LinearOProj (row parallel for output)
def __init__(self, input_size, output_size, has_bias):
    tp_info = get_tp_info()
    local_isize = div_even(input_size, tp_info.size)   # 输入 hidden 也按 TP 切
    local_osize = output_size                          # 输出 hidden 完整
    self._comm = DistributedCommunicator()
    self._tp_size = tp_info.size

def forward(self, x):
    y = F.linear(x, self.weight, self.bias)
    if self._tp_size > 1:
        y = self._comm.all_reduce(y)              ★ NCCL allreduce
    return y
用途： Attention 的 O 投影、MLP down_proj。它们的输入正好是上一个 column-parallel 层的输出——所以输入天然是按列切好的，row parallel 直接消化，最后用 allreduce 合并部分和。
关键： 一次 attention 要做 1 次 all-reduce（O 之后），一次 MLP 也要 1 次（down 之后）。每层 transformer 共 2 次 all-reduce。

③ Replicated (复制)

# layers/linear.py:35  LinearReplicated
class LinearReplicated(_LinearTPImpl):
    # 不切，每卡持有完整权重，输入输出也完整
    def __init__(self, input_size, output_size, has_bias):
        super().__init__(
            full_isize=input_size, full_osize=output_size,
            local_isize=input_size, local_osize=output_size,  # 全量
            has_bias=has_bias,
        )

用途： 小到不值得切的层。比如 MoE 的 router gate（num_experts 通常只有几十，不值得切）。

④ ParallelLMHead / VocabParallelEmbedding (按 vocab 切)

词表通常很大（Llama 128k），输出层 lm_head 是 [hidden, vocab] 的大矩阵，按 vocab 维切到各卡。embedding 反向同理。本质就是一种 column parallel，只是切的维度叫 vocab。

4 种 Linear 在一个 transformer block 里的位置

# models/utils.py: RopeAttn  (一个 attention block)
qkv = LinearQKVMerged(x)        → ① column parallel, no comm
o   = attn.forward(qkv)        → attention kernel
out = LinearOProj(o)            → ② row parallel + all_reduce ★

# models/utils.py: GatedMLP  (一个 MLP block)
gate_up = LinearColParallelMerged(x)   → ① column parallel, no comm
y       = silu_and_mul(gate_up)
out     = LinearRowParallel(y)         → ② row parallel + all_reduce ★
"成对出现"是设计的核心：column parallel 切完输出，row parallel 立刻消化它。这样中间不需要 gather，只需在 row parallel 末尾 allreduce 一次。Megatron-LM 论文称之为 "column-then-row" 模式。

把上面 4 种 Linear 串起来，看一个完整的 transformer 层在 4 张卡上是怎么算的：

整层 forward 的通信代价：

PART 5KV Cache 在 TP 下怎么切

这是一个常常被忽略的点。KV cache 不是"每张卡都存全量"，而是按 num_kv_heads 切分。

# engine/engine.py:148  _determine_num_pages
cache_per_page = (
    2  # key + value
    * config.model_config.head_dim
    * div_even(config.model_config.num_kv_heads, config.tp_info.size, allow_replicate=True)
    * config.page_size
    * self.dtype.itemsize
    * config.model_config.num_layers
)
模型num_kv_headsTP=1 KV per layerTP=4 KV per layer per GPU
Llama-3-70B88 组 KV2 组 KV
Qwen3-32B88 组2 组
Qwen3-0.6B22 组2 组（不切，复制）
注意 allow_replicate=True：当 num_kv_heads < tp_size 时（比如 Qwen3-0.6B 只有 2 个 KV head 但 TP=4），KV head 会复制到多卡，因为不能切到比头数还小。这是 GQA + TP 的一个 corner case。

为什么 KV head 切了，但 Q head 切是必然的？

  • Q head 必须切——否则 attention 的算力没法分摊。每张卡独立算自己的 Q heads × KV heads 的 scaled-dot-product。
  • KV head 切是节省显存——KV cache 是显存大头（往往占 50%+），切了之后每卡显存占用减小
  • KV cache 写入也是每卡独立的——本卡的 attention 算完本卡的 K/V，直接写本卡的 page。不需要 KV 跨卡同步。

page_table 在 TP 下是什么样的

每张卡的 page_table 是独立的 GPU tensor，但内容完全相同——因为 4 个 Scheduler 跑同一份调度算法，分配到的 page index 也一样。

# 每个 rank:
self.ctx.page_table = torch.zeros(
    (config.max_running_req + 1, aligned_max_seq_len),
    dtype=torch.int32,
    device=self.device,    # cuda:0 / cuda:1 / cuda:2 / cuda:3
)
# 写入时每个 rank 独立调用 cache.allocate_paged，但分配的 page index 完全一致
这是 mini-sglang 的一个简化设计：page_table 在每张卡上重复存储。SGLang 主线针对超大模型有更精细的切分（比如把 page_table 也切片），但 mini-sglang 选了"重复但简单"。重复的 page_table 内存量很小（max_running_req × max_seq_len × 4 字节，几十 MB），可以接受。

PART 5.5📡 集合通信原语：all-reduce / all-gather / all-to-all

这些是所有 N 张卡一起参与的通信操作（区别于"两两点对点"的 send/recv）。NCCL 提供 5 个核心原语：broadcast / reduce / all-reduce / all-gather / all-to-all。LLM 推理里最常用前 3 个，下面把它们的形状变化讲清楚。

① all-reduce · "求和后让所有人都拿到结果"

属性值
每卡输入 shape[N]
每卡输出 shape[N] （不变）
语义所有卡相同位置的元素求和，结果广播给所有卡
典型用途row parallel 之后合并 partial Y · TP 推理 99% 的通信都是它
通信量2(P-1)·N/P bytes (ring 算法)
底层实现：Ring All-Reduce
把数据切成 N 段，每张卡转一圈：第一圈每段被加上一张卡的部分和（reduce-scatter），第二圈每段被传一圈让所有人都拿到（all-gather）。带宽利用率近 100%，但延迟随 N 线性增长——这就是为什么 TP 限制在同机 NVLink 内（NVLink 600 GB/s，跨机 IB 200 GB/s 差太多）。

② all-gather · "把所有人的拼接起来"

属性值
每卡输入 shape[N]
每卡输出 shape[N · P]（变 P 倍！）
语义每张卡的数据被拼接到所有卡上
典型用途VocabParallelEmbedding（每卡持词表 1/P，查询时 gather 全表）· Sequence Parallel
与 all-reduce 的关键区别：
  • all-reduce: 求和，输出 shape 不变（数值变成 ΣaᵢN）
  • all-gather: 拼接，输出 shape 变 P 倍（数值就是各卡数据并排放）
mini-sglang 的 distributed/impl.py 里两种都实现了，但 99% 用 all-reduce。

③ all-to-all · "每个人发给每个人不同的数据"（mini-sglang 没用）

属性值
每卡输入 shape[N · P]（已切成 P 份）
每卡输出 shape[N · P]（仍是 P 份，但来自不同 rank）
语义"扑克洗牌"——P 张卡两两交换数据片
典型用途Expert Parallel (EP)：MoE token 路由到不同卡上的不同 expert，算完再发回。
DeepSeek-V3 那种大 MoE 模型靠 all-to-all 才能扩展。
mini-sglang 用了吗？❌ 没有，因为 mini-sglang 的 MoE 走 expert 复制（每卡都有所有 expert），不需要路由

三个原语对比 cheat sheet

原语shape 变化语义LLM 用途
all-reduce[N] → [N]所有卡求和★ TP row-parallel 之后
all-gather[N] → [N·P]所有卡数据拼接VocabParallelEmbedding · SP
all-to-all[N·P] → [N·P] (重排)互相分发不同片Expert Parallel (MoE 路由)

PART 6三条通信通道：NCCL / pynccl / GLOO

mini-sglang 同时使用 3 套通信库，各管一摊：

def _init_communication(self, config):

为什么自研 pynccl？

原因：标准 NCCL 在小张量上有固定开销——它内部要打包、提交 work、调度，对每次几 KB 的小 allreduce 开销比真正的传输还大。pynccl 用 tvm-ffi 直接绑 NCCL C 库，裁掉 PyTorch 中间层。 
# kernel/pynccl.py:45  init_pynccl
if tp_rank == 0:
    id_list = [module.create_nccl_uid()]
    torch.distributed.broadcast_object_list(id_list, src=0, group=tp_cpu_group)  # 用 GLOO 传 NCCL ID
else:
    id_list = [None]
    torch.distributed.broadcast_object_list(id_list, src=0, group=tp_cpu_group)
nccl_id = id_list[0]
return cls(tp_rank, tp_size, max_size_bytes, nccl_id)

DistributedCommunicator 的双实现（distributed/impl.py）

class DistributedCommunicator:
    plugins: List[DistributedImpl] = [TorchDistributedImpl()]   # 默认 torch.dist

    def all_reduce(self, x):
        return self.plugins[-1].all_reduce(x)   ★ 优先用最后注册的

# enable_pynccl_distributed 时把 PyNCCLImpl push 到末尾，自动覆盖
DistributedCommunicator.plugins.append(PyNCCLDistributedImpl(comm))

这就是为什么 LinearOProj/LinearRowParallel 里调 self._comm.all_reduce(y) 而不需要管底层是 NCCL 还是 pynccl——通信器是个 plugin chain，自动选最优。

PART 74 个 Scheduler 怎么"对齐决策"

这是 02 章 IOMixin 那节的展开。为什么 4 个 Scheduler 跑同一份代码，但只有 rank0 跟外界通信？

核心机制：rank0 收消息 + ZMQ 广播 + 全员 GLOO 同步消息数量

对应源码（scheduler/io.py）

def _recv_msg_multi_rank0(self, blocking):
    pending_raw_msgs = []
    while not self._recv_from_tokenizer.empty():
        pending_raw_msgs.append(self._recv_from_tokenizer.get_raw())

    # ★ ② 用 GLOO 广播消息数量给所有 rank
    src_tensor = torch.tensor(len(pending_raw_msgs))
    self.tp_cpu_group.broadcast(src_tensor, root=0).wait()

    for raw in pending_raw_msgs:
        # ★ ③ 用 ZMQ Pub 广播 raw bytes
        self._send_into_ranks.put_raw(raw)
        pending_msgs.append(self._recv_from_tokenizer.decode(raw))
    return pending_msgs

def _recv_msg_multi_rank1(self, blocking):
    # ★ ② 等 rank0 告诉我"应该收几条"
    dst_tensor = torch.tensor(-1)
    self.tp_cpu_group.broadcast(dst_tensor, root=0).wait()
    dst_length = int(dst_tensor.item())

    # ★ ③ 从 ZMQ Sub 收对应数量
    for _ in range(dst_length):
        pending_msgs.append(self._recv_from_rank0.get())
    return pending_msgs
为什么这么"啰嗦"？为啥不靠 ZMQ Pub/Sub 自然广播就行？
  • ZMQ Pub/Sub 是"send-and-forget"——rank1/2/3 的 SUB 不知道"我已经收完所有消息了吗"
  • 调度需要确定性——所有 rank 必须看到完全一致的消息序列，否则各 rank 的调度决策会分叉，KV cache 状态会不一致
  • 用 GLOO broadcast 一个 int32（消息数量）作为"同步点"，让 rank1/2/3 明确知道这一轮收满 N 条就停

回复 detokenizer：rank0 一人之力

def _reply_tokenizer_rank0(self, reply):
    if len(reply) == 1:
        self._send_into_tokenizer.put(reply[0])
    elif len(reply) > 1:
        self._send_into_tokenizer.put(BatchTokenizerMsg(data=reply))

def _reply_tokenizer_rank1(self, reply):
    _ = reply  # 其他 rank 啥都不做

因为所有 rank 算出的 next_tokens 是一样的（确定性 forward），所以只需要 rank0 报告就够了。其他 rank 的输出直接丢弃。

① 不变的核心

Scheduler 主循环、PrefillManager/DecodeManager/CacheManager 的内部逻辑、Req/Batch 数据结构、prepare_metadata 接口——全部不变。

这是 mini-sglang 设计很优雅的地方：单卡和多卡共用一套调度代码。

② 变了的只有"通信"和"权重切片"

多卡只是在Engine 层多了：

  • 权重按 head 切片加载
  • 每层 forward 末尾 2 次 all-reduce
  • scheduler 之间用 GLOO + ZMQ Pub/Sub 同步控制消息

③ TP 的代价 & 收益

代价：每层 2 次 all-reduce，70B 模型 ~160 次/forward（NVLink 下占 < 5%）

收益：

  • 显存切到多卡，70B 单卡装不下，4 卡 OK
  • 算力近线性 scale
  • KV cache 也被切，能跑更大 batch

  2. 用 nsys/nvprof 抓一次 forward 的 timeline，亲眼看 NCCL all-reduce 长什么样
  3. 读 layers/linear.py 全文（< 200 行）—— TP 的全部秘密都在这里
