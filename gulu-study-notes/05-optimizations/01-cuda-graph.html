PART 1先看问题：CPU launch kernel 是有开销的

很多人想象中"GPU 计算"是这样：

# 想象中
y = matmul(x, w)   # 调用 → GPU 算 → 返回

但真实的 CUDA 执行模型是这样的：

一次 kernel launch 的"管理开销"是 5-15 µs（微秒级，不是纳秒）。
  • 对一个 1ms 的大 matmul，5µs 占比 0.5% → 完全无所谓
  • 对一个 50µs 的小 matmul，5µs 占比 10% → 开始疼了
  • 当一次 forward 涉及几百个小 kernel，且每个都很短时 → CPU launch 会拖慢 GPU

具体到 LLM 推理：一次 forward 有多少个 kernel？

层组件kernel 数（粗略）说明
RMSNorm1融合 norm
QKV proj (matmul)1大 matmul
RoPE1融合
Attention (FlashInfer)2-3含 softmax 等
O proj (matmul)1
NCCL all-reduce (TP>1)1
RMSNorm1
MLP gate_up + silu_and_mul2
MLP down1
NCCL all-reduce1
每层小计~12
Llama-3-70B 80 层 + sampler 等~1000+ kernel每次 forward

如果每个 launch 5 µs，1000 个 kernel = 5 ms 纯 CPU 开销——decode 本身可能也就 5 ms，开销和有用工作 1:1。这就是 CUDA Graph 要解决的事。

PART 2CUDA Graph 是什么

CUDA Graph = "把一连串 kernel launch 操作录制成一个对象，之后整体 replay"。

类比：

Eager 模式CUDA Graph 模式
类比在电话里逐个念菜名给厨房 (1000 通)提前把菜单打印好，每次直接递过去 (1 张纸)
每次 forwardCPU 重新发起 1000 次 launch 调用CPU 调一次 graph.replay()
CPU 开销~5 ms~5 µs
灵活性每次可以不一样形状/路径必须固定

核心 API（PyTorch）

import torch

# 1. 创建空 graph 对象
graph = torch.cuda.CUDAGraph()

# 2. 准备好 stable 的输入/输出 buffer（地址不变）
static_input  = torch.zeros(bs, hidden, device="cuda")
static_output = torch.empty(bs, vocab, device="cuda")

# 3. 录制（capture）
with torch.cuda.graph(graph):
    static_output[:] = model(static_input)
    # 这里所有的 kernel launch 都被录进 graph，但不立刻执行

# 4. 之后每次 forward 只需 3 步
static_input.copy_(real_input)   # ① 把真实数据 copy 进 stable buffer
graph.replay()                 # ② replay（CPU 侧 ~5 µs，GPU 自己跑）
result = static_output.clone()    # ③ 取走结果

背后的魔法

CUDA Driver 在 capture 阶段会记录下：
  1. 哪些 kernel 被 launch
  2. 每个 kernel 的参数（包含输入/输出张量的显存地址）
  3. kernel 之间的依赖关系（哪些可以并行、哪些必须等）
形成一个"DAG"。replay 时整个 DAG 一口气提交给 GPU，CPU 完全不用再走 dispatch / 参数序列化的流程。

关键约束（理解了就不踩坑）

约束原因实际意义
所有输入/输出张量地址必须固定kernel 参数里写死了指针必须用预分配的 static buffer，每次 copy_ 进去
不能有 host-to-device 同步graph 是异步执行的不能 tensor.item()、print() 中间结果
shape 必须固定每个 kernel 的 grid/block size 录死了不同 batch size 要录不同的 graph
kernel 调用序列必须固定没有 if/while/动态分支不能根据 tensor value 选不同路径
不能用 mempool 动态分配capture 期间 alloc 会被记录死地址Workspace 必须预分配好

PART 3为什么 LLM decode 才是 CUDA Graph 的完美场景

CUDA Graph 不是万能药，它只在特定条件下才有意义。LLM 推理里 decode 阶段几乎是教科书式的好场景：

条件PrefillDecode
shape 是否固定❌ 每次 prompt 长度都不同✅ 每步 extend_len = 1
kernel 数量少（一批多个 token 摊薄）多（每个 token 都要走完整 28-80 层）
每个 kernel 多大大 matmul（compute-bound）小 matmul（memory-bound）
launch 开销占比< 1%20-50%
kernel 路径是否固定✅ 是✅ 是
CUDA Graph 收益~0%2-5x throughput

为啥 decode 的 kernel 这么"小"？

decode 的本质是 memory-bound：每一步只算 1 个 token 的 Q（很小），但要扫整个 KV cache（很大），瓶颈在显存带宽，不是算力。计算时间随之被压到极短，launch 开销就显得格外突出。

实测：mini-sglang 关掉 CUDA Graph 会怎样？

# 默认 (CUDA Graph 开启)
python -m minisgl --model "Qwen/Qwen3-0.6B"
# decode latency: ~3 ms / token

# 关闭 CUDA Graph
python -m minisgl --model "Qwen/Qwen3-0.6B" --cuda-graph-max-bs 0
# decode latency: ~12 ms / token  (慢 4x)

PART 4怎么用：3 步走

Step 1 · 准备 stable buffer

因为 graph 录死了"指针"，所以输入/输出必须用预分配好的固定显存。每次推理把真实数据 copy 进去，再 replay。

class GraphCaptureBuffer:
    input_ids: torch.Tensor      # [max_bs] int32, 复用
    out_loc:   torch.Tensor      # [max_bs] int32, 复用
    positions: torch.Tensor      # [max_bs] int32, 复用
    logits:    torch.Tensor      # [max_bs, vocab_size] fp32, 复用

    @classmethod
    def init(cls, bs, vocab_size, device):
        return GraphCaptureBuffer(
            input_ids=torch.zeros(bs, dtype=torch.int32, device=device),
            out_loc=torch.zeros(bs, dtype=torch.int32, device=device),
            positions=torch.zeros(bs, dtype=torch.int32, device=device),
            logits=torch.empty(bs, vocab_size, dtype=torch.float32, device=device),
        )

Step 2 · 录制（capture）

跑一遍 forward，让 driver 记录所有 kernel launch。这一步通常在启动时做一次。

graph = torch.cuda.CUDAGraph()
batch = Batch(reqs=[dummy_req] * bs, phase="decode")

# 用预分配 buffer 替换 batch 的张量
buffer.set_batch(batch)

with get_global_ctx().forward_batch(batch):
    # 先 warmup 一次（避免 capture 时触发 lazy init）
    buffer.logits[:bs] = model.forward()

    # 真正的 capture
    with torch.cuda.graph(graph, pool=pool, stream=self.stream):
        buffer.logits[:bs] = model.forward()

Step 3 · Replay（每次推理）

这一步发生在每次 decode iteration。3 个动作：copy 进去 → replay → 取出来。

def replay(self, batch):
    self.buffer.copy_from(batch)            # ① 真实数据 → stable buffer
    g = self.graph_map[batch.padded_size]
    self.attn_backend.prepare_for_replay(batch)
    g.replay()                              # ② 一次 launch, GPU 跑完整个 graph
    return self.buffer.logits[: batch.size]   # ③ 取走结果（切片不复制）
整个流程的"加速来源"： CPU 从"调用 1000 次 dispatcher" → "调用 1 次 graph.replay()"。GPU 干的活完全一样，但 CPU 那头省下了 99% 的 launch 开销。

PART 5mini-sglang 的实现细节

录哪些 batch size？—— 离散粒度

# engine/graph.py:49
def _determine_cuda_graph_bs(cuda_graph_bs, cuda_graph_max_bs, free_memory):
    if cuda_graph_bs is not None:
        return cuda_graph_bs
    free_memory_gb = free_memory / (1 << 30)
    if cuda_graph_max_bs is None:
        if free_memory_gb > 80:    # H200
            cuda_graph_max_bs = 256
        else:
            cuda_graph_max_bs = 160
    return [1, 2, 4] + list(range(8, cuda_graph_max_bs + 1, 8))
    # [1, 2, 4, 8, 16, 24, 32, ..., 256]  共 ~37 个 batch size
为什么不是连续的 1~256？ 录 256 个 graph 内存爆炸，且没必要——上面的离散粒度（1, 2, 4, 8, 16, 24, ...）足够覆盖典型场景。每个 graph 显存占用就是 workspace + cuda graph 本身的元数据，加起来几百 MB 到几 GB 不等。

如何处理"实际 batch size 不在录制列表里"？—— Padding

# engine/graph.py:160
def pad_batch(self, batch):
    padded_size = (
        next(bs for bs in self.graph_bs_list if bs >= batch.size)
        if self.can_use_cuda_graph(batch)
        else batch.size
    )
    batch.padded_reqs = batch.reqs + [self.dummy_req] * (padded_size - batch.size)

实际 batch size = 5 时，找到最近的录制粒度 8，用 dummy_req 凑到 8。

为什么需要 dummy_req？ 因为 graph 录的是 "处理 8 个 token" 的 kernel 序列，shape 是写死的。实际只有 5 个真实请求时，剩下 3 个槽位必须有数据（不能是 NaN/无效地址），否则 attention 读 KV pool 时会越界。dummy_req 指向一个 dummy_page（num_tokens 处的合法地址），算出垃圾结果但不会崩溃，最后切片丢掉。

Engine 里 dummy_req 是怎么准备的？

# engine/engine.py:89
self.dummy_req = Req(
    input_ids=torch.tensor([0], dtype=torch.int32, device="cpu"),
    table_idx=config.max_running_req,     # ← 多预留的槽位 (page_table 比真实槽多 1 行)

    uid=-1,
    sampling_params=None,
    cache_handle=None,

这就是为什么 page_table 形状是 [max_running_req + 1, max_seq_len]——多出来那 1 行专门给 dummy_req 用。

Capture 阶段的 3 个聪明做法

# engine/graph.py:122  _capture_graphs
pbar = tqdm(
    sorted(self.graph_bs_list, reverse=True),     ★ 1. 从大到小录
    desc="Preparing for capturing CUDA graphs...",
    disable=not get_tp_info().is_primary(),
)
pool = None
for bs in pbar:
    graph = torch.cuda.CUDAGraph()
    batch = Batch(reqs=[self.dummy_req] * bs, phase="decode")
    batch.padded_reqs = batch.reqs
    self.attn_backend.prepare_for_capture(batch)
    self.buffer.set_batch(batch)
    with get_global_ctx().forward_batch(batch):
        self.buffer.logits[:bs] = model.forward()         ★ 2. warmup 一次
        with torch.cuda.graph(graph, pool=pool, stream=self.stream):
            self.buffer.logits[:bs] = model.forward()
    if pool is None:
        pool = graph.pool()                                ★ 3. 共享 mempool
    self.graph_map[bs] = graph

从大到小

先录 bs=256 占的显存最大。如果连最大的都装不下，立刻报错；后面小的自然能装下。这种顺序避免"录到一半发现 OOM"。

warmup 一次

capture 之前先正常 forward 一次。原因：第一次 forward 会触发 cuBLAS workspace 分配、JIT 编译等"一次性副作用"，必须把它们排出去，否则会污染 graph。

共享 mempool

第一个 graph capture 时分配的中间 buffer 池，让后续所有 graph 都共用同一个池。否则每个 graph 都自己分配一份 workspace，显存占用倍增。

什么时候用 / 不用 graph？

# engine/graph.py:149
def can_use_cuda_graph(self, batch):
    return batch.is_decode and batch.size <= self.max_graph_bs
场景是否走 graph原因
纯 decode batch, bs ≤ max_bs✅ replayshape 固定 + bs 在录制范围
prefill batch❌ eagerextend_len 不固定，shape 不可预测
decode bs > max_graph_bs❌ eager没录这么大的 graph
--cuda-graph-max-bs 0❌ eager用户主动关闭

PART 63 个常见坑

坑 1 · 显存占用爆涨

录 37 个 graph，每个都自带 workspace。如果不用shared mempool，显存占用会翻倍。即使共享，CUDA Graph 元数据（block 描述、参数序列）本身也要占几百 MB。

对策：--cuda-graph-max-bs 调小（比如限制到 64），或者直接关掉换更多 KV cache 空间。

坑 2 · capture 时的"隐式同步"

如果 capture 期间有 CPU-GPU 同步操作（比如 tensor.item()、print(tensor)、检查 NaN），CUDA 会立即报错。

对策：调试 model.forward 时用 eager 跑，等正确了再开 graph。MINISGL_DISABLE_CUDA_GRAPH=1 之类环境变量在这里救命。

坑 3 · attention backend 的额外配合

FlashInfer / FlashAttention 都有"plan"阶段（参考 05 章）。这个 plan 通常在 CPU 上做、写到 GPU workspace。如果不做特殊处理，capture 时的 plan 会变成 graph 的一部分——但 plan 的输入（cu_seqlens 之类）每次 batch 都不同！

所以 mini-sglang 的 attention backend 都有 prepare_for_capture / prepare_for_replay 两个钩子：

# attention/base.py:18
class BaseAttnBackend(ABC):
    @abstractmethod
    def init_capture_graph(self, max_seq_len, bs_list): ...
    @abstractmethod
    def prepare_for_capture(self, batch): ...    # capture 时调一次
    @abstractmethod
    def prepare_for_replay(self, batch): ...     # 每次 replay 前调

具体到 FlashInfer：用 CUDAGraphBatchDecodeWithPagedKVCacheWrapper 这种特化包装器，它的 plan 阶段不会被录进 graph，replay 前用预分配的 indirect buffer 做"参数注入"。

SUM三句话总结 + 自查清单

① 解决什么问题

CPU launch kernel 有 µs 级开销。LLM decode 阶段单次 forward 几百到上千个小 kernel，launch 开销吃掉 20-50% 时间。

② 怎么解决

把 kernel 序列录成一个 graph 对象，之后整体 replay：CPU 只 launch 1 次，GPU 一口气跑完。本质是把 CPU dispatch 开销摊到启动时一次性付清。

③ 代价

shape 必须固定（按 bs 分粒度录多份）+ 显存占用增加（workspace + graph 元数据）+ 不能用动态控制流。

是否适合用 CUDA Graph 的自查清单

问题能用 Graph 吗
shape/dtype 是否固定？必须 ✅
kernel 序列是否每次相同？必须 ✅
能否预分配输入/输出 buffer？必须 ✅
kernel 数量大且每个都很短？越是 ✅ 收益越大
需要根据 tensor value 选不同分支？❌ 不行
需要 tensor.item() / print？❌ 不行
显存非常紧张？⚠️ 谨慎，graph 占内存

调试小技巧

  • 怀疑 graph 有问题时，先 --cuda-graph-max-bs 0 关掉对比 eager 结果
  • capture 报错"detected illegal stream synchronization" → 检查模型里是不是有 .item() / .tolist()
  • 用 nsys profile 抓 timeline，能直观看到 launch gap 是不是真消失了
  • graph 越多越占内存，看显存吃紧就把 --cuda-graph-max-bs 调小到刚好覆盖业务高峰即可
